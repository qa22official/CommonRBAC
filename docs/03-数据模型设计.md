# 03 · 数据模型设计（RBAC 权限系统）

> 相关文档：[文档索引](./README.md) · [需求规格](./01-需求规格说明书.md) · [总体设计](./02-总体设计说明书.md) · [演进设计](./05-RBAC0到RBAC3演进设计.md)

---

## 1. 设计原则

| 编号 | 原则 | 具体体现 |
|---|---|---|
| P-1 | **优先"加表"，避免"改表"** | RBAC2 的约束机制用一张新表 `sys_role_constraint` 承载，与现有查询完全正交，不触碰已有表 |
| P-2 | **小表可全量缓存** | 权限相关的 5 张业务表合计约 4~5 万行，可整份载入每个实例内存（< 10MB），这是鉴权零查询的基础 |
| P-3 | **单组织，不引入租户维度** | 所有表不带 `tenant_id`（ADR-02） |
| P-4 | **不做物理外键** | 约束由应用层保证。理由：本系统写入低频，外键带来的收益（防脏数据）小于代价（写入锁竞争、批量操作顺序约束、DDL 变更困难）。**代价必须由"删除前引用校验"来弥补**（见 FR-R4/FR-P4） |
| P-5 | **逻辑删除代替物理删除** | 用户、角色、权限均使用 `status` 状态位标记删除，保证审计可追溯、历史关系不悬空 |
| P-6 | **索引只建在真正被查询的列上** | 索引不是越多越好：每个索引都会拖慢写入、占用内存。本系统只有 6 张表，每条查询路径都显式论证（见第 5 节） |
| P-7 | **时间统一 UTC 存储** | `datetime(3)` 精确到毫秒；展示时区由前端处理 |

## 2. 概念模型

### 2.1 RBAC0 实体关系

```
   ┌──────────────┐            ┌──────────────────┐            ┌──────────────────┐
   │   sys_user   │            │   sys_user_role  │            │     sys_role     │
   │──────────────│ 1        N │──────────────────│ N        1 │──────────────────│
   │ id           ├────────────┤ user_id          ├────────────┤ id               │
   │ username     │            │ role_id          │            │ code             │
   │ password_hash│            │ created_at       │            │ name             │
   │ nickname     │            └──────────────────┘            │ inherit_role_id  │
   │ status       │                                            │   ◄── RBAC1 预留 │
   │ status       │                                            │ status           │
   │ token_version│                                            │ is_builtin       │
   │ role_version │                                            │ perm_version     │
   └──────────────┘                                            └────────┬─────────┘
                                                          ┌─────────────┴──────────────┐
                                                          │  sys_role_permission       │
                                                          │────────────────────────────│
                                                          │ role_id                    │
                                                          │ permission_id              │
                                                          └─────────────┬──────────────┘
                                                                        │
                                                                        ▼
                                                          ┌────────────────────────────┐
                                                          │     sys_permission         │
                                                          │────────────────────────────│
                                                          │ id                         │
                                                          │ code  (唯一，如 sys:user:create) │
                                                          │ resource_type (MENU/BUTTON/API/SYSTEM) │
                                                          │ parent_id  (权限树分组，见 4.3 说明) │
                                                          │ path / http_method (API 类) │
                                                          └────────────────────────────┘

   ┌─────────────────────────────────────────────────────────────────┐
   │  sys_audit_log （独立于权限模型，横向审计记录）                  │
   └─────────────────────────────────────────────────────────────────┘
```

### 2.2 权限的三种资源类型（`resource_type`）

| 类型 | 含义 | 关键字段 | 用途 |
|---|---|---|---|
| `MENU` | 一个可访问的页面/菜单 | `path`（前端路由路径） | 决定侧边栏可见项、动态路由注册 |
| `BUTTON` | 页面内的一个操作按钮 | 无 | 决定按钮显隐 |
| `API` | 一个后端接口 | `http_method` + `path` | **真正的安全边界**，由鉴权过滤器强制 |
| `SYSTEM` | 系统级通配权限 | 无 | 仅用于 `*`（全部权限）这类"不是具体资源点"的特殊权限码 |

**三者的关系**：一个 `MENU` 下挂若干 `BUTTON` 和 `API`，构成权限树。授权时通常整棵子树授予（前端树控件的父子联动），但模型上每一个权限点都是独立可授权的最小单位。

> **为什么不做"授予菜单自动授予其下全部按钮与接口"的服务端联动？**
> 因为这类"隐式放大"会让授权结果变得不可预测：管理员以为自己只给了一个菜单，实际上连带给了 20 个接口。**显式授权、显式审计**更安全。前端提供"一键勾选子节点"的便利即可，最终提交的仍是完整的显式权限码列表。

## 3. 表清单与容量预估

| 表名 | 说明 | 初期行数 | 远期（5 万用户） | 增长特征 |
|---|---|---|---|---|
| `sys_user` | 用户 | 10,000 | 50,000 | 随组织规模 |
| `sys_role` | 角色 | 200 | 500 | 极慢 |
| `sys_permission` | 权限点 | 1,000 ~ 3,000 | 5,000 | 随功能开发 |
| `sys_user_role` | 用户-角色关系 | 30,000 | 150,000 | 随用户数线性 |
| `sys_role_permission` | 角色-权限关系 | 10,000 | 30,000 | 缓慢 |
| `sys_audit_log` | 审计日志 | 按天增长约 几百~几千条 | 保留 180 天 | 需定期归档 |

**内存缓存占用估算（每个应用实例）**：

```
缓存B  用户→角色：50,000 用户 × 平均 3 角色 = 150,000 条
       每条：Long key(16B) + 小型 HashSet(约 100B 开销) ≈ 130B
       合计 ≈ 20 MB（远期）   初期（1 万用户）≈ 4 MB

缓存A  角色→权限：500 角色 × 平均 60 权限 = 30,000 条
       每条：角色 ID(16B) + HashSet 内含字符串引用（权限码在字符串池中共享）≈ 60B
       合计 ≈ 2 MB

总计：初期 < 10 MB，远期 < 30 MB
```

> 结论：即使按远期规模，权限缓存也只占几十分之一的堆内存。这是"整份放进内存"方案的可行性依据。**如果数据量是百万级，这个方案就不成立了**——所以数据量假设（AS-1）是这套设计的前提条件，必须在文档中写明。

## 4. 表结构定义

### 4.1 `sys_user` 用户表

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | BIGINT | PK, AUTO_INCREMENT | 主键 |
| `username` | VARCHAR(64) | NOT NULL, UNIQUE | 登录账号，**创建后不可修改**（FR-G5） |
| `password_hash` | VARCHAR(100) | NOT NULL | BCrypt 哈希（60 字符，留余量）。**严禁出现在任何日志/响应/审计中** |
| `nickname` | VARCHAR(64) | NOT NULL | 显示名 |
| `email` | VARCHAR(128) | NULL | 可空 |
| `phone` | VARCHAR(32) | NULL | 可空 |
| `status` | TINYINT | NOT NULL, DEFAULT 1 | 1=启用, 0=停用, 2=已删除（逻辑删除） |
| `token_version` | INT | NOT NULL, DEFAULT 0 | 令牌版本号。登出/改密/停用/全局作废时自增；**鉴权时与本地身份快照比对**（见 [02 文档 5.3.3](./02-总体设计说明书.md)） |
| `role_version` | INT | NOT NULL, DEFAULT 0 | **授权版本号**：该用户的角色集合每次变更就自增。用于覆盖式授权的乐观锁（见 4.4 与 [04 文档 §1.6](./04-接口设计.md)） |
| `fail_count` | SMALLINT | NOT NULL, DEFAULT 0 | 连续登录失败次数（用于锁定判定） |
| `locked_until` | DATETIME(3) | NULL | 锁定截止时间；NULL 表示未锁定 |
| `last_login_at` | DATETIME(3) | NULL | 最后登录时间 |
| `remark` | VARCHAR(255) | NULL | 备注 |
| `created_by` | BIGINT | NULL | 创建人（审计追溯） |
| `created_at` | DATETIME(3) | NOT NULL | 创建时间 |
| `updated_by` | BIGINT | NULL | 最后修改人 |
| `updated_at` | DATETIME(3) | NOT NULL | 最后修改时间 |

**索引**：
- `PRIMARY KEY (id)`
- `UNIQUE KEY uk_username (username)` —— 支撑登录查询与唯一性约束

**设计说明**：
- `fail_count` / `locked_until` 放主表而非 Redis：登录是低频操作（不是热点路径），放主表可避免引入额外的状态存储不一致问题。**代价**：每次登录失败要写一次库。鉴于登录 QPS 极低（10k 用户即使全部在 1 小时内登录，也只有约 3 QPS），这是可接受的。
- 未对 `status` 单独建索引：用户列表查询走 `status` 过滤时区分度差（绝大多数是启用），单独索引收益有限且拖慢写入。列表查询按 `id DESC` 分页（走主键），`status` 作为回表后过滤条件。**若实测列表查询变慢，再评估添加 `(status, id)` 组合索引。**

### 4.2 `sys_role` 角色表

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | BIGINT | PK, AUTO_INCREMENT | 主键 |
| `code` | VARCHAR(64) | NOT NULL, UNIQUE | 角色编码（如 `SUPER_ADMIN`），**创建后不可修改**（FR-G5） |
| `name` | VARCHAR(64) | NOT NULL | 角色名称 |
| `description` | VARCHAR(255) | NULL | 描述 |
| **`inherit_role_id`** | BIGINT | NOT NULL, DEFAULT 0 | **权限继承来源角色 ID**：当前角色自动获得该角色**及其继承链上的全部**权限。`0` 表示不从任何角色继承。**RBAC0 阶段恒为 0，为 RBAC1 预留** |
| `status` | TINYINT | NOT NULL, DEFAULT 1 | 1=启用, 0=停用, 2=已删除 |
| `is_builtin` | TINYINT | NOT NULL, DEFAULT 0 | 1=内置角色（不可删除、不可停用，FR-G1） |
| `perm_version` | INT | NOT NULL, DEFAULT 0 | **授权版本号**：该角色的权限集合每次变更就自增。用于覆盖式授权的乐观锁，并使 `sys_role` 表自身可被用作缓存版本标记 |
| `sort` | INT | NOT NULL, DEFAULT 0 | 排序 |
| `created_by` | BIGINT | NULL | |
| `created_at` | DATETIME(3) | NOT NULL | |
| `updated_by` | BIGINT | NULL | |
| `updated_at` | DATETIME(3) | NOT NULL | |

**索引**：
- `PRIMARY KEY (id)`
- `UNIQUE KEY uk_code (code)`
- `KEY idx_inherit_role_id (inherit_role_id)` —— RBAC1 阶段展开继承链时需要（按来源角色反查）

**为什么字段叫 `inherit_role_id` 而不是 `parent_id`？**

评审指出原设计的 `parent_id` 存在**语义歧义**：它既可以被读成"组织上的上级"（组织树，上级在上），也可以被读成"我继承自谁"（继承链，被继承者在上）。两种读法会推出**方向相反**的权限结果，而权限方向搞反就是真实的越权事故。

本设计**只采用一种语义**：

> **`inherit_role_id` = 当前角色从哪个角色继承权限。**
> 当前角色的有效权限 = 自身权限 ∪ 该角色（及其继承链）的全部权限。
> 简言之：**越靠近链尾的角色权限越大**。
> 配置示例：`运营主管.inherit_role_id = 运营专员.id`，`运营总监.inherit_role_id = 运营主管.id` → 总监 ⊇ 主管 ⊇ 专员。

> **注意：系统不存储"组织上下级"关系。** 组织架构（谁向谁汇报）与权限继承（谁的权限更大）是**两件事**，把它们压进同一个字段是经典的建模错误——因为组织上"上级"通常需要下级的**能力**（可以代下级操作），但绝不应该自动获得下级的**数据**，这两类需求在本系统里只有前者。若将来确实需要组织架构，应当**新增独立的表**，而不是复用本字段。

**为什么现在就要预留这个字段？**

诚实地说：**加一个字段的 DDL 本身很便宜**（MySQL 8.0 支持 instant add column，秒级完成，不需要停机）。所以"现在加"省下的不是 DDL 时间。它真正省下的是三样东西：

1. **应用层的连带改造**：`sys_role` 的实体类、MyBatis 映射、查询语句、列表接口的返回结构都要同步改。若 RBAC0 阶段没有这个字段，升级时就是"改表 + 改实体 + 改映射 + 改接口 + 改前端类型定义"一串动作。
2. **前端角色管理界面的结构**：有了这个字段，角色列表可以直接按树形组织展示（即使 RBAC0 阶段树是平的）。升级时前端只是"允许选择继承来源角色"，而不是从表格改成树。
3. **认知负担**：字段存在本身就是"这里将来会长出继承关系"的说明。

**代价**：8 字节 × 500 行 = 4KB 存储，一个索引，以及后来者要问一句"这个字段现在是干什么的"——后者通过在字段注释和本文档中写明"RBAC0 阶段恒为 0"来消除。

**结论**：收益（避免跨四层改造）明显大于代价（4KB + 一行注释）。**这是本设计中唯一预留的业务字段，其他一切不预留。**

### 4.3 `sys_permission` 权限表

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | BIGINT | PK, AUTO_INCREMENT | 主键 |
| `code` | VARCHAR(128) | NOT NULL, UNIQUE | 权限码（如 `sys:user:create`），**创建后不可修改**（FR-G5） |
| `name` | VARCHAR(64) | NOT NULL | 权限名称 |
| `resource_type` | VARCHAR(16) | NOT NULL | `MENU` / `BUTTON` / `API` / `SYSTEM`（`SYSTEM` 仅用于 `*`） |
| `parent_id` | BIGINT | NOT NULL, DEFAULT 0 | 父权限 ID，0 为根，构成**权限树（分组层级）**。**注意与 `sys_role.inherit_role_id` 区分**：这里的父子是"分组包含"关系（菜单下挂按钮和接口），**与权限继承无关**，两者语义不同、不可混用 |
| `path` | VARCHAR(255) | NULL | `MENU`：前端路由路径；`API`：接口路径（如 `/api/users/**`） |
| `http_method` | VARCHAR(16) | NULL | `API` 类专用，如 `POST`；为空表示不限方法 |
| `icon` | VARCHAR(64) | NULL | `MENU` 类专用，菜单图标 |
| `status` | TINYINT | NOT NULL, DEFAULT 1 | 1=启用, 0=停用, 2=已删除 |
| `is_builtin` | TINYINT | NOT NULL, DEFAULT 0 | 1=内置权限（不可删除） |
| `sort` | INT | NOT NULL, DEFAULT 0 | 同级排序 |
| `created_at` | DATETIME(3) | NOT NULL | |
| `updated_at` | DATETIME(3) | NOT NULL | |

**索引**：
- `PRIMARY KEY (id)`
- `UNIQUE KEY uk_code (code)`
- `KEY idx_parent_id (parent_id)`

**设计说明**：
- 权限树整体只有千级节点，**一次全量查询即可构建整棵树**，不在数据库层做递归查询（MySQL 递归 CTE 在每请求场景下是性能陷阱）。查询结果由应用层一次性组装成树。
- `path` / `http_method` 字段在本设计中**只用于生成文档与做构建期一致性校验**，不用于运行期 URL 匹配。原因见下。

> **重要设计决策：运行期鉴权不按 URL 匹配权限，只按"方法上的权限码注解"。**
>
> 常见做法是让过滤器拿请求 URL 去数据库匹配权限规则。这有三个问题：① 每次请求要做 URL 模式匹配（性能损耗，且正则匹配容易被绕过）；② 权限规则与代码脱节（改了接口忘了改数据库规则，就会出现越权）；③ 匹配规则本身就是攻击面（路径穿越、编码绕过、URL 大小写）。
>
> 我们的做法是：**权限声明写在代码里（`@RequiresPermission`），与接口在同一个文件、同一次提交中被审查**。数据库里的 `path`/`http_method` 只用于运维排查与自动化对账（校验"数据库里配的 API 权限"与"代码里声明的权限"是否一致）。

### 4.4 `sys_user_role` 用户-角色关系表

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `user_id` | BIGINT | NOT NULL | 用户 ID |
| `role_id` | BIGINT | NOT NULL | 角色 ID |
| `created_by` | BIGINT | NULL | 授权人 |
| `created_at` | DATETIME(3) | NOT NULL | 授权时间 |

**索引**：
- `PRIMARY KEY (user_id, role_id)` —— 天然去重（防止重复授权），且支撑"查某用户的所有角色"（鉴权核心查询，`user_id` 前缀）
- `KEY idx_role_id (role_id)` —— 支撑"查某角色下的所有用户"（角色删除前的引用校验、角色详情页的用户数统计）

**设计说明**：**复合主键的顺序不是随意的**。鉴权链路只用 `user_id` 查询，因此 `user_id` 必须在最左；若反过来建 `(role_id, user_id)`，每次鉴权都要全表扫描——这类"复合索引列序"的错误在高并发下是致命的。

### 4.5 `sys_role_permission` 角色-权限关系表

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `role_id` | BIGINT | NOT NULL | 角色 ID |
| `permission_id` | BIGINT | NOT NULL | 权限 ID |
| `created_by` | BIGINT | NULL | 授权人 |
| `created_at` | DATETIME(3) | NOT NULL | 授权时间 |

**索引**：
- `PRIMARY KEY (role_id, permission_id)` —— 支撑"查某角色的所有权限"（缓存 A 的重建查询，`role_id` 前缀）
- `KEY idx_permission_id (permission_id)` —— 支撑"查某权限被哪些角色引用"（权限删除前引用校验）

**设计说明**：此表不存 `role_code` / `permission_code` 冗余，只存 ID。原因：权限码可变性虽为零（FR-G5），但 ID 关系表更小、缓存重建时可以用 ID 做关联；权限码到 ID 的映射由 `sys_permission` 全量缓存提供（几千条，成本可忽略）。

### 4.6 `sys_role_constraint` 角色约束表 —— **RBAC2 阶段新增，RBAC0 阶段不建**

> 本表在 RBAC0 阶段**不创建**。此处列出是为了说明"RBAC2 的升级为什么不需要改动现有表"（详见 [05 文档](./05-RBAC0到RBAC3演进设计.md)）。

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | BIGINT | PK, AUTO_INCREMENT | |
| `constraint_type` | VARCHAR(32) | NOT NULL | `MUTEX`（互斥）/ `CARDINALITY`（基数） |
| `target_a` | BIGINT | NOT NULL | 角色 A（互斥为对等关系，基数为主角色） |
| `target_b` | BIGINT | NULL | 角色 B（互斥用；基数为 NULL） |
| `max_count` | INT | NULL | 基数约束的最大数量 |
| `scope` | VARCHAR(16) | NOT NULL | `SSD`（静态，授权时校验）/ `DSD`（动态，激活时校验） |
| `status` | TINYINT | NOT NULL, DEFAULT 1 | |
| `created_at` / `updated_at` | DATETIME(3) | NOT NULL | |

**为什么这张表可以"后加"而不产生任何改造**：它是**纯新增**——新增表、新增读取它的校验器。现有 5 张表和所有现有 SQL 完全不受影响。这印证了原则 P-1（优先加表）。

### 4.7 `sys_audit_log` 审计日志表

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | BIGINT | PK, AUTO_INCREMENT | |
| `audit_category` | VARCHAR(16) | NOT NULL | `CHANGE`（变更审计，与业务同事务）/ `SECURITY`（安全事件，独立落库）。见 [01 文档 4.5](./01-需求规格说明书.md) |
| `operator_id` | BIGINT | **NULL** | 操作人 ID。**允许为空**：登录失败时账号可能根本不存在（FR-L9） |
| `operator_name` | VARCHAR(64) | NOT NULL | 操作人账号（冗余存储：账号可能被改备注或用户被删除，审计必须保持当时事实）。账号不存在时记录**提交的账号名**（脱敏后） |
| `action` | VARCHAR(64) | NOT NULL | 操作类型，如 `USER_CREATE` / `ROLE_PERM_ASSIGN` / `LOGIN` / `PERM_DENIED` |
| `target_type` | VARCHAR(32) | NULL | 目标对象类型：`USER` / `ROLE` / `PERMISSION` / `SESSION` |
| `target_id` | BIGINT | NULL | 目标对象 ID |
| `detail_before` | JSON | NULL | 变更前快照（**脱敏后**） |
| `detail_after` | JSON | NULL | 变更后快照（**脱敏后**） |
| `result` | TINYINT | NOT NULL | 1=成功, 0=失败 |
| `fail_reason` | VARCHAR(255) | NULL | 失败原因 |
| `transaction_id` | VARCHAR(64) | NULL | 关联的业务事务标识；**仅 `CHANGE` 类有值**，用于把一次事务内的多条审计串起来 |
| `client_ip` | VARCHAR(64) | NOT NULL | 来源 IP：**必须由 `ClientIpResolver` 在可信代理边界内解析**，禁止直接取 `X-Forwarded-For` 首段（见 [02 文档 §5.7](./02-总体设计说明书.md)） |
| `user_agent` | VARCHAR(512) | NULL | |
| `trace_id` | VARCHAR(64) | NULL | 关联链路追踪 |
| `event_time` | DATETIME(3) | NOT NULL | **事件发生时间**（由应用生成）。与 `created_at` 分开的原因：安全事件允许异步/排队写入，落库时间可能明显晚于发生时间，混用会让时间线扭曲 |
| `created_at` | DATETIME(3) | NOT NULL | 记录落库时间 |

**索引**：
- `PRIMARY KEY (id)`
- `KEY idx_event_time (event_time)` —— 时间范围查询与归档删除（**归档删除必须走时间索引，否则会全表扫描并长时间锁表**）
- `KEY idx_operator_time (operator_id, event_time)` —— 支撑"查某人做过什么"（审计追责的最常用查询）

**设计说明（性能关键）**：
- **二级索引是"先建最小必要集、再用真实数据验证"的结果，不是一次性拍定的结论。** 上表的两个索引是**基于已知查询维度的初始选择**，必须按 5.3 的方法用目标数据量做 `EXPLAIN ANALYZE` 验证；验证不通过就调整，而不是"因为加了索引所以没问题"。
- **不建 `action`、`target_type`、`result` 等低区分度列的独立索引**。理由：审计表是**写多读少**的追加型表，而变更审计要求**同步落库（在业务事务内）**——每多一个二级索引，每次插入就多一次索引维护，这个成本直接计入写接口延迟。低区分度列的过滤交给"时间范围 + 回表后过滤"更划算。
- **若查询维度继续增长或数据量继续上升**（例如审计范围从 RBAC 域扩展到全业务域），正确做法是引入专门的日志存储（ClickHouse / ES）或按月分区，**而不是在 MySQL 上继续堆索引**。
- **快照脱敏**：`detail_before/after` 必须经过统一脱敏过滤器，剔除 `password_hash`、令牌等敏感字段（NFR-3 / FR-L10）。
- **归档策略**：默认保留 180 天；每日凌晨执行 `DELETE ... WHERE event_time < ? LIMIT 5000` 的分批删除（避免长事务与巨大的 binlog），或按 `event_time` 做 RANGE 分区后直接 `DROP PARTITION`（大表推荐后者）。

## 5. 关键 SQL 与索引覆盖验证

> 所有关键查询都必须能说清"走哪个索引、扫描多少行"。若某条 SQL 无法说出这一点，说明模型设计有问题。

| 场景 | SQL 形态 | 命中索引 | 预估扫描行数 | 验证状态与备注 |
|---|---|---|---|---|
| 登录：按账号查用户 | `SELECT ... FROM sys_user WHERE username = ?` | `uk_username` | 1 | 唯一索引等值查询，**可直接断言** |
| **鉴权：身份快照加载** | `SELECT token_version, status FROM sys_user WHERE id = ?` | `PRIMARY` | 1 | 单行主键查询；每个活跃用户每 30 秒一次（见 [02 文档 5.3.3](./02-总体设计说明书.md) 成本说明） |
| 鉴权：查用户角色 | `SELECT role_id FROM sys_user_role WHERE user_id = ?` | `PRIMARY(user_id, role_id)` | 平均 3 | **覆盖索引**（只取 `role_id`，无需回表）——这是频率最高的权限查询 |
| 缓存重建：全量用户-角色 | `SELECT user_id, role_id FROM sys_user_role` | 全表（或 `PRIMARY` 索引扫描） | 3 万 | 只在缓存失效后执行，低频；**单次查询换取全量内存化** |
| 缓存重建：全量角色-权限 | `SELECT role_id, permission_id FROM sys_role_permission` | 全表 | 1 万 | 同上 |
| 缓存重建：角色的继承与状态 | `SELECT id, inherit_role_id, status FROM sys_role` | 全表 | 500 | 数据量极小，与上两条合并加载 |
| 用户列表（分页） | `SELECT ... FROM sys_user WHERE status <> 2 ORDER BY id DESC LIMIT ?` | `PRIMARY` | 页大小 | 走主键倒序，**稳定分页** |
| **用户列表（关键词搜索）** | `WHERE username LIKE 'kw%'` | `uk_username` | 前缀匹配数量 | ⚠ **必须用真实数据 EXPLAIN 验证**；`LIKE '%kw%'` 无法走索引，见 5.3 |
| 角色详情：该角色用户数 | `SELECT COUNT(*) FROM sys_user_role WHERE role_id = ?` | `idx_role_id` | ~150 | 删除角色前校验提示 |
| 权限详情：被多少角色引用 | `SELECT COUNT(*) FROM sys_role_permission WHERE permission_id = ?` | `idx_permission_id` | ~30 | 删除权限前校验 |
| 权限树全量 | `SELECT ... FROM sys_permission WHERE status <> 2 ORDER BY parent_id, sort` | 全表 | 3000 | 低频（缓存，TTL 5 分钟） |
| 审计查询（时间 + 操作人） | `WHERE operator_id = ? AND event_time BETWEEN ? AND ? ORDER BY id DESC LIMIT ?` | `idx_operator_time` | 该人在该时段内的记录 | ⚠ 需用 30 万+ 条数据验证；只用时间条件时走 `idx_event_time` |
| 审计查询（仅时间范围） | `WHERE event_time BETWEEN ? AND ? ORDER BY id DESC LIMIT ?` | `idx_event_time` | 时间范围内 | 深翻页用 `id` 游标替代 `OFFSET` |
| 删除用户前检查 | `SELECT 1 FROM sys_user_role WHERE user_id = ? LIMIT 1` | `PRIMARY` | ≤1 | |
| **缓存重建（关键）** | 见 5.1、5.2 | — | — | |

### 5.1 为什么"全表查询"在重建缓存时是可接受的

`SELECT user_id, role_id FROM sys_user_role` 会扫描 3 万行。听起来很吓人，但请对比两种方案：

| 方案 | 单次鉴权成本 | 缓存重建成本 | DB 压力模型 |
|---|---|---|---|
| 每请求查库/查 Redis | 1 次往返 + 索引查询 | 无 | **2000 QPS × 每请求 1 次查询 = 2000 QPS 的 DB 负载** |
| 本方案（全量缓存） | 0 | 2 次全表扫描（约 10~30ms） | **仅在权限变更后发生，每天约几次~几百次** |

**结论**：把成本从"每请求"挪到"每次变更"，是数量级的优化。这正是原则二（减少工作优于加快工作）的应用。

### 5.2 缓存重建的并发保护（单飞）

```
缓存失效后，第一个到达的请求触发重建：
   · 使用 Caffeine 的 LoadingCache.get() —— 框架原生保证同一 key 只有一个线程执行加载
   · 或使用进程内锁 + 双检（本地缓存场景，无需分布式锁）
防雪崩：
   · 广播到达后**不立即重建**（否则 N 个实例同时打库），而是惰性重建
   · 重建失败 → 沿用旧值（**但不延长 TTL**）+ 指数退避重试 + 告警
   · 陈旧时长超过阈值 → 按 §8.2 告警（**不停服务**：本设计采用 fail-open）
   · 仅当 `rbac.cache.stale-policy=fail-closed` 时才拒绝；默认 `fail-open`，见 [02 文档 5.3.2](./02-总体设计说明书.md)
```

> **为什么不需要分布式锁？** 因为每个实例的缓存是独立的、内容是"全量事实"的快照。20 个实例各扫一次表，代价是 20 次全表查询（每天几次），完全可以接受；而引入分布式锁会带来"Redis 故障时锁失效导致重建风暴"和"锁超时导致重建被阻塞"两类新问题。**在有 20 种更简单的选择时，不要用分布式锁。**

### 5.3 索引方案必须由真实数据量验证（不是一次性结论）

**规则：本文档中列出的索引是"初始设计"，其有效性必须在建库后用目标数据量实测确认。** 方法：

```
1. 构造目标量级测试数据（初期 1 万用户 / 3 万用户-角色关系 / 30 万审计记录；远期按 5 倍）
2. 对每一条"上线后会跑的查询"执行 EXPLAIN ANALYZE，记录：命中的索引、扫描行数、实际耗时
3. 判定标准：命中预期索引、扫描行数处于同量级、单次耗时 ≤ 5ms（读） / ≤ 20ms（审计查询）
4. 不达标 → 调整索引或改写 SQL，然后把**实测结果回填到本文档**，作为后续回归的基线
```

**两个已知的高风险查询（原设计未覆盖，必须专门验证）**：

| 查询 | 风险 | 处理方式 |
|---|---|---|
| 用户列表的**关键词模糊搜索** | `LIKE '%keyword%'`（前后都有通配符）**无法使用普通 B-Tree 索引**，必然全表扫描。10 万行时耗时可能达数百毫秒，直接击穿 P99 | **明确降级为前缀查询**：`LIKE 'keyword%'` 可走 `uk_username` 索引；昵称搜索若无索引则限定"仅在账号前缀匹配为空时才回退到昵称模糊搜索，并限制结果集"。**不要假装 `%…%` 很快** |
| 审计日志的**多条件组合查询** | 时间 + 操作人 + 操作类型 + 目标对象的组合会产生多种执行计划，只建时间索引时，非时间条件只能回表后过滤 | 先统计"实际最常用的 3 种组合"，针对它们建**联合索引**（如 `(operator_id, event_time)`）；其余组合接受时间范围过滤 + 回表。**组合维度继续增长时的正确出路是换存储（ClickHouse/ES），不是继续加索引** |

**"当前不建额外索引"是阶段性结论，不是永久禁令。** 判定依据只有一个：**实测扫描行数与耗时是否达标**——达标就不加（省写入成本），不达标就加（保 P99）。

## 6. 逻辑删除与引用完整性

由于不使用物理外键（P-4），引用完整性由应用层保证。规则如下：

| 操作 | 校验规则 | 违反时的行为 |
|---|---|---|
| 删除用户 | 无需校验（用户是被引用方） | 置 `status = 2`，同时删除其 `sys_user_role` 记录 |
| 删除角色 | 校验 `sys_user_role` 是否存在引用 | 拒绝，提示"仍有 N 个用户绑定此角色" |
| 删除角色 | 校验 `is_builtin = 0` | 拒绝（FR-G1） |
| 删除权限 | 校验 `sys_role_permission` 是否存在引用 | 拒绝，提示"仍被 N 个角色引用" |
| 停用角色 | 无需校验 | 该角色的权限**立即不生效**（权限计算时过滤 `status ≠ 1`） |
| 停用权限 | 无需校验 | 该权限**立即不生效**（权限计算时过滤） |
| 停用用户 | 校验"至少保留 1 个启用状态的超级管理员"（FR-G2） | 拒绝 |

**关键点**：**停用角色/权限后权限立即不生效，是通过"权限计算时过滤状态"实现的，而不是通过删除关系记录。** 这样停用是可逆的（重新启用即恢复），且不破坏审计痕迹。

> 这就意味着权限解析器在计算时必须做两次状态过滤：
> ① 角色必须 `status = 1`；② 权限必须 `status = 1`。
> 详见 [05 文档的算法定义](./05-RBAC0到RBAC3演进设计.md)。

### 6.1 并发更新保护（覆盖式授权必须防"丢失更新"）

`PUT /api/users/{id}/roles` 与 `PUT /api/roles/{id}/permissions` 采用**完整集合覆盖**提交。它是幂等的，但会出现经典的**丢失更新**：

```
管理员 A 读取当前角色 [R1]
管理员 B 读取当前角色 [R1]
A 提交 [R1, R2]   → 数据库变为 [R1, R2]
B 提交 [R1, R3]   → 数据库变为 [R1, R3]，A 刚加的 R2 被静默丢弃
```

**这是"静默数据丢失"**：A 会以为自己的授权成功了（接口返回 200），而实际上被覆盖。授权场景下这属于**严重问题**——管理员可能因此漏掉一个必需的角色，或以为自己收回过某个角色。

**解决办法：两道防线，各自解决不同问题，必须都有。**

| 防线 | 机制 | 解决什么 |
|---|---|---|
| **乐观锁（版本号）** | `sys_user.role_version` / `sys_role.perm_version`。请求必须携带 `expectedVersion`；不匹配则返回 **40950**，提示"数据已被他人修改，请刷新后重试" | 发现"编辑期间数据已被改过"，把**静默丢失**变成**显式冲突** |
| **行级锁（悲观锁）** | 事务内先 `SELECT ... FROM sys_user WHERE id = ? FOR UPDATE`（角色权限同理锁 `sys_role` 行），再做约束校验与写入 | 保证"校验 → 写入"这段时间内，**同一对象的其他变更被串行化**；这是 [05 文档 §5.5](./05-RBAC0到RBAC3演进设计.md) 中约束校验不被并发绕过的基础 |

**为什么两者都要，不能只留一个？**

| 只留乐观锁 | 只留行锁 |
|---|---|
| 两个事务可能同时通过约束校验（因为校验读的是提交前的状态），然后先后写入，**约束被绕过**（例如两人同时授予互斥角色） | 后提交者会**静默覆盖**先提交者的结果，数据丢失且无人知晓 |

> **代价说明**：行锁会让"同一用户的授权操作"串行执行。授权操作每天只有几十次，锁等待可以忽略；而**它换来的是约束在并发下不可被绕过**——这是 RBAC2 能成立的前提。低频操作用简单可靠的锁是正解，不要引入分布式锁（详见 [05 文档 §5.5](./05-RBAC0到RBAC3演进设计.md)）。
