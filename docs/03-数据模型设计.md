# 03 · 数据模型设计

相关文档：[00 基线](./00-编码代理工作基线.md) · [01 需求](./01-需求规格说明书.md) · [02 总体设计](./02-总体设计说明书.md) · [04 接口](./04-接口设计.md) · [05 演进](./05-RBAC0到RBAC3演进设计.md) · [07 修订记录](./07-修订记录.md)

## 1. 建模规则

| 编号 | 规则 | 落地要求 |
|---|---|---|
| P-1 | 优先加表，避免改表 | RBAC2 的约束用新表 `sys_role_constraint` 承载，不触碰已有表 |
| P-2 | 表必须小到可全量缓存 | 权限相关 5 张表合计 ≤ 5 万行、≤ 10MB，这是鉴权零查询的前提 |
| P-3 | 单组织，不引入租户维度 | 所有表不带 `tenant_id` |
| P-4 | 不使用物理外键 | 引用完整性由应用层在事务内校验；删除前必须做引用检查 |
| P-5 | 逻辑删除代替物理删除 | 用户、角色、权限用 `status = 2` 标记删除 |
| P-6 | 索引只建在被查询的列上 | 每条索引必须在 §5 有对应查询场景 |
| P-7 | 时间统一 UTC 存储 | 类型 `datetime(3)`，毫秒精度；时区转换由前端处理 |

## 2. 实体关系

```text
sys_user ──1:N── sys_user_role ──N:1── sys_role ──1:N── sys_role_permission ──N:1── sys_permission
   │                                        │
   │ token_version / status                 │ inherit_role_id（RBAC1 预留，RBAC0 恒为 0）
   │ role_version                           │ perm_version

sys_audit_log    独立表，与权限模型无外键关系
sys_role_constraint     RBAC2 阶段创建，RBAC0 阶段不建
```

### 2.1 resource_type 取值

| 类型 | 含义 | 关键字段 | 用途 |
|---|---|---|---|
| `MENU` | 页面或菜单 | `path` | 菜单显隐、动态路由注册 |
| `BUTTON` | 页面内按钮 | 无 | 按钮显隐 |
| `API` | 后端接口 | `http_method` + `path` | 安全边界，由鉴权拦截器强制 |
| `SYSTEM` | 系统级通配权限 | 无 | 仅用于 `*` |

- 一个 `MENU` 下挂若干 `BUTTON` 与 `API`，构成权限树。
- 每个权限点都是可独立授权的最小单位。
- 禁止服务端做"授予菜单自动授予其下全部子节点"的联动。前端可提供父子联动勾选，但提交的必须是完整显式权限码列表。
  依据：隐式放大使授权结果不可预测，与显式审计冲突。

## 3. 表清单与容量

| 表名 | 说明 | 初期行数 | 远期（5 万用户） |
|---|---|---|---|
| `sys_user` | 用户 | 10,000 | 50,000 |
| `sys_role` | 角色 | 200 | 500 |
| `sys_permission` | 权限点 | 1,000 ~ 3,000 | 5,000 |
| `sys_user_role` | 用户-角色关系 | 30,000 | 150,000 |
| `sys_role_permission` | 角色-权限关系 | 10,000 | 30,000 |
| `sys_audit_log` | 审计日志 | 每天数百至数千条 | 保留 180 天，需归档 |

内存缓存占用（每个应用实例）：

| 缓存 | 计算 | 初期 | 远期 |
|---|---|---|---|
| userId→roleIds | 用户数 × 平均 3 角色 × 约 130B | 约 4MB | 约 20MB |
| roleId→permissionCodes | 角色数 × 平均 60 权限 × 约 60B | 约 1MB | 约 2MB |
| userId→{tokenVersion,enabled,mustChangePassword} | 活跃用户数 × 约 64B | 约 1MB | 约 5MB |
| 合计 | — | < 10MB | < 30MB |

数据量上限假设：用户 ≤ 5 万时本方案成立。用户数达到 10 万以上需重新设计缓存架构（改为分片或引入二级缓存）。

## 4. 表结构

### 4.1 sys_user

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | BIGINT | PK, AUTO_INCREMENT | 主键 |
| `username` | VARCHAR(64) | NOT NULL, UNIQUE | 登录账号；创建后不可修改 |
| `password_hash` | VARCHAR(100) | NOT NULL | BCrypt 哈希；不得出现在日志、响应、审计快照中 |
| `nickname` | VARCHAR(64) | NOT NULL | 显示名 |
| `email` | VARCHAR(128) | NULL | |
| `phone` | VARCHAR(32) | NULL | |
| `status` | TINYINT | NOT NULL, DEFAULT 1 | 1 启用 / 0 停用 / 2 已删除 |
| `token_version` | INT | NOT NULL, DEFAULT 0 | 登出、改密、停用时 +1；**登录与续期不改**；鉴权时与身份快照比对 |
| `must_change_password` | TINYINT | NOT NULL, DEFAULT 0 | 1 表示必须改密；初始 admin、管理员新增用户、重置密码后置 1，改密后置 0；随身份快照加载 |
| `role_version` | INT | NOT NULL, DEFAULT 0 | 该用户角色集合变更时 +1；用于覆盖式授权的乐观锁 |
| `fail_count` | SMALLINT | NOT NULL, DEFAULT 0 | 连续登录失败次数 |
| `locked_until` | DATETIME(3) | NULL | 锁定截止时间；NULL 表示未锁定 |
| `last_login_at` | DATETIME(3) | NULL | |
| `remark` | VARCHAR(255) | NULL | |
| `created_by` | BIGINT | NULL | |
| `created_at` | DATETIME(3) | NOT NULL | |
| `updated_by` | BIGINT | NULL | |
| `updated_at` | DATETIME(3) | NOT NULL | |

索引：

- `PRIMARY KEY (id)`
- `UNIQUE KEY uk_username (username)`

设计约束：

- `fail_count` / `locked_until` 放主表，不放 Redis。登录 QPS 极低（1 万用户 1 小时内全部登录约 3 QPS），无需引入额外状态存储。
- 登录成功后 `fail_count` 清零、`locked_until` 置 NULL；锁定到期后允许重试。
- `token_version` 是账号级撤销水位，不是会话标识；多会话下它不区分设备或进程。需要单令牌撤销时必须新增会话表或 `jti`。
- `username` 唯一键包含已删除用户，删除后账号不可复用；角色码、权限码同理。
- `status` 不单独建索引：区分度差（绝大多数为启用），且会拖慢写入。列表查询按 `id DESC` 分页，`status` 回表后过滤。若实测列表查询超时，再评估 `(status, id)` 组合索引。

### 4.2 sys_role

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | BIGINT | PK, AUTO_INCREMENT | |
| `code` | VARCHAR(64) | NOT NULL, UNIQUE | 角色编码；创建后不可修改 |
| `name` | VARCHAR(64) | NOT NULL | |
| `description` | VARCHAR(255) | NULL | |
| `inherit_role_id` | BIGINT | NOT NULL, DEFAULT 0 | 权限继承来源角色 ID；0 表示不继承。RBAC0 阶段恒为 0 |
| `status` | TINYINT | NOT NULL, DEFAULT 1 | 1 启用 / 0 停用 / 2 已删除 |
| `is_builtin` | TINYINT | NOT NULL, DEFAULT 0 | 1 表示内置角色，不可删除、不可停用 |
| `perm_version` | INT | NOT NULL, DEFAULT 0 | 该角色权限集合变更时 +1；用于覆盖式授权的乐观锁 |
| `sort` | INT | NOT NULL, DEFAULT 0 | |
| `created_by` | BIGINT | NULL | |
| `created_at` | DATETIME(3) | NOT NULL | |
| `updated_by` | BIGINT | NULL | |
| `updated_at` | DATETIME(3) | NOT NULL | |

索引：

- `PRIMARY KEY (id)`
- `UNIQUE KEY uk_code (code)`
- `KEY idx_inherit_role_id (inherit_role_id)`

`inherit_role_id` 语义（唯一解释，禁止其他读法）：

当前角色的有效权限 = 自身权限 ∪ 其 `inherit_role_id` 所指角色及该链上全部角色的权限。越靠近链尾权限越大。

配置示例：`运营主管.inherit_role_id = 运营专员.id`，`运营总监.inherit_role_id = 运营主管.id`，则 总监 ⊇ 主管 ⊇ 专员。

- 不使用 `parent_id` 命名，避免被读成"组织上级"。
- 系统不存储组织上下级关系。若将来需要，另建独立的表。
  依据：组织上级应获得下级的能力但不自动获得下级的数据，两个概念不可压进同一字段。
- 字段保留（而非升级时再加）的理由：避免升级时的跨层改造（表 + 实体 + MyBatis 映射 + 接口响应 + 前端类型）。代价为 8 字节 × 500 行。

### 4.3 sys_permission

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | BIGINT | PK, AUTO_INCREMENT | |
| `code` | VARCHAR(128) | NOT NULL, UNIQUE | 权限码，如 `sys:user:create`；创建后不可修改 |
| `name` | VARCHAR(64) | NOT NULL | |
| `resource_type` | VARCHAR(16) | NOT NULL | `MENU` / `BUTTON` / `API` / `SYSTEM` |
| `parent_id` | BIGINT | NOT NULL, DEFAULT 0 | 权限树分组层级；0 为根 |
| `path` | VARCHAR(255) | NULL | `MENU` 为前端路由；`API` 为接口路径 |
| `http_method` | VARCHAR(16) | NULL | 仅 `API` 类；为空表示不限方法 |
| `icon` | VARCHAR(64) | NULL | 仅 `MENU` 类 |
| `status` | TINYINT | NOT NULL, DEFAULT 1 | 1 启用 / 0 停用 / 2 已删除 |
| `is_builtin` | TINYINT | NOT NULL, DEFAULT 0 | 1 表示内置权限，不可删除 |
| `sort` | INT | NOT NULL, DEFAULT 0 | 同级排序 |
| `created_at` | DATETIME(3) | NOT NULL | |
| `updated_at` | DATETIME(3) | NOT NULL | |

索引：

- `PRIMARY KEY (id)`
- `UNIQUE KEY uk_code (code)`
- `KEY idx_parent_id (parent_id)`

设计约束：

- 权限树为千级节点，一次全量查询后由应用层组装成树；禁止在数据库层做递归查询（MySQL 递归 CTE 在每请求场景下不可用）。
- `path` / `http_method` 不用于运行期 URL 匹配，只用于文档生成与构建期一致性校验。
  依据：运行期 URL 匹配需要模式匹配（性能损耗、可被绕过）、规则与代码脱节（改了接口忘改规则即越权）、匹配规则本身是攻击面。权限声明必须写在代码里（`@RequiresPermission`），与接口同文件同提交被审查。
- `parent_id` 是分组包含关系，与 `inherit_role_id` 语义无关，不得混用。

### 4.4 sys_user_role

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `user_id` | BIGINT | NOT NULL | |
| `role_id` | BIGINT | NOT NULL | |
| `created_by` | BIGINT | NULL | 授权人 |
| `created_at` | DATETIME(3) | NOT NULL | 授权时间 |

索引：

- `PRIMARY KEY (user_id, role_id)`：去重，且支撑"查某用户的角色"（`user_id` 前缀）
- `KEY idx_role_id (role_id)`：支撑"查某角色下的用户"与角色删除前引用校验

列序不可调换：鉴权链路只按 `user_id` 查询，`user_id` 必须在最左。建成 `(role_id, user_id)` 会导致每次鉴权全表扫描。

### 4.5 sys_role_permission

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `role_id` | BIGINT | NOT NULL | |
| `permission_id` | BIGINT | NOT NULL | |
| `created_by` | BIGINT | NULL | 授权人 |
| `created_at` | DATETIME(3) | NOT NULL | 授权时间 |

索引：

- `PRIMARY KEY (role_id, permission_id)`：支撑"查某角色的权限"（缓存重建查询）
- `KEY idx_permission_id (permission_id)`：支撑"查某权限被哪些角色引用"

只存 ID，不冗余 `role_code` / `permission_code`。权限码到 ID 的映射由 `sys_permission` 全量缓存提供。

### 4.6 sys_role_constraint（RBAC2 阶段创建，RBAC0 阶段不建）

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | BIGINT | PK, AUTO_INCREMENT | |
| `constraint_type` | VARCHAR(32) | NOT NULL | `MUTEX`（互斥）/ `CARDINALITY`（基数） |
| `target_a` | BIGINT | NOT NULL | 角色 A |
| `target_b` | BIGINT | NULL | 角色 B；基数约束时为 NULL |
| `max_count` | INT | NULL | 基数上限 |
| `scope` | VARCHAR(16) | NOT NULL | `SSD`（静态，授权时校验）/ `DSD`（动态） |
| `status` | TINYINT | NOT NULL, DEFAULT 1 | |
| `created_at` / `updated_at` | DATETIME(3) | NOT NULL | |

本表为纯新增，RBAC0 阶段的表和 SQL 不受影响。

### 4.7 sys_audit_log

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | BIGINT | PK, AUTO_INCREMENT | |
| `audit_category` | VARCHAR(16) | NOT NULL | `CHANGE` / `SECURITY` |
| `operator_id` | BIGINT | NULL | 允许为空：登录失败时账号可能不存在 |
| `operator_name` | VARCHAR(64) | NOT NULL | 操作人账号；账号不存在时记提交的账号名（脱敏） |
| `action` | VARCHAR(64) | NOT NULL | 如 `USER_CREATE` / `ROLE_PERM_ASSIGN` / `LOGIN` / `PERM_DENIED` |
| `target_type` | VARCHAR(32) | NULL | RBAC 域用 `USER`/`ROLE`/`PERMISSION`/`SESSION`；业务域为开放取值（如 `ORDER`） |
| `target_id` | BIGINT | NULL | 与 `target_type` 配对 |
| `detail_before` | JSON | NULL | 变更前快照，已脱敏 |
| `detail_after` | JSON | NULL | 变更后快照，已脱敏；导出类操作在此存放条件与条数 |
| `result` | TINYINT | NOT NULL | 1 成功 / 0 失败 |
| `fail_reason` | VARCHAR(255) | NULL | |
| `transaction_id` | VARCHAR(64) | NULL | 仅 `CHANGE` 类有值，用于串联同一事务内的多条审计 |
| `client_ip` | VARCHAR(64) | NOT NULL | 必须由 `ClientIpResolver` 解析，禁止直接取 `X-Forwarded-For` 首段 |
| `user_agent` | VARCHAR(512) | NULL | |
| `trace_id` | VARCHAR(64) | NULL | |
| `event_time` | DATETIME(3) | NOT NULL | 事件发生时间，由应用生成；与落库时间区分 |
| `created_at` | DATETIME(3) | NOT NULL | 落库时间 |

索引：

- `PRIMARY KEY (id)`
- `KEY idx_event_time (event_time)`：时间范围查询与归档删除
- `KEY idx_operator_time (operator_id, event_time)`：支撑"查某人做过什么"

设计约束：

- 不建 `action`、`target_type`、`result` 的独立索引。审计表写多读少，且 CHANGE 类在业务事务内同步写入，多一个二级索引就多一次索引维护成本，直接计入写接口延迟。低区分度列用"时间范围 + 回表过滤"。
- 上述两个二级索引是初始选择，必须按 §5.3 用目标数据量做 `EXPLAIN ANALYZE` 验证，不达标则调整。
- 查询维度继续增长时，出路是换存储（ClickHouse / ES）或按月分区，不是在 MySQL 上继续加索引。
- `detail_before` / `detail_after` 脱敏：统一脱敏器只覆盖 RBAC 域字段（密码、令牌、密钥）；业务字段的脱敏由业务模块在传入前完成。
- 应用层 `AuditRecord` 必须能承载本表全部业务列，并额外承载导出类的 `scope` / `resultCount` / `condition`。
  依据：字段不足会使审计白名单退化为"只记下谁干过、记不下干了什么"。
- 归档：默认保留 180 天。每日凌晨分批删除 `DELETE ... WHERE event_time < ? LIMIT 5000`；数据量大时改用按 `event_time` 的 RANGE 分区 + `DROP PARTITION`。清理由独立运维任务执行；应用账号不提供删除审计日志的接口。

## 5. 关键 SQL 与索引验证

每条上线会跑的查询都必须能说出命中哪个索引、扫描多少行。

| 场景 | SQL 形态 | 命中索引 | 扫描行数 | 状态 |
|---|---|---|---|---|
| 登录按账号查用户 | `SELECT ... FROM sys_user WHERE username = ?` | `uk_username` | 1 | 可直接断言 |
| 身份快照加载 | `SELECT token_version, status FROM sys_user WHERE id = ?` | `PRIMARY` | 1 | 每活跃用户每 30 秒一次 |
| 查用户角色 | `SELECT role_id FROM sys_user_role WHERE user_id = ?` | `PRIMARY(user_id, role_id)` | 平均 3 | 覆盖索引，无回表 |
| 快照重建：用户角色 | `SELECT user_id, role_id FROM sys_user_role` | 全表 | 3 万 | 仅快照失效后执行 |
| 快照重建：角色权限 | `SELECT rp.role_id, p.id, p.code FROM sys_role_permission rp JOIN sys_permission p ON p.id = rp.permission_id WHERE p.status = 1` | 全表 + 主键 | 1 万 | 与上一条合并加载 |
| 快照重建：角色状态与继承 | `SELECT id, inherit_role_id, status FROM sys_role` | 全表 | 500 | 与上两条合并加载 |
| 用户列表分页 | `SELECT ... FROM sys_user WHERE status <> 2 ORDER BY id DESC LIMIT ?` | `PRIMARY` | 页大小 | |
| 用户列表关键词 | `WHERE username LIKE 'kw%'` | `uk_username` | 前缀匹配数 | 需实测验证 |
| 角色用户数 | `SELECT COUNT(*) FROM sys_user_role WHERE role_id = ?` | `idx_role_id` | 约 150 | |
| 权限被引用数 | `SELECT COUNT(*) FROM sys_role_permission WHERE permission_id = ?` | `idx_permission_id` | 约 30 | |
| 权限树全量 | `SELECT ... FROM sys_permission WHERE status <> 2 ORDER BY parent_id, sort` | 全表 | 约 3000 | B 档，直接查库 |
| 审计查询（时间+操作人） | `WHERE operator_id = ? AND event_time BETWEEN ? AND ? ORDER BY id DESC LIMIT ?` | `idx_operator_time` | 该人该时段 | 需实测验证 |
| 审计查询（仅时间） | `WHERE event_time BETWEEN ? AND ? ORDER BY id DESC LIMIT ?` | `idx_event_time` | 时间范围内 | 游标翻页 |
| 删除用户前引用检查 | `SELECT 1 FROM sys_user_role WHERE user_id = ? LIMIT 1` | `PRIMARY` | ≤ 1 | |

### 5.1 缓存重建使用全表查询的依据

| 方案 | 单次鉴权成本 | 重建成本 | 数据库压力 |
|---|---|---|---|
| 每请求查库或查 Redis | 1 次往返 + 索引查询 | 无 | 2000 QPS × 1 = 2000 QPS |
| 全量快照（本方案） | 0 | 3 次全表扫描，约 10~60ms | 仅权限变更后发生，每天几次到几百次 |

### 5.2 缓存重建的并发保护

```text
失效后第一个到达的请求触发重建：
  PermissionSnapshot 是单个对象；用 AtomicReference/单飞锁保证同一时刻只有一个线程加载
  一次性加载完整快照（用户角色、角色权限、角色状态、权限启用、继承关系）
  加载完成后原子替换引用；不先清空
广播到达后不立即重建（避免 N 个实例同时打库），惰性重建
重建失败：沿用旧值，不刷新 loadedAt，指数退避重试 + 告警
陈旧时长超阈值：按 01 §5.1/§5.4 的指标告警；默认 fail-open 继续服务
仅当 rbac.cache.stale-policy=fail-closed 时拒绝请求
```

不使用分布式锁：各实例缓存内容相同且可独立重建，20 个实例各扫一次表的代价可接受；引入分布式锁会新增"锁失效导致重建风暴"与"锁超时阻塞重建"两类问题。

### 5.3 索引必须由真实数据量验证

验证流程：

1. 构造目标量级数据：初期 1 万用户 / 3 万用户角色关系 / 30 万审计记录；远期按 5 倍
2. 对每条上线会跑的查询执行 `EXPLAIN ANALYZE`，记录命中索引、扫描行数、实际耗时
3. 判定标准：命中预期索引；扫描行数处于同量级；单次耗时 ≤ 5ms（读）/ ≤ 20ms（审计查询）
4. 不达标则调整索引或改写 SQL，并把实测结果回填本表作为回归基线

两个必须专门验证的高风险查询：

| 查询 | 风险 | 处理 |
|---|---|---|
| 用户列表关键词搜索 | `LIKE '%kw%'` 无法使用 B-Tree 索引，必然全表扫描 | 只实现前缀查询 `LIKE 'kw%'`；昵称模糊搜索如需启用，必须限定结果集上限并单独验证执行计划 |
| 审计多条件组合 | 时间 + 操作人 + 类型 + 目标的组合产生多种执行计划 | 统计最常用的 3 种组合并为它们建联合索引；其余组合接受时间范围过滤 + 回表 |

"不建额外索引"是阶段性结论，判定依据只有实测扫描行数与耗时是否达标。

## 6. 逻辑删除与引用完整性

不使用物理外键，引用完整性由应用层在事务内保证。

| 操作 | 校验 | 违反时行为 |
|---|---|---|
| 删除用户 | 校验至少保留 1 个启用的超级管理员 | 拒绝；否则置 `status = 2`，同时删除其 `sys_user_role` 记录 |
| 删除角色 | 校验 `sys_user_role` 引用 | 拒绝，提示仍有 N 个用户绑定 |
| 删除角色 | 校验 `is_builtin = 0` | 拒绝 |
| 删除权限 | 校验 `sys_role_permission` 引用 | 拒绝，提示仍被 N 个角色引用 |
| 删除权限 | 校验 `is_builtin = 0` | 拒绝 |
| 停用角色 | 无 | 权限立即不生效 |
| 停用权限 | 无 | 该权限立即不生效 |
| 停用用户 | 校验至少保留 1 个启用的超级管理员 | 拒绝 |

停用不删除关系记录，而是由权限计算过滤状态，因此停用可逆且不破坏审计痕迹。权限解析器计算时过滤角色 `status = 1`；权限 `status = 1` 在 `PermissionSnapshot` 加载时完成。

无外键时的并发窗口：删除角色与分配角色同时发生时，双方都必须对目标角色行加锁（或事务内二次校验），避免产生“已删除角色被绑定”的关系。

### 6.1 覆盖式授权的并发保护

覆盖式提交（`PUT /api/users/{id}/roles`、`PUT /api/roles/{id}/permissions`）是幂等的，但会出现丢失更新：A 与 B 同时读到 `[R1]`，A 提交 `[R1,R2]`，B 提交 `[R1,R3]`，结果是 B 覆盖 A，A 的 R2 被静默丢弃。

两道防线都必须有：

| 防线 | 机制 | 解决 |
|---|---|---|
| 乐观锁 | `sys_user.role_version` / `sys_role.perm_version`；请求带 `expectedVersion`，不匹配返回 40950 | 把静默丢失变成显式冲突 |
| 行级锁 | 事务内 `SELECT ... FOR UPDATE` 锁目标行，再做约束校验与写入 | 使同一对象的变更串行化，防止约束被并发绕过 |

只留乐观锁：两个事务可能同时通过约束校验（读的是提交前状态），约束被绕过。
只留行锁：后提交者静默覆盖先提交者，数据丢失且无人知晓。
