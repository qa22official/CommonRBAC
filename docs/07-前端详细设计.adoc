== 1. 引言

=== 1.1 编写目的

本文档描述「基于 RBAC 模型的权限管理系统」前端的详细设计，作为课程设计
「前端界面设计」与「详细设计文档」的交付物，用于指导前端编码、测试与口试陈述。

=== 1.2 设计范围

* 登录认证界面
* 用户管理、角色管理、权限管理、审计日志四大管理界面
* 整体布局、动态菜单、按钮级权限控制
* 前端与后端接口的对接（axios 统一封装）

=== 1.3 术语

|===
|术语 |说明

|RBAC |基于角色的访问控制（Role-Based Access Control）
|SPA |单页应用（Single Page Application）
|token |登录后后端签发的令牌，前端每次请求随请求头携带
|permissions |用户拥有的权限码集合，是前端权限判断的唯一数据源
|v-perm |前端按钮级权限指令，无权限时移除对应按钮
|===

== 2. 总体设计

=== 2.1 技术选型及理由

|===
|技术 |选型 |理由

|框架 |Vue 3.5 |老师指定；组合式 API 逻辑复用性强
|语言 |TypeScript |静态类型，接口契约清晰，减少联调错误
|构建 |Vite 6 |启动快，HMR 开发体验好
|UI 库 |Element Plus |后台管理最成熟，表格/表单/树组件齐全
|路由 |Vue Router 4 |动态路由 + 路由守卫支撑权限控制
|状态 |Pinia 2 |轻量，统一管理登录态与动态菜单
|请求 |Axios |拦截器统一加 token、统一错误处理
|===

=== 2.2 前端架构分层

[source,text]
----
视图层（views / layout）
        ↓ 调用
状态层（stores：auth、permission）
        ↓ 调用
接口层（api / request：axios 封装）
        ↓ HTTP
后端 /api（JavaEE）
----

分层的理由：视图层只负责展示与交互，接口层统一处理 HTTP 与错误码，
状态层共享登录态与权限，避免各页面重复编写鉴权与请求逻辑。

=== 2.3 目录结构

[source,text]
----
web/src/
├── api/            # axios 实例 + 各模块接口封装
│   ├── request.ts  # 拦截器（Bearer 令牌、错误码、401 跳登录）
│   ├── auth.ts / user.ts / role.ts / permission.ts / audit.ts
├── types/          # 与后端契约对齐的 TS 类型（camelCase）
├── stores/         # pinia：auth（登录态/权限）、permission（动态菜单）
├── router/         # 静态路由 + 动态路由注册 + 守卫
├── directives/     # v-perm 按钮级权限指令
├── layout/         # 整体布局（侧边栏递归菜单 + 顶栏）
└── views/          # 登录 / 首页 / 个人中心 / 用户 / 角色 / 权限 / 审计
----

== 3. 模块设计

=== 3.1 登录认证模块

需求：账号密码登录，失败给出中文提示（账号错误 / 停用 / 锁定 / 限流）。

设计：登录页调用 `POST /api/auth/login`，成功后把 `accessToken` 存入
`localStorage`，再调用 `GET /api/auth/me` 拉取用户信息与权限码集合。
修改密码后后端 `token_version` 自增，当前令牌作废，前端自动登出回登录页。

=== 3.2 用户管理模块

需求：用户列表分页查询、新增、编辑、删除、启用停用、重置密码、分配角色。

设计：表格 + 弹窗表单；分配角色使用多选下拉，携带 `expectedVersion`
乐观锁，收到 `40950` 冲突时自动重新拉取并提示用户，禁止静默重放。

=== 3.3 角色管理模块

需求：角色增删改查、启用停用、授权权限树；内置角色不可删除/停用。

设计：授权使用 `el-tree` 且开启 `check-strictly`（显式勾选），提交时
收集完整权限码列表，避免父子联动导致隐式放大授权。

=== 3.4 权限管理模块

需求：权限树形展示、增删改、新增子节点，资源类型分 MENU / BUTTON / API / SYSTEM 四类。

设计：`el-table` 树形数据（`row-key` + `tree-props`），权限码创建后不可修改。

=== 3.5 审计日志模块

需求：按时间范围查询（必填）、按类别/动作/结果筛选、游标翻页、查看详情快照。

设计：游标分页（上一页 / 下一页按钮），时间范围必填以避免大表全表扫描；
详情以 JSON 展示变更前 / 变更后快照。

== 4. 路由与权限控制设计

=== 4.1 路由设计

* 静态路由：`/login`、`/`（布局）、`/dashboard`、`/profile`
* 动态路由：登录后按权限码过滤权限树，注册 `/system/users` 等页面路由
* 路由守卫：未登录跳登录页；已登录先加载用户信息与菜单再放行

=== 4.2 权限控制（三层）

. 菜单过滤 —— 无权限的菜单不渲染
. 路由守卫 —— 无权限即使直接输入 URL 也被拦截
. 按钮权限 `v-perm` —— 无权限的按钮自动移除

=== 4.3 权限码模型

权限码格式为 `<模块>:<资源>:<操作>`，例如 `sys:user:create`；
通配码 `*` 命中一切，`sys:user:*` 前缀匹配用户模块全部权限。
前端权限唯一数据源是 `GET /api/auth/me` 返回的 `permissions` 数组。

== 5. API 调用设计

=== 5.1 axios 统一封装

* 请求拦截器：自动附加 `Authorization: Bearer <token>`
* 响应拦截器：`code === 0` 解包 `data`；`40100/40101` 清除令牌并跳登录；
  `40950` 交调用方重新拉取；其余错误透传错误码与中文提示

=== 5.2 主要接口对照表

|===
|页面 |接口 |说明

|登录 |POST /api/auth/login |账号密码登录，返回 token
|首页 |GET /api/auth/me |获取用户信息与权限码
|用户管理 |GET/POST/PUT/DELETE /api/users |查/增/改/删用户
|用户管理 |PUT /api/users/{id}/status |启用 / 停用
|用户管理 |PUT /api/users/{id}/password:reset |重置密码
|用户管理 |GET/PUT /api/users/{id}/roles |查 / 分配角色
|角色管理 |GET/POST/PUT/DELETE /api/roles |查/增/改/删角色
|角色管理 |GET/PUT /api/roles/{id}/permissions |查 / 分配权限
|权限管理 |GET /api/permissions/tree |权限树
|权限管理 |POST/PUT/DELETE /api/permissions |增/改/删权限点
|审计日志 |GET /api/audit-logs |游标分页查询
|个人中心 |PUT /api/auth/password |修改密码
|===

== 6. 关键设计决策

=== 6.1 为什么用动态菜单而非写死菜单

菜单由后端权限树驱动，权限变更无需改前端代码，实现「权限即配置」，
符合 RBAC 权限集中管理的思想。

=== 6.2 为什么授权树使用 check-strictly

保证提交的是完整显式权限码列表，避免父子联动造成隐式放大授权，
使授权结果可预测、可审计。

=== 6.3 为什么用 expectedVersion 乐观锁

覆盖式授权存在丢失更新风险，携带版本号可把并发覆盖变为显式冲突
（40950），由用户确认后重试，保证数据一致。

== 7. 实现效果

* 可运行：`npm install && npm run dev`，登录后进入后台管理界面
* 可构建：`npm run build` 通过 `vue-tsc` 类型检查与 Vite 打包
* 开发环境 `/api` 由 Vite 代理到后端 `http://localhost:8080`
