## 1. 通用约定

### 1.1 基础约定

| 项 | 约定 |
|---|---|
| 基础路径 | `/api` |
| 风格 | RESTful；资源名复数、小写、连字符 |
| 数据格式 | 请求与响应均为 `application/json; charset=utf-8` |
| 时间格式 | ISO-8601 带时区偏移，如 `2026-10-12T20:15:30.123+08:00`；禁止无时区的时间串 |
| 认证方式 | 请求头 `Authorization: Bearer <token>`；不放 URL 参数，不使用 Cookie 会话 |
| 客户端 IP | 只能由 `ClientIpResolver` 在可信代理边界内解析；不接受请求体、查询参数或未校验请求头传入的 IP |
| 版本策略 | 不使用 `/v1` 前缀；契约变更通过新增字段或新增接口实现，不修改既有字段语义 |
| 字段命名 | 驼峰，如 `createdAt` |
| 令牌失效时效 | 多会话：登录不撤销既有令牌；登出/改密/停用撤销该账号全部令牌。正常 ≤ 1 秒；Redis 故障 ≤ 30 秒（见 01 FR-A9）；禁止承诺"立即失效" |

### 1.2 统一响应体

```json
{ "code": 0, "message": "ok", "data": {}, "traceId": "b7f2c1a9e4d3" }
```

| 字段 | 说明 |
|---|---|
| `code` | 0 表示成功；非 0 为业务错误码（见 1.3） |
| `message` | 面向用户的中文提示 |
| `data` | 业务数据；无数据时为 `null` |
| `traceId` | 链路追踪 ID，同时写入响应头 `X-Trace-Id` |

### 1.3 错误码

| HTTP | `code` | 含义 | 前端处理 |
|---|---|---|---|
| 200 | 0 | 成功 | 正常处理 |
| 400 | 40000 | 参数校验失败 | 表单内联提示字段级错误 |
| 401 | 40100 | 令牌本身无效（缺失/签名错误/已过期） | 清除本地令牌，跳转登录页 |
| 401 | 40101 | 令牌有效但已被作废（登出/改密/停用） | 同上，提示"登录状态已失效" |
| 403 | 40300 | 无操作权限 | 提示"无操作权限"；不得返回所需权限码 |
| 404 | 40400 | 资源不存在 | 提示并返回列表 |
| 409 | 40900 | 唯一性冲突（账号/角色码/权限码重复） | 表单内联提示 |
| 409 | 40950 | 并发冲突，`expectedVersion` 不匹配 | 重新拉取最新数据并提示"数据已被他人修改"；禁止静默重放 |
| 429 | 42900 | 限流 | 提示稍后重试，展示倒计时 |
| 503 | 50300 | 服务降级：鉴权数据从未成功加载，或已切到 fail-closed 姿态 | 展示"系统暂时不可用"，按 `Retry-After` 重试 |
| 500 | 50000 | 服务器内部错误 | 提示"系统繁忙"，展示 `traceId`；响应体不得含堆栈 |

HTTP 状态按 code 前缀映射：`400xx→400`、`401xx→401`、`403xx→403`、`409xx→409`、`429xx→429`、`5xxxx→5xx`。业务码完整清单见 §2.1、§3、§4、§5；前端必须用 `code` 判断语义，不能只看 HTTP 状态。

必须分开的三组状态，不得合并：

- 40101 与 40100：前者是"有效但被作废"，后者是"令牌无效"。合并会丢失"批量踢下线/令牌滥用"的监测能力。
- 50300 与 500：前者是按设计降级，后者是程序错误。合并会让运维把设计内降级误判为代码缺陷。
- 40950 与 40900：前者是版本冲突（刷新后重试可解决），后者是唯一约束冲突（必须换值）。

### 1.4 分页

浅翻页（默认）：

| 参数 | 类型 | 默认 | 约束 |
|---|---|---|---|
| `page` | int | 1 | 从 1 开始 |
| `size` | int | 20 | 上限 200；超过返回 40000 |

响应结构：

```json
{ "records": [], "total": 1234, "page": 1, "size": 20 }
```

游标分页（仅审计日志使用）：

| 参数 | 说明 |
|---|---|
| `lastId` | 上一页最后一条 ID；首页不传 |
| 响应额外字段 | `nextLastId`，无更多数据时为 `null` |

审计日志禁止使用 `OFFSET`：`LIMIT 100000, 20` 会先扫描并丢弃前 10 万行。必须用 `WHERE id < lastId ORDER BY id DESC LIMIT ?`。

### 1.5 鉴权声明（强制）

每个 `@RequestMapping` 方法必须有且只有一个鉴权声明：

| 注解 | 含义 | 使用场景 |
|---|---|---|
| `@PublicApi` | 无需登录 | 登录、健康检查 |
| `@RequiresLogin` | 需要登录，不需要权限码 | `/api/auth/me`、登出、改自己的密码、`/api/auth/permit`、`/api/auth/permission-check` |
| `@RequiresPermission("码")` | 需要登录且拥有该权限码 | 全部管理类接口 |

- 三者都不标注：默认拒绝，返回 403 并记录告警；由构建门禁拦截。Actuator、`/error`、CORS `OPTIONS` 走显式 allowlist。
- `@RequiresPermission` 只接受 API 类权限码或通配码（`*`、`sys:*`、`sys:user:*`）；引用 `MENU` 类权限码由门禁拦截；仅支持方法级，类级注解不被识别。
- 一个接口只声明一个权限码。需要两个权限码时拆成两个接口，禁止引入 `anyOf` / `allOf` 组合。

### 1.6 审计声明（强制，仅业务接口）

鉴权声明回答"能不能调这个接口"，审计声明回答"这次操作要不要留痕"。业务接口必须同时给出两者。

| 做法 | 含义 |
|---|---|
| 方法体内调用 `AuditRecorder` | 需要审计 |
| 方法上标注 `@NoAudit("原因")` | 明确声明无需审计，并写明理由 |
| 两者皆无 | 视为未完成，构建失败 |

`@NoAudit` 契约：

| 项 | 约定 |
|---|---|
| 位置 | `rbac-api` 注解包，与 `@RequiresPermission` 同模块 |
| 作用目标 | `@Target(METHOD)`；不支持类级 |
| 属性 | `value()` 必填，不得为空串 |
| 保留策略 | `@Retention(RUNTIME)`，供门禁与测试读取 |
| 门禁 | 业务 Controller 的方法名或路径命中敏感关键词（`export`/`download`/`print`/`delete`/`clear`/`batch`/`import`/`approve`/`grant`/`revoke`），且既未调用 `AuditRecorder` 也未标注 `@NoAudit` → 构建失败 |

门禁局限：基于关键词匹配，只能提醒不能判定。名字不含关键词的敏感操作（如 `POST /orders/{id}/submit` 触发外部转账）查不出来，不替代评审。

当前仓库没有 `biz-*` 业务模块；RBAC 管理端写接口的审计由应用服务层（`CoreAuditor`/`SecurityAuditor`）在业务事务内或独立事务中完成，因此“方法体引用 `AuditRecorder`”门禁只约束未来的业务模块 Controller。新增 `biz-*` 模块时必须补上该门禁。

### 1.7 幂等性与并发更新

| 操作类型 | 策略 |
|---|---|
| 覆盖式更新 | 集合操作天然幂等，但会丢失更新，必须叠加 `expectedVersion`（见下表） |
| 创建类（POST） | 依赖数据库唯一约束兜底；冲突返回 40900 |
| 删除类 | 天然幂等；重复删除返回成功 |
| 状态切换 | 请求体传目标状态值（如 `{"status": 0}`），禁止 toggle 语义 |

覆盖式更新的版本控制规则：

| 编号 | 规则 |
|---|---|
| V-1 | `PUT /api/users/{id}/roles` 与 `PUT /api/roles/{id}/permissions` 的请求体必须携带 `expectedVersion` |
| V-2 | 对应的 GET 接口必须返回 `version` 字段 |
| V-3 | 服务端条件更新：版本匹配则覆盖写入并将版本号 +1；不匹配返回 40950 |
| V-4 | 版本号取自 `sys_user.role_version` / `sys_role.perm_version` |
| V-5 | 事务内先锁行再校验：`SELECT ... FOR UPDATE` → 约束校验 → 覆盖写入 → 版本号 +1 |
| V-6 | 乐观锁负责发现丢失更新；行锁负责防止约束被并发绕过；两者必须同时存在 |
| V-7 | 前端收到 40950 后必须重新拉取数据，禁止静默重放 |

## 2. 认证接口

### 2.1 POST /api/auth/login — `@PublicApi`

请求：

```json
{ "username": "admin", "password": "<明文密码>" }
```

响应：

```json
{
  "code": 0,
  "data": {
    "accessToken": "<JWT>",
    "expiresIn": 7200,
    "user": { "id": 1, "username": "admin", "nickname": "管理员" },
    "mustChangePassword": false
  }
}
```

错误码：

| code | 场景 | 提示 |
|---|---|---|
| 40110 | 账号或密码错误 | "账号或密码错误"（不区分两者，防账号枚举） |
| 40111 | 账号已停用 | "账号已停用，请联系管理员" |
| 40112 | 账号已锁定 | "账号已锁定，请 X 分钟后重试" |
| 42900 | 触发限流 | "操作过于频繁，请稍后重试" |

限流：同一账号 5 次/分钟；同一 IP 20 次/分钟（滑动窗口）；超限返回 429。Redis 故障时关闭基于 Redis 的账号/IP 限流并告警，数据库账号锁定仍生效。

登录**不修改** `token_version`（多会话），也不发布失效事件；账号不存在也执行一次 dummy BCrypt，避免用响应时间枚举账号。

### 2.2 GET /api/auth/me — `@RequiresLogin`

响应：

```json
{
  "code": 0,
  "data": {
    "user": { "id": 1, "username": "admin", "nickname": "管理员", "email": "a@b.com" },
    "permissions": ["*"],
    "roles": [{ "id": 1, "code": "SUPER_ADMIN", "name": "超级管理员" }],
    "mustChangePassword": false
  }
}
```

| 字段 | 用途与约束 |
|---|---|
| `permissions` | 前端权限的唯一数据源：菜单过滤、路由注册、`v-perm` 均依赖它 |
| `roles` | 仅用于个人中心展示；前端不得用角色编码做权限判断 |
| `mustChangePassword` | 为 true 时前端跳转改密页；后端仅放行改密、登出与该接口 |
| `permissions`（外部服务） | 服务账号可调用本接口拉取权限集并本地缓存；缓存时长不得超过 30 秒 |

外部系统不以本接口渲染最终用户菜单：本接口只返回令牌主体（服务账号本人）的权限；18 个外部系统只做 API 鉴权，不共享本系统菜单。

### 2.3 POST /api/auth/logout — `@RequiresLogin`

行为：`token_version` 自增 → 广播作废通知 → 各实例拒绝该账号既有令牌。响应 `{"code": 0}`。

语义约束：

| 项 | 说明 |
|---|---|
| 撤销范围 | **账号级**：该账号全部令牌失效，包括调用方自己的令牌和其他设备、其他进程的令牌 |
| 不是单令牌撤销 | 无 `jti`、无会话表，做不到"只登出当前设备" |
| 本实例生效 | 立即 |
| 其他实例生效 | Redis 正常 ≤ 1 秒；Redis 故障 ≤ 30 秒 |
| 重复调用 | 同一令牌第二次调用返回 40101；客户端应视为已登出 |
| 幂等建议 | 客户端把 40101 当作登出成功，不重试、不告警 |
| 审计 | 写 SECURITY 事件，操作人为该账号 |

调用方注意：

1. 调用前令牌必须仍然有效，因此必须先 logout 再丢弃本地令牌。
2. 多副本部署时不要在进程关闭钩子里调用 logout，否则会误伤其他副本；进程退出只丢弃本地令牌。
3. 账号被共用时，任一方 logout 会让其余方立即失效；因此外部服务必须一服务一账号。

### 2.4 POST /api/auth/refresh — `@RequiresLogin`

行为：校验当前令牌有效（未过期）→ 读取最新 `token_version` 与账号状态 → 签发新令牌。不递增 `token_version`；状态或版本已变更则返回 40101。

响应：

```json
{ "code": 0, "data": { "accessToken": "<JWT>", "expiresIn": 7200 } }
```

多会话下本接口可被同一账号的多个客户端重复调用，彼此不影响。

### 2.5 PUT /api/auth/password — `@RequiresLogin`

请求：`{ "oldPassword": "...", "newPassword": "..." }`

行为：校验旧密码 → 校验强度策略 → 更新哈希 → `must_change_password = 0` → `token_version` 自增 → 写安全事件。

### 2.6 POST /api/auth/permit — `@RequiresLogin`

供外部服务逐次判定时使用；也可由前端调用，但前端只用 `/api/auth/me` 即可。

请求：

```json
{ "permissionCode": "biz:order:export" }
```

响应：

```json
{ "code": 0, "data": { "allowed": true, "userId": 42, "degraded": false } }
```

| 字段 | 说明 |
|---|---|
| `allowed` | 判定结果；**拒绝时仍返回 `code = 0`**，不使用 403 |
| `userId` | 令牌主体，供调用方记录 |
| `degraded` | true 表示判定基于陈旧快照（fail-open），调用方可自行决定是否采信 |

档位：A（纯内存判定，无 DB 访问；快照未命中时由缓存层单飞重建，仅影响该请求）。

约束：

- 只能查询令牌主体自己的权限，**不接受** `userId`、`username` 之类参数，避免横向探测权限结构。
- 响应头 `Cache-Control: no-store`；禁止被代理或 CDN 缓存。
- 纯读、不改数据、不外带数据，标注 `@NoAudit("纯鉴权判定")`；拒绝靠 403/40101 指标观测。
- 缺参数或权限码格式非法返回 40000。
- 令牌无效返回 40100；已作废返回 40101；从未成功加载过快照且 fail-closed 时返回 50300。

18 个外部系统判断最终用户时使用 §2.7，不使用本接口；本接口只判定服务账号自己。

### 2.7 POST /api/auth/permission-check — `@RequiresLogin`

查询**指定用户**是否拥有指定权限码。与 §2.6 的区别：`/permit` 只能查令牌主体自己，本接口可以查任意用户。

请求：

```json
{ "userId": 42, "permissionCodes": ["oa:doc:receive.view", "oa:doc:receive.approve"] }
```

响应：

```json
{
  "code": 0,
  "data": {
    "userId": 42,
    "degraded": false,
    "results": [
      { "permissionCode": "oa:doc:receive.view",    "allowed": true,  "reason": "ALLOWED" },
      { "permissionCode": "oa:doc:receive.approve", "allowed": false, "reason": "NO_PERMISSION" }
    ]
  }
}
```

| 字段 | 说明 |
|---|---|
| `userId` | 与请求一致；用户不存在时原样回显 |
| `degraded` | true 表示判定基于陈旧快照（fail-open） |
| `results[].allowed` | 判定结果；**拒绝时仍返回 `code = 0`** |
| `results[].reason` | `ALLOWED` / `NO_PERMISSION` / `USER_NOT_FOUND` / `USER_DISABLED` |

规则：

| 项 | 约定 |
|---|---|
| `permissionCodes` | 1~50 个；为空或超过 50 返回 40000 |
| 权限码格式 | 必须符合 `<模块>:<资源>:<操作>`，或为通配码 `*`、`sys:user:*`；外部系统按 §7.3 使用 `app:module:function.action`；非法返回 40000 |
| 用户不存在或已删除 | 全部 `allowed=false`，`reason=USER_NOT_FOUND` |
| 用户已停用 | 全部 `allowed=false`，`reason=USER_DISABLED` |
| 权限码未定义 | `allowed=false`，`reason=NO_PERMISSION`；不报错 |
| 判定依据 | 与内部鉴权同一套规则（`PermissionResolver` + `PermissionMatcher`），含角色状态与继承 |
| 用户状态来源 | `IdentityQuery`（`IdentitySnapshot`，30 秒软 TTL）；冷缓存或未命中时一次主键查询 |
| 响应头 | `Cache-Control: no-store` |
| 审计 | 纯读，标注 `@NoAudit("纯鉴权判定")`；不写审计表 |
| 档位 | A（权限判定纯内存；身份状态通常命中快照，未命中时一次主键查询） |
| 鉴权 | 保持 `@RequiresLogin`：任何已登录账号可查询任意用户；不新增 `sys:auth:check`，靠专用服务账号、网络白名单与审计治理 |

**18 个外部系统使用约束**（当前最小方案）：

| 项 | 约定 |
|---|---|
| 调用者 | 每个外部系统一个专用服务账号；不新增 `sys:auth:check`；调用者边界靠服务账号治理与网络白名单 |
| 目标用户 | 只接受 `userId`；外部系统自行维护工号/用户名到 `userId` 的映射 |
| 应用隔离 | 无 `appCode`；应用用权限码前缀区分（见 §7.3）；本接口不校验调用者与目标权限码是否属于同一应用 |
| 批量 | 单次 1~50 个；外部系统分批调用并合并 |
| 菜单 | 不返回菜单树或权限全集；外部系统只做 API 鉴权，不渲染中心菜单 |
| 数据范围 | 只判功能权限；本人/部门/分公司/项目过滤由外部系统负责 |
| 缓存与时效 | 外部系统可缓存结果；端到端时效 = 本系统 1s/30s + 外部缓存 TTL；`degraded=true` 时必须按外部系统自己的降级策略处理 |
| 审计 | 本接口 `@NoAudit`；外部系统记录自己的操作审计，中心不记录查询 |
| 网络与限流 | 本接口无按应用限流；外部系统自限并发，中心侧以网络白名单/出口访问控制补偿 |

残余风险：任何已登录账号仍可查询任意用户。该风险已接受；如后续要收紧，最小改动是新增 `sys:auth:check` 并给服务账号授予。

调用示例：

```http
POST /api/auth/permission-check HTTP/1.1
Authorization: Bearer <service JWT>
Content-Type: application/json

{"userId":42,"permissionCodes":["oa:doc:receive.view"]}
```

错误码：`40000` 参数非法；`40100` 令牌无效；`40101` 令牌已作废；`50300` 从未成功加载快照且 fail-closed。

### 2.8 服务型客户端约定

外部服务接入使用上述认证接口，不新增登录协议。

18 个外部系统（OA、HR、财务、PMIS 等）的接入口径：

- 外部系统自行认证最终用户；本系统不做 SSO/OIDC，只回答权限判定。
- 一系统一服务账号；服务账号只调用 `/permission-check`，不用于 Web 登录。
- 不建应用表、不传 `appCode`；应用用权限码前缀区分（见 §7.3）。
- 判断最终用户只用 `/permission-check`，按 1~50 个码分批；没有全量权限接口。
- 外部系统不渲染中心菜单；菜单/按钮由各系统自己维护，服务端 API 必须调用本接口。
- 数据范围由外部系统负责；本系统只判功能权限。
- 10,000 名员工的 5 类角色由中心管理员统一分配；外部系统只查询，不调用用户/角色管理接口。
- 外部系统自行缓存时，端到端生效时效 = 本系统 1s/30s + 外部 TTL。

生命周期：

```text
1. 启动   POST /api/auth/login      专用服务账号，取 token（2h）
2. 运行   POST /api/auth/refresh    约 90 分钟续期，避免反复传密码
3. 鉴权   判断服务账号自己：
             GET  /api/auth/me         拉权限集，本地缓存 ≤ 30 秒后本地判定
             或 POST /api/auth/permit  逐次判定
          判断指定用户：
             POST /api/auth/permission-check  { userId, permissionCodes[] }
4. 40101  停止重试，指数退避 + 抖动后重新 login
5. 退出   只丢弃本地令牌，不调 logout
6. 止损   凭据泄露或整服务下线时，人工/脚本调用 logout 或停用账号
```

| 场景 | 用哪个接口 |
|---|---|
| 外部服务代表自己判断能不能调某功能 | `/api/auth/me` 或 `/api/auth/permit` |
| 外部服务判断某个最终用户有没有某项权限 | `/api/auth/permission-check` |
| 需要一次判多个权限码 | `/api/auth/permission-check`（单次最多 50 个） |
| 18 个外部系统判断最终用户 | `/api/auth/permission-check`（按 1~50 个码分批） |
| 18 个外部系统渲染菜单 | 不支持：本系统不返回菜单树/权限全集；外部系统只做 API 鉴权 |

硬性约束：

| 约束 | 原因 |
|---|---|
| 一服务一账号 | logout 与改密是账号级，共用账号会互相踢下线 |
| 服务账号不得用于 Web 登录 | 避免服务令牌与人工会话相互影响；当前模型不强制，靠运维约束 |
| 不授予 `sys:*` | 服务账号只授予完成接入所需的权限码；18 个外部系统只调 `permission-check`，可不授予业务权限码 |
| 不得代最终用户操作 | `permission-check` 只回答判定，不产生以该用户身份执行的令牌；代用户操作属 SSO/OIDC 范畴，本期不做 |
| 令牌只放 `Authorization` 头 | 不进 URL、不进 query、不进日志 |
| 本地判定的调用方必须可信 | 模式 A 把最终判定权交给调用方；模式 B 保留在本系统 |
| 不建应用表 | 18 个系统只用权限码前缀区分；没有应用级限流、审计或管理员 |
| 外部系统自行维护用户映射 | 接口只接受 `userId`；工号/用户名映射由外部系统维护 |
| 外部系统自行做数据范围 | 本系统只判功能权限，不返回 scope |
| 菜单不共享 | 本系统不返回菜单树；外部系统只做 API 鉴权 |

## 3. 用户管理接口

| 方法 | 路径 | 权限码 | 说明 | 档 |
|---|---|---|---|---|
| GET | `/api/users` | `sys:user:read` | 分页列表，支持 `keyword`（账号前缀匹配）、`status` | A |
| GET | `/api/users/{id}` | `sys:user:read` | 详情 | A |
| POST | `/api/users` | `sys:user:create` | 新增，响应 `{ "id": n }` | B |
| PUT | `/api/users/{id}` | `sys:user:update` | 编辑（不含角色） | B |
| DELETE | `/api/users/{id}` | `sys:user:delete` | 逻辑删除 | B |
| PUT | `/api/users/{id}/status` | `sys:user:toggle` | 启用/停用，传目标状态 | B |
| PUT | `/api/users/{id}/password:reset` | `sys:user:reset-password` | 请求体 `{newPassword}`；重置后置 `must_change_password = 1` | B |
| GET | `/api/users/{id}/roles` | `sys:user:read` | 查询已分配角色，响应含 `version` | A |
| PUT | `/api/users/{id}/roles` | `sys:user:assign-role` | 覆盖式设置角色集合，必须带 `expectedVersion` | B |

`POST /api/users` 请求体：

```json
{
  "username": "zhangsan",
  "nickname": "张三",
  "email": "z@b.com",
  "phone": "13800000000",
  "status": 1,
  "remark": "运维组",
  "initialPassword": "Admin@12345"
}
```

创建成功响应：`{ "code": 0, "data": { "id": 1 } }`；创建后置 `must_change_password = 1`。

`PUT /api/users/{id}` 请求体（只编辑资料，不含账号、状态、密码）：

```json
{
  "nickname": "张三",
  "email": "z@b.com",
  "phone": "13800000000",
  "remark": "运维组"
}
```

账号 `username` 创建后不可修改；启停使用 `PUT /api/users/{id}/status`；密码使用重置接口或本人改密接口。`PUT` 不接受 `username`、`status`、密码字段，传了也不会生效（服务端不读取）。

`PUT /api/users/{id}/roles` 请求体：

```json
{ "roleIds": [2, 5, 7], "expectedVersion": 12 }
```

`GET /api/users/{id}/roles` 响应：

```json
{ "code": 0, "data": { "roleIds": [2, 5], "version": 12 } }
```

角色集合变更成功后 `role_version + 1` 并发布 `PERM_CHANGED`，使各实例的 `PermissionSnapshot` 失效。

校验规则与错误码：

| 规则 | code | 提示 |
|---|---|---|
| 账号重复 | 40900 | "该账号已存在" |
| 删除/停用自己 | 40310 | "不能停用或删除当前登录账号" |
| 移除自己最后一个管理类角色 | 40311 | "不能移除自己的最后一个管理角色" |
| 停用/删除最后一个超级管理员 | 40312 | "系统必须保留至少一个启用的超级管理员" |
| 密码强度不足 | 40010 | "密码需至少 8 位，且包含大小写字母与数字" |
| 角色集合版本不匹配 | 40950 | 见 1.3 |

关键词搜索实现约束：`keyword` 只做账号前缀匹配 `LIKE 'kw%'`；禁止 `LIKE '%kw%'`。昵称模糊搜索如需启用，必须限定结果集上限并单独验证执行计划。

## 4. 角色管理接口

| 方法 | 路径 | 权限码 | 说明 | 档 |
|---|---|---|---|---|
| GET | `/api/roles` | `sys:role:read` | 分页列表，支持 `keyword`、`status` | A |
| GET | `/api/roles/options` | `sys:role:read` | 下拉选项（不分页，仅启用角色） | A |
| GET | `/api/roles/tree` | `sys:role:read` | 按 `inheritRoleId` 组织的角色树（含停用角色，不返回删除角色） | A |
| GET | `/api/roles/{id}` | `sys:role:read` | 详情（含已绑定权限数、用户数） | A |
| POST | `/api/roles` | `sys:role:create` | 新增，响应 `{ "id": n }` | B |
| PUT | `/api/roles/{id}` | `sys:role:update` | 编辑 | B |
| DELETE | `/api/roles/{id}` | `sys:role:delete` | 逻辑删除，需先校验引用 | B |
| PUT | `/api/roles/{id}/status` | `sys:role:toggle` | 启用/停用，传目标状态 | B |
| GET | `/api/roles/{id}/permissions` | `sys:role:read` | 查询已授权限，响应含 `version` | A |
| PUT | `/api/roles/{id}/permissions` | `sys:role:assign-perm` | 覆盖式设置权限集合，必须带 `expectedVersion` | B |

角色响应与创建/编辑请求包含可选 `inheritRoleId`（0 或 null 表示不继承），列表/详情额外返回 `inheritRoleName`；继承方向、环与深度错误见 [05 §4.6](./05-RBAC0到RBAC3演进设计.md)。

`GET /api/roles/tree` 返回 `RoleTreeNode[]`：每个节点包含 `id/code/name/description/status/builtin/sort/inheritRoleId/inheritRoleName/children`，节点挂在它继承的来源角色下，根为 `inheritRoleId=0`（脏数据成环时按根降级展示）；该接口一次返回全部角色，不分页。

`PUT /api/roles/{id}/permissions` 请求体：

```json
{
  "permissionCodes": ["sys:user:read", "sys:user:create", "sys:role:read"],
  "expectedVersion": 7
}
```

使用 `permissionCodes` 而非 `permissionIds`：前端权限树节点自带 code，勾选即得；请求体可读，便于排障。服务端在授权事务内按 code 查询 `sys_permission` 的启用记录并取得 id（`rbac-core` 不能反向依赖 `rbac-cache` 的快照）。

提交成功后发布 `PERM_CHANGED`；角色编辑（含 `inheritRoleId`）、启停、删除同样发布该事件，使各实例的 `PermissionSnapshot` 失效。

校验规则与错误码：

| 规则 | code | 提示 |
|---|---|---|
| 角色码重复 | 40900 | "该角色编码已存在" |
| 删除被用户引用的角色 | 40910 | "该角色仍被 N 个用户绑定，无法删除" |
| 修改/删除内置角色 | 40320 | "内置角色不允许此操作" |
| 修改内置角色的 `*` 权限 | 40321 | "不允许修改内置角色的全部权限" |
| 权限集合版本不匹配 | 40950 | 见 1.3 |

## 5. 权限管理接口

| 方法 | 路径 | 权限码 | 说明 | 档 |
|---|---|---|---|---|
| GET | `/api/permissions/tree` | `sys:perm:read` | 全量权限树（直接查库） | B |
| GET | `/api/permissions/{id}` | `sys:perm:read` | 详情 | A |
| POST | `/api/permissions` | `sys:perm:create` | 新增权限点，响应 `{ "id": n }` | B |
| PUT | `/api/permissions/{id}` | `sys:perm:update` | 编辑；`code` 不可修改 | B |
| DELETE | `/api/permissions/{id}` | `sys:perm:delete` | 逻辑删除，需先校验引用 | B |

权限启停没有独立路径，使用 `PUT /api/permissions/{id}` 的 `status` 字段（0 停用 / 1 启用）；`status` 变更同样发布 `PERM_CHANGED`，使 `PermissionSnapshot` 失效。

权限树响应：

```json
{
  "code": 0,
  "data": [
    {
      "id": 10, "code": "sys:user", "name": "用户管理", "resourceType": "MENU",
      "path": "/system/users", "icon": "user", "sort": 10,
      "children": [
        { "id": 11, "code": "sys:user:read", "name": "查询用户", "resourceType": "API", "children": [] },
        { "id": 12, "code": "sys:user:create", "name": "新增用户", "resourceType": "API", "children": [] }
      ]
    }
  ]
}
```

`sys:user` 这类无操作后缀的节点是 `MENU` 类，用于菜单显隐与路由注册，不得作为 `@RequiresPermission` 的取值。这样可保证通配码 `sys:user:*` 只命中 API 权限码。

校验规则与错误码：

| 规则 | code |
|---|---|
| 权限码重复 | 40900 |
| 权限码格式非法（不符合 `<模块>:<资源>:<操作>`） | 40020 |
| 授权时权限码格式合法但未定义或已停用 | 40020 |
| 修改 `code` | 40330 |
| 删除被角色引用的权限 | 40920 |
| 删除内置权限 | 40331 |

权限新增、编辑、删除、启停后必须发布 `PERM_CHANGED`；`status` 停用必须让 `PermissionSnapshot` 失效，否则“停用权限立即不生效”无法保证。

外部系统权限码示例：

```text
oa:doc:receive              收文登记与流转（MENU）
oa:doc:receive.view         查看
oa:doc:receive.edit         编辑
oa:doc:receive.approve      审批
oa:doc:*                    公文管理下全部
oa:*                        OA 系统全部（仅系统管理员角色）
admin:user:read             系统管理后台的用户查看
```

- `sys` 保留给 RBAC 平台自身；清单中的“系统管理后台”使用 `admin`。
- `app:module:function.action` 仍是三段式（第三段含 `.action`），符合 §7 与 02 §12 的格式；`app:*`、`app:module:*` 可做应用/模块级通配。
- 18 个系统不建应用表；前缀是唯一隔离手段，上线后不得修改。
- 本次只固化命名，不新增 Flyway 迁移与表结构，也不导入 359 个功能点、1,156 个动作点；外部系统首次接入前，由中心管理员录入所需权限点，否则 `permission-check` 会返回 `NO_PERMISSION`。
- 外部系统不渲染中心菜单；权限码到菜单/按钮的映射由各系统自己维护。

外部系统新增权限码步骤：

1. 确认应用前缀（上表）。
2. 按 `app:module:function.action` 定义权限码，动作使用查看/新增/编辑/审批/导出等稳定英文词。
3. 由中心管理员在权限管理中创建权限点；当前不提供外部系统自动注册接口。
4. 外部系统在服务端 API 调用 `/api/auth/permission-check`；不能依赖 `@RequiresPermission`（那是同进程注解）。

同进程业务模块新增权限码步骤保持不变：

1. 在本业务模块自己的常量类中定义常量（如 `biz-order` 模块的 `OrderPermissions.EXPORT`）
2. 接口方法标注 `@RequiresPermission(OrderPermissions.EXPORT)`
3. 通过 Flyway 新增权限点数据（MENU / BUTTON / API 按需）
4. 更新本文档 7.3

步骤 2 与步骤 3 的一致性由构建门禁校验：代码引用的权限码若在初始化数据中无定义，构建失败。

## 8. 性能档位

| 档位 | 指标 | 判定依据 | 实现手段 |
|---|---|---|---|
| A | P99 ≤ 30ms | 主键或唯一索引等值查询，返回 ≤ 20 条；或纯内存计算无 DB 访问 | `PermissionSnapshot` 零 DB 查询；`/api/auth/permit` 纯内存；`/api/auth/permission-check` 判定纯内存，身份状态未命中时一次主键查询；分页走主键；权限树归 B 档 |
| B | P99 ≤ 200ms | 含写操作 + CHANGE 审计；多条件筛选；全量权限树 | 单事务提交；审计表仅时间索引；游标分页 |
| 例外 | 无硬指标 | BCrypt 登录；导出与批量导入；白名单内的导出操作 | 登录靠限流；导出/批量用独立线程池并限并发（5） |

档位归属规则：

- 导出类接口一律归例外档，不得归 A 档。
- 新接口必须在本文档对应接口表填写档位。
- 压测按档位分别统计 P99，A 档不达标即阻断发布。

## 9. 接口变更规则

| 项 | 规则 |
|---|---|
| 破坏性变更 | 禁止（删除字段、改字段类型、改路径）。需要时新增接口或字段，旧接口标记废弃并保留一个版本周期 |
| 权限码变更 | 禁止修改已发布权限码。需要调整语义时新增权限码并迁移授权关系 |
| 同步更新 | 接口变更必须同步更新本文档、01 文档的功能追踪表、前端 API 封装 |
| 契约校验 | 构建门禁：每个 `@RequestMapping` 方法必须有 `@PublicApi` / `@RequiresLogin` / `@RequiresPermission` 之一 |
| 审计声明 | 每个业务接口必须显式声明审计意图（`AuditRecorder` 或 `@NoAudit`） |
| 新增接口自查 | 逐项确认：权限码已定义且有初始化数据 / 性能档位已归类 / 归属校验是否需要 / 审计意图已声明 |
