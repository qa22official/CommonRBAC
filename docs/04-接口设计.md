## 1. 通用约定

### 1.1 基础约定

| 项 | 约定 | 理由 |
|---|---|---|
| 基础路径 | `/api` | 便于 Nginx 统一转发与前端代理配置 |
| 风格 | RESTful，资源名用复数、小写、连字符 | 一致性优先，避免同一系统多种风格 |
| 数据格式 | 请求与响应均为 `application/json; charset=utf-8` | |
| 时间格式 | ISO-8601 带时区偏移（`2026-10-12T20:15:30.123+08:00`） | 避免"这是本地时间还是 UTC"的经典事故 |
| 认证方式 | 请求头 `Authorization: Bearer <JWT>` | 不放 URL/Cookie（避免进日志、避免 CSRF） |
| 客户端 IP | 一律由 `ClientIpResolver` 在**可信代理边界**内解析（见 [02 文档 §5.7](./02-总体设计说明书.md)）；**不接受请求体、查询参数或未经校验的请求头传入的 IP** |
| 令牌失效时效 | 见 [01 文档 FR-A9](./01-需求规格说明书.md)：正常 ≤ 1 秒，Redis 故障 ≤ 30 秒。**接口文档不得再承诺"立即失效"** |
| 版本策略 | 不引入 `/v1` 前缀 | 单前端、同团队同时发布前后端时，版本前缀带来的是双倍维护成本而非兼容性收益。**契约变更通过"新增字段/新增接口"实现，不修改既有字段语义** |
| 字段命名 | 驼峰（`createdAt`） | 前后端统一，避免下划线/驼峰来回转换的隐蔽 bug |

### 1.2 统一响应体

```json
{
  "code": 0,
  "message": "ok",
  "data": { },
  "traceId": "b7f2c1a9e4d3"
}
```

| 字段 | 说明 |
|---|---|
| `code` | 0 表示成功；非 0 为业务错误码（见 1.3） |
| `message` | 面向用户的可读提示（已国际化准备，本期中文） |
| `data` | 业务数据；无数据时为 `null` |
| `traceId` | 链路追踪 ID，**用户报障时只需提供这个 ID 即可定位**，也是排查慢请求的入口 |

### 1.3 错误码表

| HTTP | `code` | 含义 | 前端处理 |
|---|---|---|---|
| 200 | 0 | 成功 | 正常处理 |
| 400 | 40000 | 参数校验失败 | 表单内联提示字段级错误 |
| 401 | 40100 | 未认证（无令牌 / 签名错误 / 已过期） | 清除本地令牌 → 跳转登录页 |
| 401 | 40101 | 令牌已作废（登出/改密/停用/全局作废） | 同上，提示"登录状态已失效" |
| 403 | 40300 | 无操作权限 | 提示"无操作权限"（**不泄露所需权限码**） |
| 404 | 40400 | 资源不存在 | 提示并返回列表 |
| 409 | 40900 | 唯一性冲突（账号/角色码/权限码重复） | 表单内联提示 |
| **409** | **40950** | **并发冲突**：`expectedVersion` 与服务端不一致 | 提示"数据已被他人修改，请刷新后重试"，并**自动重新拉取最新数据**；**绝不静默覆盖** |
| 429 | 42900 | 请求过于频繁（限流） | 提示稍后重试，倒计时 |
| **503** | **50300** | **服务降级**：鉴权数据从未成功加载，或已切到 fail-closed 姿态（见 [02 文档 5.3.2](./02-总体设计说明书.md)）。**默认 fail-open 下不会因此返回该码** | 展示"系统暂时不可用，请稍后重试"，按 `Retry-After` 自动重试 |
| 500 | 50000 | 服务器内部错误 | 提示"系统繁忙"，展示 `traceId` |

> **40101 与 40100 必须分开**：前者是"令牌本身无效"，后者是"令牌有效但已被主动作废"。合并会让我们无法监测"批量踢人/令牌滥用"这类事件。
> **50300 与 500 必须分开**：503 表示"系统按设计自我保护"，500 表示"程序出错了"。混在一起会让运维把**设计内的降级**误判为**代码缺陷**。

> **注意 40100 与 40101 的区别**：前者是"令牌本身无效"，后者是"令牌有效但已被主动作废"（用户被停用、改了密码）。分开的原因是可观测性——如果 40101 突然增多，运维需要立刻知道"有人在大量踢下线"或"某个账号被攻击"。

### 1.4 分页约定

**常规分页（浅翻页）**

| 参数 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `page` | int | 1 | 从 1 开始 |
| `size` | int | 20 | 上限 200（超过则截断为 200，防止恶意大分页拖垮系统） |

响应 `data` 结构：

```json
{ "records": [], "total": 1234, "page": 1, "size": 20 }
```

**游标分页（深翻页专用，用于审计日志）**

| 参数 | 说明 |
|---|---|
| `lastId` | 上一页最后一条的 ID；首页不传 |

响应额外返回 `nextLastId`（无更多数据时为 `null`）。

> **为什么审计日志不能用 `OFFSET` 深翻页？** `LIMIT 100000, 20` 要求数据库先扫描并丢弃前 10 万行，页码越深越慢（这是**索引失效的经典陷阱**，表大了会直接拖垮数据库）。游标分页用 `WHERE id < lastId ORDER BY id DESC LIMIT 20`，每一页都是索引定位，耗时恒定。

### 1.5 接口鉴权声明约定（强制）

| 注解 | 含义 | 使用场景 |
|---|---|---|
| `@PublicApi` | 完全公开，无需登录 | 登录接口、健康检查 |
| `@RequiresLogin` | 需要登录，但不需要特定权限码 | `/api/auth/me`、登出、改自己的密码 |
| `@RequiresPermission("码")` | 需要登录 **且** 拥有指定权限码 | 全部管理类接口 |
| **（不加任何注解）** | **默认拒绝**，返回 403 并记录告警 | 属于设计缺陷，由构建门禁拦截 |

**多权限声明规则**：一个接口只声明**一个**权限码。若某接口看起来需要两个权限码（且关系为"任一即可"），正确做法是**拆成两个接口**，而不是引入 `anyOf` 逻辑。

> **为什么不支持 `@RequiresPermission({"A","B"})` 这类多码组合？**
> 因为一旦支持，就会有人写 `@RequiresPermission(anyOf={"A","B"})`，接着是 `allOf`、`not`、`unless`……最终在注解里长出一套表达式语言，权限判定重新变成"代码里散落各处的规则"——这正是我们要消灭的东西。**保持单一权限码，让授权关系全部收敛到角色配置里。**

### 1.6 幂等性与并发更新约定

| 操作类型 | 幂等策略 |
|---|---|
| **覆盖式更新**（如"设置用户的角色列表"） | 集合操作**天然幂等**（重复提交同一集合结果相同），但**不防"丢失更新"**——必须叠加乐观锁，见 1.7 |
| 创建类（POST） | 依赖数据库唯一约束（`uk_username` / `uk_code`）兜底，冲突返回 40900 |
| 删除类 | 天然幂等（重复删除返回成功或 40400，均不报错） |
| 状态切换（启用/停用） | 请求体显式传目标状态值，而非"切换（toggle）语义" |

> **为什么状态操作要传"目标值"而不是"toggle"？**
> `toggle`（翻转）在网络重试下会**翻转两次回到原状**，是典型的幂等性陷阱。传目标值（`{"status": 0}`）无论重试多少次结果都相同。

### 1.7 覆盖式更新必须携带版本号（防"静默丢失更新"）

**问题**：两个管理员同时给同一个用户授权，后提交者的完整集合会**静默覆盖**先提交者的结果。先提交者看到接口返回成功，实际上他的授权被丢掉了。

**规则**：

| 编号 | 约定 |
|---|---|
| V-1 | 所有**覆盖式授权接口**（`PUT /api/users/{id}/roles`、`PUT /api/roles/{id}/permissions`）的请求体**必须**携带 `expectedVersion` |
| V-2 | 对应的 GET 接口**必须**返回 `version` 字段，供前端在编辑前读取 |
| V-3 | 服务端条件更新：`当前版本 == expectedVersion` → 覆盖写入并**版本号 +1**；否则返回 **40950** |
| V-4 | 版本号来自 `sys_user.role_version` / `sys_role.perm_version`（见 [03 文档 §4](./03-数据模型设计.md)） |
| V-5 | **乐观锁与行锁必须同时使用**：乐观锁负责"发现编辑期间数据被改过"，行锁负责"保证约束校验与写入之间不被并发穿透"。两者解决不同问题，缺一不可（论证见 [03 文档 §6.1](./03-数据模型设计.md)） |
| V-6 | 前端收到 40950 后，**必须**重新拉取最新数据并明确提示用户"数据已变化"，**不允许静默重放请求**（重放会把别人的修改再次覆盖掉） |

## 2. 认证接口

### 2.1 登录

```
POST /api/auth/login
注解：@PublicApi
```

请求体：

```json
{ "username": "admin", "password": "********" }
```

响应：

```json
{
  "code": 0,
  "data": {
    "accessToken": "eyJhbGciOiJIUzI1NiIs...",
    "expiresIn": 7200,
    "user": { "id": 1, "username": "admin", "nickname": "管理员" },
    "mustChangePassword": false
  }
}
```

| 业务错误码 | 场景 | 提示 |
|---|---|---|
| 40110 | 账号或密码错误 | "账号或密码错误"（**不区分是哪一个**，防账号枚举） |
| 40111 | 账号已停用 | "账号已停用，请联系管理员" |
| 40112 | 账号已锁定 | "账号已锁定，请 X 分钟后重试" |
| 42900 | 触发登录限流 | "操作过于频繁，请稍后重试" |

**限流规则**：同一账号 5 次/分钟；同一 IP 20 次/分钟（滑动窗口）。超限返回 429。

> **为什么按"账号 + IP"双维度限流？**
> 只按账号限流挡不住"用一个 IP 撞一万个账号"（撞库）；只按 IP 限流挡不住"用一万个 IP 撞一个账号"（分布式暴力破解）。两个维度叠加，才覆盖主要攻击形态。

### 2.2 获取当前用户信息（前端权限的入口）

```
GET /api/auth/me
注解：@RequiresLogin
```

响应：

```json
{
  "code": 0,
  "data": {
    "user": { "id": 1, "username": "admin", "nickname": "管理员", "email": "a@b.com" },
    "permissions": ["*"],
    "roles": [{ "id": 1, "code": "SUPER_ADMIN", "name": "超级管理员" }]
  }
}
```

| 字段 | 用途 |
|---|---|
| `permissions` | **前端权限的唯一数据源**：菜单过滤、路由注册、`v-perm` 按钮控制全部依赖它 |
| `roles` | 仅用于个人中心展示"我的角色"，**前端不得用角色编码做权限判断**（否则 RBAC 升级时前端要跟着改，违反 NFR-5） |

> **`roles` 字段要不要给前端？** 给，但必须限定用途。
> 前端如果写成 `if (roles.includes('ADMIN')) showButton()`，就等于把权限规则硬编码进了前端——升级 RBAC1 时（角色有了继承），前端必须同步改。**因此这条约定要写进前端开发规范：任何权限判断只允许使用 `permissions` 数组或 `v-perm` 指令。**

### 2.3 登出

```
POST /api/auth/logout
注解：@RequiresLogin
```

行为：账号 `token_version` 自增 → 广播作废通知 → 各实例立即拒绝该账号的所有既有令牌。

响应：`{"code": 0}`

### 2.4 续期

```
POST /api/auth/refresh
注解：@RequiresLogin
```

行为：校验当前令牌有效（未过期或处于宽限期内）→ 读取**最新**的 `token_version` 与账号状态 → 签发新令牌。

> **续期时的隐式收益**：用户在令牌有效期内被停用/改了密码，其 `token_version` 已变化，续期时会被拒绝。这让长时间连着系统的用户也能被及时清理，而不是等到令牌自然过期。

### 2.5 修改自己的密码

```
PUT /api/auth/password
注解：@RequiresLogin
```

请求体：

```json
{ "oldPassword": "********", "newPassword": "********" }
```

行为：校验旧密码 → 校验新密码强度策略 → 更新哈希 → `token_version` 自增（**所有历史令牌作废，时效见 [01 文档 FR-A9](./01-需求规格说明书.md)**）→ 写安全事件。

## 3. 用户管理接口

| 方法 | 路径 | 权限码 | 说明 | 性能档 |
|---|---|---|---|---|
| GET | `/api/users` | `sys:user:read` | 分页列表，支持 `keyword`（账号/昵称模糊）、`status` 筛选 | **A（P99 ≤ 30ms）** |
| GET | `/api/users/{id}` | `sys:user:read` | 详情 | A |
| POST | `/api/users` | `sys:user:create` | 新增 | B（P99 ≤ 200ms） |
| PUT | `/api/users/{id}` | `sys:user:update` | 编辑（不含角色） | B |
| DELETE | `/api/users/{id}` | `sys:user:delete` | 逻辑删除 | B |
| PUT | `/api/users/{id}/status` | `sys:user:toggle` | 启用/停用（传目标状态） | B |
| PUT | `/api/users/{id}/password:reset` | `sys:user:reset-password` | 重置密码（管理员操作） | B |
| GET | `/api/users/{id}/roles` | `sys:user:read` | 查询用户已分配角色，**响应含 `version`**（供覆盖式更新做乐观锁） | A |
| PUT | `/api/users/{id}/roles` | `sys:user:assign-role` | **覆盖式**设置用户的角色集合，**必须携带 `expectedVersion`** | B |

**`PUT /api/users` 请求体（示例）**

```json
{
  "username": "zhangsan",
  "nickname": "张三",
  "email": "z@b.com",
  "phone": "13800000000",
  "status": 1,
  "remark": "运维组"
}
```

**`PUT /api/users/{id}/roles` 请求体**

```json
{ "roleIds": [2, 5, 7], "expectedVersion": 12 }
```

| 字段 | 说明 |
|---|---|
| `roleIds` | 目标角色集合（覆盖式，幂等） |
| `expectedVersion` | **必填**。取自 `GET /api/users/{id}/roles` 返回的 `version`。不匹配返回 40950 |

**`GET /api/users/{id}/roles` 响应体**

```json
{ "code": 0, "data": { "roleIds": [2, 5], "version": 12 } }
```

| 业务错误码 | 场景 | 前端行为 |
|---|---|---|
| 40950 | 并发冲突，版本不匹配 | 重新拉取最新角色集合，提示"数据已被他人修改，请确认后重试" |
| 40311 | 移除自己最后一个管理类角色（FR-G4） | 提示具体原因 |
| 40312 | 停用/删除最后一个超级管理员（FR-G2） | 提示具体原因 |

**校验规则（返回业务错误码）**

| 规则 | 错误码 | 提示 |
|---|---|---|
| 账号重复 | 40900 | "该账号已存在" |
| 删除/停用自己 | 40310 | "不能停用或删除当前登录账号" |
| 移除自己最后一个管理类角色 | 40311 | "不能移除自己的最后一个管理角色"（FR-G4） |
| 试图停用/删除最后一个超级管理员 | 40312 | "系统必须保留至少一个启用的超级管理员"（FR-G2/G1） |
| 密码强度不足 | 40010 | "密码需至少 8 位，且包含大小写字母与数字" |

> **FR-G2/G4 这两条"自锁保护"校验，就是 RBAC2 约束机制的雏形**，它们的实现载体是 `ConstraintValidator` 校验链（见 [05 文档](./05-RBAC0到RBAC3演进设计.md)）。**这不是为将来预留的额外工作量，而是"顺手把该放的地方放对了"。**

## 4. 角色管理接口

| 方法 | 路径 | 权限码 | 说明 | 性能档 |
|---|---|---|---|---|
| GET | `/api/roles` | `sys:role:read` | 分页列表，支持 `keyword`、`status` | A |
| GET | `/api/roles/options` | `sys:role:read` | 下拉选项（不分页，仅返回启用角色） | A |
| GET | `/api/roles/{id}` | `sys:role:read` | 详情（含已绑定权限码数量、已绑定用户数） | A |
| POST | `/api/roles` | `sys:role:create` | 新增 | B |
| PUT | `/api/roles/{id}` | `sys:role:update` | 编辑 | B |
| DELETE | `/api/roles/{id}` | `sys:role:delete` | 逻辑删除（需校验引用） | B |
| PUT | `/api/roles/{id}/status` | `sys:role:toggle` | 启用/停用 | B |
| GET | `/api/roles/{id}/permissions` | `sys:role:read` | 查询角色已授权限，**响应含 `version`** | A |
| PUT | `/api/roles/{id}/permissions` | `sys:role:assign-perm` | **覆盖式**设置角色的权限集合，**必须携带 `expectedVersion`** | B |

**`PUT /api/roles/{id}/permissions` 请求体**

```json
{
  "permissionCodes": ["sys:user:read", "sys:user:create", "sys:role:read"],
  "expectedVersion": 7
}
```

| 字段 | 说明 |
|---|---|
| `permissionCodes` | 目标权限码集合（覆盖式，幂等） |
| `expectedVersion` | **必填**。取自 `GET /api/roles/{id}/permissions` 返回的 `version`；不匹配返回 40950 |

**为什么用 `permissionCodes` 而不是 `permissionIds`？**

| 维度 | 用 codes | 用 ids |
|---|---|---|
| 前端契合度 | 高（权限树节点天然带 code，勾选即得） | 低（需额外维护 id 映射） |
| 可读性与排查 | 高（请求体能直接看懂授权了什么） | 低（一串数字） |
| 请求体大小 | 略大 | 略小（几十字节差异，可忽略） |
| 服务端成本 | 需要一次 code→id 映射（**走内存缓存，纳秒级**） | 无 |

**结论**：codes 胜出。表体积的差异在"请求体"这个层面完全可以忽略，而可读性对运维排障的价值是长期的。

**校验规则**

| 规则 | 错误码 | 提示 |
|---|---|---|
| 角色码重复 | 40900 | "该角色编码已存在" |
| 删除被用户引用的角色 | 40910 | "该角色仍被 N 个用户绑定，无法删除" |
| 修改/删除内置角色 | 40320 | "内置角色不允许此操作" |
| 修改内置角色的 `*` 权限 | 40321 | "不允许修改内置角色的全部权限"（FR-G1） |

## 5. 权限管理接口

| 方法 | 路径 | 权限码 | 说明 | 性能档 |
|---|---|---|---|---|
| GET | `/api/permissions/tree` | `sys:perm:read` | 全量权限树（服务端缓存 5 分钟） | A |
| GET | `/api/permissions/{id}` | `sys:perm:read` | 详情 | A |
| POST | `/api/permissions` | `sys:perm:create` | 新增权限点 | B |
| PUT | `/api/permissions/{id}` | `sys:perm:update` | 编辑（**`code` 不可修改**） | B |
| DELETE | `/api/permissions/{id}` | `sys:perm:delete` | 逻辑删除（需校验引用） | B |

**权限树响应结构**

```json
{
  "code": 0,
  "data": [
    {
      "id": 10, "code": "sys:user", "name": "用户管理", "resourceType": "MENU",
      "path": "/system/users", "icon": "user", "sort": 10,
      "children": [
        { "id": 11, "code": "sys:user:read", "name": "查询用户", "resourceType": "API", "children": [] },
        { "id": 12, "code": "sys:user:create", "name": "新增用户", "resourceType": "API", "children": [] }
      ]
    }
  ]
}
```

> **注意 `sys:user`（无操作后缀）的定位**：它是 `MENU` 类权限点（用于菜单显隐与路由注册），不是 `API` 类权限点，因此**不作为 `@RequiresPermission` 的取值**。约定：`@RequiresPermission` 只允许引用 `API` 类权限码或通配码（`sys:user:*`、`sys:*`、`*`），由构建门禁校验。这样做同时保证了"通配码 `sys:user:*` 只命中 API 权限码，不会误命中 MENU 权限码"。

**校验规则**

| 规则 | 错误码 |
|---|---|
| 权限码重复 | 40900 |
| 权限码格式非法（不符合 `<模块>:<资源>:<操作>` 规范） | 40020 |
| 修改 `code` | 40330（"权限码创建后不可修改"） |
| 删除被角色引用的权限 | 40920 |
| 删除内置权限 | 40331 |

| GET | `/api/audit-logs` | `sys:audit:read` | 游标分页查询 | B（P99 ≤ 200ms） |

**查询参数**

| 参数 | 类型 | 说明 |
|---|---|---|
| `startTime` / `endTime` | ISO-8601 | 时间范围，**必填**（防止无范围全表扫描）；比较的是 `event_time` 而非落库时间 |

> **`startTime` 强制必填是刻意的设计约束**，不是偷懒。审计表是最大的表（180 天 50~150 万行），一旦允许"无时间范围、按操作人过滤"，就会退化为全表扫描，耗时可能达数秒。**把"容易被误用成慢查询"的入口在设计阶段直接关掉，比事后加索引补救更可靠。**

> **`startTime` 强制必填**，是刻意的设计约束。审计表是最大的表，一旦允许"无时间范围查询并按操作人过滤"，就会变成全表扫描，在 150 万行数据上可能耗时数秒——**把"容易被误用成慢查询"的入口在设计阶段直接关掉**，比事后加索引补救更可靠。

### 7.2 内置角色与权限映射

| 角色 | 权限码 |
|---|---|
| `SUPER_ADMIN` | `*` |
| `PERM_ADMIN`（权限管理员） | `sys:user:*`、`sys:role:*`、`sys:perm:*`、`sys:audit:read` + 对应 MENU 权限 |
| `AUDITOR`（审计员） | `sys:audit:read`、`sys:audit` |

> **通配码的判定规则**：`*` 命中一切；`sys:user:*` 命中所有以 `sys:user:` 开头的权限码。判定逻辑是**字符串前缀匹配**，只在"用户权限集合包含通配项"时触发（绝大多数用户没有通配权限，因此绝大多数请求只走一次 `HashSet.contains` 精确匹配，零额外开销）。实现细节见 [05 文档权限计算算法](./05-RBAC0到RBAC3演进设计.md)。

### 7.3 业务权限码示例（供业务模块参考）

| 权限码 | 说明 |
|---|---|
| `biz:order` | 订单管理菜单 |
| `biz:order:read` / `biz:order:create` / `biz:order:export` | 订单相关操作 |
| `biz:report:view` | 报表查看 |

> **业务模块新增权限码的流程**：① 在 `rbac-core` 的权限码常量类中定义 → ② 在接口上加 `@RequiresPermission` → ③ 通过 Flyway 新增权限点数据 → ④ 更新本文档。第 ③ 步与第 ② 步的一致性由构建门禁自动校验（扫描代码中引用的权限码是否都在数据库中有定义）。

## 8. 接口性能分级

| 档位 | 指标 | 包含接口 | 设计手段 |
|---|---|---|---|
| **A 档** | P99 ≤ 30ms | 鉴权链路本身；`/api/auth/me`；用户/角色/权限列表与详情（读）；权限树 | 本地缓存零 DB 查询；权限树服务端缓存 5 分钟；分页走主键 |
| **B 档** | P99 ≤ 200ms | 所有管理类写接口（含同步审计落库）；审计日志查询；批量授权 | 单事务；审计表仅时间索引；游标分页 |
| **例外档** | 无硬指标 | 登录（BCrypt 故意慢，约 50~150ms）；数据导入导出 | 独立线程池隔离，避免占用通用线程池 |

> **为什么登录可以例外？** 因为①它的 QPS 极低（一个用户一天登录几次）；②它"慢"是安全设计的一部分，压缩它会降低抗暴力破解能力；③用线程池隔离后，它不会影响 A 档接口。**把"不可优化的接口"识别出来并隔离，比强行优化它更明智。**

## 9. 接口变更管理约定

| 约定 | 内容 |
|---|---|
| 破坏性变更 | 禁止（如删除字段、改字段类型、改路径）。需要变更时**新增接口/字段**，旧接口标记废弃并保留一个版本周期 |
| 权限码变更 | 禁止修改权限码（FR-G5）。需要调整语义时新增权限码并迁移授权关系 |
| 同步更新 | 任何接口变更必须同步更新本文档、[01 需求文档](./01-需求规格说明书.md) 的功能追踪表、以及前端 API 封装 |
| 契约校验 | 构建门禁：每个 `@RequestMapping` 方法必须有 `@PublicApi` / `@RequiresLogin` / `@RequiresPermission` 之一（NFR-8） |
