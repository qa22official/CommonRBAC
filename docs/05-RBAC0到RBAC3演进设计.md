## 1. 先讲清楚 RBAC0/1/2/3 是什么

这四个词来自同一篇学术论文对"基于角色的访问控制"的四个层次定义。它们**不是四种不同的系统，而是同一套模型逐层加功能**：

```
        RBAC0  用户 → 角色 → 权限
          │
          ├─────────────┐
          ▼             ▼
        RBAC1         RBAC2
    （+ 角色继承）  （+ 约束规则）
          │             │
          └──────┬──────┘
                 ▼
              RBAC3  = RBAC1 + RBAC2
```

### 1.1 用一个公司类比

| 层次 | 类比 | 具体例子 |
|---|---|---|
| **RBAC0** | 定岗位职责，人入岗即获得该岗位的全部职责 | "财务专员"能创建报销单；张三被授予"财务专员"角色，于是张三能创建报销单 |
| **RBAC1** | 岗位有上下级，上级**自动拥有**下级的全部职责 | "财务主管"的上级是"财务专员"→ 财务主管自动能做财务专员能做的一切，不必重复配置 |
| **RBAC2** | 公司制度：某些岗位不能由同一人兼任；某些岗位有编制上限 | "付款申请"和"付款审批"不能给同一个人；"部门经理"这个角色最多只能有 1 个人 |
| **RBAC3** | 上面两套同时生效 | 财务主管**且**受"不相容岗位分离"约束 |

### 1.2 三个层次各自"新加的是什么"

| 层次 | 新增机制 | 影响的对象 |
|---|---|---|
| RBAC0 | 用户-角色、角色-权限两层关系 + 权限判定 | 全部 |
| RBAC1 | **角色之间**多了一条"父子"关系 | 只影响"角色集合 → 权限集合"这一步的计算 |
| RBAC2 | **授权动作**上增加校验规则 | 只影响"写入授权关系"这一刻的校验 |

> **这是本文档最重要的一句话**：
> RBAC1 改变的是「**怎么从角色算出权限**」，RBAC2 改变的是「**允许不允许建立这条授权关系**」。
> 这两件事发生在完全不同的位置，彼此不干扰——**它们天然正交**。因此 RBAC3 = RBAC1 + RBAC2 不需要任何额外设计。

## 2. 演进总览

> **口径纪律（本节的读法）**：下表的"业务代码变化"与"鉴权主链路变化"两列，含义被**严格限定**为：
> ① **业务接口上的权限声明不需要改**（`@RequiresPermission` 的取值不变）；② **鉴权入口的接口与调用方式不需要改**（过滤器、拦截器、注解契约不变）。
> 它**不**意味着"升级不需要工作量"。**升级仍然会有改动**，只是被限制在少数几处：权限计算的内部实现、缓存加载语句、管理端接口、前端配置界面、数据库脚本、回归测试。完整的代价拆解见 §8。

| 阶段 | 目标 | 数据变化 | 代码变化 | 业务接口的权限声明 | 鉴权入口契约 | 前端变化 | 预估工作量 |
|---|---|---|---|---|---|---|---|
| **阶段 0** | RBAC0 上线 | 6 张表（继承字段已预留） | 全新实现 | 加注解 | 全新实现 | 全新实现 | 主体工程 |
| **阶段 1** | RBAC1 角色继承 | **仅数据操作**（填继承关系值） | 权限计算实现 + 缓存加载 SQL（见 4.3 决策 D-1） | **不变** | **不变** | 角色管理页改为树形；开放"继承来源角色"选择 | 2~4 人日 |
| **阶段 2** | RBAC2 约束 | 新增 1 张表 `sys_role_constraint` + 初始约束数据 | 新增若干校验器实现类 | **不变** | **不变** | 新增「角色约束」管理页；授权时展示被拒原因 | 3~5 人日 |
| **阶段 3** | RBAC3 | **无** | **无** | **不变** | **不变** | **无** | 0（由阶段 1、2 叠加自然达成） |

**"权限声明不变、鉴权入口不变"不是巧合，而是设计目标。** 做到这一点靠三件东西，在下面第 3 节之后逐一解释。

**各阶段的代价必须按六个维度分别估算**（不要用"改动很小"这类模糊表述做决策）：

| 维度 | 阶段 1（RBAC1） | 阶段 2（RBAC2） |
|---|---|---|
| 代码变更 | 权限计算实现（继承链展开 + 环检测）、缓存加载 SQL | 2 个校验器实现类 |
| 数据迁移 | 填继承关系（可通过界面逐步灰度） | 新增约束规则数据 |
| 接口新增 | `GET /api/roles/tree`；角色接口新增可选字段 | 约束规则 CRUD 接口 |
| 前端变更 | 角色列表改树形、表单单选 | 新增约束管理页、授权失败提示文案 |
| 测试与回归 | 单层/多层/菱形/成环/停用 + **权限快照零差异比对** | 互斥/基数 + **并发授权测试** + RBAC0 校验器回归 |
| 灰度与回滚 | 灰度：逐个角色配置；回滚：清空继承关系（**改数据，不发版本**） | 灰度：新增规则时提示历史冲突；回滚：停用规则 |

## 3. 阶段 0：RBAC0 设计

### 3.1 数据模型

见 [03 数据模型设计 §4](./03-数据模型设计.md)。核心是 5 张关系表 + 1 张审计表。

**RBAC0 阶段的两个"额外动作"**（它们不是为将来预留，而是"顺手做对"）：

| 动作 | 表面上是"预留" | 实质上是什么 |
|---|---|---|
| `sys_role.inherit_role_id` 字段存在且恒为 0 | 为 RBAC1 预留 | 让"角色继承链"这个数据结构从第一天就存在（虽然当前是平的），避免升级时跨四层改造 |
| `ConstraintValidator` 校验链已存在并挂了 4 个实现（超管保护、自锁保护、内置保护、引用校验，见 3.4） | 为 RBAC2 预留 | 这 4 条**本身就是约束规则**（其中超管保护与自锁保护属于基数约束），现在就必须实现。**顺理成章地放在将来要放的地方，零额外成本** |

> **命名说明**：为什么把校验器叫 `ConstraintValidator`（约束校验器）而不是 `AssignRoleValidator`？因为 RBAC2 的官方术语就是"约束（constraint）"。名字对齐领域术语，将来做 RBAC2 时不需要改名。

### 3.2 权限计算算法（RBAC0）

```
输入：userId
输出：权限码集合 Set<String>

1. roleIds ← userRoleMap[userId]                        // 缓存 B
2. roleIds ← { r ∈ roleIds | roleStatusMap[r] = 启用 }   // 过滤停用角色
3. codes   ← ∪ { rolePermMap[r] | r ∈ roleIds }          // 缓存 A（角色权限矩阵）
4. codes   ← { c ∈ codes | permEnabledMap[c] = true }     // 过滤停用权限
5. return codes
```

**关键性质（必须一直保持）**：

| 性质 | 说明 | 为什么重要 |
|---|---|---|
| 纯函数、无副作用 | 相同输入必得相同输出，不写库、不发消息 | 可单元测试、可放心放在任何线程、可缓存 |
| 只读两个缓存映射 | 不查数据库 | 零查询鉴权的来源 |
| 复杂度 O(角色数 × 每角色权限数) | 几十到几百次操作，微秒级 | 30ms 预算内的开销可忽略 |
| 不做任何"拒绝"判定 | RBAC0 只有正向授权（有就是有） | 若引入"拒绝优先"，会与 RBAC2 的约束语义纠缠，必须避免 |

### 3.3 鉴权判定

```
boolean hasPermission(userId, requiredCode):
    codes ← resolve(userId)
    return codes.contains(requiredCode)                 // O(1)
        || codes.contains("*")
        || codes.contains(子通配码(requiredCode))         // 如 sys:user:* 命中 sys:user:delete
```

通配码判定只在"用户权限集合里含通配项"时触发（少数管理员），普通用户只走一次 `HashSet.contains`。

### 3.4 写入路径的校验链（RBAC0 版）

所有"写授权关系"的操作（给用户分配角色、给角色分配权限、启停用户/角色）都必须经过同一条校验链：

```
AuthorizationCommand
      │
      ▼
[校验链]  for each ConstraintValidator v:  v.validate(command)  →  不通过则抛业务异常
      │
      ▼
[写入]    事务内：写关系表 + 写审计日志 → 提交
      │
      ▼
[通知]    事务提交后：版本号自增 + Redis 广播失效
```

RBAC0 阶段链上的校验器：

| 校验器 | 规则 | 来源 |
|---|---|---|
| `LastSuperAdminValidator` | 系统必须保留 ≥1 个启用的超级管理员 | FR-G2 |
| `SelfLockoutValidator` | 不能删除/停用自己；不能移除自己最后一个管理类角色 | FR-G3 / FR-G4 |
| `BuiltinRoleProtectionValidator` | 内置角色不可删除/停用，其 `*` 权限不可移除 | FR-G1 |
| `RoleReferenceValidator` | 角色被用户引用时不可删除 | FR-R4 |

**这 4 个校验器在 RBAC2 阶段会继续留在链上，只是链上又多了互斥、基数两类校验器。** 这就是"零额外成本预留"的含义：我们本来就要写这些校验，只是把它们放在了将来必然要扩展的位置上。

## 4. 阶段 1：升级到 RBAC1（角色继承）

### 4.1 模型变化

仅仅在 `sys_role.inherit_role_id` 上填入真实值，形成一条条**继承链**：

```
   ┌────────────────┐        ┌────────────────┐        ┌────────────────┐
   │  运营专员      │◄───────┤  运营主管      │◄───────┤  运营总监      │
   │  基础角色      │        │                │        │                │
   │ inherit = 0    │        │ inherit=专员.id│        │ inherit=主管.id│
   └────────────────┘        └────────────────┘        └────────────────┘
      权限最小                 权限 ⊇ 主管自身+专员         权限 ⊇ 全部三级

   "◄──" 读作"从……继承权限"：运营主管从运营专员继承，运营总监从运营主管继承。
   有效权限 = 自身权限 ∪ 继承链上全部角色的权限，因此越靠右权限越大。
```

**语义约定（必须写死，否则不同人理解不同）**：

| 约定 | 内容 | 理由 |
|---|---|---|
| **字段含义** | `inherit_role_id` = **我从哪个角色继承权限**。它**不是**"组织上级" | 组织汇报关系与权限继承是两件事。压进同一个字段是经典建模错误（详见 [03 文档 §4.2](./03-数据模型设计.md)） |
| **继承方向** | 沿 `inherit_role_id` **向链尾方向收集**：当前角色权限 = 自身 ∪ 链上全部角色的权限 | 与业界（NIST RBAC）的主流存法一致，将来引入 RBAC2/3 的标准概念能直接对应 |
| 继承是"并集" | 当前角色权限 = 自身权限 ∪（递归地）继承链上全部角色的权限 | 与个人拥有多角色时的并集语义一致，避免两套规则打架 |
| 不支持"减去" | 不存在"链上有 A，但当前角色明确不要 A"的表达 | 一旦支持"减"，权限结果就依赖遍历顺序，可预测性崩溃 |
| 无继承时行为不变 | `inherit_role_id = 0` 表示不从任何角色继承，与 RBAC0 行为**完全一致** | **这保证了升级是渐进、可分批、可回滚的** |
| 链的深度 | 建议 ≤ 5 层 | 现实中不存在更深的权限继承；深链会拉长计算与缓存重载时间 |
| **界面展示方向可以不同** | 管理界面**可以**把权限最大的角色画在顶部（"总监在上"），这只是**展示方向** | 让管理员看到符合直觉的视图，同时不让"界面直觉"污染数据模型 |

> **为什么界面上可以"反着画"？** 因为展示层只需要把继承关系**渲染**成一棵树，渲染方向是自由的；而数据层必须只有一个明确的、能被算法正确消费的方向。**把展示的便利性要求转嫁到数据模型上，正是原设计出现歧义的根源。**

### 4.2 数据变化：不需要任何 DDL

| 动作 | 说明 |
|---|---|
| 是否加列 | **不需要**（`inherit_role_id` 已在阶段 0 存在） |
| 是否加表 | 不需要 |
| 是否加索引 | **不需要**（`idx_inherit_role_id` 已在阶段 0 建好） |
| 实际动作 | 通过管理界面或一条 `UPDATE sys_role SET inherit_role_id = ? WHERE id = ?` 填值；存量角色保持 `inherit_role_id = 0` |

**分批灰度**：可以先给 1~2 个角色配置继承关系，观察一天，再逐步放开。**因为无继承的角色行为完全不变，灰度过程中的风险被限制在"被配置了继承的那几个角色"上。**

### 4.3 代码变化：一个决策点（D-1）

这里有一个设计选择，必须明说，因为它决定"升级时是否需要改代码"：

**方案甲（推荐）：从阶段 0 就实现继承链展开算法**

```
步骤 2 改为：
2'. roleIds ← 展开继承链(roleIds)      // 沿 inherit_role_id 一路收集，去重，做环检测
```

在 RBAC0 数据下（所有 `inherit_role_id = 0`），这个展开是**恒等变换**——一层都不加。所以行为与 RBAC0 完全一致，**测试可以通过同一套用例**。

| 项 | 方案甲：现在就实现展开 | 方案乙：升级时再改实现 |
|---|---|---|
| 代码量 | 约 40 行（展开 + 环检测 + 去重）+ 单元测试 | 0 行（现在），升级时约 40 行 |
| 升级时需要的动作 | **仅数据操作（填 `inherit_role_id`）+ 前端放开一个下拉框** | 数据操作 + 改 `PermissionResolver` 实现 + 重新测试 + 重新部署 |
| **升级回滚** | **把 `inherit_role_id` 全部置 0 即回到 RBAC0 行为（不部署、不停机）** | 需要回滚部署到旧版本 |
| 风险 | 有一段当前"不生效"的逻辑（依赖单元测试覆盖，见下） | 升级时算法变更与数据变更同时发生，出问题时难以区分是哪一边的错 |
| 是否算过度设计 | 40 行、零运行期开销、有测试覆盖，不构成"为小功能引大框架" | — |

**推荐甲**，核心理由是**回滚能力**：方案甲让 RBAC1 的升级与回滚都变成"改数据"，而不是"发版本"。在生产环境，**能一键回滚的变更价值远超 40 行代码**。

**对方案甲风险的应对**（必须做，否则就是"写了但没验证过的代码"）：

| 风险 | 对策 |
|---|---|
| 展开逻辑在 RBAC0 阶段从未在生产环境生效 | ① 单元测试必须覆盖非零 `inherit_role_id` 的多层、菱形汇聚、成环场景；② 在阶段 0 末期的**升级预演**（AC-8）中，在测试环境真实启用一次继承，跑通全量回归 |
| 环检测本身可能有 bug | 用"访问集合 + 最大深度上限"双重保护：即使环检测失效，深度上限也会终止循环并抛错，而不是死循环 |
| 深链导致计算变慢 | 深度上限 5 层；展开结果按角色 ID 去重，避免重复计算 |

> 如果团队倾向"最小实现、不写暂时不生效的代码"，方案乙是可接受的替代（升级时多花 1 人日 + 一次部署）。**这是一个有意识的取舍，不是对错问题**，但必须在阶段 0 开始前定下来，因为它决定第 4.4 节的算法是"现有实现"还是"待实现"。

### 4.4 升级后的权限计算算法（RBAC1）

```
输入：userId
输出：权限码集合 Set<String>

1.  directRoles ← userRoleMap[userId]                       // 缓存 B
2.  directRoles ← { r | roleStatusMap[r] = 启用 }
3.  effectiveRoles ← 展开继承链(directRoles)                 ★ 唯一的新增步骤
4.  codes ← ∪ { rolePermMap[r] | r ∈ effectiveRoles }        // 缓存 A
5.  codes ← { c | permEnabledMap[c] = true }
6.  return codes

展开继承链(起步角色集合):
    result ← {}; queue ← 起步角色集合
    while queue 非空:
        r ← queue.poll()
        if r ∈ result: continue                 // 去重（菱形汇聚：两条链汇到同一个角色）
        if result.size() > 深度上限: 抛异常       // 环/超深保护
        result.add(r)
        src ← inheritRoleMap[r]                 // 我继承自哪个角色
        if src ≠ 0: queue.add(src)              // 沿继承链继续收集
    return result
```

**逐句解释这个算法在做什么**（对应上面的编号）：

| 步骤 | 含义 |
|---|---|
| 1~2 | 取出这个用户**直接**被授予的角色，并剔除已停用的 |
| 3 | 把"直接角色"扩展成"直接角色 + 它们各自的继承链上的全部角色" |
| 4~5 | 把所有相关角色的权限合并，再剔除已停用的权限点 |
| 去重 | 两条链汇到同一个角色时只算一次（否则会重复计算） |
| 深度上限 | 即使数据里被人为配出环，也会终止并报错，**不会死循环** |

**注意几个设计细节，它们决定了这个算法在高并发下是否安全**：

| 细节 | 做法 | 为什么 |
|---|---|---|
| 数据来源 | 走**内存缓存**（`inheritRoleMap`、`roleStatusMap`），不查库 | 保持"零查询鉴权"不变式（I-6） |
| 是否缓存"最终权限集合" | **不缓存**（只缓存事实，现场计算） | 若缓存派生结果，则"给某个被继承角色加了权限"要作废所有下游角色的用户缓存，失效范围爆炸。现场计算只花微秒，不值得 |
| 环的处理 | 检测到超深/成环 → 记录严重告警 + **按"不加继承"处理**（降级为 RBAC0 行为）而非拒绝请求 | 权限系统故障时应当"少给权限"还是"拒绝服务"？**我们的选择是：宁可少给权限，也不要让整个系统不可用**——角色链配置错误是管理员的配置问题，不应导致全体用户无法办公。同时立刻告警，让管理员快速修正 |
| 停用角色的处理 | 停用某个角色后，它仍在树中，但仍被视为"不在有效集合中" | 停用 = 当前不生效，但不破坏结构 |

### 4.5 缓存结构的变化

| 缓存 | RBAC0 | RBAC1 | 变化 |
|---|---|---|---|
| A：`roleId → Set<权限码>` | 有 | 有 | **不变** |
| B：`userId → Set<roleId>` | 有 | 有 | **不变** |
| C：`roleId → inheritRoleId` | 需要 | 需要 | **新增一张极小的映射**（500 条，几十 KB） |
| D：`roleId → status` | 有 | 有 | 不变 |
| E：`permissionCode → enabled` | 有 | 有 | 不变 |

> C 表数据量极小，可以并入缓存 A 的重载查询（`SELECT id, inherit_role_id, status FROM sys_role` 一次取回）。**升级时缓存的重建 SQL 会改（多取一列），这是必须同步检查的地方**——见 [03 文档 §10 变更影响矩阵](./03-数据模型设计.md) 的警示行。

### 4.6 接口变化

| 接口 | 变化 | 是否破坏性 |
|---|---|---|
| `GET /api/roles` | 响应新增 `inheritRoleId`、`inheritRoleName` 字段 | 否（新增字段） |
| `GET /api/roles/tree` | **新增**接口：返回**按继承关系组织**的角色视图（展示方向由前端决定，见 4.1） | 否（新增） |
| `POST /api/roles`、`PUT /api/roles/{id}` | 请求体新增可选 `inheritRoleId`（选择"继承来源角色"） | 否（新增可选字段，旧请求体仍可用） |
| 其他全部接口 | **不变** | — |

**新增/调整的业务错误码**：

| 错误码 | 场景 |
|---|---|
| 40930 | 设置继承来源形成环（"不允许将角色设置为其自身或其后代"） |
| 40931 | 超过最大继承链深度 |
| 40932 | 选择的继承来源角色已被停用 |

### 4.7 前端变化

| 项 | 变化 |
|---|---|
| 角色列表 | 从表格改为**树形表格**（Element Plus 的 `el-table` 支持 `tree-props`，无需换组件）；**展示方向可按管理员直觉把权限最大的角色放在顶部**，这只是渲染选择 |
| 角色表单 | 新增"继承来源角色"下拉（带搜索，**排除自身与其继承链上的角色**，防止形成环） |
| 权限判断 | **不变**（前端只用 `permissions` 权限码，从不用角色关系，见 [04 文档 §2.2](./04-接口设计.md)） |
| 授权页面 | **不变**（给角色授权限的交互完全一样；继承关系由后端计算，前端不感知） |

> **"授权页面不变"是这次升级代价被压住的最直观体现**：管理员给"运营专员"授权限时，不需要知道"运营主管会继承它"——那是模型语义，不是操作步骤。

### 4.8 明确不需要改的东西（升级代价的正面清单）

这一节是本文档最有价值的部分之一。**升级 RBAC1 时，以下东西一行都不用改**（注意：这是**正面清单**，不构成"升级不需要工作量"的结论——完整代价见 §2 的六维度表和 §8 的量化对比）：

| 类别 | 具体项 | 为什么不用改 |
|---|---|---|
| 业务代码 | 所有 `@RequiresPermission("...")` 注解 | 注解只声明权限码，与角色结构无关（不变式 I-1） |
| 业务代码 | 所有"是否有权"的判断逻辑 | 同上 |
| 鉴权主链路 | `JwtAuthFilter` | 只处理令牌，不涉及权限 |
| 鉴权主链路 | `PermissionInterceptor` | 只做"权限码集合包含判定"（不变式 I-2） |
| 鉴权主链路 | `PermissionResolver` 的**接口** | 契约不变，只有实现内部多了展开步骤（方案甲下连实现也不变） |
| 数据表 | 所有 6 张表的**已有字段与索引** | 继承字段已存在；若为 RBAC2 只做"新增表" |
| 前端 | `v-perm` 指令、路由守卫、菜单过滤 | 只用权限码 |
| 前端 | 用户授权页面 | 与角色继承无关 |
| 认证模块 | 全部 | 认证与鉴权本来就是分开的模块（模块切分的收益在此兑现） |

### 4.9 升级回归测试点（Checklist）

| # | 测试点 | 预期 |
|---|---|---|
| 1 | 无继承的既有角色 | 权限与升级前**逐条一致**（这是最重要的回归点：升级不能改变任何既有用户的权限） |
| 2 | 单层继承 | 继承方用户获得被继承角色的权限 |
| 3 | 多层链式继承（3 层） | 链尾角色用户获得链上全部角色的权限 |
| 4 | 菱形汇聚（两条链汇到同一角色） | 该角色权限只计一次，无重复、无报错 |
| 5 | 被继承角色被停用 | 该角色权限不生效，继承方自身权限仍生效 |
| 6 | **正向方向验证（必测）** | 按本设计的语义配置（`主管.inherit=专员`），**主管拥有专员的权限**；反向配置（`专员.inherit=主管`）时，**专员拥有主管的权限**——即"谁 inherit 谁就获得谁的能力"，不得出现反向结果 |
| 7 | 配置成环的尝试 | 被接口拒绝（40930） |
| 8 | 已存在的环（脏数据） | 鉴权降级为 RBAC0 行为 + 告警，**不导致接口 500** |
| 9 | 权限变更广播 | 修改被继承角色的权限后，链尾角色用户 1s 内生效 |
| 10 | 缓存重建 | 重建后包含 `inheritRoleId` 数据（**加载 SQL 必须与新算法一致**） |
| 11 | 全量既有用户权限快照对比 | 升级前后**零差异**（对未配置继承的用户） |

> **第 6 项是本次评审新增的"方向断言"**。原设计只测"出现环会不会崩"，没有测"继承方向对不对"——而方向搞反是一个**不会报错、只会静默越权**的缺陷，只能靠断言方向来发现。
>
> **第 11 项做法**：升级前，用脚本导出全部用户的权限码集合快照；升级后（未配置任何继承时）再导出一次，逐条比对。**这是唯一能证明"升级没改坏任何东西"的方法**，且成本很低。

## 5. 阶段 2：升级到 RBAC2（约束）

### 5.1 约束是什么（人话版）

约束不是权限本身，而是**对"授权"这个动作的限制**：即使你有权给别人分配角色，也不能分配出违反公司制度的结果。

常见的三类约束：

| 约束类型 | 人话解释 | 例子 | 术语 |
|---|---|---|---|
| **互斥（静态）** | 这两个岗位不能是同一个人 | "付款申请"和"付款审批"不能同时给张三 | SSD（Static Separation of Duty） |
| **基数（静态）** | 这个岗位最多/最少几个人 | "部门经理"最多 1 人；"审批人"至少 2 人 | Cardinality |
| **互斥（动态）** | 可以同时拥有，但不能在同一时刻同时"激活" | 某人有两个角色的能力，但当前会话只能以其中一个身份操作 | DSD（Dynamic Separation of Duty） |

> **本期（RBAC2）要做哪些？** 建议只做**静态互斥**与**基数**两类。**DSD 需要"会话/激活角色"概念**（用户登录后要选择"以哪个角色身份工作"），这会改动登录流程与前端交互，代价明显高于前两类。**即使将来要做 DSD，它也只是"新增一张表 + 新增一个校验器 + 新增一个会话概念"，不会推翻已有结构。**

### 5.2 数据模型变化：只加一张表

见 [03 文档 §4.6 `sys_role_constraint`](./03-数据模型设计.md)。

**这张表的特点：**

| 特点 | 说明 |
|---|---|
| 纯新增 | 现有 5 张表和所有现有 SQL 完全不受影响（原则 P-1） |
| 数据量极小 | 几十到几百条（约束规则数量天然很少） |
| 可全量缓存 | 与权限映射一样，整体载入内存 |
| 变更频率极低 | 一年可能改几次 |

### 5.3 代码变化：往校验链上"挂新校验器"

```
                RBAC0 已有的校验链
                        │
                        ▼
   ┌────────────────────────────────────────────────┐
   │ LastSuperAdminValidator        （基数类）      │
   │ SelfLockoutValidator           （基数类）      │
   │ BuiltinRoleProtectionValidator （保护类）      │
   │ RoleReferenceValidator         （引用类）      │
   │ ──────────────── 以下为 RBAC2 新增 ───────────  │
   │ MutexConstraintValidator       （互斥类）★新增 │
   │ CardinalityConstraintValidator （基数类）★新增 │
   └────────────────────────────────────────────────┘
                        │
                        ▼
                 通过 → 写入 + 审计 + 广播
```

| 项 | 说明 |
|---|---|
| 新增类 | 2 个校验器实现类（互斥、基数） |
| 修改已有类 | **0 个** |
| 修改接口 | **0 个**（校验链接口不变） |
| 修改表 | **0 个**（只新增表） |
| 业务代码 | **0** |

### 5.4 校验器的契约（阶段 0 就定下来，RBAC2 直接实现）

```
interface ConstraintValidator {
    void validate(AuthorizationCommand cmd);   // 不通过则抛 ConstraintViolatedException(错误码, 提示)
}
```

**契约的关键性质**：

| 性质 | 说明 |
|---|---|
| 输入是"一次授权变更的意图"，不是数据库状态 | 校验器自己去读缓存/库，调用方不需要为每个校验器准备参数（符合"调用方无需记忆调用顺序、参数尽量少") |
| 校验器之间互不感知 | 新增校验器不需要改任何已有代码（开闭原则的实际收益） |
| 失败即整体拒绝 | 一次授权操作要么全过、要么全不过，不做"部分成功" |
| 校验器不写库 | 只读（读缓存为主），保证链可以重复执行 |

### 5.5 并发下的约束校验（**容易被忽略的漏洞**）

**问题场景**：两个管理员同时给同一用户授权。

```
时刻 T1:  管理员 A 给张三加角色 R1（R1 与 R2 互斥）
时刻 T1:  管理员 B 给张三加角色 R2
          ↓
如果两个校验都读到"张三当前没有 R1/R2"，两个校验都通过
          ↓
结果：张三同时拥有 R1 和 R2 —— 约束被绕过
```

**对策（按代价从低到高）**：

| 方案 | 做法 | 代价 | 评价 |
|---|---|---|---|
| **行级锁串行化（推荐）** | 授权操作的事务中，先 `SELECT ... FROM sys_user WHERE id = ? FOR UPDATE` 锁住目标用户（角色容量约束则锁目标角色行），使同一对象的授权操作串行 | 授权 QPS 极低（每天几十次），锁等待完全无感 | ✅ 采用。**没有并发压力时，最简单的正确解就是最优解** |
| 唯一约束/统计表 | 把约束表达成数据库约束 | 互斥关系难以用唯一索引表达（需要两行对称插入） | ❌ 复杂度不划算 |
| Redis 分布式锁 | 加分布式锁 | 引入锁超时、锁失效、Redis 故障等新问题 | ❌ 低频操作用分布式锁是过度设计 |

> **判断依据**：并发问题只值得用"与并发量匹配"的手段去解决。授权操作每天几十次，用行锁串行化的代价接近于零；而分布式锁会让系统在 Redis 故障时**无法授权**——把一个低频操作变成对关键组件的强依赖，是显而易见的得不偿失。

> **行锁与乐观锁的关系（两者都要，不可互相替代）**：本文档描述的行锁负责"保证校验与写入之间不被并发穿透"，[04 文档 §1.7](./04-接口设计.md) 的乐观锁（`expectedVersion`）负责"发现前端编辑期间数据已被他人改动"。**行锁挡不住"丢失更新"**（后提交者仍会静默覆盖），**乐观锁挡不住"同时通过约束校验"**（两个事务都读到了提交前的状态）。缺少任何一个都会留下真实漏洞，详见 [03 文档 §6.1](./03-数据模型设计.md)。

### 5.5.1 约束语义的三条硬规则（必须在本阶段写死，否则实现会各自发挥）

| # | 规则 | 为什么必须这样定 |
|---|---|---|
| C-1 | **约束只检查"直接授予的角色"，不检查继承来的角色** | 约束管的是"这个人身上挂了哪些岗位"，不是"他因此获得了哪些能力"。若按展开后的有效角色判定，会出现"给用户加一个低权角色、却因链上某个远处角色而被拒"的费解情况；更糟的是——**继承关系一改，历史授权可能突然变成非法**，管理员会陷入无解的清理工作 |
| C-2 | **新增约束规则时允许存在历史冲突数据，但必须同时输出冲突清单** | 若要求"清理干净才能保存规则"，系统上线后就**再也加不了新规则**（历史数据里通常已有同时拥有两个互斥角色的用户）。正确做法：规则**保存成功** + 返回冲突用户清单 + 提示逐步清理；清理完成前，**新增授权受约束，既有授权不强制收回** |
| C-3 | **基数"下限"只做告警，不做写入拦截；基数"上限"才拦截** | 若下限做成硬拒绝，会出现死锁：当前只有 1 个"审批人"时，想改这个用户的其他信息（甚至想把他停用）都会被拒绝，**系统进入无法修复的状态**。下限是监控项，不是校验项 |

### 5.6 接口与前端变化

| 项 | 变化 | 破坏性 |
|---|---|---|
| 新增 `GET/POST/PUT/DELETE /api/role-constraints` | 约束规则管理（新权限码 `sys:constraint:read/create/update/delete`） | 否（新增） |
| `PUT /api/users/{id}/roles` | 无接口变化，但**可能返回新的业务错误码** 40940（违反互斥）/ 40941（违反基数） | 否（错误码是新增的） |
| 前端 | 新增「角色约束」管理页 | 否 |

**前端交互要求**：授权失败时，错误提示必须**说清违反了哪条规则**（如"角色『付款审批』与已有角色『付款申请』互斥，不能同时授予"），而不是笼统的"操作失败"。这是约束功能能否被正确使用的关键——管理员看不懂拒绝原因，就会反复重试或绕过系统。

> **注意错误码 4094x 与 4032x 的区别**：403 类是"你没有操作权限"，409 类是"你有权限，但这次操作违反了业务规则"（含 40940 违反互斥、40941 违反基数）。**混淆这两者会让用户以为是自己权限不够，去找管理员要权限，而管理员也无能为力。**
>
> **还要与 40950 区分**：40950 是**乐观锁冲突**（[04 文档 §1.7](./04-接口设计.md)），含义是"你手上的数据已经过期了，刷新后重试"；4094x 的含义是"就算你刷新了数据，这个操作也不被允许"。**前者的正确动作是重试，后者的正确动作是改方案**——前端提示文案必须区分开。

### 5.7 升级回归测试点

| # | 测试点 | 预期 |
|---|---|---|
| 1 | 无任何约束规则时 | 行为与 RBAC1 完全一致（回归基线） |
| 2 | 互斥：先授 R1 再授 R2 | 第二次被拒 40940 |
| 3 | 互斥：后加的互斥规则与已有授权冲突 | 规则**可以保存**，但需提示"存在 N 个用户已同时拥有，请先清理"（见下） |
| 4 | 互斥：批量授权中出现冲突 | 整体回滚，明确指出冲突项 |
| 5 | 基数：超过上限 | 被拒 40941 |
| 6 | 基数：低于下限（如"至少 2 人"） | 被视为"配置告警"而非拒绝（否则会造成无法修改的僵局） |
| 7 | 并发授权（两个线程同时授权互斥角色） | 最终结果**必定不违反约束** |
| 8 | 既有 RBAC0 校验器 | 全部仍然生效（回归） |

> **第 3 项的语义要特别小心**：如果"新增互斥规则"要求现存数据必须先满足约束，管理员会在系统上线后无法添加新规则（因为历史数据里已经有同时拥有两个角色的用户）。**正确的处理是：新规则允许保存，但系统给出冲突用户清单，允许管理员逐步清理；冲突用户在清理完成前，"新增授权"受约束，"既有授权"不强制收回。** 这属于"规则生效策略"，必须在做 RBAC2 时明确定义，否则会导致线上僵局。

**第 6 项的说明**：基数下限（"这个角色至少要有 2 个人"）如果做成硬拒绝，就会出现"当前只有 1 人，此时想改这个用户的其他信息也被拒绝"的死锁。**下限应当是监控告警项，不是写入拦截项**。

## 6. 阶段 3：RBAC3

### 6.1 需要的动作

**没有动作。**

```
RBAC3 ≡ RBAC1（角色继承） + RBAC2（约束）

阶段 1 完成后：继承生效
阶段 2 完成后：约束生效
两者叠加 = RBAC3
```

**为什么可以这样叠加？** 回到第 1.2 节的核心洞察：

| 机制 | 作用位置 | 何时生效 |
|---|---|---|
| RBAC1 继承 | **读路径**：把"用户直接拥有的角色集合"扩展为"含继承链上全部角色的集合" | 每次鉴权时 |
| RBAC2 约束 | **写路径**：授权时校验合法性 | 每次授权时 |

**一个在读书、一个在写书，互不干扰。** 这就是"正交"的实际含义。

### 6.2 唯一需要确认的交互点

两者之间只有**一处**可能出现语义纠缠，必须显式定义：

> **问题**：角色 R 从角色 S 继承了权限（`R.inherit_role_id = S`），而 **S** 与另一个角色 Q 互斥。此时"给用户授予 R"是否算违反互斥？

| 方案 | 语义 | 评价 |
|---|---|---|
| **按"直接授予的角色"判定（采用）** | 互斥只检查**显式授予**的角色集合；继承来的角色不参与互斥判定 | ✅ 语义简单、可解释：约束管的是"这个人身上挂了哪些岗位"，而不是"他因此获得了哪些能力"。管理员能直观理解"为什么被拒" |
| 按"展开后的有效角色集合"判定 | 继承来的角色也参与互斥判定 | ❌ 会出现"给用户加一个角色，却因链上某个远处角色被拒"的费解情况；且继承关系一改，历史授权可能突然"变成非法" |

**选定方案：按直接授予的角色判定。** 并将此规则写入 RBAC2 的校验器实现与本文档，作为长期契约。

## 7. 三个扩展点的正式定义

以下三个抽象是整个升级路径的承重墙。**它们的接口在阶段 0 定稿后不允许随意修改**——改了它们，就等于改了所有升级动作的成本。

### 7.1 扩展点一：`PermissionResolver`（权限解析器）

```
位置：rbac-api 模块
职责：给定用户，返回其有效权限码集合

    interface PermissionResolver {
        Set<String> resolve(long userId);
    }

实现方：rbac-cache 模块（缓存装饰 + 惰性重建 + 单飞）
真正的计算：rbac-core 模块（纯计算，读缓存映射）
```

| 要求 | 说明 |
|---|---|
| 返回只读集合 | 调用方不得修改（避免共享状态被污染） |
| 必须是无副作用的 | 重复调用结果相同 |
| 必须自行处理"用户不存在/被停用" | 返回空集合，而不是抛异常或返回 null（**封装默认值，调用方不需要判空**） |
| 不得抛出与权限无关的异常 | 缓存重建失败时返回旧值或空集合 + 告警 |

> **注意最后两条**：这是"把复杂逻辑下沉到模块内部"的具体体现。`PermissionInterceptor` 里不应该出现 `try/catch` 或 `!= null` 判断——**调用方越干净，鉴权主链路越不会在升级中被改动。**

### 7.2 扩展点二：`ConstraintValidator`（约束校验器链）

```
位置：rbac-api 模块（接口），实现散在 rbac-core 内部
职责：判断一次授权变更是否被允许

    interface ConstraintValidator {
        void validate(AuthorizationCommand cmd);   // 违反则抛 ConstraintViolatedException
    }

    interface AuthorizationCommand {         // 只暴露"意图"所需的最小信息
        long operatorId();                   // 谁在操作
        long targetUserId();                 // 给谁授权（用户角色授权时）
        long targetRoleId();                 // 给哪个角色授权（角色权限授权时）
        Set<Long> finalRoleIds();            // 本次操作完成后的最终角色集合（用户角色授权时）
    }
```

**为什么命令对象要提供"最终集合"而不是"增量"？**

因为约束判定本质上是"结果是否合法"，而不是"这次改动是否合法"。提供最终集合让每个校验器都能用最直观的方式判断（"集合里是否同时有互斥的两个角色"），而不需要每个校验器自己去做"当前集合 + 增量"的推演——**把推演逻辑收敛到一处，校验器只做判断。**

### 7.3 扩展点三：版本号与失效通知

```
位置：rbac-api 模块（事件定义）
职责：让"权限/身份相关数据发生了变化"这件事，能被所有实例在 1s 内感知

    record CacheInvalidateEvent(
        ChangeType type,     // PERM_CHANGED / TOKEN_REVOKED / TOKEN_REVOKED_GLOBAL
        long version,        // 全局版本号（自增，用于可观测与排查）
        Long targetUserId    // TOKEN_REVOKED 时指定用户；其余为 null（全局）
    ) {}

发布：任意写操作的事务提交之后，由 rbac-cache 发布到 Redis 频道
订阅：所有实例，收到后**只把对应缓存标记为不可信/丢弃**，不立即重载（惰性）
     PERM_CHANGED          → 丢弃缓存 A、B
     TOKEN_REVOKED(userId) → 丢弃缓存 C 中该用户的条目
     TOKEN_REVOKED_GLOBAL  → 丢弃整个缓存 C
```

> **注意本设计采用"失效而非更新"语义**：事件只让缓存**失效**，不携带权限数据本身；失效后由下一个请求自己去数据库重新加载。这带来一个重要结论——**不存在"旧事件覆盖新状态"的问题**，因为无论事件到达顺序如何，重新加载拿到的都是数据库**当前**的状态。事件仍携带 `version`，用途是**可观测与排查**（例如发现某实例版本长期落后），而不是用于"比大小决定要不要覆盖"。

**契约要求（升级时不得破坏）**：

| 要求 | 原因 |
|---|---|
| 必须在**事务提交之后**发布 | 见 [01 文档 UC-2 的说明](./01-需求规格说明书.md)：顺序错了会把旧数据写回缓存 |
| 发布失败不得影响业务操作成功 | Redis 是加速器而非关键路径；TTL 兜底 |
| 消息体保持极小（不含权限数据） | 消息只是"通知丢弃缓存"，具体内容由各实例自己重载。这避免了"N 个实例各持有一份不同的消息体"的不一致风险 |
| 新增缓存对象时必须同步更新失效逻辑 | **这是升级时最容易漏的一步**（RBAC1 引入 `inheritRoleId` 映射就属于此类）。因此 [03 文档 §10 变更影响矩阵](./03-数据模型设计.md) 明确把这条列为必查项 |

## 10. 如果现在就要 RBAC3，怎么办？

**可以直接做，但顺序不能变。** 因为 RBAC3 = RBAC1 + RBAC2，跳过中间阶段意味着一次引入两个变量，出问题时无法区分是哪一层的语义错误。

**推荐路径**：按阶段 0 → 1 → 2 推进，但**把阶段 1 与阶段 2 之间的间隔压缩**（阶段 1 上线观察 1~2 周即可进入阶段 2）。**不要试图把阶段 1 和 2 合并为一次上线**——它们虽然正交，但同时上线会让回归测试的组合爆炸（继承 × 约束 × 停用状态的组合），而分开上线时每个阶段的回归面都是可控的。

## 11. 必须始终保持的不变式（Invariants）

这六条是每次升级时的**红线**。任何设计变更如果破坏了其中一条，都必须重新评审。

| 编号 | 不变式 | 破坏的后果 |
|---|---|---|
| **I-1** | 业务代码只依赖**权限码字符串**，不得依赖角色、继承关系、约束规则 | 每次模型升级都要改动大量业务代码，升级代价失控 |
| **I-2** | 鉴权主链路只做"**权限码集合包含判定**"，不得内嵌任何权限模型逻辑 | 权限模型的变化会渗透到鉴权链路，安全核心变得脆弱 |
| **I-3** | 权限计算必须是**纯函数**（无副作用、无写库、无消息） | 无法单测、无法在并发下安全使用、无法缓存 |
| **I-4** | 任何权限相关变更都必须在 **1 秒内**使所有实例失效缓存 | 权限回收不生效，形成安全事故 |
| **I-5** | 表结构演进只允许**加表、加列、加索引**，禁止改列语义或删列 | 升级被迫停机且不可回滚 |
| **I-6** | 鉴权链路必须保持**零数据库查询、零网络调用** | 30ms 目标破产，10k 并发下存储层被打爆 |

**每次升级前的自检问题**：

1. 这次改动会出现在 I-1 到 I-6 的哪一条上？
2. 如果答案是"多条"，说明这次改动跨越了多个关注点，应当拆分。
