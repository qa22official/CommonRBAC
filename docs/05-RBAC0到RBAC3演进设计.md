# 05 · RBAC0 → RBAC3 演进设计

相关文档：[00 基线](./00-编码代理工作基线.md) · [01 需求](./01-需求规格说明书.md) · [02 总体设计](./02-总体设计说明书.md) · [03 数据模型](./03-数据模型设计.md) · [04 接口](./04-接口设计.md) · [07 修订记录](./07-修订记录.md)

## 1. 四个层次的定义

```text
RBAC0  用户 → 角色 → 权限
  ├─ RBAC1  + 角色继承
  ├─ RBAC2  + 约束规则
  └─ RBAC3  = RBAC1 + RBAC2
```

| 层次 | 新增机制 | 影响位置 |
|---|---|---|
| RBAC0 | 用户-角色、角色-权限两层关系与权限判定 | 全部 |
| RBAC1 | 角色之间多一条继承关系 | 只影响"角色集合 → 权限集合"的计算 |
| RBAC2 | 授权动作上增加校验规则 | 只影响"写入授权关系"时的校验 |

RBAC1 改变读路径（怎么算出权限），RBAC2 改变写路径（允不允许建立这条授权关系）。两者作用位置不同，互不干扰，因此 RBAC3 不需要额外设计。

## 2. 演进总览

口径限定：下表的"业务接口权限声明"与"鉴权入口契约"两列，含义仅为——`@RequiresPermission` 的取值不变、过滤器与拦截器契约不变。这不意味着升级无工作量，见 §8。

| 阶段 | 目标 | 数据变化 | 代码变化 | 权限声明 | 鉴权入口 | 前端变化 |
|---|---|---|---|---|---|---|
| 0 | RBAC0 上线 | 6 张表（继承字段已预留） | 全新实现 | 新增 | 全新实现 | 全新实现 |
| 1 | RBAC1 继承 | 填继承关系值 | 权限计算实现 + 快照加载 SQL | 不变 | 不变 | 角色列表改树形；新增继承来源选择 |
| 2 | RBAC2 约束 | 新增 `sys_role_constraint` + 规则数据 | 新增校验器实现类 | 不变 | 不变 | 新增约束管理页；授权失败提示 |
| 3 | RBAC3 | 无 | 无 | 不变 | 不变 | 无 |

各阶段代价按六个维度估算：

| 维度 | 阶段 1 | 阶段 2 |
|---|---|---|
| 代码变更 | 继承链展开 + 环检测、快照加载 SQL | 2 个校验器实现类 |
| 数据迁移 | 填继承关系（可按角色灰度） | 新增约束规则 |
| 接口新增 | `GET /api/roles/tree`；角色接口新增可选字段 | 约束规则 CRUD |
| 前端变更 | 角色列表改树形、表单单选 | 约束管理页、失败提示文案 |
| 测试回归 | 单层/多层/菱形/成环/停用 + 权限快照零差异比对 | 互斥/基数 + 并发授权 + RBAC0 校验器回归 |
| 灰度与回滚 | 回滚方式：清空继承关系（改数据，不发版本） | 回滚方式：停用规则 |

## 3. 阶段 0：RBAC0

### 3.1 数据模型与预留

表结构见 [03 §4](./03-数据模型设计.md)。两处预留：

| 项 | 要求 |
|---|---|
| `sys_role.inherit_role_id` | 字段存在，RBAC0 阶段恒为 0 |
| `ConstraintValidator` 校验链 | 链已存在，挂 4 个实现（见 3.4） |

命名使用 `ConstraintValidator` 而非 `AssignRoleValidator`：RBAC2 的领域术语是"约束"，对齐术语可避免将来改名。

### 3.2 权限计算算法（RBAC0）

```text
输入：userId
输出：Set<String> 权限码集合

1. roleIds ← userRoleMap[userId]
2. roleIds ← { r | roleStatus[r] = 启用 }
3. codes   ← ∪ { rolePermMap[r] | r ∈ roleIds }
4. codes   ← { c | permEnabled[c] = true }
5. return codes
```

必须保持的性质：

| 性质 | 约束 |
|---|---|
| 纯函数 | 相同输入必得相同输出；不写库、不发消息 |
| 只读缓存 | 不查数据库 |
| 复杂度 | O(角色数 × 每角色权限数)，微秒级 |
| 无拒绝语义 | 只有正向授权；不引入"拒绝优先"（会与 RBAC2 约束语义纠缠） |

### 3.3 鉴权判定

```text
hasPermission(userId, requiredCode):
    return PermissionMatcher.matches(resolve(userId), requiredCode)
    // 内部：精确匹配优先；再按 ':' 逐层尝试前缀通配，如 sys:user:* 命中 sys:user:delete
```

前缀通配匹配只在用户权限集合含通配项时触发；普通用户只走一次 `HashSet.contains`。

### 3.4 写入校验链

所有写授权关系的操作（分配角色、分配权限、启停用户或角色）必须经过同一条链：

```text
AuthorizationCommand
  → 校验链：for each ConstraintValidator v: v.validate(command)，不通过则抛业务异常
  → 事务内写入关系表 + 写 CHANGE 审计 → 提交
  → 提交后：版本号自增 + 发布失效通知
```

RBAC0 链上的校验器：

| 校验器 | 规则 |
|---|---|
| `LastSuperAdminValidator` | 系统必须保留 ≥ 1 个启用的超级管理员 |
| `SelfLockoutValidator` | 不能删除或停用自己；不能移除自己最后一个管理类角色 |
| `BuiltinRoleProtectionValidator` | 内置角色不可删除或停用；其 `*` 权限不可移除 |
| `RoleReferenceValidator` | 角色被用户引用时不可删除 |

这 4 个校验器在 RBAC2 阶段继续留在链上，只追加互斥与基数校验器。

## 4. 阶段 1：升级到 RBAC1

### 4.1 模型变化与语义

在 `sys_role.inherit_role_id` 上填入值，形成继承链：

```text
运营专员 (inherit=0)  ←── 运营主管 (inherit=专员.id)  ←── 运营总监 (inherit=主管.id)
   权限最小                 权限 ⊇ 自身 + 专员              权限 ⊇ 全部三级

"←──" 读作"从…继承权限"。有效权限 = 自身权限 ∪ 继承链上全部角色的权限。
```

语义约定（唯一解释）：

| 约定 | 内容 |
|---|---|
| 字段含义 | `inherit_role_id` 表示"我从哪个角色继承权限"，不是组织上级 |
| 继承方向 | 沿 `inherit_role_id` 向链尾收集，取并集 |
| 并集语义 | 当前角色权限 = 自身 ∪ 链上全部角色的权限 |
| 不支持减去 | 不存在"链上有 A 但本角色不要 A"的表达；否则结果依赖遍历顺序 |
| 无继承行为不变 | `inherit_role_id = 0` 时与 RBAC0 行为完全一致 |
| 链深上限 | 5 层（沿 `inherit_role_id` 的边数） |
| 继承形态 | 单父链：每个角色最多一个 `inherit_role_id`；标准 RBAC1 的多父 DAG 不在本期，未来需新增 `sys_role_inheritance` 表 |
| 界面展示方向 | 渲染方向自由（可把权限最大的角色画在顶部），不影响数据方向 |

数据层只能有一个明确方向；展示方向是渲染问题，不得转嫁到数据模型。

### 4.2 数据变化

| 项 | 结论 |
|---|---|
| 加列 | 不需要（字段已存在） |
| 加表 | 不需要 |
| 加索引 | 不需要（`idx_inherit_role_id` 已存在） |
| 实际操作 | `UPDATE sys_role SET inherit_role_id = ? WHERE id = ?`；存量角色保持 0 |

灰度：先给 1~2 个角色配置，观察后再放开。未配置继承的角色行为不变，风险被限制在已配置的角色上。

### 4.3 实现时机决策（待定）

| 项 | 方案甲：阶段 0 就实现展开 | 方案乙：升级时再实现 |
|---|---|---|
| 代码量 | 约 40 行 + 单元测试 | 现在 0 行，升级时约 40 行 |
| 升级时动作 | 仅填数据 + 前端放开选择 | 填数据 + 改实现 + 重新测试 + 重新部署 |
| 升级回滚 | 把 `inherit_role_id` 置 0，不部署不停机 | 需回滚部署旧版本 |
| 风险 | 有一段当前不生效的逻辑 | 算法与数据同时变更，出问题难区分来源 |

方案甲在 RBAC0 数据下是恒等变换（一层都不加），行为与 RBAC0 一致。

若选方案甲，必须配套：

| 风险 | 对策 |
|---|---|
| 逻辑在生产从未生效 | 单元测试覆盖多层、菱形汇聚、成环；阶段 0 末期做一次升级预演 |
| 环检测本身有缺陷 | 访问集合 + 路径深度上限双重保护，深度上限保证不死循环 |
| 深链拖慢计算 | 深度上限 5；按角色 ID 去重 |

### 4.4 权限计算算法（RBAC1）

```text
1. directRoles ← userRoleMap[userId]
2. effectiveRoles ← 展开继承链(directRoles)        ★ 唯一新增步骤
3. codes ← ∪ { rolePermMap[r] | r ∈ effectiveRoles }   // 快照只含启用权限，无需再过滤

展开继承链(起步集合):
    result ← {}
    for start in 起步集合:
        if roleStatus[start] ≠ 启用: continue
        path ← [start]; r ← start; depth ← 0; cycle ← false
        while true:
            src ← inheritRoleMap[r]
            if src = 0: break
            if src ∈ path: 告警("环"); cycle ← true; break
            if depth + 1 > 5: 告警("超深"); break
            path.add(src); r ← src; depth ← depth + 1
        if cycle:
            result.add(start)                  // 降级为 RBAC0：只保留直接角色
        else:
            for x in path:
                if roleStatus[x] ≠ 启用: break // 停用角色及其上游链不生效
                result.add(x)
```

深度是沿 `inherit_role_id` 的边数，不是 `result` 的大小。6 个直接角色、宽菱形都不得触发深度告警；成环时只保留直接角色并告警，不抛异常。

实现约束：

| 项 | 要求 |
|---|---|
| 数据来源 | `PermissionSnapshot`（`inheritRoleMap`、`roleStatus`、`rolePermMap`），不查库 |
| 是否缓存最终权限集合 | 不缓存；只缓存事实。否则"给被继承角色加权限"会使所有下游角色用户的缓存失效 |
| 环的处理 | 告警 + 按"不加继承"处理（降级为 RBAC0 行为），不拒绝请求 |
| 停用角色 | 停用角色及其上游链不进入有效集合；继承方自身权限仍生效 |

### 4.5 缓存变化

| 缓存 | 变化 |
|---|---|
| `PermissionSnapshot` | 新增 `roleId → {status, inheritRoleId}`；角色权限、用户角色、权限启用仍在同一快照内 |
| `IdentitySnapshot` | 不变 |
| 权限树 | 直接查库，不新增缓存 |

继承关系与角色状态一起进入 `PermissionSnapshot`：快照加载查询多取 `SELECT id, inherit_role_id, status FROM sys_role`。升级时必须同步修改快照加载 SQL，不新增独立缓存对象。

### 4.9 回归测试点

| # | 测试点 | 预期 |
|---|---|---|
| 1 | 无继承的既有角色 | 权限与升级前逐条一致 |
| 2 | 单层继承 | 继承方获得被继承角色的权限 |
| 3 | 多层链式（3 层） | 链尾角色获得链上全部角色的权限 |
| 4 | 菱形汇聚 | 共同角色权限只计一次 |
| 5 | 被继承角色停用 | 该角色权限不生效，继承方自身权限仍生效 |
| 6 | 方向断言（必测） | `主管.inherit=专员` 时主管拥有专员权限；反向配置时结果相反。方向不得反转 |
| 7 | 配置成环 | 接口拒绝（40930） |
| 8 | 已存在的环（脏数据） | 降级为 RBAC0 行为 + 告警，不返回 500 |
| 9 | 权限变更广播 | 修改被继承角色权限后，链尾角色用户 1 秒内生效 |
| 10 | 快照重建 | 重建后包含 `inheritRoleId` |
| 11 | 全量权限快照对比 | 未配置继承的用户升级前后零差异 |
| 12 | 6 个直接角色、无继承 | 不抛异常，权限为 6 个角色并集 |
| 13 | 深度 5 / 6 | 5 层可用；第 6 层告警并跳过，不抛异常 |

第 6 项覆盖"不会报错、只会静默越权"的缺陷类型。

第 11 项做法：升级前导出全部用户的权限码集合快照，升级后（未配置任何继承时）再导出一次逐条比对。

## 5. 阶段 2：升级到 RBAC2

### 5.1 约束类型

约束是对"授权动作"的限制，不是权限本身。

| 类型 | 含义 | 例子 | 术语 |
|---|---|---|---|
| 互斥（静态） | 两个角色不能同时授予同一人 | "付款申请"与"付款审批" | SSD |
| 基数（静态） | 角色人数上限 | "部门经理"最多 1 人 | Cardinality |
| 互斥（动态） | 可同时拥有，但不能同时激活 | 需"会话激活角色"概念 | DSD |

本期只实现静态互斥与基数。DSD 需要改动登录流程与前端交互，成本明显更高；将来实现也只是"新增表 + 新增校验器 + 新增会话概念"，不推翻已有结构。

### 5.2 数据变化

新增 `sys_role_constraint`（见 [03 §4.6](./03-数据模型设计.md)）。纯新增，现有表与 SQL 不受影响。

### 5.3 代码变化

在既有校验链上追加 2 个实现类（互斥、基数）。修改已有类：0。修改接口：0。修改表：0。业务代码：0。

### 5.4 校验器契约

```java
interface ConstraintValidator {
    void validate(AuthorizationCommand cmd);   // 不通过则抛 ConstraintViolatedException(错误码, 提示)
}
```

| 性质 | 要求 |
|---|---|
| 输入 | 一次授权变更的意图，不是数据库状态；校验器自行读取所需数据 |
| 互不感知 | 新增校验器不改动已有代码 |
| 失败即整体拒绝 | 不允许部分成功 |
| 只读 | 不写库，保证链可重复执行 |

命令对象需提供操作完成后的**最终集合**，而非增量。理由：约束判定针对"结果是否合法"，提供最终集合可避免每个校验器各自推演"当前集合 + 增量"。角色分配用 `finalRoleIds`，权限分配用 `finalPermissionCodes`；两者按 `targetType` 取用。

### 5.5 并发下的约束校验

问题场景：两个管理员同时给同一用户授予互斥的两个角色，若两者都读到"当前无冲突"的状态，则约束被绕过。

对策：

| 方案 | 做法 | 结论 |
|---|---|---|
| 行级锁串行化 | 事务内先 `SELECT ... FROM sys_user WHERE id = ? FOR UPDATE` 锁目标用户；角色容量约束锁目标角色行 | 采用 |
| 唯一约束表达 | 互斥关系需要两行对称插入，无法用唯一索引表达 | 不采用 |
| Redis 分布式锁 | 引入锁超时、锁失效、Redis 故障等新问题 | 不采用 |

授权操作每天几十次，行锁等待可忽略。

行锁与乐观锁分工：行锁保证"校验与写入之间不被并发穿透"，`expectedVersion` 保证"发现编辑期间数据已被改动"。两者不可互相替代（见 [03 §6.1](./03-数据模型设计.md)）。

### 5.6 约束语义硬规则

| 编号 | 规则 | 依据 |
|---|---|---|
| C-1 | 约束只检查直接授予的角色，不检查继承来的角色 | 约束管理的是"身上挂了哪些角色"，不是"因此获得了哪些能力"。若按展开后的集合判定，改继承关系会使历史授权突然非法 |
| C-2 | 新增约束规则时允许存在历史冲突数据，但必须同时输出冲突用户清单 | 若要求清理干净才能保存，上线后就再也加不了新规则。规则保存成功后，新增授权受约束，既有授权不强制收回 |
| C-3 | 基数下限只告警，不拦截写入；只有上限才拦截 | 下限做成硬拒绝会导致死锁：当前只有 1 个审批人时，连修改该用户其他信息都会被拒 |

### 5.7 接口与前端变化

| 项 | 变化 | 破坏性 |
|---|---|---|
| `GET/POST/PUT/DELETE /api/role-constraints` | 新增，权限码 `sys:constraint:read/create/update/delete` | 否 |
| `PUT /api/users/{id}/roles` | 接口不变，新增业务错误码 40940（违反互斥）/ 40941（违反基数） | 否 |
| 前端 | 新增角色约束管理页 | 否 |

授权失败的提示必须说清违反了哪条规则，而不是笼统的"操作失败"。

错误码区分：

| 类别 | 含义 | 前端动作 |
|---|---|---|
| 403xx | 没有操作权限 | 找管理员要权限 |
| 4094x | 有权限但违反业务规则 | 修改授权方案 |
| 40950 | 数据版本过期 | 刷新后重试 |

### 5.8 回归测试点

| # | 测试点 | 预期 |
|---|---|---|
| 1 | 无约束规则 | 行为与 RBAC1 一致 |
| 2 | 互斥：先授 R1 再授 R2 | 第二次被拒 40940 |
| 3 | 新增互斥规则与已有授权冲突 | 规则可保存，并返回冲突用户清单 |
| 4 | 批量授权中出现冲突 | 整体回滚，指出冲突项 |
| 5 | 基数超过上限 | 被拒 40941 |
| 6 | 基数低于下限 | 仅告警，不拒绝 |
| 7 | 并发授予互斥角色 | 最终结果不违反约束 |
| 8 | RBAC0 的 4 个校验器 | 仍生效 |

## 6. 阶段 3：RBAC3

不需要任何动作。RBAC1 已在阶段 1 生效，RBAC2 已在阶段 2 生效，两者叠加即为 RBAC3。

唯一需要确认的交互点：继承得到的角色是否参与互斥判定。

| 方案 | 结论 |
|---|---|
| 按直接授予的角色判定 | 采用。语义可解释，且改继承关系不会使历史授权变非法 |
| 按展开后的有效角色集合判定 | 不采用。会出现"加一个角色却因链上远处角色被拒"的费解情况 |

此规则已写入 §5.6 的 C-1。

## 7. 三个扩展点

这三个抽象是升级路径的承重结构，接口一旦定稿不得随意修改。

### 7.1 PermissionResolver

```java
Set<String> resolve(long userId);
```

| 要求 | 说明 |
|---|---|
| 返回只读集合 | 调用方不得修改 |
| 无副作用 | 重复调用结果相同 |
| 自行处理异常情况 | 用户不存在或已停用返回空集合，不抛异常、不返回 null |
| 不抛出与权限无关的异常 | 重载失败时返回旧值或空集合并告警 |

实现方在 `rbac-cache`（`PermissionSnapshot` + 单飞重建）；快照数据由 `rbac-core` 通过 `PermissionSnapshotSource` 提供，计算逻辑在 core。cache 不直接依赖 core 实现。

### 7.2 ConstraintValidator（rbac-core 内部）

```java
interface ConstraintValidator {
    void validate(AuthorizationCommand cmd);
}

record AuthorizationCommand(
    long operatorId,
    TargetType targetType,              // USER_ROLES / ROLE_PERMISSIONS / USER_STATUS / ROLE_STATUS / ROLE_DELETE / PERMISSION_DELETE
    long targetUserId,
    long targetRoleId,
    Set<Long> finalRoleIds,             // 角色分配时使用
    Set<String> finalPermissionCodes)   // 权限分配时使用
{}
```

`ConstraintValidator` 与 `AuthorizationCommand` 是 **core 内部扩展点**，不进入 `rbac-api`。`rbac-api` 只暴露 `UserAdminService` / `RoleAdminService` 作为入口；`rbac-admin` 调用入口，core 在事务内执行校验链。这样既保持严格模块依赖，又避免把内部约束模型变成公共契约。

### 7.3 失效通知

```java
record CacheInvalidateEvent(
    ChangeType type,     // PERM_CHANGED / TOKEN_REVOKED
    long version,
    Long targetUserId)
{}
```

| 要求 | 依据 |
|---|---|
| 必须在事务提交后发布 | 顺序错误会把旧数据写回缓存 |
| 发布失败不影响业务成功 | 软 TTL 兜底 |
| 消息体保持极小，不含数据 | 只通知标记失效，内容由各实例自行重载 |
| 采用失效而非更新语义 | 无论事件到达顺序如何，重载都取数据库当前状态，不存在旧事件覆盖新状态 |
| 新增缓存对象时必须同步更新失效逻辑 | 升级时最易漏的一项 |
| 登录与刷新不发布事件 | 多会话：不改 `token_version`，无失效需要广播 |

## 10. 不变式

每次升级都不得破坏以下六条：

| 编号 | 不变式 | 破坏后果 |
|---|---|---|
| I-1 | 业务代码只依赖权限码字符串，不依赖角色、继承关系、约束规则 | 每次模型升级都要改动大量业务代码 |
| I-2 | 鉴权主链路只做"权限码集合包含判定"，不内嵌权限模型逻辑 | 权限模型变化会渗透进安全核心 |
| I-3 | 权限计算必须是纯函数（无副作用、不写库、不发消息） | 无法单测、无法并发安全使用、无法缓存 |
| I-4 | 任何权限变更必须在 1 秒内使所有实例标记 `PermissionSnapshot` stale | 权限回收不生效 |
| I-5 | 表结构演进只允许加表、加列、加索引，禁止改列语义或删列 | 升级被迫停机且不可回滚 |
| I-6 | 鉴权判定必须保持零数据库查询、零网络调用；快照重建由缓存层单飞执行 | 30ms 目标失效，存储层被打爆 |

升级前自检：本次改动落在哪几条不变式上？若跨多条，说明改动跨越了多个关注点，应拆分。
