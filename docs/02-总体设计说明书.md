## 1. 设计目标与原则

### 1.1 三条不可让步的目标

| 优先级 | 目标 | 判据 |
|---|---|---|
| 1 | **升级代价最小** | 升级 RBAC1/RBAC2 时，业务代码与鉴权主链路改动为 0 行；已有表无破坏性变更 |
| 2 | **响应速度达标** | 鉴权类接口 P99 ≤ 30ms（10k 并发在线用户，约 2k QPS） |
| 3 | **资源占用克制** | 组件数量少、单实例资源可控、不为低频功能付出高频成本 |

### 1.2 三大设计原则（通俗版 + 术语）

**原则一：把变化关进一个盒子里，盒子外面永远不变。**

遇到需求要变，人的第一反应是"加个 if 分支"。但分支加在主干道上，下次再变就要再动主干道，越改越乱。正确做法是**先找到"将来一定会变的东西"，把它抽象成一个接口，让变化只发生在接口的实现里**。这在设计上叫"稳定抽象原则"。

在本系统中，"一定会变"的是**"用户的权限集合怎么算出来"**：
- RBAC0：用户 → 角色的权限，并集。
- RBAC1：还要把角色的**祖先**角色的权限也并集进来。
- RBAC2：算完之后还要根据约束**剔除**一些（例如某人与某角色冲突时该角色失效）。

而"永远不变"的是：**接口只需要一个权限码，判断"在不在集合里"**。

所以我们的盒子就是 `PermissionResolver`（权限解析器）这一个接口。业务接口、鉴权过滤器、前端，全都只跟"权限码集合"打交道，没人知道这个集合是怎么算出来的。

**原则二：性能优化的正确顺序是"减少工作"，而不是"加快工作"。**

绝大多数性能问题的解法不是"用更快的框架"，而是"根本不用做这件事"。本设计中最典型的一步是：**让鉴权链路一次数据库查询都不做**。

怎么做到？关键洞察是——**权限相关的数据总量极小**（用户-角色关系约 3 万条、角色-权限关系约 1 万条，加起来不到 10MB），小到可以**整份放进每个后端实例的内存里**。于是：
- 请求来了 → 内存里查一下（纳秒级）→ 判定完成。
- 数据库只在"权限被修改后"被访问一次（重新加载这两张表），与在线用户数无关。

对比常见做法（每次请求查 Redis 或查库），我们把 2000 QPS 的存储访问压力直接降到接近 0。这是"10k 在线用户 + 30ms"能轻松达标的根本原因，而不是靠某个高性能框架。

**原则三：每一份冗余都必须能说出理由，否则就是负债。**

我们不预留 `tenant_id`（不做多租户）、不预留数据权限字段（不做）、不预建用不到的表。只预留两样东西：`sys_role.inherit_role_id` 一个字段，和两个代码扩展点。**预留字段的成本不是磁盘空间，而是"每个后来者都要猜它是干什么的"的心智负担。**

### 1.3 我们明确拒绝的三种常见做法

| 常见做法 | 为什么不采用 | 代价对比 |
|---|---|---|
| 引入 Spring Security 全套 + OAuth2 服务 | 我们只需"验令牌 + 查权限码"，而全套框架的核心价值（会话管理、表单登录、OAuth2 授权服务器、过滤器链编排）我们全用不上。同时它的过滤器链是"配置式黑盒"，出问题时排查成本高 | 自研版约 300 行代码 + 单元测试；换成框架需配置 5~10 个组件并理解其执行顺序，长期维护反而更重 |
| 用 WebFlux 响应式框架应对"高并发" | **10k 在线用户 ≠ 10k 同时在处理的请求**。按 2000 QPS × 30ms 计算，同时在处理的请求只有约 60 个（计算过程见 [06 文档第 1 节](./06-性能与容量设计.md)）。响应式框架解决的是"海量空闲长连接"，我们的场景根本不存在这个问题，却要付出调试困难、栈信息不可读、生态兼容坑多的代价 | 同步阻塞模型：200 个线程足够；响应式：代码复杂度上升数倍，换来用不上的能力 |
| 引入 Spring Cloud + 网关 + 配置中心 + 注册中心 | 模块化单体的模块间是**方法调用**，没有网络，不需要注册与发现；配置量很小，不需要配置中心 | 少维护 3~5 个组件，少消耗数 GB 内存 |

## 2. 总体架构

### 2.1 部署视图

```
        ┌──────────────────────────────────────────────────────────────┐
        │  浏览器（Vue 3 单页应用）                                     │
        │  · 登录页 / 权限管理后台 / 业务页面                           │
        │  · 路由守卫 + 按钮级权限指令 v-perm                           │
        └───────────────────────────┬──────────────────────────────────┘
                                    │ HTTPS（Authorization: Bearer <JWT>）
                                    ▼
        ┌──────────────────────────────────────────────────────────────┐
        │  Nginx（静态资源 + 反向代理 + keepalive 上游）                │
        └───────────────────────────┬──────────────────────────────────┘
                                    │ HTTP 内网
        ┌───────────────────────────┴──────────────────────────────────┐
        │                    应用实例 ×3（无状态，可随时增减）          │
        │  ┌────────────────────────────────────────────────────────┐  │
        │  │  rbac-bootstrap                                        │  │
        │  │    ├── rbac-guard   鉴权入口（过滤器 + 注解 + 上下文） │  │
        │  │    ├── rbac-admin   管理端 REST 接口                   │  │
        │  │    ├── rbac-auth    认证（登录/令牌/密码）             │  │
        │  │    ├── rbac-core    领域逻辑 + 权限计算 + 持久化        │  │
        │  │    ├── rbac-cache   本地缓存 + 失效广播 + 版本号        │  │
        │  │    ├── rbac-audit   审计写入与查询                     │  │
        │  │    └── rbac-api     模块间契约（接口 + DTO）           │  │
        │  └────────────────────────────────────────────────────────┘  │
        │      本地内存：用户→角色 / 角色→权限 两张映射（< 10MB）       │
        └───────┬───────────────────────────────────┬──────────────────┘
                │ JDBC（仅写操作与缓存重建）        │ Redis 协议（订阅失效广播）
                ▼                                   ▼
        ┌───────────────────────┐         ┌──────────────────────────┐
        │ MySQL 8.0（主，可选从）│         │ Redis（失效广播频道）    │
        │ 业务表 6 张 + 审计表   │         │ 内存占用 < 10MB          │
        └───────────────────────┘         └──────────────────────────┘
```

### 2.2 为什么是这个形状

| 设计点 | 理由 |
|---|---|
| Nginx 前置 | 静态资源直接由 Nginx 返回，不占用 Java 实例资源；反向代理屏蔽实例伸缩；上游 keepalive 减少连接建立开销 |
| 应用无状态 | 本地缓存只存"权限映射"这类**可重建**的数据，不存用户会话。因此实例可以随意增减，不需要会话粘滞（sticky session），负载均衡策略自由 |
| MySQL 只承担写与重载 | 鉴权链路零 DB 查询，DB 的读压力极低，一台中等规格机器足够 |
| Redis 只做广播 | 不存业务数据、不做缓存，只做进程间通知。因此它**不是关键路径**：挂了也不会让系统不可用，只会让权限变更生效变慢（TTL 兜底） |
| 每个实例持有全量权限映射 | 数据量小（< 10MB），全量持有可以让鉴权零查询；若用"按用户缓存"方案，10k 用户需存 10k 份权限集合，内存放大且失效粒度复杂 |

### 2.3 核心数据结构（缓存内容）

```
缓存 A：roleId         → Set<permissionCode>      // 角色权限矩阵
缓存 B：userId         → Set<roleId>              // 用户角色关系
缓存 C：userId         → { tokenVersion, status, loadedAt, expiresAt }   // 身份快照（TTL 30s）
派生值：用户有效权限码  =  ∪ 缓存A[roleId]（roleId ∈ 缓存B[userId]，且角色启用、权限启用）
```

| 缓存 | 用途 | 失效时机 |
|---|---|---|
| A / B | 权限判定（见 5.2 第 3 步） | 收到权限变更广播、或 TTL 到期 |
| **C 身份快照** | **令牌作废判定**（见 5.3.3）：`token.ver` 必须等于 `snapshot.tokenVersion` | 收到令牌作废广播、或 TTL（30s）到期 |

> **为什么 A、B 与 C 必须分开？** 因为它们的**失效触发条件完全不同**：改一个角色的权限，会让所有持有该角色的用户的**权限**失效，但**不应影响他们的登录状态**；反之，一个用户被停用，只需要作废**他一个人**的身份快照，与全局权限矩阵无关。混在一张缓存里，任何一种变更都会导致另一类数据被无谓地清空（**失效范围爆炸**）。

**为什么缓存 A + B，而不是直接缓存"userId → 权限码集合"？**

因为 A、B 是最小的、彼此独立的事实，它们的数据量与"角色数"和"用户-角色关系数"成正比（约 4 万条）；而"用户→权限码"是**派生结果**，其体积与用户数 × 平均权限数成正比，会明显更大，且每次权限变更要作废的数量更多。缓存事实、现场求派生——一次集合求并集的耗时是微秒级，几乎免费。

> **类比**：与其给每个员工打印一份"你能进哪些门"的清单（改一次规则就要重印上万份），不如贴两张表：一张"岗位→门禁权限"，一张"员工→岗位"。员工进门时看一眼这两张表现算即可。

## 3. 模块划分与职责

模块划分的判据来自设计标准：**变化原因不同则拆，接口因此更小更清晰则拆；功能共享、合并后更简单则合。**

| 模块 | 职责（一句话） | 允许依赖 | 为什么单独成模块（不合并的理由） |
|---|---|---|---|
| `rbac-api` | 模块间契约：接口、DTO、事件定义、常量 | 无（仅 JDK） | 它是所有模块的共同依赖，必须零实现、零第三方依赖，否则会形成传递依赖链 |
| `rbac-core` | 领域模型（用户/角色/权限）、权限计算、约束校验器链、持久化 | `rbac-api` | 领域逻辑是系统的稳定内核，**变化原因单一**（权限模型演进） |
| `rbac-auth` | 认证：登录、令牌签发/验签、密码策略、失败锁定 | `rbac-api` | **与鉴权的变化原因完全不同**：认证随"登录方式"变（将来可能加 SSO），鉴权随"权限模型"变。而 RBAC 升级只会动鉴权侧——这是升级代价控制的关键切分 |
| `rbac-guard` | 鉴权入口：过滤器、`@RequiresPermission`、请求上下文 | `rbac-api` | 它是"接入层"（与 HTTP 协议绑定），领域逻辑不应知道 HTTP。测试领域逻辑时不需要起 Web 容器 |
| `rbac-cache` | 本地缓存、失效广播订阅、权限版本号 | `rbac-api` | 缓存是**性能基础设施**，不是领域概念。若并入 core，领域单元测试就必须携带缓存环境，且"缓存策略调整"会污染领域模块 |
| `rbac-audit` | 审计记录的写入与查询 | `rbac-api` | 被 core / auth / admin 三处调用，是横向关注点；且其变化原因（合规要求、保留策略）与业务无关 |
| `rbac-admin` | 管理端 REST 接口（用户/角色/权限/授权/审计查询） | `rbac-api` | 对外契约层，改接口不应改动领域逻辑 |
| `rbac-bootstrap` | 启动类、配置装配、Web 全局配置（CORS、统一异常、拦截器注册） | 全部 | **唯一知道所有实现的地方**（组装根）。其他模块之间只认接口 |

### 3.1 为什么不用"一个模块一大包"的简单做法

单模块 + 分包当然能跑起来，但它有一个致命弱点：**模块边界只是口头约定，编译器不管**。三个月后某人为了省事在 `guard` 里直接 `new` 了 `core` 的 Mapper，所有分层瞬间失效，而没人会发现。

用 Maven 多模块，**依赖方向由编译器强制**——`rbac-core` 的 pom 里没有 `rbac-admin`，它就连不上去。这是成本极低而收益极高的物理隔离。

### 3.2 为什么引入 Spring Modulith

**不引入。** 它提供的是"模块化治理 + 事务性事件日志"，会把事件发布记录额外写入数据库表。而我们的需求是"跨实例广播一条失效通知"，用 Redis 发布订阅 30 行代码即可完成；可追溯性由审计日志承担。为一个用不上的能力增加依赖与表，违反"每引入一个依赖都要能回答它换来了什么"。模块边界校验改用 **ArchUnit**（测试期校验，零运行期开销，且能表达比模块划分更细的规则，比如"Mapper 只允许被 core 内部访问"）。

## 4. 模块边界与依赖规则

### 4.1 允许的依赖方向

```
        rbac-bootstrap  ──────────────►  全部模块（唯一组装点）
              │
              ├── rbac-admin   ──┐
              ├── rbac-guard   ──┤
              ├── rbac-auth    ──┼──► rbac-api  ◄── rbac-cache
              ├── rbac-core    ──┤         ▲          rbac-audit
              └── rbac-audit   ──┘         └──（实现方在各自模块内）
```

### 4.2 硬性规则（由 ArchUnit 在构建时强制，违反即构建失败）

| 规则 | 内容 | 违反后果 |
|---|---|---|
| R-1 | 除 `rbac-bootstrap` 外，任何模块之间**不得直接依赖** | 模块化单体退化为"大泥球" |
| R-2 | `rbac-core` 不得依赖任何 Web 类型（`jakarta.servlet.*`、`@RestController`） | 领域逻辑与协议耦合，无法脱离 HTTP 测试 |
| R-3 | `rbac-auth` 不得依赖 `rbac-core` 的权限计算能力 | 认证与鉴权重新纠缠，RBAC 升级时要动认证模块 |
| R-4 | 业务接口不得引用角色（`Role`）、授权关系等概念，只允许使用**权限码字符串** | 升级 RBAC 时业务代码被迫改动（违反 NFR-5） |
| R-5 | Mapper（`*Mapper`）只允许被同模块内的领域服务引用 | SQL 散落到各处，索引优化失控 |
| R-6 | `rbac-*` 模块内不得出现 `import` 其他模块的 `internal` 包（约定：模块内私有类放 `internal` 子包） | 契约外的隐性耦合 |

### 4.3 模块间通信方式

| 场景 | 方式 | 说明 |
|---|---|---|
| 同步查询/命令（如 admin 调用"给用户分配角色"） | 通过 `rbac-api` 的**接口**调用（编译期只依赖接口，运行期由 Spring 注入实现） | 同进程方法调用，无序列化、无网络，延迟纳秒级 |
| 跨实例通知（权限变更） | **Redis 发布订阅**（消息体只含通知类型与版本号，不含数据） | 目的是"通知别人丢弃旧缓存"，不是"传数据"。消息极小，且丢了也能被 TTL 兜底 |
| 变更审计写入（`CHANGE` 类） | 通过 `rbac-api` 的接口同步调用，且**沿用调用者事务** | 必须与业务同事务（强合规），因此不允许异步、不允许走消息 |
| 安全事件写入（`SECURITY` 类） | 同一个接口，但**不参与业务事务**（独立提交或排队） | 安全事件多数**没有对应的业务变更**（如一次登录失败）。若强行纳入业务事务，会导致"记录失败就回滚了一个根本不存在的业务操作"，还会把日志压力传导进业务链路。详见 [01 文档 4.5](./01-需求规格说明书.md) |

> **为什么不全走消息？** "模块间通过消息间接交互"能带来解耦，但代价是**放弃同步语义**：调用者拿到的是"已投递"而不是"已成功"。对于"给用户分配角色"这类需要立即告诉用户成败的操作，改成消息会让前端陷入"提交成功但不知道有没有生效"的困境，并被迫引入补偿查询、幂等表、死信处理——**为了解耦而把简单问题复杂化**。因此我们的取舍是：**只有本质异步的、且丢得起的那一条通知走消息，其余走接口**。这个边界必须在模块设计阶段就写清楚，否则会被后来的同学"顺手改成消息"。

## 5. 关键设计

### 5.1 认证链路（你是谁）

```
POST /api/auth/login
   │
   ├─ 1. 登录限流检查（账号维度 + IP 维度，Redis 计数器，滑动窗口）
   ├─ 2. 账号存在性与状态检查
   ├─ 3. 失败锁定检查（连续失败 ≥5 次 → 锁 15 分钟）
   ├─ 4. BCrypt 校验（耗时 50~100ms，正常且必须慢）
   ├─ 5. 通过 → 令牌版本号（tokenVersion）自增（使该账号历史令牌作废，时效见 5.3.3）
   ├─ 6. 生成 JWT：payload = { sub, ver, kid, iss, aud, iat, exp }
   └─ 7. 写登录**安全事件**（`SECURITY` 类，独立落库，见 4.3）
```

**令牌载荷的取舍（重要）**：

| 载荷内容 | 放 / 不放 | 理由 |
|---|---|---|
| 用户 ID（`sub`） | 放 | 身份标识，鉴权需要 |
| 令牌版本号（`ver`） | 放 | 与本地**身份快照**比对以判定令牌是否已被作废，见 5.3.3 |
| 密钥标识（`kid`） | 放 | 密钥轮换期间据此选择验签密钥，见下方"密钥轮换协议" |
| 签发时间（`iat`）、过期时间（`exp`） | 放 | 标准字段；校验时允许 60 秒时钟偏移 |
| 签发方（`iss`）、受众（`aud`） | 放 | 防止本系统令牌被其他系统误用；验签时**强制校验**，不匹配即拒绝 |
| **令牌唯一 ID（`jti`）** | **不放** | 本系统按"用户维度"作废令牌（版本号）。引入 `jti` 就必须维护一张逐令牌黑名单（写入量 = 登录量，且需跨实例共享），成本与收益不成比例 |
| **用户角色列表** | **不放** | 角色变了令牌就是脏的，必须等过期，不可接受 |
| **权限码列表** | **不放** | 权限数量多会让令牌体积膨胀（每个请求都要传输与验签），且权限变更无法即时生效 |
| 用户昵称/头像 | 不放 | 会变更的非权威数据，应通过 `/api/auth/me` 获取 |

**签名算法选型：HMAC-SHA256（对称），不用 RS256（非对称）。**

| 算法 | 验签耗时 | 适用场景 | 我们的选择 |
|---|---|---|---|
| HS256 | 约 5~10 微秒 | 签发方与验证方是同一套系统（共享一个密钥） | ✅ 采用 |
| RS256 | 约 100~300 微秒 | 签发方与验证方分离（第三方也要验签，但不能签发） | ❌ 我们不需要 |

代价说明：HS256 的密钥一旦泄露，持有者可伪造任意令牌。因此要求：密钥长度 ≥ 256 位、通过环境变量/配置中心下发、支持双密钥轮换。若将来有第三方系统需要离线验签，再切换 RS256（令牌格式不变，只换算法与密钥，属于可替换的内部实现）。

**密钥的保存与分发**：

| 项 | 要求 |
|---|---|
| 长度 | ≥ 256 位随机字节（32 字节，Base64 后存放） |
| 存放位置 | 环境变量或配置中心（如 K8s Secret）；**严禁进入代码仓库、镜像层、配置文件模板** |
| 多实例一致性 | 所有实例读取同一份配置；启动时校验实例间 `kid → 密钥` 映射一致，不一致**直接启动失败**（避免"新旧密钥集合不同"导致随机 401） |
| 泄露处置 | 立即轮换 + **批量作废全部令牌**（全局令牌版本基线自增，见 5.3.3） |

**密钥轮换协议（可执行步骤，不是原则）**：

```
阶段 1  生成新密钥 K2，分配 kid = 2
        · 配置变为 { kid=1: K1, kid=2: K2 }，验签时按 kid 选择密钥（O(1)，不逐个尝试）
        · 签发改用最新 kid(=2)；tokenVersion 不递增（不踢人下线）
        · 发布顺序强制：先把"支持双密钥"的版本发到全部实例，再切换签发密钥
阶段 2  等待 ≥ 访问令牌最长有效期（2 小时）+ 时钟偏移余量
        · 期间 K1 只用于验签，不再用于签发
阶段 3  从配置移除 K1，只保留 K2
        · 移除前必须确认监控中已无任何 kid=1 的验签记录
```

| 风险 | 对策 |
|---|---|
| 轮换中实例配置不一致 | 启动时一致性校验 + 强制发布顺序（先全员支持新密钥，再切换签发） |
| 轮换失败需要回滚 | 回滚 = 配置改回 `{kid=1, kid=2}` 继续用 K1 签发。**因为阶段 3 之前 K1 一直保留，所以阶段 1、2 的任何时刻都可安全回滚** |
| 密钥泄露（紧急轮换） | 跳过等待期：立即生成 K2、签发切 K2，**同时全局自增令牌版本基线**（等价于踢所有人下线重新登录） |
| 密钥全部不可用 | 灾难场景：所有令牌失效，用户重新登录即可。**系统数据不受影响**，故障面被限制在"会话"上 |

> **为什么用 `kid` 而不是"逐个尝试所有密钥验签"？** 逐个尝试会让验签耗时随密钥数量线性上升，且无法区分"密钥不对"与"令牌伪造"，排查困难。`kid` 让选择是 O(1)，并且**可观测**——监控能看到每个 kid 的验签量，从而安全地决定何时淘汰旧密钥。

> **BCrypt 与 30ms 的关系**：BCrypt 故意慢（这才是它的价值），因此**登录接口不受 30ms 约束**。为避免它拖累其他接口，登录校验使用独立线程池隔离（见 [06 文档 §6.4](./06-性能与容量设计.md)）。

### 5.2 鉴权链路（你能不能做这件事）——**全链路零网络、零数据库**

```
HTTP 请求（Authorization: Bearer <JWT>）
   │
   ▼
[1] JwtAuthFilter（rbac-guard，OncePerRequestFilter）
   │   · 解析并验签（按 kid 选密钥，HS256，~10µs）
   │   · 检查 exp / iat / iss / aud（允许 60s 时钟偏移）
   │   · 身份快照校验（见 5.3.3）：
   │       snap = identityCache.get(userId)      ← 内存；未命中则单飞查库
   │       要求 snap.tokenVersion == token.ver 且 snap.status == 启用
   │   · 通过 → 把 CurrentUser{userId, tokenVersion} 写入请求上下文
   │
   ▼
[2] PermissionInterceptor（HandlerInterceptor）
   │   · 读取目标方法上的 @RequiresPermission("sys:user:create")
   │   · @PublicApi（无需登录）/ @RequiresLogin（只需登录）→ 直接放行
   │   · 三个注解都没有 → 直接拒绝（安全默认：默认拒绝）
   │
   ▼
[3] PermissionResolver（rbac-api 接口，实现由 rbac-cache 提供缓存装饰）
   │   · Set<String> codes = resolver.resolve(userId)   ← 纯内存计算
   │   · 缓存未命中 → 单飞重载（单线程查库，其余等待结果）
   │
   ▼
[4] 判定：codes.contains("*") || codes.contains(requiredCode)
   │   · true  → 放行（~5 纳秒的 HashSet 查询）
   │   · false → 403，不进入业务方法
```

**这条链路为什么能稳定在 3ms 以内（其实是 0.1ms 量级）**：

| 步骤 | 耗时量级 | 是否访问网络/磁盘 |
|---|---|---|
| JWT 验签 | 10 微秒 | 否 |
| 身份快照校验（内存命中） | 纳秒 | 否（未命中时一次单行主键查询，见 5.3.3 成本说明） |
| 权限解析（命中缓存） | 微秒 | 否 |
| 权限码比对 | 纳秒 | 否 |
| **合计** | **< 0.1 毫秒** | **无** |

也就是说，**30ms 的预算中，鉴权本身只花掉不到 1%**（P99 约 0.19ms），剩下 99% 留给业务逻辑。这正是"减少工作"优于"加快工作"的体现。

**安全默认（默认拒绝）**：未标注 `@RequiresPermission`、`@RequiresLogin`、`@PublicApi` 三者之一的接口**一律拒绝**（返回 403 并记录告警）。这看起来激进，但它把"漏加注解"从**安全漏洞**降级为**可见的功能缺陷**（开发期立刻发现），配合 NFR-8 的构建门禁，可以做到零遗漏。

### 5.3 权限缓存与失效机制（三层保障）

这是全系统唯一需要仔细权衡"一致性 vs 性能"的地方。

**第一层：主动失效（正常路径，目标 ≤ 1 秒）**

```
管理员修改权限 / 用户登出、改密、被停用
   │
   ├─ 事务内：写业务数据 + 写变更审计 → 提交
   │
   └─ 事务提交成功之后（顺序不可颠倒，见 01 文档 UC-2）：
        · 自增全局版本号（Redis 单键 INCR，用于可观测与排查）
        · 按事件类型发布：
            PERM_CHANGED   {"ver":123}                        → 全局权限变更
            TOKEN_REVOKED  {"userId":7,"ver":12}              → 单个用户令牌作废
            TOKEN_REVOKED_GLOBAL {"ver":1}                    → 全局令牌作废（密钥泄露）
              │
              ▼
        各实例订阅回调（**只丢弃，不立刻重载**）：
            PERM_CHANGED          → 清空缓存 A、B
            TOKEN_REVOKED(userId) → 丢弃该用户的缓存 C 条目
            TOKEN_REVOKED_GLOBAL  → 清空整个缓存 C
              │
              ▼
        下一个请求触发惰性重载（单飞防雪崩）
```

> **为什么"只丢弃、不立刻重载"？** 因为立即重载会让 N 个实例在同一瞬间一起查库，形成人为的流量尖峰。丢弃是"标记为不可信"，重载由随后的真实请求触发，天然被摊薄。
>
> **广播去抖**：1 秒内的多次变更合并为一次广播（反正都是全量失效），避免批量操作产生广播风暴。

**第二层：TTL 兜底（Redis 故障时，最坏 30 秒）**

| 缓存 | TTL | 兜底效果 |
|---|---|---|
| A / B（权限） | 30 秒（`expireAfterWrite`） | 广播完全丢失时，30 秒后自动重建，权限变更最终一定生效 |
| C（身份快照） | 30 秒（`expireAfterWrite`） | 广播完全丢失时，30 秒后重载，**拿到的是数据库当前版本**，旧令牌随即失效 |

> **为什么必须有 TTL？** Redis 的发布订阅**不保证投递**：实例在广播发生时正在重连、重启、或网络抖动，就永远收不到那条消息。如果只依赖广播，系统会**永久**停留在旧权限上——这是最危险的一类 bug（"我明明把权限收回了，对方还能用"）。所以广播负责"快"，TTL 负责"对"。
>
> **TTL 与需求承诺是一一对应的**：调大 TTL 会同时延长"Redis 故障时的收敛时间"，因此**修改 TTL 必须同步修改 [01 文档 FR-A9](./01-需求规格说明书.md) 的承诺**。这两处不允许只改一处。

**第三层：实例生命周期兜底**

| 场景 | 处理 |
|---|---|
| 实例启动 | 主动全量加载缓存 A、B；**缓存 C 不预加载**（首个请求按需查库，从而天然获得数据库最新状态，见 5.3.3） |
| Redis 订阅连接重连成功 | 强制清空缓存（因为断连期间的广播都丢了） |
| Redis 完全不可用 | 记录告警；系统降级为"TTL 生效模式"，登录与鉴权不受影响 |
| 缓存重载失败（DB 抖动） | **不允许无限使用旧值**，见 5.3.2 |

#### 5.3.1 缓存必须携带"新鲜度"元数据

缓存条目只存权限集合是不够的——**没有元数据就无法判断"这份数据还能不能用"**。因此每个缓存条目（以及全量缓存的全局元信息）都必须携带：

| 元数据 | 含义 | 用途 |
|---|---|---|
| `cacheVersion` | 本次加载时数据库侧的版本标记（取相关表 `MAX(updated_at)` 或全局版本表） | 可观测：能一眼看出各实例版本是否一致 |
| `loadedAt` | 本次**成功**加载的时间 | 计算陈旧时长（**只由成功加载更新**） |
| `expiresAt` | `loadedAt + TTL` | 到达时**触发重载**，而**不是**丢弃数据 |
| `state` | 见下表 | 决定当前请求如何处理 |

**缓存状态机**：

| 状态 | 含义 | 请求如何被处理 |
|---|---|---|
| `VALID` | 数据新鲜（未收到失效通知，且 `expiresAt` 未到） | 正常鉴权 |
| `STALE` | 已收到失效通知，或 `expiresAt` 已到；**最后一份成功加载的数据仍然可用** | 用旧数据正常鉴权 + 触发**异步**重载（不阻塞本请求） |
| `RELOADING` | 正在单飞重载 | 其他请求不重复触发，直接用旧数据处理，不等待 |
| `FAILED` | 重载失败 | **继续用最后一份成功数据服务**（本设计的选择，见 5.3.2）+ 告警 + 指数退避重试 |

**三条硬规则**：

1. **数据一旦成功加载过，就永不丢弃**（保留"最后一份已知良好数据"）。这是 fail-open 能成立的前提——如果 TTL 到点就把数据丢掉，重载又失败，系统就会**因为拿不到数据而被动拒绝服务**，fail-open 实际上无法实现。
2. **`loadedAt` 只由"成功加载"更新，绝不允许伪刷新**。这条是上一轮评审的核心修正：如果重载失败时顺手把 `loadedAt` 重置成"现在"，那么"陈旧时长"这个指标就永远是 0，**监控将彻底失去发现"我们在用过期权限"的能力**。宁可它难看，也不能让它说谎。
3. **陈旧时长必须可观测且必须告警**：上报 `now - loadedAt` 的当前值与分布、重载失败次数、**受影响的用户数**。见 §8.2 的阈值。

> **注意规则 1 与规则 2 看起来矛盾，实际上是一对**：**数据要留着（不能丢）**，**但必须如实记录它有多旧（不能假装新鲜）**。把这两件事分开，才能同时获得可用性与可观测性。原设计只写了前者、没写后者，所以"可能长期使用过期权限"这个问题在文档里是**不可见**的。

#### 5.3.2 重载失败时的放行策略：**fail-open（可用优先）**

数据库不可用导致缓存无法重载时，系统只有两种选择，**必须明确写死是哪一种**：

| 策略 | 表现 | 换来了什么 | 代价 |
|---|---|---|---|
| **fail-open（可用优先）← 本设计采用** | **继续用最后一份成功数据服务**，同时强告警 | 数据库抖动或长时间故障都不影响用户办公（管理类后台常有连续作业需求） | **权限撤销在故障期间可能延迟生效**（最长可达整个故障时长，可能是数小时）；合规上较难解释 |
| fail-closed（安全优先） | 拒绝请求（503） | 绝不放行可能已撤销的权限 | 数据库一次短抖动即导致全员不可用 |

**唯一保留的 fail-closed 分支（必须保留，理由见下）**：

| 场景 | 处理 | 为什么不能 fail-open |
|---|---|---|
| 收到 `TOKEN_REVOKED(userId=X)`，但 X 的身份快照重载失败 | **拒绝 X 的请求**（40101） | 这是"我们已经**明确知道** X 的状态变了，只是不知道变成了什么"。放行等于**主动**接受一个已知被作废的令牌。而且代价极小——只影响这一个/这几个用户，不是"全员不可用" |
| 数据库完全不可用，且实例启动后**从未成功加载过**任何缓存 | 拒绝需鉴权的请求（503） | 此时**没有任何可信数据**，放行等于靠猜。这是"无数据"而非"数据陈旧"，与本节的取舍无关 |

> **为什么全局选择 fail-open，却仍然保留"已知变化的用户必须拒绝"？**
> 因为这两件事的**代价结构完全不同**：
> - 全局 fail-closed 的代价是"**所有用户**都用不了系统"，而它防住的是"某个可能已被撤销的权限被继续放行"——**用全员的可用性去换极少数的确定性，不成比例**。
> - 针对性 fail-closed 的代价是"**那几个状态已变的用户**需要重新登录（而数据库故障期间他们也登录不上，反正用不了）"，防住的是"明确已知被作废的令牌继续通行"——**代价小、收益明确**。
>
> 一句话：**不因为"可能有问题"就拒绝所有人，但也绝不放过"已知有问题"的那一个。**

**允许通过配置切换为全局 fail-closed（预留的运维开关）**：

| 配置项 | 默认 | 说明 |
|---|---|---|
| `rbac.cache.stale-policy` | `fail-open` | 可选 `fail-closed`。用于将来合规要求提高时，**无需改代码**即可收紧姿态 |

> **为什么预留这个开关？** 因为"可用优先 vs 安全优先"是一个会随**合规要求、业务阶段**变化的判断，而不是一个技术事实。今天选 fail-open 很有道理（内网管理后台、断网时希望继续干活）；但如果将来要做外部合规审计，很可能要求 fail-closed。**把它做成配置而不是硬编码，等于用几行代码买下了一次"不用改架构就能改姿态"的权利**——这与本项目"为升级预留最小扩展点"的整体思路一致。

**必须配套的运维要求（fail-open 的代价必须被管理起来，而不是被忽略）**：

| # | 要求 | 说明 |
|---|---|---|
| 1 | 陈旧时长与受影响用户数**必须**有监控与告警 | 见 §8.1、§8.2。失去可观测性后，"fail-open"就退化为"悄悄用过期权限" |
| 2 | 故障恢复后**必须立即全量失效并重载**一次 | 否则实例可能长期停留在故障期间的旧数据上 |
| 3 | 故障期间发生的权限撤销**必须能在恢复后被追溯** | 通过审计日志（`CHANGE` 类，同事务落库）确认；这与缓存无关，因此不会丢 |
| 4 | 恢复演练与故障复盘时，**必须明确回答"这次故障期间有多少请求是用陈旧权限放行的"** | 这个数字只能来自 §8.1 的指标。**没有这个数字，就无法评估影响面，也无法向审计解释** |

#### 5.3.3 身份快照（解决令牌作废的可靠性问题）

**旧设计的问题**：把"已作废用户"记在一份内存集合 `revokedTokens` 里。它有两个漏洞：

1. **实例重启后集合为空**，而重启期间发出的广播已经丢失——旧令牌会被重新接受，用户"登出/改密/停用"形同虚设；
2. **广播丢失且没有兜底过期**时，旧令牌会被**永久**接受。

**改为"本地身份快照 + 版本比对"**，让正确性来源于数据库，而不是来源于"消息是否送达"：

```
缓存 C：userId → { tokenVersion, status, loadedAt, expiresAt }

请求校验：token.ver == snapshot.tokenVersion  且  snapshot.status == 启用
```

| 事项 | 设计 |
|---|---|
| 数据来源 | `sys_user` 的 `token_version` 与 `status`（单行主键查询，约 0.1ms） |
| TTL | **30 秒**（`expireAfterWrite`）；它既是兜底，也是广播丢失时的**收敛渠道** |
| 失效通知 | 收到 `TOKEN_REVOKED(userId)` → 丢弃该用户快照（**只丢弃，不立即重载**）；下一个请求惰性重载 |
| 实例启动 | **不需要预加载**：首个请求按需加载，天然拿到数据库最新状态 |
| 未命中 | 单飞查库加载；用户不存在/已删除 → 缓存"拒绝"的负结果（同样 30 秒到期） |
| 全局作废 | 收到"全局令牌版本基线自增"（密钥泄露等场景）→ 丢弃全部身份快照 |

**为什么这样就不存在"重启后旧令牌仍可用"？** 因为实例重启后缓存是空的，第一个请求必然去查数据库，拿到的是**当前**的 `token_version`；旧令牌携带的 `ver` 与之不同，立即被拒。**正确性不再依赖"是否收到过那条广播"。**

**降级语义（诚实口径，不再宣称无条件"立即失效"）**：

| 条件 | 令牌作废生效时间 |
|---|---|
| 正常（Redis 可用） | ≤ 1 秒（广播触发失效，下一次请求重载） |
| Redis 不可用 / 广播丢失 | ≤ 30 秒（TTL 到期后重载） |
| 实例重启 | **立即**（缓存为空，首个请求即读库） |
| 数据库不可用 | 无法重载 → 按 5.3.2：**受影响用户被拒绝**；其他用户沿用旧快照**继续放行**（fail-open）并强告警 |

**成本（诚实说明）**：每个活跃用户每 30 秒触发一次单行主键查询。1 万活跃用户 ≈ **333 QPS** 的主键查询。这是为"可靠的令牌作废"付出的确定成本，MySQL 轻松承受。**TTL 与降级窗口一一对应**：调大 TTL 可降低这 333 QPS，但必须同步修改本表与 [01 文档的承诺口径](./01-需求规格说明书.md)。

> **与"零查询鉴权"的关系**：身份快照的加载**不改变**"每个请求零查询"的性质——请求只读内存，只有缓存未命中（TTL 到期或刚被失效）时才查库，且是单行主键查询。权限解析（5.2 第 3 步）仍完全走内存。因此 30ms 预算不受影响。

> **为什么不用"每次请求查 Redis 里的作废名单"？** 那等于在零网络链路上打洞：2000 QPS × 每请求一次 Redis 往返，既增加延迟，又让 Redis 变成关键路径。本地快照 + 30 秒 TTL 的代价（最坏 30 秒收敛）是可以接受的，换来的是延迟与依赖的完全解除。

> **关于"高风险账号"**：若某类账号（如财务、超管）需要严格得多的失效时效，正确做法是**收窄其令牌有效期**（例如 15 分钟自动续期），而不是为它单独开一条查询通道。原因：短有效期把"作废延迟"的上界压到令牌有效期内，且对所有账号都是同一套机制，不引入特例。

### 5.4 权限码规范

权限码是业务代码与权限系统之间的**唯一契约**，因此必须严格规范：

```
格式：  <模块>:<资源>:<操作>[.<子操作>]
示例：  sys:user:create         创建用户
        sys:user:reset-password 重置密码
        biz:order:export        导出订单
通配：  sys:user:*              某资源下全部操作
        sys:*                   某模块下全部
        *                       全部（仅超级管理员角色持有）
```

| 规则 | 说明 |
|---|---|
| 全小写、`:` 分隔、`-` 连接词 | 便于阅读与排序 |
| 创建后不可修改 | 修改等于让所有引用它的代码失效 |
| 权限码与后端接口一一对应（API 类） | 由构建门禁校验（NFR-8） |
| 权限码与菜单/按钮对应（MENU/BUTTON 类） | 前端据此渲染 |
| 权限码由 `rbac-core` 提供统一校验工具 | 避免各模块自行拼接字符串导致拼写错误 |

### 5.5 统一响应与异常

| 场景 | HTTP 状态 | 响应体 `code` | 说明 |
|---|---|---|---|
| 成功 | 200 | 0 | 统一 `{code, message, data, traceId}` |
| 未认证（无令牌/过期/签名错/`iss`·`aud` 不匹配） | 401 | 40100 | 前端拦截 → 跳转登录 |
| **令牌已作废**（登出/改密/停用/全局作废） | 401 | 40101 | 与 40100 分开是为了**可观测**：40101 突增意味着批量踢人或令牌被滥用 |
| 无权限 | 403 | 40300 | 前端提示"无操作权限"，**不提示需要什么权限**（避免信息泄露） |
| 参数校验失败 | 400 | 40000 | 附带字段级错误信息 |
| 业务规则拒绝（如删除被引用的角色） | 200 | 4xxxx | 用业务码而非 400，便于前端精确提示 |
| **并发冲突**（乐观锁 `expectedVersion` 不匹配） | 409 | 40950 | 提示"数据已被他人修改，请刷新后重试"。**绝不静默覆盖**，见 [04 文档 §1.6](./04-接口设计.md) |
| 限流 | 429 | 42900 | 附带 `Retry-After` |
| **服务降级**（鉴权数据从未成功加载过；或已切换到 fail-closed 姿态，见 5.3.2） | 503 | 50300 | 附带 `Retry-After`；前端展示"系统暂时不可用，请稍后重试" |
| 服务器异常 | 500 | 50000 | 记录 traceId，**响应体不含堆栈** |

> **50300 是本设计新增的一类响应**，它对应 5.3.2 的 fail-closed 分支（"从未成功加载过缓存"或运维切到 fail-closed 姿态）。**默认的 fail-open 姿态下不会因数据陈旧而返回它。** 它必须与 500 区分开：500 表示"代码出错了"，503 表示"系统在按设计自我保护"。**混在一起会让运维误判为程序缺陷。**

> **为什么权限不足不告诉对方"你需要 `sys:user:delete` 权限"？** 因为这句话等于向攻击者泄露了系统的权限结构，便于其针对性试探。**错误信息本身也是攻击面。**

### 5.6 前端权限设计

| 层次 | 实现 | 说明 |
|---|---|---|
| 动态菜单 | 登录后调用 `/api/auth/me`，后端返回**权限码集合**，前端根据本地菜单配置表过滤出可见菜单 | 后端不返回菜单树结构，只返回权限码（菜单也是权限的一种） |
| 动态路由 | 根据可见菜单注册路由；未授权路由不注册，直接访问 404 | 比"注册后再守卫拦截"更彻底 |
| 按钮级 | 自定义指令 `v-perm="'sys:user:delete'"`，无权限则移除 DOM | 只是体验优化，**不作为安全边界** |
| 请求拦截 | Axios 拦截器统一处理 401（跳登录）与 403（提示） | 一处处理，避免每个页面各写一遍 |

> **前端权限的唯一职责是"不让用户看到点了会报错的按钮"**。真正的安全边界只在后端。任何"前端隐藏了所以安全"的想法都是错觉——攻击者可以直接调用接口。

### 5.7 可信代理与客户端 IP

`X-Forwarded-For`（XFF）是**客户端可以随意伪造**的请求头。限流、审计、安全告警如果无条件信任它，就等于把攻击者自己填的 IP 当成证据。规则如下：

| 编号 | 规则 |
|---|---|
| IP-1 | 应用实例端口**不对公网开放**，只允许 Nginx / 负载均衡所在网段访问（安全组 + 主机防火墙双向限制） |
| IP-2 | 应用**只信任来自可信代理网段**的 XFF；来源不在可信网段时，**直接忽略 XFF**，使用 TCP 对端地址 |
| IP-3 | 可信代理必须**覆盖（set）** XFF，而不是追加（append）。追加会让攻击者预先塞入的假 IP 留在链首 |
| IP-4 | 由唯一组件 `ClientIpResolver` 负责解析：可信代理层数已知时取链上对应位置，层数不确定时取**最右侧的可信代理写入值** |
| IP-5 | **限流、审计、安全告警必须调用同一个 `ClientIpResolver`**，禁止各模块自行解析 XFF |
| IP-6 | 日志中额外记录**原始 TCP 对端地址**（不进审计表），用于代理配置错误时排障 |
| IP-7 | 记录"收到无效/不可信 XFF"的计数并告警——这是探测行为的信号 |

> **为什么必须由同一个组件解析？** 因为限流与审计是"同一个事实"的两个用途。若两者对"客户端是谁"的判断不一致，攻击者只需构造一个请求头，就能让限流统计到一个身份、审计记录另一个身份，**两套数据都无法作为证据**。

## 6. 技术选型清单与理由

**规则：每一个依赖都必须能回答"它换来了什么？不用它会多花多少成本？"**

### 6.1 后端

| 组件 | 选择 | 换来了什么 | 不用它会多花什么成本 |
|---|---|---|---|
| 语言/运行时 | **Java 21 (LTS)** | 长期支持、模式匹配等语法糖、字符串模板（可选） | 停留在 Java 8/11 会缺少长期安全更新，且后续升级更痛 |
| 基础框架 | **Spring Boot 3.x** | 自动装配、内嵌容器、统一配置、生态成熟；团队熟悉度最高 | 不用它要自己组装 Web 层、事务、数据源——成本远高于收益。**注意：引入 Spring Boot 是"基础地基"，不属于"为小功能引大框架"** |
| Web 容器 | **内嵌 Tomcat（默认，阻塞模型）** | 零额外配置，栈信息可读 | 换 Jetty/Undertow 收益 < 1%，切换成本与风险大于收益 |
| 数据访问 | **MyBatis** | SQL 完全可见可控，每条查询都能被索引精确覆盖，无隐式 N+1 与懒加载意外 | 用 JPA：省掉写 SQL，但要额外花时间排查框架生成的意外查询，并在高并发下承担触发器式脏检查开销。本系统仅 6 张表，手写 SQL 总量很小 |
| 连接池 | **HikariCP（Spring Boot 默认）** | 默认即最优，无需额外引入 | 换 Druid 主要为监控面板，而 Micrometer + Actuator 已覆盖；无必要 |
| 数据库 | **MySQL 8.0** | 已限定 | — |
| 本地缓存 | **Caffeine** | W-TinyLFU 淘汰策略、高并发读性能、`expireAfterWrite` 与单飞加载支持；是本地缓存的事实标准 | 自己用 `ConcurrentHashMap` + 定时清理：要自己处理过期、淘汰、内存上限、并发热点，工作量与出错概率都更高 |
| 分布式通知 | **Redis 发布订阅**（`spring-boot-starter-data-redis`） | 30 行代码完成跨实例缓存失效通知，无需消息中间件 | 自建：需引入 MQ（更重）；不用通知只靠 TTL：权限变更生效延迟不可控（依赖 TTL 值） |
| 令牌库 | **jjwt（io.jsonwebtoken）** | 轻量三件套（api/impl/jackson），API 直白，HS256 支持完整 | 自己实现 JWT 编解码：需正确处理 Base64URL、签名比对（**容易被时序攻击**）、声明校验——安全代码自己写风险高 |
| 密码哈希 | **spring-security-crypto（仅此一个包）** | 只引入 `BCryptPasswordEncoder`，不引入 Spring Security 框架的过滤器链与自动配置 | 自己实现 BCrypt：密码学实现自己写是明确的反模式（盐值处理、常数时间比较都容易出错） |
| 数据库版本管理 | **Flyway** | DDL 版本化、可重复执行、升级脚本可审计——**与 RBAC 分阶段升级天然契合** | 手工执行 SQL：多环境不一致、升级漏执行、无法回滚审计。成本远高于引入成本 |
| 指标监控 | **Spring Boot Actuator + Micrometer + Prometheus Registry** | P99、缓存命中率等指标可观测；**没有它就无法验收 30ms** | 自建埋点：工作量不小且不标准 |
| 模块边界检查 | **ArchUnit**（仅测试期依赖） | 依赖规则在构建期强制生效，零运行期开销 | 不做：模块化单体会在数月内退化 |
| 结构化日志 | **Spring Boot 3.4+ 内置结构化日志（ECS 格式）** | 无需额外依赖即输出 JSON 日志 | 引入 logstash-logback-encoder：多一个依赖，而新版本已内置同等能力 |
| 限流 | **自研（Redis 计数器 + 滑动窗口）** | 仅需"计数 + 过期"，几十行代码 | 引入 Sentinel：为一个登录限流引入整套流量治理框架，配置与资源开销均不划算 |

## 7. 部署拓扑与容量（摘要）

### 7.1 部署拓扑

> 完整测算过程见 [06 性能与容量设计](./06-性能与容量设计.md)。此处只给结论。

| 组件 | 规格 | 数量 | 说明 |
|---|---|---|---|
| Nginx | 2C4G | **1** | 入口，**单点**（见 7.2） |
| 应用实例 | 4C8G（堆 3~4G） | **3** | **性能上 1 台就够**（峰值 2k QPS 对单实例是小负载），3 台是为了"单机故障不影响"与"滚动发布不中断" |
| MySQL | 8C16G + SSD | **1** | 读压力极低（鉴权零查询），主要压力来自审计写入与缓存重载。**单点**（见 7.2） |
| Redis | 1C2G | **1** | 只做广播，内存占用 < 10MB。**单点，且不在关键路径上** |

**关键结论：本项目不是"高负载系统"，而是"高在线用户数、低请求量"系统。** 3 台应用实例是可用性需求而非性能需求。请不要按"10k 并发"的字面意思采购机器——推导过程见 [06 文档](./06-性能与容量设计.md)。

### 7.2 高可用边界与 RTO/RPO（**必须如实声明**）

**现状**：应用层做了冗余（3 实例 + 无状态），但 **MySQL、Redis、Nginx 都是单实例，没有自动故障切换**。

> **这是成本取舍，不是"系统已具备高可用"。** 说清楚这一点极其重要：如果文档暗示了自动切换能力，故障发生时运维会先花时间判断"是不是应用的问题"，再发现"其实存储根本没切换机制"，从而延误恢复。

**各组件故障的真实影响与恢复时间（人工恢复）**：

| 组件 | 故障时系统表现 | RTO | RPO |
|---|---|---|---|
| 应用实例（3 台中的 1 台） | 用户无感知（负载均衡摘除） | ≤ 5 分钟（重启） | 无（无状态） |
| Nginx | **全员不可用**（入口被切断） | ≤ 30 分钟（重启）；机器损坏需重建则 ≤ 4 小时 | 无（无状态） |
| MySQL | **鉴权继续可用**（fail-open，走内存缓存，但权限判断可能已过期）；写操作立即失败 | ≤ 1 小时（**前提：binlog 完好**）；只能靠每日备份恢复则最长 24 小时 | **≈ 0**（前提：binlog 开启且**备份文件存放在数据库主机之外**）；不满足前提则退化为自上次全备以来（最长 24 小时） |
| Redis | **登录与鉴权完全不受影响**；权限变更/令牌作废延迟到 30 秒生效（TTL 兜底） | ≤ 5 分钟（重启即可，期间服务不中断） | 不适用（无可持久化数据） |

**目标可用性的口径（不要混为一谈）**：

| 口径 | 目标 | 依据 |
|---|---|---|
| **鉴权读路径**可用性 | **99.9%** | 应用层多实例 + 本地缓存；**MySQL 故障期间鉴权仍能服务**（fail-open），因此该路径的可用性不受单点存储直接约束 |
| **含写操作的端到端**可用性 | **受 MySQL 单点约束，不承诺 99.9%** | MySQL 单点故障期间，管理类操作与缓存重载不可用 |
| 若业务确实要求整体 99.9% | **必须为 MySQL 做高可用**（见下方扩展点），这是唯一的前置条件 | — |

**"保留扩展点"的具体含义——现在必须遵守的约束（否则将来加高可用要改代码）**：

| 组件 | 将来怎么加高可用 | **现在必须守住的约束** | 违反的后果 |
|---|---|---|---|
| Nginx | 加第二台 + keepalived/VIP，或换成云 SLB | ① 应用实例必须无状态（已满足）；② **不得引入任何形式的会话粘滞**（基于 IP 或 Cookie 的 sticky session）——因为 JWT 放在请求头里，本来就无需粘滞 | 引入粘滞后就无法自由增加/替换 Nginx 或应用实例 |
| MySQL | 加只读从库 / 主从半自动切换 / 换成云托管高可用版 | ① **必须开启 binlog**（否则无法搭从库、无法做增量恢复）；② 数据访问必须严格分层（DAO 层清晰，便于将来插入读写分离路由）；③ **不使用跨库事务**；④ 避免长事务（binlog 开启后长事务会放大主从延迟与磁盘占用）；⑤ 不使用多主不兼容的特性 | 没有 binlog 就等于放弃了"RPO≈0"这一档，且搭从库必须先停机 |
| Redis | 单实例 → Sentinel / Cluster（**只需改配置**） | ① **不依赖 Redis 的任何持久状态**：广播是"即发即忘"，限流计数丢失也不致命，因此 Redis 可以随时被替换或重启；② 客户端使用支持 Sentinel 的配置方式；③ **禁止跨 key 的多键操作**（`MGET` 跨 key、跨槽的 Lua 脚本等），否则无法平滑切到 Cluster | 一旦依赖了 Redis 的持久数据，Redis 就从"可丢弃的加速器"变成"必须高可用的存储"，成本和风险都会跳升 |

> **为什么"不依赖 Redis 的持久状态"是一条硬约束？** 因为它决定了 Redis 在架构里的**定位**。只要它是"可丢弃的"，它就可以在故障时被直接重启或替换（RTO ≤ 5 分钟，且服务不中断）；一旦有业务数据落在里面，它就必须升级为必须做高可用的关键组件——**同样的组件，因使用方式不同，运维代价相差数倍**。

**必须配套的运维动作（缺一不可）**：

| # | 动作 | 为什么 |
|---|---|---|
| 1 | 每日全量备份 + binlog 增量归档 | 这是 RPO≈0 的唯一来源 |
| 2 | **备份文件与 binlog 必须存放在数据库主机之外** | 与数据库同机备份，在机器损坏时等于没有备份——这是最常见的"以为有备份"事故 |
| 3 | **每季度至少一次恢复演练**（从备份恢复到一个干净实例并验证业务） | **RTO/RPO 无法从文档证明，只能从演练证明**。没演练过的恢复流程，实际耗时常是预估的 3~5 倍 |
| 4 | 各组件的人工恢复手册 + 值班响应流程 | 单点架构下，人就是故障切换机制 |
| 5 | 明确数据库账号对审计表的权限 | 应用账号无删除审计表权限（NFR-3） |

## 9. 工程结构规划（不写代码，只定结构）

```
rbac-system/                      (Maven 聚合工程)
├── pom.xml
├── rbac-api/                     契约层：接口、DTO、事件、常量、注解定义
│   └── src/main/java/.../api/
│       ├── permission/           PermissionResolver、PermissionSource（端口）
│       ├── identity/             CurrentUser、IdentityQuery（身份快照的数据来源，见 5.3.3）
│       ├── audit/                AuditRecorder（区分 CHANGE / SECURITY）、AuditQuery
│       ├── event/                PermissionChangedEvent（含 TOKEN_REVOKED 变体）
│       ├── support/              ClientIpResolver（唯一可信 IP 解析入口，见 5.7）
│       └── annotation/           @RequiresPermission、@RequiresLogin、@PublicApi
├── rbac-core/                    领域层：模型、权限计算、校验器链、持久化
├── rbac-auth/                    认证层
├── rbac-guard/                   鉴权接入层
├── rbac-cache/                   缓存与失效
├── rbac-audit/                   审计
├── rbac-admin/                   管理端接口层
├── rbac-bootstrap/               启动与装配（唯一可依赖全部模块）
└── docs/                         本设计文档（与代码同仓，保证同步）
```

每个业务模块内部统一分层：

```
<module>/src/main/java/.../<module>/
├── api/           对外的接口实现（实现 rbac-api 中的契约）
├── internal/      模块私有的实现细节（ArchUnit 禁止外部 import）
│   ├── domain/        领域模型与领域服务
│   ├── mapper/        持久化（仅 core 有）
│   └── support/       模块内部工具
└── config/        模块自己的 Bean 装配（不包含全局配置）
```

前端结构：

```
web/
├── src/
│   ├── api/           接口封装（按模块分文件）
│   ├── directives/    v-perm 权限指令
│   ├── router/        静态路由 + 动态路由注册
│   ├── stores/        Pinia：user（含权限码集合）
│   ├── views/         页面
│   └── components/    通用组件（权限树选择器、角色穿梭框等）
```

## 10. 设计自检（对照设计标准逐条核对）

| 设计标准 | 本设计的落点 | 结论 |
|---|---|---|
| 拒绝为小功能引入大框架 | 不引 Spring Security 全套、不引 WebFlux、不引网关/注册中心/配置中心/MQ/Sentinel/Spring Modulith | ✅ |
| 每个依赖给出理由 | 见 6.1 / 6.2 / 6.3，逐项列出"换来什么 / 不用会多花什么" | ✅ |
| 高内聚 | 8 个模块按"变化原因"切分，每模块单一职责（见第 3 节） | ✅ |
| 低耦合 | 模块间只通过 `rbac-api` 的接口与 DTO 交互；唯一的消息通道用于本质异步的缓存失效通知（见 4.3） | ✅ |
| 复杂逻辑下沉 | 调用方只需 `@RequiresPermission("码")` 一个注解；令牌解析、缓存重建、单飞、失效广播、默认拒绝策略全在模块内部；调用顺序无需记忆 | ✅ |
| 检查清单：参数少 | 外部接口参数为普通 DTO；鉴权入口零配置 | ✅ |
| 检查清单：封装异常与默认值 | 缓存重建失败沿用旧值；Redis 故障自动降级；未标注注解默认拒绝；统一异常出口 | ✅ |
| 检查清单：改内部实现不改对外接口 | RBAC0→1→2 升级只改 `PermissionResolver` 实现与校验器链，注解、接口路径、表结构（除新增）均不变 | ✅ |
| 模块合并判据 | 未发现可合并项（合并 cache 进 core 会引入基础设施耦合；合并 audit 进 admin 会造成依赖方向错误） | ✅ |
| 模块拆分判据 | auth 与 guard 拆分依据是"变化频率与变化原因不同"；cache 拆分依据是"通用基础设施 vs 专用业务" | ✅ |
| 高并发下优先响应速度 | 鉴权零网络零 DB；缓存失效采用惰性重载 + 单飞；日志异步；登录慢接口线程隔离 | ✅ |
| 考虑服务器资源有限 | 3 台 4C8G + 1 台 8C16G + 1 台 1C2G Redis；不引入集群型组件 | ✅ |
| 以面向对象为主 | 领域模型（User/Role/Permission/AuthorizationPolicy）+ 多态扩展点（`PermissionResolver`、`ConstraintValidator` 接口族） | ✅ |
| **承诺与实现一致** | 令牌作废写为"正常 ≤1s / Redis 故障 ≤30s / 重启立即"，不再是"立即失效"（见 [01 FR-A9](./01-需求规格说明书.md)） | ✅ |
| **故障时行为写死** | 明确采用 **fail-open**（重载失败继续服务）+ 唯一的针对性 fail-closed（已知状态变化的用户被拒）+ 配置开关 `stale-policy`；并写清"数据要留住、`loadedAt` 绝不伪刷新"这对互补规则（见 5.3.1/5.3.2） | ✅ |
| **不使用含糊的工作量承诺** | "升级改动 0 行"改为"权限声明与鉴权入口契约不变"，并给出六维度代价拆解（见 [05 §2](./05-RBAC0到RBAC3演进设计.md)） | ✅ |
| **预算与实测分离** | 性能数字标注为"预算假设"，验收以压测实测为准（见 [06 §2.2/§10](./06-性能与容量设计.md)） | ✅ |
