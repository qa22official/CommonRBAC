# 02 · 总体设计

相关文档：[00 基线](./00-编码代理工作基线.md) · [01 需求](./01-需求规格说明书.md) · [03 数据模型](./03-数据模型设计.md) · [04 接口](./04-接口设计.md) · [05 演进](./05-RBAC0到RBAC3演进设计.md) · [06 修订记录](./06-修订记录.md)

## 1. 设计约束

| 编号 | 约束 | 依据 |
|---|---|---|
| D-1 | 权限集合的计算只允许出现在 `PermissionResolver` 的实现中 | 业务代码、拦截器、前端一律只消费权限码集合；RBAC1/2/3 升级只改这一处 |
| D-2 | 鉴权判定本身禁止访问数据库与 Redis；未命中时由缓存层单飞重建快照 | 30ms 预算中鉴权占比必须 < 1ms |
| D-3 | 缓存只存事实，不存派生结果 | 派生结果（userId→权限码）会让"改一个角色"作废上万条缓存 |
| D-4 | 优先减少工作量，其次才是加快执行 | 现状：鉴权零查询；不引入响应式框架 |
| D-5 | 每一份冗余必须能说出理由 | 只预留 `inherit_role_id` 一个业务字段与两个代码扩展点 |

## 2. 部署形态

```text
浏览器（Vue 3 SPA）
  └─ HTTPS
      └─ Nginx（静态资源 + 反向代理 + keepalive）
          └─ HTTP 内网
              └─ 应用实例 × 3（无状态，可增减）
                  ├─ 本地内存：PermissionSnapshot（< 30MB）+ IdentitySnapshot
                  ├─ MySQL 8：仅写操作与快照重建
                  └─ Redis：失效广播 + 登录限流
```

| 组件 | 角色 | 关键约束 |
|---|---|---|
| Nginx | 入口与静态资源 | 单实例，无自动故障切换 |
| 应用 | 无状态，可横向扩 | 本地缓存只存可重建数据，不存会话 |
| MySQL | 唯一事实来源 | 鉴权不查它；只承担写与快照重建 |
| Redis | 失效通知与登录限流 | 不存业务数据；故障只影响生效速度与 IP 限流 |

## 3. 缓存结构

每实例持有两份缓存：

| 缓存 | 形态 | TTL | 用途 |
|---|---|---|---|
| `PermissionSnapshot` | 单个不可变对象：`roleId→Set<permissionCode>`、`userId→Set<roleId>`、`roleId→{status,inheritRoleId}`、`permissionCode→id`（仅启用权限）、`loadedAt`、`version`、`state` | 30 秒软 TTL | 权限判定 |
| `IdentitySnapshot` | `userId → {tokenVersion, enabled, mustChangePassword, loadedAt, expiresAt}` | 30 秒软 TTL | 令牌作废与强制改密判定 |

- 权限事实合并成一份快照，避免 A/B/C 分键缓存带来的局部加载、重复回源与失效遗漏。
- 派生值不缓存：用户有效权限码 = 对 `userRoles` 中的角色，在 `rolePermissions` 中求并集，并过滤 `roleMeta.status`；停用权限不在 `rolePermissions` 中。
- 失效时只标记快照 stale，不立即重载；下一个请求单飞加载完整快照后原子替换。
- 身份快照按 `userId` 单独缓存；登录、登出、改密、停用只影响该用户条目。

## 4. 模块划分

| 模块 | 职责 | 允许依赖 |
|---|---|---|
| `rbac-api` | 契约层：应用服务接口、DTO、快照模型、事件、框架级权限码常量、鉴权注解 | 无（仅 JDK） |
| `rbac-core` | 实现 `rbac-api` 应用服务契约；领域模型、权限计算、约束校验器链、持久化 | rbac-api |
| `rbac-auth` | 登录、令牌签发与验签、密码策略、失败锁定 | rbac-api |
| `rbac-guard` | 鉴权过滤器、拦截器、请求上下文 | rbac-api |
| `rbac-cache` | `PermissionSnapshot`、`IdentitySnapshot`、失效广播订阅 | rbac-api |
| `rbac-audit` | 实现 `AuditRecorder` 与 `AuditQueryService` | rbac-api |
| `rbac-admin` | 管理端 REST 接口 | rbac-api |
| `rbac-bootstrap` | 启动、配置装配、Web 全局配置 | 全部 |
| `biz-*` | 业务模块（使用方） | 仅 rbac-api |

拆分依据：`rbac-auth` 与 `rbac-guard` 分开，因为认证随登录方式变化（将来可能加 SSO），鉴权随权限模型变化，RBAC 升级只动后者。`rbac-cache` 分开，因为它属性能基础设施而非领域概念。

模块内部统一分层：

```text
<module>/src/main/java/...<module>/
├── api/          对外接口实现
├── internal/     模块私有实现（domain/ mapper/ support/）
└── config/       模块自己的 Bean 装配
```

### 4.1 跨模块契约（rbac-api 最小集合）

| 契约 | 使用方 | 实现方 | 职责 |
|---|---|---|---|
| `UserAuthService` | rbac-auth | rbac-core | 按账号查认证信息、记录登录成功/失败、改密、递增 `token_version` |
| `UserAdminService` | rbac-admin | rbac-core | 用户 CRUD、启停、重置密码、分配角色 |
| `RoleAdminService` | rbac-admin | rbac-core | 角色 CRUD、启停、分配权限、约束校验链入口 |
| `PermissionAdminService` | rbac-admin | rbac-core | 权限 CRUD、权限树查询 |
| `PermissionSnapshotSource` | rbac-cache | rbac-core | 一次性加载完整权限快照（用户角色、角色权限、角色状态、权限启用、继承关系） |
| `IdentitySnapshotSource` | rbac-cache | rbac-core | 按 userId 加载 `{tokenVersion, enabled, mustChangePassword}` |
| `PasswordHasher` / `PasswordPolicy` | rbac-auth / rbac-admin | rbac-auth | BCrypt 哈希与校验、密码强度校验 |
| `AuditRecorder` / `AuditQueryService` | 业务模块 / rbac-admin | rbac-audit | CHANGE / SECURITY 写入、审计查询 |
| `PermissionResolver` / `IdentityQuery` | rbac-guard | rbac-cache | 权限码集合、身份快照 |
| `PermissionStatusQuery` | rbac-guard / rbac-auth | rbac-cache | 快照是否可用/是否陈旧（fail-closed 判定） |
| `TokenVerifier` / `VerifiedToken` | rbac-guard | rbac-auth | JWT 验签与载荷（userId/tokenVersion/username/kid） |
| `PermissionCodeFormat` | rbac-admin / rbac-core / rbac-auth | rbac-api | 权限码格式的唯一校验实现 |
| `RequestContext` / `ClientIpResolver` | guard / auth / admin / audit | rbac-api | 请求级 traceId、用户、客户端 IP |

约束：接口放 `rbac-api`，实现放对应模块，`rbac-bootstrap` 负责 Bean 装配；`rbac-api` 不出现 Mapper、SQL、Spring 实现类。

## 5. 模块依赖规则

由 ArchUnit 在构建期强制，违反即构建失败。当前测试覆盖 R-1/R-2/R-3/R-5/R-6/R-8；R-4/R-7 在仓库暂无 `biz-*` 模块时没有可检查对象，由评审替代；R-9 由“契约单实现 + 实现类在 internal”的构造约束保证。

| 规则 | 内容 | 依据 |
|---|---|---|
| R-1 | 模块间只允许依赖 `rbac-api`；除 `rbac-bootstrap` 外任何模块不得依赖其他模块 | 依赖方向由编译器强制 |
| R-2 | `rbac-core` 不得依赖 Web 类型（`jakarta.servlet.*`、`@RestController`） | 领域逻辑需能脱离 HTTP 测试 |
| R-3 | `rbac-auth` 不得依赖 `rbac-core` 的权限计算 | 防止认证与鉴权重新纠缠 |
| R-4 | 业务接口不得引用 `Role`、授权关系等概念，只允许使用权限码 | RBAC 升级时业务代码零改动 |
| R-5 | `*Mapper` 只允许被同模块内的领域服务引用 | SQL 集中，索引可控 |
| R-6 | 模块内私有类放 `internal` 子包，禁止跨模块 import | 防止契约外耦合 |
| R-7 | 业务模块不得引用 `rbac-core` / `rbac-cache` / `rbac-audit` 的任何类型 | 业务与权限系统只保留一个接口面 |
| R-8 | `rbac-api` 只允许放接口、DTO、注解、事件、常量；不得出现 Mapper、SQL、Spring Bean 实现 | 契约层保持无实现依赖 |
| R-9 | 每个应用服务契约只能有一个实现模块；实现类放该模块 `internal` 包 | 避免同一契约多处实现导致行为分叉 |

## 6. 模块通信方式

| 场景 | 方式 | 约束 |
|---|---|---|
| 同步命令与查询 | 通过 `rbac-api` 应用服务契约调用（编译期依赖接口，运行期注入实现） | 同进程调用，无序列化 |
| 权限快照重建 | `rbac-cache` 调用 `PermissionSnapshotSource` | 单飞加载完整快照，原子替换 |
| 跨实例失效通知 | Redis Pub/Sub，消息体只含通知类型、版本号、userId | 只通知标记失效，不传数据；丢失由软 TTL 兜底 |
| 变更审计写入（CHANGE） | 通过 `AuditRecorder` 同步调用，传播语义 `REQUIRED`/`MANDATORY` | 不允许异步、不允许走消息 |
| 安全事件写入（SECURITY） | 同一接口，传播语义 `REQUIRES_NEW` 或独立执行器 | 写入失败不回滚业务 |
| 业务白名单审计 | 业务模块直接调用 `AuditRecorder` | 业务模块已依赖 rbac-api，无需新增依赖 |
| 登出 / 改密 / 停用 | `rbac-auth` 调用 `UserAuthService`，提交后发布 `TOKEN_REVOKED` | 账号级撤销：该账号全部令牌失效 |
| 登录 / 刷新 | `rbac-auth` 调用 `UserAuthService`，只读 `token_version` | 不写版本号、不发事件，多会话 |

只有"本质异步且丢得起"的失效通知走消息，其余走接口调用。禁止把同步命令改为消息——会让调用方无法判断成败。

## 7. 权限码常量归属

| 类别 | 归属 | 示例 |
|---|---|---|
| 框架级权限码 | `rbac-api` 常量包 | `*`、`sys:user:read` |
| 业务级权限码 | 各业务模块自己的常量类 | `biz:order:read` 定义在 `biz-order` 模块内 |

不得把所有权限码集中到 `rbac-api`。依据：那会使契约层成为所有人的公共变更点，并行开发必然冲突。

业务模块引用权限码时使用常量而非字面量，拼写错误在编译期即暴露。

## 9. 认证链路

```text
POST /api/auth/login
1. 登录限流检查（账号维度 + IP 维度，Redis 滑动窗口；Redis 故障时关闭基于 Redis 的限流并告警，数据库失败锁定仍生效）
2. 账号存在性与 status 检查；账号不存在也执行一次 dummy BCrypt
3. 失败锁定检查（连续失败 ≥ 5 次 → 锁 15 分钟）
4. BCrypt 校验（50~150ms，故意慢）
5. 通过 → 读取当前 token_version（不递增；多会话）
6. 生成 JWT（ver = 当前版本）
7. 写登录安全事件（SECURITY 类，独立落库）
```

JWT 载荷：

| 字段 | 说明 |
|---|---|
| `sub` | userId |
| `username` | 账号名，仅用于审计操作人展示；不含角色或权限 |
| `ver` | tokenVersion，与身份快照比对 |
| `kid` | 密钥标识，验签时据此选择密钥 |
| `iss` / `aud` | 签发方与受众，验签时强制校验 |
| `iat` / `exp` | 签发与过期时间；校验允许 60 秒时钟偏移 |

不得放入：角色列表、权限码列表、昵称头像。不使用 `jti`（逐令牌黑名单的写入量与跨实例共享成本不成比例）。

多会话语义：

| 项 | 行为 |
|---|---|
| 登录 | 不写 `token_version`，新令牌与既有令牌共存，可多设备/多进程同时在线 |
| 刷新 | 不写 `token_version`，只读取最新版本与账号状态 |
| 登出 / 改密 / 停用 | `token_version + 1`，该账号全部令牌失效 |
| 跨实例可用性 | 登录不改版本，新令牌签发即可在全部实例使用，不存在等待广播的窗口 |
| 局限 | 没有 `jti`，无法只登出单个令牌或单台设备 |

签名：HS256。密钥 ≥ 256 位，由环境变量或配置中心下发，禁止进入代码仓库与镜像层。所有实例启动时校验 `kid → 密钥` 映射一致，不一致则启动失败。

密钥轮换三阶段：

```text
阶段 1  配置变为 {kid=1: K1, kid=2: K2}；签发改用 K2；token_version 不递增
        发布顺序强制：先让全部实例支持双密钥，再切换签发
阶段 2  等待 ≥ 访问令牌最长有效期（2 小时）+ 时钟偏移余量；K1 仅用于验签
阶段 3  确认无 kid=1 的验签记录后，从配置移除 K1
```

回滚：阶段 1、2 任意时刻把配置改回双密钥并继续用 K1 签发即可。密钥泄露时跳过等待期，直接从配置移除旧密钥；旧令牌验签失败返回 40100（全局作废）。不新增全局版本字段或接口。

BCrypt 使登录接口不受 30ms 约束；登录以限流和账号锁定为主要保护，不单独建线程池（同步 MVC 下独立池仍占用 Tomcat 工作线程）。

### 9.1 服务型客户端接入

外部服务复用认证接口，不新增登录协议：

| 用途 | 接口 |
|---|---|
| 取令牌 / 续期 | `POST /api/auth/login`、`POST /api/auth/refresh` |
| 判断服务账号自己 | `GET /api/auth/me`（本地判定）或 `POST /api/auth/permit`（逐次判定） |
| 判断指定用户 | `POST /api/auth/permission-check`（`userId` + 权限码列表） |

| 约束 | 说明 |
|---|---|
| 账号隔离 | 一服务一账号；服务账号不得用于 Web 登录。当前模型不区分服务账号与真人账号，靠账号治理约束 |
| 权限最小化 | 只授予完成接入所需的权限码，禁止授予 `sys:*`；18 个外部系统只调 `permission-check`，可不授予任何业务权限码 |
| 判定权威 | `me` 模式由调用方本地判定，调用方必须可信；`permit` / `permission-check` 由本系统判定 |
| 判定一致性 | 三条路径共用 `PermissionResolver` 与 `PermissionMatcher`，不得在调用方另写通配规则 |
| 禁止用途 | 不用于代最终用户操作；`permission-check` 只回答判定，不签发以用户身份执行的令牌 |

**18 个外部系统的接入边界**（已确认：外部系统自行登录，中心只做授权判定）：

| 项 | 约定 |
|---|---|
| 身份模型 | 外部系统自行认证最终用户；本系统只回答“该用户有没有该权限码”，不做 SSO/OIDC，不签发以最终用户身份执行的令牌 |
| 服务账号 | 一系统一账号；服务账号只用于调用本系统，不用于 Web 登录；当前数据模型不强制区分，靠账号治理与网络策略约束 |
| 应用隔离 | 不建 `sys_application` 表；应用用权限码前缀区分（见 §12.1）；没有应用级限流、审计或管理员 |
| 判定接口 | 外部系统判断最终用户只用 `/api/auth/permission-check`；`/me`、`/permit` 只判断服务账号自己，不能用于最终用户 |
| 批量上限 | `permission-check` 单次 1~50 个权限码；外部系统按批调用并自行合并结果，本系统不新增全量权限接口 |
| 菜单 | 本系统不向外部系统返回菜单树或权限全集；外部系统只做 API 鉴权，不渲染中心菜单 |
| 数据范围 | 本系统只判功能权限；本人/部门/分公司/项目的数据过滤由外部系统负责 |
| 角色分配 | 10,000 名员工的 5 类角色由中心管理员统一分配；外部系统只查询，不调用用户/角色管理接口 |
| 生效时效 | 1 秒/30 秒只承诺本系统内部快照；外部系统自行缓存时，端到端时效为其缓存 TTL + 本系统时效 |
| 残余风险 | `/permission-check` 仍为 `@RequiresLogin`，任何登录账号可查任意用户；以网络白名单、专用服务账号、出口访问控制和审计补偿，不新增 `sys:auth:check` |

完整生命周期与调用约定见 [04 §2.8](./04-接口设计.md)。

## 10. 鉴权链路

固定顺序：

```text
1. JwtAuthFilter
   解析并验签（按 kid 选密钥，HS256）
   校验 exp / iat / iss / aud（允许 60 秒偏移）
   身份快照校验：snapshot.tokenVersion == token.ver 且 snapshot.enabled == true
   强制改密检查：mustChangePassword=true 时仅放行改密/登出/me
    多会话：token.ver 只需等于当前版本，不要求是签发时的唯一令牌
   通过 → 写入请求上下文 CurrentUser{userId, tokenVersion}

2. PermissionInterceptor
   读取方法上的 @RequiresPermission（仅方法级）
   @PublicApi / @RequiresLogin → 直接放行
   三者都无 → 拒绝（403 + 告警）；Actuator/error/OPTIONS 走显式 allowlist

3. PermissionResolver.resolve(userId) → Set<String>（纯内存，从 PermissionSnapshot 计算）
   快照 stale/未命中 → 单飞加载完整快照并原子替换

4. 判定：PermissionMatcher.matches(codes, requiredCode)
   精确匹配优先；只有用户持有通配项时才做前缀匹配
   通过 → 进入业务方法；不通过 → 403，不进入业务方法
```

耗时预算（P99）：

| 步骤 | 耗时 | 是否访问外部 |
|---|---|---|
| JWT 验签 | 10μs | 否 |
| 身份快照校验（命中） | ns | 否 |
| 权限解析（命中） | 0.1ms | 否 |
| 权限码比对 | 20ns | 否 |
| 合计 | < 0.2ms | 无 |

默认拒绝策略：未标注三种注解之一的接口一律拒绝并记录告警。这把"漏加注解"从安全漏洞降级为可见的功能缺陷。

`@RequiresPermission` 只接受 API 类权限码或通配码；引用 MENU 类权限码由门禁拦截。

## 11. 缓存失效与降级

### 11.1 三层失效机制

第一层，主动失效（正常路径，目标 ≤ 1 秒）：

```text
写操作事务提交成功后（顺序不可颠倒）：
  自增快照版本号（Redis INCR，用于可观测）
  按类型发布：
    PERM_CHANGED        {"ver":123}            → 各实例标记 PermissionSnapshot stale
    TOKEN_REVOKED       {"userId":7,"ver":12}  → 各实例丢弃该用户 IdentitySnapshot 条目
  登录与刷新不发布事件、不改版本，因此不会触发任何失效
  订阅方只标记失效，不立即重载；由后续请求惰性重载（单飞）
```

广播去抖：1 秒内同类型、同 userId 的多次变更合并；首条立即发送，窗口结束前若又发生变化则补发一条包含最新版本的 trailing 通知，避免第二笔变更丢失。不同 userId 不得合并丢失。

第二层，软 TTL 兜底：`PermissionSnapshot` 与 `IdentitySnapshot` 均设 30 秒软 TTL（`refreshAfterWrite` 或等价机制）。到期只触发刷新，不丢弃数据；广播丢失时 30 秒内收敛。禁止使用 `expireAfterWrite` 丢弃权限数据。TTL 与降级窗口一一对应，调整 TTL 必须同步修改 01 文档 FR-A9 的承诺。

第三层，实例生命周期：

| 场景 | 处理 |
|---|---|
| 实例启动 | 加载 `PermissionSnapshot`；`IdentitySnapshot` 不预加载，首个请求按需读库 |
| 订阅重连成功 | 标记全部快照 stale（断连期间的广播已丢失） |
| Redis 不可用 | 告警；降级为软 TTL 生效模式；登录与鉴权不中断；IP 限流关闭 |
| 重载失败 | 见 11.3 |

### 11.2 缓存元数据

`PermissionSnapshot` 必须携带：

| 元数据 | 用途 |
|---|---|
| `snapshotVersion` | 本次加载时的数据版本标记，用于观测各实例是否一致 |
| `loadedAt` | 本次成功加载时间；只由成功加载更新 |
| `expiresAt` | `loadedAt + TTL`；到点触发重载，不丢弃数据 |
| `state` | `VALID` / `STALE` / `RELOADING` / `FAILED` |

`IdentitySnapshot` 至少携带 `loadedAt`、`expiresAt`；状态含义相同。

状态处理：

| 状态 | 请求处理 |
|---|---|
| VALID | 正常鉴权 |
| STALE | 用旧数据鉴权 + 触发异步重载 |
| RELOADING | 不重复触发，直接用旧数据 |
| FAILED | 继续用最后一份成功数据 + 告警 + 指数退避重试 |

`PermissionSnapshot` 是整体状态；`IdentitySnapshot` 按 `userId` 独立状态。

两条互补规则：

- 数据一旦成功加载过就永不丢弃。依据：丢弃会导致重载失败时无数据可用而被动拒绝服务，fail-open 无法成立。
- `loadedAt` 绝不伪刷新。依据：若重载失败时把它重置为当前时间，陈旧时长指标恒为 0，监控将无法发现正在使用过期权限。

必须暴露的指标：当前陈旧时长、重载失败次数、受影响用户数、用陈旧权限放行的请求数。

### 11.3 重载失败策略：fail-open

| 策略 | 行为 |
|---|---|
| fail-open（默认） | 继续用最后一份成功数据服务，同时强告警 |
| fail-closed（可配置） | 拒绝请求，返回 503 |

配置项 `rbac.cache.stale-policy`，默认 `fail-open`，可选 `fail-closed`。

强制 fail-closed 的两个分支：

| 场景 | 处理 | 依据 |
|---|---|---|
| 收到 `TOKEN_REVOKED(X)` 但 X 的身份快照重载失败 | 拒绝 X 的请求（40101） | 已知 X 状态变化，放行等于主动接受已作废令牌；影响面仅这一个用户 |
| 数据库不可用且实例从未成功加载过 PermissionSnapshot 或目标 IdentitySnapshot | 拒绝需鉴权的请求（503） | 没有任何可信数据，放行等于靠猜 |

配套运维要求（fail-open 的代价必须被管理）：

1. 陈旧时长、受影响用户数、放行请求数必须有监控与告警。
2. 故障恢复后必须立即全量失效并重载一次。
3. 故障期间的权限撤销必须可通过审计日志追溯（CHANGE 类同事务落库，不受缓存影响）。
4. 故障复盘必须给出"本次故障期间有多少请求用陈旧权限放行"。

### 11.4 身份快照（IdentitySnapshot）

```text
键：userId
值：{ tokenVersion, enabled, mustChangePassword, loadedAt, expiresAt }
校验：token.ver == snapshot.tokenVersion 且 snapshot.enabled == true
```

| 事项 | 设计 |
|---|---|
| 数据来源 | `sys_user.token_version`、`status`（映射为 `enabled`）、`must_change_password`，单行主键查询 |
| TTL | 30 秒软 TTL（`refreshAfterWrite` 或等价机制） |
| 失效通知 | 收到 `TOKEN_REVOKED(userId)` 时丢弃该条目，不立即重载 |
| 登录 / 刷新 | 不递增 `token_version`，无需失效；其他实例的旧快照值仍然正确 |
| 实例启动 | 不预加载；首个请求按需读库 |
| 未命中 | 单飞查库；用户不存在或已删除则缓存否定结果（同样 30 秒到期） |
| 全局作废 | 不通过缓存事件；按密钥轮换执行，旧令牌验签失败返回 40100 |

令牌作废生效时间：

| 条件 | 生效时间 |
|---|---|
| 登出 / 改密 / 停用 | 广播后 ≤ 1 秒；广播丢失 ≤ 30 秒 |
| Redis 正常 | ≤ 1 秒 |
| Redis 故障或广播丢失 | ≤ 30 秒 |
| 实例重启 | 立即（缓存为空，首个请求即读库） |
| 数据库不可用 | 受影响用户拒绝；其他用户按 11.3 处理 |

成本：每活跃用户每 30 秒一次主键查询；1 万活跃用户约 333 QPS。禁止改为"每请求查 Redis 名单"（会把 Redis 变成关键路径，并在零网络链路上开洞）。

高风险账号若需要更严格的失效时效，做法是缩短其令牌有效期，不新增特例通道。

## 13. HTTP 响应与异常

HTTP 状态按 code 前缀映射：`400xx→400`、`401xx→401`、`403xx→403`、`409xx→409`、`429xx→429`、`5xxxx→5xx`。前端必须用 `code` 判断业务语义，不能只看 HTTP 状态。

| 场景 | HTTP | code | 说明 |
|---|---|---|---|
| 成功 | 200 | 0 | `{code, message, data, traceId}` |
| 未认证 | 401 | 40100 | 令牌无效；含密钥轮换后旧令牌 |
| 令牌已作废 | 401 | 40101 | 登出/改密/停用；与 40100 分开以便监测批量撤销与令牌滥用 |
| 无权限 | 403 | 40300 | 不返回所需权限码（避免泄露权限结构） |
| 参数校验失败 | 400 | 40000 | 字段级错误 |
| 业务规则拒绝 | 403/409/400 | 403xx/409xx/400xx | 完整业务码见 04 §1.3 |
| 并发冲突 | 409 | 40950 | `expectedVersion` 不匹配；不得静默覆盖 |
| 限流 | 429 | 42900 | 附带 `Retry-After` |
| 服务降级 | 503 | 50300 | 仅 fail-closed 姿态或从未成功加载缓存时返回 |
| 服务器异常 | 500 | 50000 | 响应体不含堆栈 |

## 14. 前端权限

| 层次 | 实现 |
|---|---|
| 动态菜单 | 登录后调用 `/api/auth/me` 获取权限码集合，前端按本地菜单配置过滤；后端不返回菜单树结构 |
| 动态路由 | 按可见菜单注册路由；未授权路由不注册，直接 404 |
| 按钮级 | `v-perm="'sys:user:delete'"` 指令，无权限则移除 DOM |
| 强制改密 | 登录或 `/api/auth/me` 返回 `mustChangePassword=true` 时，跳转改密页，不注册业务路由 |
| 请求拦截 | Axios 拦截器统一处理 401（跳登录）与 403（提示） |

约束：前端权限只决定展示，不是安全边界。任何权限判断只允许使用 `permissions` 数组或 `v-perm` 指令，禁止使用角色编码。

**18 个外部系统不使用本系统前端**：本系统 Vue 前端只服务 RBAC 管理端；外部系统不把 `/api/auth/me` 当作最终用户菜单数据源，也不依赖本系统菜单树。外部系统的菜单/按钮由各系统自行维护，服务端 API 鉴权必须调用 `/api/auth/permission-check`；前端隐藏不是安全边界。

## 15. 可信代理与客户端 IP

| 编号 | 规则 |
|---|---|
| IP-1 | 应用端口不对公网开放，只允许 Nginx 与负载均衡网段访问 |
| IP-2 | 只信任来自可信代理网段的 `X-Forwarded-For`；来源不可信时忽略该头，使用 TCP 对端地址 |
| IP-3 | 可信代理必须覆盖（set）该头，不得追加（append） |
| IP-4 | `ClientIpResolver` 是唯一解析入口；代理层数已知时取对应位置，不确定时取最右侧可信代理写入值 |
| IP-5 | 限流、审计、安全告警必须调用同一个 `ClientIpResolver` |
| IP-6 | 日志额外记录原始 TCP 对端地址，用于排查代理配置错误 |
| IP-7 | 记录并告警"不可信 XFF"计数 |

## 18. 高可用边界与 RTO/RPO

现状：应用层有冗余，MySQL / Redis / Nginx 均为单实例，无自动故障切换。这是成本取舍，不得在任何文档或代码注释中宣称具备整体自动容灾能力。

| 组件 | 故障影响 | RTO | RPO |
|---|---|---|---|
| 应用实例（3 中 1） | 用户无感知 | ≤ 5 分钟 | 无（无状态） |
| Nginx | 全员不可用 | ≤ 30 分钟（重启）；机器损坏 ≤ 4 小时 | 无 |
| MySQL | 鉴权继续（fail-open，权限判断可能过期）；写操作失败 | ≤ 1 小时（binlog 完好）；仅靠每日备份则 ≤ 24 小时 | ≈ 0（binlog 开启且备份与数据库异机）；不满足则退化为自上次全备 |
| Redis | 登录与鉴权不受影响；权限与令牌变更延迟 ≤ 30 秒 | ≤ 5 分钟 | 不适用 |

可用性口径：

| 口径 | 目标 |
|---|---|
| 鉴权读路径 | 99.9% |
| 含写操作的端到端 | 受 MySQL 单点约束，不承诺 99.9% |

扩展点约束（将来加高可用不得改代码）：

| 组件 | 现在必须遵守 |
|---|---|
| Nginx | 应用必须无状态；不得引入会话粘滞 |
| MySQL | 必须开启 binlog；数据访问分层清晰；不使用跨库事务；避免长事务 |
| Redis | 不依赖其持久状态；使用支持 Sentinel 的客户端配置；禁止跨 key 多键操作 |

运维要求：每日全量备份 + binlog 增量，备份与 binlog 必须存放在数据库主机之外；每季度至少一次恢复演练；各组件需人工恢复手册与值班流程。

## 19. 质量门禁

| 门禁 | 检查内容 | 失败处理 |
|---|---|---|
| 接口权限覆盖 | 每个 `@RequestMapping` 方法必须有且只有一个方法级鉴权注解；Actuator/OPTIONS 走 allowlist | 构建失败 |

| 首次改密 | mustChangePassword 时仅允许改密/登出/me | 构建失败 |
| 缓存快照 | 失效后整体重载、原子替换、失败保留旧值 | 构建失败 |

| SQL 索引覆盖 | 关键 SQL 的 `EXPLAIN` 断言 | 待目标环境执行 |
| 性能回归 | 按档位压测，A 档 P99 不达标 | 待目标环境执行，阻断发布 |
