# 02 · 总体设计

相关文档：[00 基线](./00-编码代理工作基线.md) · [01 需求](./01-需求规格说明书.md) · [03 数据模型](./03-数据模型设计.md) · [04 接口](./04-接口设计.md) · [05 演进](./05-RBAC0到RBAC3演进设计.md) · [06 性能](./06-性能与容量设计.md)

## 1. 设计约束

| 编号 | 约束 | 依据 |
|---|---|---|
| D-1 | 权限集合的计算只允许出现在 `PermissionResolver` 的实现中 | 业务代码、拦截器、前端一律只消费权限码集合；RBAC1/2/3 升级只改这一处 |
| D-2 | 鉴权链路禁止访问数据库与 Redis | 30ms 预算中鉴权占比必须 < 1ms |
| D-3 | 缓存只存事实，不存派生结果 | 派生结果（userId→权限码）会让"改一个角色"作废上万条缓存 |
| D-4 | 优先减少工作量，其次才是加快执行 | 现状：鉴权零查询；不引入响应式框架 |
| D-5 | 每一份冗余必须能说出理由 | 只预留 `inherit_role_id` 一个业务字段与两个代码扩展点 |

## 2. 部署形态

```text
浏览器（Vue 3 SPA）
  └─ HTTPS
      └─ Nginx（静态资源 + 反向代理 + keepalive）
          └─ HTTP 内网
              └─ 应用实例 × 3（无状态，可增减）
                  ├─ 本地内存：权限映射（< 30MB）+ 身份快照
                  ├─ MySQL 8：仅写操作与缓存重建
                  └─ Redis：仅失效广播
```

| 组件 | 角色 | 关键约束 |
|---|---|---|
| Nginx | 入口与静态资源 | 单实例，无自动故障切换 |
| 应用 | 无状态，可横向扩 | 本地缓存只存可重建数据，不存会话 |
| MySQL | 唯一事实来源 | 鉴权不查它；只承担写与缓存重建 |
| Redis | 失效通知通道 | 不存业务数据；故障只影响生效速度 |

## 3. 缓存结构

每实例持有三份缓存：

| 缓存 | 键 → 值 | TTL | 用途 |
|---|---|---|---|
| A | roleId → Set\<permissionCode\> | 30 秒 | 角色权限矩阵 |
| B | userId → Set\<roleId\> | 30 秒 | 用户角色关系 |
| C | userId → {tokenVersion, status} | 30 秒 | 令牌作废判定 |

派生值不缓存：用户有效权限码 = 对缓存 B 中的角色，在缓存 A 中求并集，并过滤停用角色与停用权限。

A、B、C 必须分开：修改角色权限只需清空 A，不应影响任何人的登录状态；停用某个用户只需丢弃 C 中该用户条目。

## 4. 模块划分

| 模块 | 职责 | 允许依赖 |
|---|---|---|
| `rbac-api` | 契约层：接口、DTO、事件、框架级权限码常量、鉴权注解 | 无（仅 JDK） |
| `rbac-core` | 领域模型、权限计算、约束校验器链、持久化 | rbac-api |
| `rbac-auth` | 登录、令牌签发与验签、密码策略、失败锁定 | rbac-api |
| `rbac-guard` | 鉴权过滤器、拦截器、请求上下文 | rbac-api |
| `rbac-cache` | 本地缓存、失效广播订阅、版本号 | rbac-api |
| `rbac-audit` | 审计写入与查询 | rbac-api |
| `rbac-admin` | 管理端 REST 接口 | rbac-api |
| `rbac-bootstrap` | 启动、配置装配、Web 全局配置 | 全部 |
| `biz-*` | 业务模块（使用方） | 仅 rbac-api |

拆分依据：`rbac-auth` 与 `rbac-guard` 分开，因为认证随登录方式变化（将来可能加 SSO），鉴权随权限模型变化，RBAC 升级只动后者。`rbac-cache` 分开，因为它属性能基础设施而非领域概念。

模块内部统一分层：

```text
<module>/src/main/java/...<module>/
├── api/          对外接口实现
├── internal/     模块私有实现（domain/ mapper/ support/）
└── config/       模块自己的 Bean 装配
```

## 5. 模块依赖规则

由 ArchUnit 在构建期强制，违反即构建失败。

| 规则 | 内容 | 依据 |
|---|---|---|
| R-1 | 模块间只允许依赖 `rbac-api`；除 `rbac-bootstrap` 外任何模块不得依赖其他模块 | 依赖方向由编译器强制 |
| R-2 | `rbac-core` 不得依赖 Web 类型（`jakarta.servlet.*`、`@RestController`） | 领域逻辑需能脱离 HTTP 测试 |
| R-3 | `rbac-auth` 不得依赖 `rbac-core` 的权限计算 | 防止认证与鉴权重新纠缠 |
| R-4 | 业务接口不得引用 `Role`、授权关系等概念，只允许使用权限码 | RBAC 升级时业务代码零改动 |
| R-5 | `*Mapper` 只允许被同模块内的领域服务引用 | SQL 集中，索引可控 |
| R-6 | 模块内私有类放 `internal` 子包，禁止跨模块 import | 防止契约外耦合 |
| R-7 | 业务模块不得引用 `rbac-core` / `rbac-cache` / `rbac-audit` 的任何类型 | 业务与权限系统只保留一个接口面 |

## 6. 模块通信方式

| 场景 | 方式 | 约束 |
|---|---|---|
| 同步命令与查询 | 通过 `rbac-api` 接口调用（编译期依赖接口，运行期注入实现） | 同进程调用，无序列化 |
| 跨实例失效通知 | Redis Pub/Sub，消息体只含通知类型与版本号 | 只通知丢弃缓存，不传数据；丢失由 TTL 兜底 |
| 变更审计写入（CHANGE） | 通过 `AuditRecorder` 同步调用，沿用调用者事务 | 不允许异步、不允许走消息 |
| 安全事件写入（SECURITY） | 同一接口，不参与业务事务 | 写入失败不回滚业务 |
| 业务白名单审计 | 业务模块直接调用 `AuditRecorder` | 业务模块已依赖 rbac-api，无需新增依赖 |

只有"本质异步且丢得起"的失效通知走消息，其余走接口调用。禁止把同步命令改为消息——会让调用方无法判断成败。

## 7. 权限码常量归属

| 类别 | 归属 | 示例 |
|---|---|---|
| 框架级权限码 | `rbac-api` 常量包 | `*`、`sys:user:read` |
| 业务级权限码 | 各业务模块自己的常量类 | `biz:order:read` 定义在 `biz-order` 模块内 |

不得把所有权限码集中到 `rbac-api`。依据：那会使契约层成为所有人的公共变更点，并行开发必然冲突。

业务模块引用权限码时使用常量而非字面量，拼写错误在编译期即暴露。

## 8. 新增模块或接口的约定

| 编号 | 约定 | 依据 |
|---|---|---|
| A-1 | 业务表与 RBAC 表同库 | CHANGE 审计要求同事务；禁止跨库事务 |
| A-2 | Flyway 单一序列，脚本名带模块前缀；并行开发分段分配版本号（V20x、V21x） | 同名版本号会导致迁移冲突 |
| A-3 | 新接口必须归入性能档位（A/B/例外），导出类不得归 A 档 | 30ms 预算只给业务逻辑留约 24ms |
| A-4 | 涉及"只能操作自己的数据"的接口必须写归属校验并配负向测试 | 权限码回答不了水平越权；门禁也查不出 |
| A-5 | 业务表结构遵循与 RBAC 域相同规范（逻辑删除 + created_by/at + updated_by/at） | 全库审计可追溯性一致 |
| A-6 | 业务模块不得在 Redis 存放业务数据 | 否则 Redis 从可丢弃的加速器变成必须高可用的存储 |
| A-7 | 新模块引入新缓存对象时必须同步更新失效逻辑 | 缓存加载语句与计算逻辑不一致会导致权限错误 |
| A-8 | 业务模块不得绕过 `rbac-api` 依赖 RBAC 内部类型 | 见 R-7 |
| A-9 | 每个业务接口必须显式声明审计意图（`AuditRecorder` 或 `@NoAudit`） | 审计范围含业务白名单，判断依据见 01 文档 |
| A-10 | 导出类操作必须记录条件、结果条数、范围；归 B 档或例外档 | 只记"谁导出了"无价值 |

门禁覆盖 A-3、A-4 之外的所有项。A-3 与 A-4 无自动化检查，需人工负责。

## 9. 认证链路

```text
POST /api/auth/login
1. 登录限流检查（账号维度 + IP 维度，Redis 滑动窗口）
2. 账号存在性与 status 检查
3. 失败锁定检查（连续失败 ≥ 5 次 → 锁 15 分钟）
4. BCrypt 校验（50~150ms，故意慢）
5. 通过 → token_version 自增（作废该账号历史令牌）
6. 生成 JWT
7. 写登录安全事件（SECURITY 类，独立落库）
```

JWT 载荷：

| 字段 | 说明 |
|---|---|
| `sub` | userId |
| `ver` | tokenVersion，与身份快照比对 |
| `kid` | 密钥标识，验签时据此选择密钥 |
| `iss` / `aud` | 签发方与受众，验签时强制校验 |
| `iat` / `exp` | 签发与过期时间；校验允许 60 秒时钟偏移 |

不得放入：角色列表、权限码列表、昵称头像。不使用 `jti`（逐令牌黑名单的写入量与跨实例共享成本不成比例）。

签名：HS256。密钥 ≥ 256 位，由环境变量或配置中心下发，禁止进入代码仓库与镜像层。所有实例启动时校验 `kid → 密钥` 映射一致，不一致则启动失败。

密钥轮换三阶段：

```text
阶段 1  配置变为 {kid=1: K1, kid=2: K2}；签发改用 K2；token_version 不递增
        发布顺序强制：先让全部实例支持双密钥，再切换签发
阶段 2  等待 ≥ 访问令牌最长有效期（2 小时）+ 时钟偏移余量；K1 仅用于验签
阶段 3  确认无 kid=1 的验签记录后，从配置移除 K1
```

回滚：阶段 1、2 任意时刻把配置改回双密钥并继续用 K1 签发即可。密钥泄露时跳过等待期，同时全局自增令牌版本基线（等价于全员重新登录）。

BCrypt 使登录接口不受 30ms 约束，必须使用独立线程池隔离。

## 10. 鉴权链路

固定顺序：

```text
1. JwtAuthFilter
   解析并验签（按 kid 选密钥，HS256）
   校验 exp / iat / iss / aud（允许 60 秒偏移）
   身份快照校验：snapshot.tokenVersion == token.ver 且 snapshot.status == 启用
   通过 → 写入请求上下文 CurrentUser{userId, tokenVersion}

2. PermissionInterceptor
   读取方法上的 @RequiresPermission
   @PublicApi / @RequiresLogin → 直接放行
   三者都无 → 拒绝（403 + 告警）

3. PermissionResolver.resolve(userId) → Set<String>（纯内存）
   未命中 → 单飞重载

4. 判定：codes.contains("*") || codes.contains(requiredCode)
   通过 → 进入业务方法；不通过 → 403，不进入业务方法
```

耗时预算（P99）：

| 步骤 | 耗时 | 是否访问外部 |
|---|---|---|
| JWT 验签 | 10μs | 否 |
| 身份快照校验（命中） | ns | 否 |
| 权限解析（命中） | 0.1ms | 否 |
| 权限码比对 | 20ns | 否 |
| 合计 | < 0.2ms | 无 |

默认拒绝策略：未标注三种注解之一的接口一律拒绝并记录告警。这把"漏加注解"从安全漏洞降级为可见的功能缺陷。

`@RequiresPermission` 只接受 API 类权限码或通配码；引用 MENU 类权限码由门禁拦截。

## 11. 缓存失效与降级

### 11.1 三层失效机制

第一层，主动失效（正常路径，目标 ≤ 1 秒）：

```text
写操作事务提交成功后（顺序不可颠倒）：
  自增全局版本号（Redis INCR，用于可观测）
  按类型发布：
    PERM_CHANGED        {"ver":123}            → 各实例丢弃缓存 A、B
    TOKEN_REVOKED       {"userId":7,"ver":12}  → 各实例丢弃缓存 C 中该用户条目
    TOKEN_REVOKED_GLOBAL{"ver":1}              → 各实例丢弃整个缓存 C
  订阅方只标记失效，不立即重载；由后续请求惰性重载（单飞）
```

广播去抖：1 秒内的多次变更合并为一次。

第二层，TTL 兜底：A、B、C 均设 30 秒 `expireAfterWrite`。广播丢失时 30 秒内收敛。TTL 与降级窗口一一对应，调整 TTL 必须同步修改 01 文档 FR-A9 的承诺。

第三层，实例生命周期：

| 场景 | 处理 |
|---|---|
| 实例启动 | 加载 A、B；C 不预加载，首个请求按需读库 |
| 订阅重连成功 | 强制清空全部缓存（断连期间的广播已丢失） |
| Redis 不可用 | 告警；降级为 TTL 生效模式；登录与鉴权不中断 |
| 重载失败 | 见 11.3 |

### 11.2 缓存元数据

每个缓存条目必须携带：

| 元数据 | 用途 |
|---|---|
| `cacheVersion` | 本次加载时的数据版本标记，用于观测各实例是否一致 |
| `loadedAt` | 本次成功加载时间；只由成功加载更新 |
| `expiresAt` | `loadedAt + TTL`；到点触发重载，不丢弃数据 |
| `state` | `VALID` / `STALE` / `RELOADING` / `FAILED` |

状态处理：

| 状态 | 请求处理 |
|---|---|
| VALID | 正常鉴权 |
| STALE | 用旧数据鉴权 + 触发异步重载 |
| RELOADING | 不重复触发，直接用旧数据 |
| FAILED | 继续用最后一份成功数据 + 告警 + 指数退避重试 |

两条互补规则：

- 数据一旦成功加载过就永不丢弃。依据：丢弃会导致重载失败时无数据可用而被动拒绝服务，fail-open 无法成立。
- `loadedAt` 绝不伪刷新。依据：若重载失败时把它重置为当前时间，陈旧时长指标恒为 0，监控将无法发现正在使用过期权限。

必须暴露的指标：当前陈旧时长、重载失败次数、受影响用户数、用陈旧权限放行的请求数。

### 11.3 重载失败策略：fail-open

| 策略 | 行为 |
|---|---|
| fail-open（默认） | 继续用最后一份成功数据服务，同时强告警 |
| fail-closed（可配置） | 拒绝请求，返回 503 |

配置项 `rbac.cache.stale-policy`，默认 `fail-open`，可选 `fail-closed`。

唯一的强制 fail-closed 分支：

| 场景 | 处理 | 依据 |
|---|---|---|
| 收到 `TOKEN_REVOKED(X)` 但 X 的身份快照重载失败 | 拒绝 X 的请求（40101） | 已知 X 状态变化，放行等于主动接受已作废令牌；影响面仅这一个用户 |
| 数据库不可用且实例从未成功加载过任何缓存 | 拒绝需鉴权的请求（503） | 没有任何可信数据，放行等于靠猜 |

配套运维要求（fail-open 的代价必须被管理）：

1. 陈旧时长、受影响用户数、放行请求数必须有监控与告警。
2. 故障恢复后必须立即全量失效并重载一次。
3. 故障期间的权限撤销必须可通过审计日志追溯（CHANGE 类同事务落库，不受缓存影响）。
4. 故障复盘必须给出"本次故障期间有多少请求用陈旧权限放行"。

### 11.4 身份快照（缓存 C）

```text
键：userId
值：{ tokenVersion, status, loadedAt, expiresAt }
校验：token.ver == snapshot.tokenVersion 且 snapshot.status == 启用
```

| 事项 | 设计 |
|---|---|
| 数据来源 | `sys_user.token_version` 与 `status`，单行主键查询 |
| TTL | 30 秒 |
| 失效通知 | 收到 `TOKEN_REVOKED(userId)` 时丢弃该条目，不立即重载 |
| 实例启动 | 不预加载；首个请求按需读库 |
| 未命中 | 单飞查库；用户不存在或已删除则缓存否定结果（同样 30 秒到期） |
| 全局作废 | 收到全局令牌作废事件时清空整个缓存 C |

令牌作废生效时间：

| 条件 | 生效时间 |
|---|---|
| Redis 正常 | ≤ 1 秒 |
| Redis 故障或广播丢失 | ≤ 30 秒 |
| 实例重启 | 立即（缓存为空，首个请求即读库） |
| 数据库不可用 | 受影响用户拒绝；其他用户按 11.3 处理 |

成本：每活跃用户每 30 秒一次主键查询；1 万活跃用户约 333 QPS。禁止改为"每请求查 Redis 名单"（会把 Redis 变成关键路径，并在零网络链路上开洞）。

高风险账号若需要更严格的失效时效，做法是缩短其令牌有效期，不新增特例通道。

## 12. 权限码规范

格式：`<模块>:<资源>:<操作>[.<子操作>]`

```text
sys:user:create           创建用户
sys:user:reset-password   重置密码
biz:order:export          导出订单
sys:user:*                某资源下全部操作
sys:*                     某模块下全部
*                         全部（仅超级管理员角色持有）
```

| 规则 | 约束 |
|---|---|
| 字符 | 全小写，`:` 分隔层级，`-` 连接复合词 |
| 不可修改 | 创建后不得修改 |
| 与接口对应 | API 类权限码与后端接口一一对应，由门禁校验 |
| 与界面对应 | MENU / BUTTON 类与菜单、按钮对应，前端据此渲染 |
| 通配判定 | 字符串前缀匹配；仅在用户权限集合含通配项时触发 |

## 13. HTTP 响应与异常

| 场景 | HTTP | code | 说明 |
|---|---|---|---|
| 成功 | 200 | 0 | `{code, message, data, traceId}` |
| 未认证 | 401 | 40100 | 令牌无效 |
| 令牌已作废 | 401 | 40101 | 登出/改密/停用/全局作废；与 40100 分开以便监测批量踢人与令牌滥用 |
| 无权限 | 403 | 40300 | 不返回所需权限码（避免泄露权限结构） |
| 参数校验失败 | 400 | 40000 | 字段级错误 |
| 业务规则拒绝 | 200 | 4xxxx | 用业务码便于前端精确提示 |
| 并发冲突 | 409 | 40950 | `expectedVersion` 不匹配；不得静默覆盖 |
| 限流 | 429 | 42900 | 附带 `Retry-After` |
| 服务降级 | 503 | 50300 | 仅 fail-closed 姿态或从未成功加载缓存时返回 |
| 服务器异常 | 500 | 50000 | 响应体不含堆栈 |

## 14. 前端权限

| 层次 | 实现 |
|---|---|
| 动态菜单 | 登录后调用 `/api/auth/me` 获取权限码集合，前端按本地菜单配置过滤；后端不返回菜单树结构 |
| 动态路由 | 按可见菜单注册路由；未授权路由不注册，直接 404 |
| 按钮级 | `v-perm="'sys:user:delete'"` 指令，无权限则移除 DOM |
| 请求拦截 | Axios 拦截器统一处理 401（跳登录）与 403（提示） |

约束：前端权限只决定展示，不是安全边界。任何权限判断只允许使用 `permissions` 数组或 `v-perm` 指令，禁止使用角色编码。

## 15. 可信代理与客户端 IP

| 编号 | 规则 |
|---|---|
| IP-1 | 应用端口不对公网开放，只允许 Nginx 与负载均衡网段访问 |
| IP-2 | 只信任来自可信代理网段的 `X-Forwarded-For`；来源不可信时忽略该头，使用 TCP 对端地址 |
| IP-3 | 可信代理必须覆盖（set）该头，不得追加（append） |
| IP-4 | `ClientIpResolver` 是唯一解析入口；代理层数已知时取对应位置，不确定时取最右侧可信代理写入值 |
| IP-5 | 限流、审计、安全告警必须调用同一个 `ClientIpResolver` |
| IP-6 | 日志额外记录原始 TCP 对端地址，用于排查代理配置错误 |
| IP-7 | 记录并告警"不可信 XFF"计数 |

## 18. 高可用边界与 RTO/RPO

现状：应用层有冗余，MySQL / Redis / Nginx 均为单实例，无自动故障切换。这是成本取舍，不得在任何文档或代码注释中宣称具备整体自动容灾能力。

| 组件 | 故障影响 | RTO | RPO |
|---|---|---|---|
| 应用实例（3 中 1） | 用户无感知 | ≤ 5 分钟 | 无（无状态） |
| Nginx | 全员不可用 | ≤ 30 分钟（重启）；机器损坏 ≤ 4 小时 | 无 |
| MySQL | 鉴权继续（fail-open，权限判断可能过期）；写操作失败 | ≤ 1 小时（binlog 完好）；仅靠每日备份则 ≤ 24 小时 | ≈ 0（binlog 开启且备份与数据库异机）；不满足则退化为自上次全备 |
| Redis | 登录与鉴权不受影响；权限与令牌变更延迟 ≤ 30 秒 | ≤ 5 分钟 | 不适用 |

可用性口径：

| 口径 | 目标 |
|---|---|
| 鉴权读路径 | 99.9% |
| 含写操作的端到端 | 受 MySQL 单点约束，不承诺 99.9% |

扩展点约束（将来加高可用不得改代码）：

| 组件 | 现在必须遵守 |
|---|---|
| Nginx | 应用必须无状态；不得引入会话粘滞 |
| MySQL | 必须开启 binlog；数据访问分层清晰；不使用跨库事务；避免长事务 |
| Redis | 不依赖其持久状态；使用支持 Sentinel 的客户端配置；禁止跨 key 多键操作 |

运维要求：每日全量备份 + binlog 增量，备份与 binlog 必须存放在数据库主机之外；每季度至少一次恢复演练；各组件需人工恢复手册与值班流程。

## 19. 质量门禁

| 门禁 | 检查内容 | 失败处理 |
|---|---|---|
| 接口权限覆盖 | 每个 `@RequestMapping` 方法必须有三种鉴权注解之一 | 构建失败 |
| 权限码定义一致性 | 代码引用的权限码必须在初始化数据中有定义 | 构建失败 |
| 审计声明检查 | 敏感关键词接口必须调用 `AuditRecorder` 或标注 `@NoAudit` | 构建失败 |
| 模块依赖规则 | ArchUnit 校验 R-1 ~ R-7 | 构建失败 |
| 权限计算单元测试 | 覆盖无角色、单角色、多角色、停用角色、停用权限、超级管理员 | 构建失败 |
| 越权集成测试 | 低权账号访问高权接口必须返回 403 | 构建失败 |
| SQL 索引覆盖 | 关键 SQL 的 `EXPLAIN` 断言 | 构建失败 |
| 性能回归 | 按档位压测，A 档 P99 不达标 | 阻断发布 |

审计声明门禁的局限：基于关键词匹配，只能提醒不能判定。名字不含关键词的敏感操作查不出来，不替代评审。
