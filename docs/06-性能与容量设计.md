## 1. 先把指标口径算清楚：10k 在线用户到底是多少负载

**这是整个性能设计中最容易出错的一步。** "10k 并发"被误读为"10k QPS"时，采购的机器会多出 5~10 倍。

### 1.1 负载模型推导

| 参数 | 取值 | 来源 |
|---|---|---|
| 并发在线用户 | 10,000 | 需求 |
| 每用户操作频率 | 6~10 次/分钟（取上限 10） | 需求澄清 |
| 峰值系数 | 1.5（早晚高峰集中登录与操作） | 经验值 |
| **推导峰值** | **10,000 × 10 ÷ 60 × 1.5 ≈ 2,500 QPS** | 计算值。**这是"最坏情况按最保守假设推导出来的上界"，不是承诺的容量** |
| **设计目标（sizing 依据）** | **2,000 QPS** | 在推导峰值上预留 **25% 余量**。它的含义是"按此容量配置机器"，**不是"超过就拒绝服务"的限流阈值** |
| **验收场景** | **2,500 QPS 稳态 + 4,000 QPS 冲刺** | 见 §7.2 的 S10、S11。设计目标与验收场景不同是**刻意**的：设计留余量，验收按推导上界甚至更高 |

### 1.2 用利特尔法则算"同时在处理的请求数"

利特尔法则（Little's Law）是排队论的基本公式，一句话解释：**"系统里正在排队和服务的人" = "到达速度" × "每人平均停留时间"**。超市里每秒进来 2 个人、每人逛 30 秒，那么超市里平均就有 60 个人。

```
同时在处理的请求数 L = 到达速率 λ × 平均处理时间 W
                    = 2,000 请求/秒 × 0.03 秒
                    = 60 个并发请求
```

**结论：10,000 个在线用户，真正"同时在跑"的请求只有 60 个。**

这两个数字差了 166 倍，是整个容量设计的基石：

| 数字 | 含义 | 决定了什么 |
|---|---|---|
| 10,000 | 同时保持的 **TCP 连接数**（用户的浏览器挂着 keep-alive） | 决定 `max-connections`、文件描述符上限、内存中的连接缓冲区 |
| 60 | 同时占用的**工作线程数** | 决定Tomcat 线程池大小（200 个线程已有 3 倍余量） |

> **一个常见误解**：认为"10k 并发"意味着"需要 10k 个线程"。**连接是连接，线程是线程。** Tomcat 的 NIO 连接器用少量线程（Acceptor/Poller）管理大量空闲连接，只有真正在处理请求时才占用工作线程。这也是"不需要响应式框架"的根本原因——见第 5 节。

## 2. 30ms 预算拆解

### 2.1 验收口径先说明

| 口径 | 定义 | 用途 |
|---|---|---|
| **服务器侧 P99 ≤ 30ms**（验收口径） | 从应用收到请求到应用写出响应的时间，不含公网传输 | 压测在同内网进行，工具测量该值。**这是我们的硬指标** |
| 端到端参考值 | 服务器侧 + 内网/公网传输 | 仅作参考与用户体验评估（同城内网约 +2~4ms） |

### 2.2 服务器侧耗时预算（A 档接口：鉴权 + 一次索引查询）

> **口径声明：下表中的数字是"预算假设"**，用于指导设计与判断优化方向，**不是实现保证**。任何对外引用都必须标明是"预算"还是"实测"。实测结果见 §7.4 的验收清单。

| # | 环节 | P50 | P99 | 说明 |
|---|---|---|---|---|
| 1 | Tomcat 接收请求、构建对象 | 0.15ms | 0.4ms | NIO 复用连接，无握手开销 |
| 2 | 过滤器链（JWT 解析 + 验签，HS256） | 0.02ms | 0.06ms | 对称签名验签，约 10 微秒 |
| 3 | 令牌作废检查（内存集合） | 0.001ms | 0.005ms | 纯内存 |
| 4 | **权限解析（本地缓存命中）** | **0.02ms** | **0.1ms** | 缓存 B 查角色 + 缓存 A 求并集，微秒级 |
| 5 | 权限码判定（`HashSet.contains`） | 0.005ms | 0.02ms | O(1) |
| 6 | 业务逻辑 + MyBatis 索引查询 | 1.5ms | 4ms | 内网 DB 往返 0.3ms + 索引查询 1~3ms |
| 7 | JSON 序列化 | 0.3ms | 1ms | 小对象 |
| 8 | 日志（异步 Appender） | 0.01ms | 0.05ms | 写入内存队列即返回 |
| 9 | 响应写出 | 0.1ms | 0.3ms | |
| | **服务器侧合计** | **≈ 2.1ms** | **≈ 6.0ms** | **余量 24ms（80%）** |

### 2.3 这张表说明了什么

| 观察 | 含义 |
|---|---|
| 鉴权链路（第 2~5 项） | P99 合计约 **0.19ms** | 仅占服务器侧 P99（6ms）的 3%、占 30ms 目标的 0.6% |
| 最大的一项是业务数据库查询 | **性能优化的重点应该在业务查询的索引上，而不是在鉴权上** |
| P99 是 P50 的 3 倍 | 差距来自 DB 查询的长尾（锁等待、缓冲池未命中）。因此**慢查询治理是保障 P99 的第一优先级** |
| B 档接口（含同步审计写入） | 增加约 1~3ms（简单 INSERT + 同行事务提交），P99 约 10ms，远低于 200ms 上限 |

> **重要结论**：本设计**不是"勉强达标"而是"大幅度超标"**。达标靠的不是某个高性能组件，而是把鉴权链路上的每一份工作都消掉了。这意味着未来有充裕的性能余量去承载业务逻辑的增长——**这正是"降低升级代价"在性能维度的体现**。

### 2.4 缓存未命中时的额外开销（必须量化）

| 场景 | 额外耗时 | 发生频率 |
|---|---|---|
| 缓存全量重建（两张映射表全表加载，合计约 4 万行） | 30~60ms | 仅权限变更后首次请求，或 TTL 过期后首次请求 |
| 影响范围 | **只有触发重建的请求**，其他请求继续命中旧缓存（单飞机制） | — |
| 对策 | ① 单飞保证同时只有一个线程重建；② 重建前旧缓存继续服务，避免"清空瞬间全部请求穿透" | — |

> **这是"分层缓存"的关键细节**：我们**先加载新数据、再原子替换缓存引用**，而不是"先清空、再加载"。否则在清空的 30~60ms 窗口内，2000 QPS 的请求会同时穿透到数据库（每秒数万次全表扫描）——这是**典型的缓存雪崩**。

### 2.5 例外：登录接口

| 项 | 值 | 说明 |
|---|---|---|
| BCrypt 校验耗时 | 50~150ms | **故意慢**，这是抗暴力破解的设计目的，不是缺陷 |
| 结论 | 登录接口**不受 30ms 约束** | 用独立线程池隔离（见 §6.4），保护 A 档接口 |

## 3. 容量测算

### 3.1 应用实例

| 项 | 计算 | 结果 |
|---|---|---|
| 单请求服务器侧 CPU 时间 | 验签 0.01ms + 缓存与判定 0.03ms + 序列化 0.3ms + 框架与日志 0.15ms ≈ **0.5ms**（不含 DB 等待） | — |
| 单实例理论 CPU 上限 | 4 vCPU × 可用率 70% ÷ 0.0005 秒 = **5,600 QPS** | — |
| 安全系数 | 取 1/3（考虑 GC、突发、序列化大对象、慢请求） | **单实例约 1,800 QPS** |
| 峰值需求 | 2,000 QPS | — |
| **所需实例数** | 理论上 **2 台**（一台承担 1,000 QPS）；**建议部署 3 台** | 第 3 台用于：单机故障不影响服务 + 滚动发布不中断 |
| 实际负载率 | 2,000 ÷ (3 × 1,800) ≈ **37%**（含 DB 等待时 CPU 实际占用更低） | 余量充足 |

> **诚实结论**：这个系统**不是高负载系统**。3 台应用实例是**可用性需求**，不是性能需求。请勿按"10k 并发"的字面印象采购机器。

### 3.2 内存

| 项 | 估算 | 说明 |
|---|---|---|
| 权限缓存（缓存 A + B + C） | 初期 < 10MB；远期（5 万用户）< 30MB | 见 [03 文档 §3](./03-数据模型设计.md) |
| Caffeine 内部结构与淘汰开销 | ≈ 缓存数据的 30~50% | 即 < 15MB |
| 线程栈 | 200 工作线程 + 50 其他 ≈ 250 × 1MB = 250MB | 栈大小可用 `-Xss512k` 降到 128MB |
| JVM 元空间、编译缓存、Direct Buffer | ≈ 500MB | NIO 连接缓冲：10k 连接 × 8KB ≈ 80MB |
| **结论** | 堆设 **3~4GB** 已非常宽松（4C8G 实例，留 4G 给操作系统与文件缓存） | 不需要 16G |

### 3.3 数据库连接池（HikariCP）

**这是最容易被配错的地方。** 很多团队的经验是"连接数设大一点保险"，实际上**连接数设得过大反而更慢**（线程上下文切换、数据库端锁竞争、内存占用）。

| 项 | 值 | 理由 |
|---|---|---|
| 计算公式 | `连接数 ≈ (CPU 核心数 × 2) + 磁盘数` | 业界广泛验证的经验公式；核心是"连接数应与 CPU 核心数同量级，而不是与并发请求数同量级" |
| `maximumPoolSize` | **20**（4 vCPU） | 单连接在 2ms 查询下每秒可完成 500 次，20 连接 = 10,000 QPS 上限，而实际 DB QPS < 1,000 |
| `minimumIdle` | 5 | 保持热连接，避免突发时建连 |
| `connectionTimeout` | 3,000ms | 超时快速失败，避免请求线程被无限挂起 |
| 3 实例总连接数 | 3 × 20 = 60 | MySQL `max_connections` 建议调至 300（为运维连接与未来扩容留余量） |

### 3.4 数据库（MySQL）

| 指标 | 估算 | 说明 |
|---|---|---|
| 读 QPS | **< 1,100** | 列表/详情页查询约占请求的 30%（600 QPS）+ **身份快照加载约 333 QPS**（见下方说明）+ 缓存重建几乎不占。**注意：鉴权本身仍然零 DB 查询** |
| 写 QPS | **< 1** | RBAC 配置类操作每天几十到几百次 |
| 单机能力对比 | 简单索引查询：单机可轻松承受 3,000~5,000 QPS | 实际负载率 < 20% |
| 数据量 | 业务表 < 20 万行；审计表 180 天约 50~150 万行 | 全量数据可放入 InnoDB 缓冲池，**热点查询不会读磁盘** |
| 结论 | **单主 8C16G + SSD 足够**，无需读写分离、无需分库分表 | 增加从库只会增加复杂度，且主从延迟会带来"刚改的配置看不到"的困惑 |

> **什么时候才需要读从库？** 当读 QPS 超过 2,000 且慢查询占比上升时。当前负载率的 5 倍以内都不需要。**先测量，再扩容**——这是"考虑服务器资源有限"的正确用法：不是省到不够用，而是不买用不上的。

**身份快照带来的额外读负载（必须计入，不能忽略）**：

| 项 | 计算 |
|---|---|
| 机制 | 每个活跃用户的身份快照（`token_version` + `status`）TTL = 30 秒，到期后由下一个请求惰性重载 |
| 额外 QPS | 10,000 活跃用户 ÷ 30 秒 ≈ **333 QPS** 的单行主键查询 |
| 性质 | 全部是 `PRIMARY` 等值查询，单次约 0.1ms；**无排序、无范围扫描、无回表** |
| 结论 | MySQL 轻松承受（远低于它数千 QPS 的能力）。**这是"可靠的令牌作废"必须付出的确定成本**，见 [02 文档 5.3.3](./02-总体设计说明书.md) |
| 可调性 | 调大 TTL（如 60s）可把它降到 ~167 QPS，但**必须同步修改 [01 文档 FR-A9 的时效承诺](./01-需求规格说明书.md)**（Redis 故障时的收敛窗口会随之变长）。**TTL 与降级窗口是一一对应的，不允许只改一个** |

### 3.5 Redis

| 指标 | 估算 | 说明 |
|---|---|---|
| 用途 | **仅缓存失效广播**（+ 可选的登录限流计数器） | 不存业务数据、不做数据缓存 |
| 发布消息量 | 权限变更次数：每天几次到几百次 → **QPS ≈ 0.01** | 比设计能力低 5 个数量级 |
| 订阅连接数 | 每实例 1 条（外加限流计数器的少量连接） | — |
| 内存占用 | < 10MB（计数器 + 少量元数据） | — |
| 结论 | **1C2G 单实例足够**，无需哨兵/集群 | 其故障只影响"权限变更生效速度"（降级为 30s TTL），不影响可用性 |

### 3.6 网络与磁盘

| 项 | 估算 |
|---|---|
| 带宽（应用←→客户端经 Nginx） | 2,000 QPS × 平均 5KB ≈ **10MB/s ≈ 80Mbps**（千兆网卡足够） |
| 带宽（应用←→MySQL/Redis 内网） | 更低（查询结果小） |
| 磁盘（审计） | 每天几千行 × 约 1KB ≈ 几 MB/天，180 天 < 1GB |
| 文件描述符 | 10k 连接 + 60 DB 连接 + 内部 → `ulimit -n` 建议 ≥ 65,536 |

### 3.7 单点组件与可用性（性能之外的真实约束）

应用层是**唯一**做了冗余的一层。**MySQL、Redis、Nginx 均为单实例，无自动故障切换**——这是明确的成本取舍，完整的影响与 RTO/RPO 见 [02 文档 §7.2](./02-总体设计说明书.md)。

对性能工作的直接含义：

| 含义 | 说明 |
|---|---|
| 数据库故障 → 鉴权**仍继续服务**，但可能在用过期权限 | **fail-open**（[02 §5.3.2](./02-总体设计说明书.md)）：鉴权不停，但必须在监控上体现"陈旧时长"与"受影响用户数"。**数据库的可用性决定了"我们的权限判断有多旧"，而不是"服务是否可用"** |
| 应用层的压测结论不能代表全链路可用性 | S1~S11 测的是"存储正常时的性能"。**存储故障下的行为由 S14（数据库故障注入）与 S6（Redis 降级）验证**，两者不可互相替代 |
| 评审/汇报时必须区分口径 | "鉴权读路径 99.9%"与"含写操作的端到端 99.9%"是两件事，后者在 MySQL 单点下**不成立** |

### 3.8 容量汇总表

| 组件 | 规格 | 数量 | 负载率（峰值时） |
|---|---|---|---|
| Nginx | 2C4G | 1（可选 2 主备） | < 5% |
| 应用 | 4C8G（堆 3~4G） | 3 | CPU < 20%，内存 < 50% |
| MySQL | 8C16G + SSD | 1 | CPU < 30%，连接 60/300 |
| Redis | 1C2G | 1 | 内存 < 5%，QPS ≈ 0 |

## 4. 关键性能设计决策回顾

| 决策 | 性能收益 | 位置 |
|---|---|---|
| 权限映射全量放本地内存 | 鉴权链路 **0 次网络 + 0 次数据库**，节省约 0.5~2ms/请求，并把 2,000 QPS 的存储压力降到接近 0 | [02 文档 5.2/5.3](./02-总体设计说明书.md) |
| 缓存"事实"而非"派生结果" | 缓存体积小 10 倍，失效范围可控（改一个角色的权限不会让上万用户的派生缓存失效） | [02 文档 2.3](./02-总体设计说明书.md) |
| 惰性重建 + 单飞 | 广播后不会出现"N 个实例同时打库"的尖峰；重建期间旧缓存继续服务，无穿透 | [02 文档 5.3](./02-总体设计说明书.md) |
| 先加载后原子替换 | 避免"清空瞬间"的缓存雪崩 | 本文 2.4 |
| 日志异步 Appender | 每请求节省 0.2~2ms 的同步磁盘写入（**日志同步写在 SSD 上是 30ms 预算的隐形杀手**） | [01 文档 NFR-4](./01-需求规格说明书.md) |
| 权限码判定用 `HashSet` | O(1)，纳秒级 | [05 文档 3.3](./05-RBAC0到RBAC3演进设计.md) |
| 连接池按核心数配置（20 而非 200） | 避免连接过多导致的上下文切换与 DB 端竞争 | 本文 3.3 |
| 深翻页用游标 | `OFFSET` 深翻页是索引失效陷阱，游标使每页耗时恒定 | [04 文档 1.4](./04-接口设计.md) |
| 列表分页 `size` 上限 200 | 防止恶意/误操作的大分页拖垮内存与数据库 | [04 文档 1.4](./04-接口设计.md) |
| 审计表只建时间索引 | 写入路径（在事务内）保持轻量 | [03 文档 4.7](./03-数据模型设计.md) |

## 5. 澄清三个常见误区

### 5.1 "高并发就要用 WebFlux / 响应式"

| 事实 | 数据 |
|---|---|
| 同时在处理的请求数 | **60**（利特尔法则） |
| 同步阻塞模型所需线程 | 60 ÷ 平均利用率 = 远小于 200 |
| 响应式模型解决的问题 | "海量空闲长连接 + 每个请求要等下游 IO" |
| 我们的情况 | 10k 空闲连接由 NIO 连接器处理（**不占工作线程**）；每个请求的阻塞点只有一次 1~3ms 的 DB 查询 |

**结论**：响应式框架能带来的是"用更少线程支撑更多并发阻塞请求"，而我们的并发阻塞请求只有 60 个。**为一个不存在的问题引入一套全链路异步的框架，会让调试困难、栈信息不可读、事务与 ThreadLocal 语义变化，收益为负。**

### 5.2 "Java 21 有虚拟线程，应该开"

虚拟线程的价值在于"让**海量**阻塞等待不占操作系统线程"。我们的阻塞等待只有 60 个并发。而虚拟线程会带来新问题：

| 问题 | 说明 |
|---|---|
| **失去背压** | 平台线程池 + 有界队列在过载时会排队并快速失败（保护数据库）；虚拟线程几乎无限创建，过载时会**同时压垮数据库**，把小故障放大成大故障 |
| 固定与兼容问题 | `synchronized` 块内的阻塞、部分本地库会"固定（pin）"虚拟线程，反而降低吞吐 |
| 行为可预测性 | 线程池大小是运维可观测、可调节的旋钮；虚拟线程的行为更难预测 |

**结论**：**不开启虚拟线程。使用平台线程 + 有界线程池**，因为**"有界"本身就是一种保护机制**。

> **唯一例外**：如果将来出现大量"纯等待外部 IO（如调用第三方接口）"的接口，可以针对那部分单独使用虚拟线程——因为那时阻塞的耗时与数量都远超现在。

### 5.3 "本地缓存不可靠，应该用 Redis 集中缓存"

| 方案 | 单次鉴权成本 | 存储层压力 |
|---|---|---|
| 本地缓存 | **0**（纳秒级内存访问） | ≈ 0 |
| Redis 集中缓存 | 1 次网络往返（0.3~1ms），2,000 QPS 下 Redis 需承受 2,000 QPS 读 | 中 |
| 两级缓存（本地 + Redis） | 大部分命中本地，未命中查 Redis | 低但引入两层失效一致性 |

**结论**：本地缓存是性能最优解，唯一代价是"失效需要通知"。而我们的数据量（< 30MB）和变更频率（每天几次）让这个代价极小。**引入 Redis 做数据缓存，等于把已经消掉的一次网络往返又加了回来。**

## 6. P99 达标的风险点与对策

P99（最差 1% 请求）与平均值的差距，几乎总是由**长尾**造成的。下表是全部已知风险点。

### 6.1 垃圾回收（GC）

| 风险 | 堆设得过大（如 16G）导致单次 Full GC 停顿数百毫秒，一次性击穿 P99 |
|---|---|
| 对策 | ① 堆设 3~4GB（**小堆比大堆更容易控制停顿**）；② 使用 G1（默认）并设置 `-XX:MaxGCPauseMillis=100`；③ 避免产生大对象（大分页已限制 `size ≤ 200`；导出功能走流式输出） |
| 为什么不建议默认用 ZGC | ZGC 停顿更低，但吞吐略降且 CPU 开销更高。**当前堆小、对象少，G1 足够**。若压测中出现 GC 引起的 P99 尖峰，再切 ZGC（Java 21 支持分代 ZGC），切换成本仅为 JVM 参数 |

### 6.2 同步日志

| 风险 | 同步写盘的日志在磁盘抖动时耗时数十毫秒，直接击穿 P99 |
|---|---|
| 对策 | 异步 Appender + 有界队列（如 8,192）+ `discardingThreshold=0`（**不丢弃** WARN/ERROR） |
| 注意 | 丢弃策略必须同时上报指标（"丢弃日志条数"），否则会静默丢失排查线索。**宁可慢一点，不可丢证据** |

### 6.3 审计同步落库（用户明确选择的强合规口径）

| 风险 | 每次写操作多一次事务与磁盘写入 |
|---|---|
| 实际影响评估 | RBAC 域写操作的 QPS **< 1**，因此对整体指标影响**可忽略**；B 档接口 P99 增加 1~3ms，仍远低于 200ms 上限 |
| 唯一需要单独设计的场景 | **批量操作**（如一次性导入 5,000 个用户、批量授权 500 个角色）。若不处理，会产生一个持有数秒的长事务 |
| 批量场景对策 | ① 分批提交（每 200 条一个事务）；② 走独立线程池并限速（不与在线请求争抢连接池）；③ 单条审计记录改为"批次摘要 + 明细文件"，避免单事务写入数万行；④ 前端明确展示进度与预计耗时 |

### 6.4 慢接口拖垮线程池

| 风险 | 200 个工作线程被慢请求（登录、导出、批量操作）占满后，**所有** A 档接口一起变慢——**这是最典型的"一个功能拖垮整个系统"** |
|---|---|
| 对策 | ① **登录独立线程池**（如 20 线程），因 BCrypt 注定慢；② **导出/批量独立线程池**并限并发（如 5）；③ 设置请求级超时；④ 监控各线程池的活跃数与队列长度，队列堆积即告警 |

### 6.5 缓存重建与雪崩

| 风险 | 权限变更广播后，所有实例同时重建 → 数据库被 N 倍全表扫描打爆 |
|---|---|
| 对策 | ① **惰性重建**（收到广播只丢弃，不立即重建）；② **单飞**（同一时刻只有一个线程真正查库）；③ **先加载后原子替换**（2.4 节）；④ 重建失败**继续用最后一份成功数据**（fail-open）+ 指数退避重试；⑤ 广播去抖：1 秒内多次变更只广播一次（反正都是全量失效）；⑥ **陈旧时长与受影响用户数必须可观测并告警**（见 2.4 与 §8） |

> **本次修订同时纠正了原设计的两个问题**：
> ① 原设计只写"沿用旧值"，没写"**不得伪造 `loadedAt`**"——若实现时顺手把它重置成"现在"，陈旧时长指标永远是 0，**监控就再也发现不了"我们在用过期权限"**。
> ② 反过来，**数据本身不能丢**：若 TTL 到点就把缓存丢弃、重载又失败，系统会因为"拿不到数据"而被动拒绝服务，**fail-open 根本无法实现**。
> **"数据要留住"与"必须如实记录它有多旧"必须同时成立**——详见 [02 文档 5.3.1](./02-总体设计说明书.md)。

### 6.6 Redis 故障

| 风险 | 广播通道失效，权限变更与令牌作废无法及时传播 |
|---|---|
| 对策 | ① 权限缓存与身份快照的 TTL（30s）兜底，最坏 30s 收敛（见 [01 文档 FR-A9](./01-需求规格说明书.md)）；② **登录与鉴权完全不受影响**（Redis 不在关键路径上）；③ 订阅重连成功后强制全量失效一次（断连期间的广播都丢了）；④ 监控订阅连接状态与断连次数 |

### 6.7 数据库抖动或故障

| 风险 | 缓存重建失败；写操作失败；**fail-open 下可能长时间使用已撤销的权限** |
|---|---|
| 对策 | ① 重建失败**继续用最后一份成功数据**放行（fail-open，见 [02 §5.3.2](./02-总体设计说明书.md)）；② **绝不伪造 `loadedAt`**，陈旧时长必须如实增长并告警；③ **已知状态变化的用户立即被拒绝**；④ 从未成功加载过缓存的新实例拒绝鉴权（503）；⑤ 写操作失败返回明确错误，前端可重试；⑥ 连接池超时 3s 快速失败，避免线程堆积；⑦ **数据库恢复后立即全量失效并重载**，把陈旧窗口关闭；⑧ 告警必须包含**缓存版本、陈旧时长、受影响用户数、用陈旧权限放行的请求数** |

> **这组策略是本项目明确的取舍**：选择 fail-open，是因为管理类后台常有连续作业需求，且数据库抖动的概率远高于"恰好在抖动窗口内有人撤销权限"。**但它的代价必须被管理，而不是被忽略**：可观测性、恢复后立即重载、故障期间撤销可追溯（审计日志与缓存无关，因此不会丢），三者缺一不可。
>
> **若将来合规要求提高**，把配置 `rbac.cache.stale-policy` 改为 `fail-closed` 即可收紧，**无需改动架构或代码**——这是刻意预留的运维开关。

### 6.8 多实例重启期间的令牌失效

| 风险 | 原设计的本地作废集合在实例重启后会**变空**，而重启期间发出的广播已丢失 → 旧令牌被重新接受（**"登出/停用"形同虚设**） |
|---|---|
| 对策 | 改为**身份快照 + 版本比对**：缓存为空时首个请求必然读库，拿到当前 `token_version`，旧令牌立即被拒。正确性**不再依赖消息是否送达**（见 [02 文档 5.3.3](./02-总体设计说明书.md)） |
| 验证方式 | 场景 S12：滚动重启全部实例，同时用旧令牌发起请求，**必须全部被拒** |

### 6.9 长连接数与文件描述符

| 风险 | 10k keep-alive 连接超过 `max-connections` 默认值（8,192），新连接被拒绝 |
|---|---|
| 对策 | ① `server.tomcat.max-connections=20000`；② `accept-count=500`（等待队列，过载时的缓冲）；③ `ulimit -n ≥ 65536`；④ `server.tomcat.connection-timeout` 配合 Nginx 的 keepalive 超时（建议 60s），避免连接长期占用 |

### 6.10 时间不同步

| 风险 | JWT 的签发/过期时间依赖时钟；实例间时钟漂移会导致令牌被误判为"尚未生效"或"已过期" |
|---|---|
| 对策 | 所有服务器启用 NTP 同步；令牌校验允许 60 秒的时钟偏移容忍 |

### 6.11 密钥轮换期间的多实例不一致

| 风险 | 轮换时若各实例支持的 `kid` 集合不同，会出现**随机 401**（同一个人时而能登录时而不能），且极难定位 |
|---|---|
| 对策 | ① 启动时校验实例间 `kid → 密钥` 映射一致，不一致**直接启动失败**；② 强制发布顺序（先全员支持新密钥，再切换签发）；③ 移除旧密钥前必须确认监控中已无该 `kid` 的验签记录（见 [02 文档 §5.1](./02-总体设计说明书.md)） |
| 验证方式 | 场景 S13 |

### 6.12 风险清单汇总

| # | 风险 | 影响 | 对策 | 验证方式 |
|---|---|---|---|---|
| 1 | GC 停顿 | P99 尖峰 | 小堆 + G1 + 限大对象 | 压测时观察 GC 日志 |
| 2 | 同步日志 | P99 尖峰 | 异步 Appender | 压测时对比开关日志的差异 |
| 3 | 审计同事务 | B 档变慢 | 低频可接受；批量分批 | 批量操作演练 |
| 4 | 慢接口占线程 | A 档整体劣化 | 独立线程池 + 超时 | 场景 S3 |
| 5 | 缓存雪崩 | DB 被击穿 | 惰性 + 单飞 + 原子替换 | 场景 S5 |
| 6 | Redis 故障 | 生效变慢（≤30s） | TTL 兜底 + 重连失效 | 场景 S6 |
| 7 | DB 抖动 | 重建失败 → 可能用陈旧权限 | **fail-open（继续放行）+ 绝不伪造 loadedAt + 强告警 + 恢复后立即重载** | 场景 S14（故障注入） |
| 8 | **实例重启后旧令牌可用** | **越权/停机失效形同虚设** | **身份快照（首位请求读库）** | **场景 S12** |
| 9 | 连接数不足 | 拒绝新连接 | 调高 max-connections + ulimit | 场景 S7 |
| 10 | 时钟漂移 | 令牌误判 | NTP + 容忍偏移 | 部署检查项 |
| 11 | 密钥轮换不一致 | 随机 401，难定位 | 启动校验 + 发布顺序 | 场景 S13 |
| 12 | 并发授权丢失更新 | **静默丢权限** | 乐观锁 + 行锁双防线 | 场景 S15 |

## 7. 压测方案

### 7.1 工具与环境

| 项 | 选择 | 理由 |
|---|---|---|
| 压测工具 | **JMeter**（或 Gatling / k6） | JMeter 图形化、团队上手快；**压测脚本必须进版本库**，否则无法复现 |
| 压测机 | 与被测系统同内网，独立机器 | 避免压测机本身成为瓶颈（需监控压测机 CPU） |
| 数据规模 | 1 万用户、200 角色、3,000 权限点、平均每用户 3 个角色 | 与容量假设（AS-1）一致 |
| 前置条件 | 缓存已预热（除非测试目标是冷启动） | 否则测的是缓存重建而非稳态性能 |
| 观测 | 应用 P99、Tomcat 忙碌线程数、CPU、GC 日志、DB 慢查询、缓存命中率、错误率、线程池队列 | **只看 P99 数字而不看内部指标，无法定位瓶颈** |

### 7.2 场景设计

| 场景 | 描述 | 目标 QPS | 通过标准 |
|---|---|---|---|
| **S1 鉴权稳态** | 持续调用 `/api/auth/me` 与轻量读接口，缓存全命中 | 2,000 | 服务器侧 P99 ≤ 30ms，错误率 < 0.1% |
| **S2 混合业务读** | 70% 简单读 + 30% 列表分页查询 | 2,000 | P99 ≤ 30ms，无慢 SQL（> 50ms 的查询为 0） |
| **S3 混合慢接口** | 95% 业务读 + 5% 登录（触发 BCrypt） | 2,100 | A 档接口 P99 **不劣化**（验证线程池隔离有效） |
| **S4 变更抖动** | 在 S1 压力下，**每秒触发一次权限变更广播** | 2,000 | P99 抬升 < 10ms；无请求因重建失败而报错 |
| **S5 冷启动/雪崩** | 清空全部实例缓存后立即加压 | 2,000 | 仅首个请求变慢（≤ 100ms），其余不受影响；DB QPS 不出现尖峰 |
| **S6 Redis 降级** | 压测中停掉 Redis | 2,000 | **P99 无变化**；权限变更在 30s 内生效；无错误 |
| **S7 长连接** | 维持 10,000 条 keep-alive 连接，同时 2,000 QPS | 2,000 | 无连接被拒；文件描述符与内存无异常增长 |
| **S8 峰值冲刺** | 1 分钟内从 0 拉到 4,000 QPS（2 倍冗余） | 4,000 | 无雪崩；可通过限流/排队平滑降级，错误率可控 |
| **S9 长时间稳定性** | S2 场景持续运行 8 小时 | 2,000 | 无内存泄漏（堆使用平稳）、P99 无随时间劣化 |
| **S10 推导峰值稳态** | S2 场景，按**推导峰值**加压 | **2,500** | P99 ≤ 30ms，错误率 < 0.1%（**这是正式验收场景，不是加测**） |
| **S11 峰值冲刺** | 1 分钟内从 0 拉到 4,000 QPS（2 倍设计目标） | 4,000 | 无雪崩；允许通过限流/排队平滑降级，**错误率可控且不出现 500** |
| **S12 重启期间令牌失效** | 滚动重启**全部**实例，同时用重启前签发的旧令牌（已登出/已改密）持续请求 | 2,000 | **全部返回 40101**，无任何旧令牌被放行（验证身份快照正确性） |
| **S13 密钥轮换** | 按 [02 文档 §5.1](./02-总体设计说明书.md) 的三阶段协议执行一次完整轮换，期间持续压测 | 2,000 | 轮换期间**无因 kid 不匹配导致的 401**；阶段 1、2 任意时刻可回滚 |
| **S14 数据库故障注入** | 压测中停掉数据库（先 10 秒短抖动，再延长到 10 分钟），同时用另一个线程执行权限撤销 | 2,000 | ① 鉴权**不中断**（fail-open），错误率 < 0.1%；② **陈旧时长指标如实增长**，不会被伪刷新为 0；③ 被撤销权限的用户在其快照重载失败时**被拒绝**；④ **数据库恢复后缓存立即全量重载**，陈旧时长归零；⑤ 陈旧时长与受影响用户数告警被正确触发 |
| **S15 并发授权（丢失更新）** | 两个线程用**同一个 `expectedVersion`** 同时提交覆盖式授权 | — | 恰好一个成功、一个返回 **40950**；**绝不出现"两个都成功且其中一个被静默覆盖"** |
| **S16 Redis 丢消息** | 停止实例的订阅连接（但不停止 Redis），执行权限变更后再恢复连接 | 2,000 | 恢复后强制全量失效；权限变更在 30s 内生效（TTL 兜底），**不会永久停留旧权限** |
| **S17 用户/审计查询索引** | 用目标数据量（1 万用户 / 30 万审计记录）执行 `EXPLAIN ANALYZE` | — | 见 [03 文档 §5.3](./03-数据模型设计.md) 的判定标准：命中预期索引、扫描行数量级正确、单次 ≤ 5ms（读）/ ≤ 20ms（审计） |
| **S18 备份恢复演练** | 从最近一次全量备份 + binlog 恢复到一台干净实例，并跑通登录与鉴权 | — | 实测恢复耗时**符合 [02 §7.2](./02-总体设计说明书.md) 的 RTO 承诺**；恢复后数据完整（RPO 达标）。**每季度至少一次** |

> **S4 是整个压测方案中最重要、也最容易被跳过的一项**。绝大多数团队只测"稳态压测"，而线上事故往往发生在"稳态 + 一次变更"的组合下（例如广播后所有实例同时重建，把数据库打爆）。**必须专门测它。**
>
> **S12、S14、S15 是本次评审新增的"安全闭环"场景**，它们验证的不是性能，而是**"系统在最坏情况下是否还在正确地拒绝"**。这三项不通过，意味着性能达标也没有意义。

### 7.3 压测与故障演练执行顺序

```
1. 单接口基准测试（找单请求耗时与 CPU 成本）
2. S1 → 确认鉴权链路达标
3. S2 → 确认业务查询不成为瓶颈（此步通常会暴露索引问题）
4. S5 → 确认缓存重建机制正确
5. S4 / S6 / S16 → 确认失效与 Redis 降级机制
6. S3 → 确认线程池隔离
7. S7 → 确认连接层
8. S8 / S10 / S11 → 确认过载保护与峰值容量
9. S9 → 长稳定性
10. S12 → 重启期间的令牌失效（安全闭环）
11. S14 → 数据库故障注入（安全闭环）
12. S15 → 并发授权（数据一致性闭环）
13. S13 → 密钥轮换（运维闭环）
14. S17 → 索引验证（数据库层闭环）
15. S18 → 备份恢复演练（**每季度重复执行**，验证 RTO/RPO 承诺）
```

**每一步都必须先通过，再进入下一步**。如果 S2 阶段 P99 超标，不要继续往下压测（S3 的结论会被污染），先解决慢 SQL。**第 10~12 步属于"功能正确性验证"，它们与性能无关，因此不受"性能未达标就暂停"的约束，应当并行推进。**

### 7.4 性能验收清单

| # | 验收项 | 标准 |
|---|---|---|
| 1 | A 档接口服务器侧 P99 | ≤ 30ms（**在 2,500 QPS 验收场景下测量**） |
| 2 | B 档接口服务器侧 P99 | ≤ 200ms |
| 3 | 鉴权链路自身耗时 | ≤ 1ms（用埋点单独测量，验证 2.2 的预算表）；**必须标明是预算值还是实测值** |
| 4 | 缓存命中率 | > 99.9% |
| 5 | 错误率 | < 0.1% |
| 6 | 应用 CPU 峰值 | < 60% |
| 7 | 应用堆使用 | 稳定，无持续增长（S9） |
| 8 | DB 慢查询（> 50ms） | 0 条 |
| 9 | DB 连接池等待超时次数 | 0 |
| 10 | GC 停顿 | P99 < 100ms，无 Full GC（S9 期间） |
| 11 | Redis 故障时 | A 档接口 P99 无劣化 |
| 12 | 权限变更生效时间 | ≤ 1s（Redis 正常）/ ≤ 30s（Redis 故障） |

## 8. 监控指标与告警

### 8.1 必须暴露的指标

| 类别 | 指标 | 用途 |
|---|---|---|
| 接口 | 每接口耗时分位图（P50/P95/P99） | 验收 30ms、定位劣化 |
| 接口 | 每接口 QPS、错误率（按 401/403/5xx 分类） | 容量与异常监测 |
| 鉴权 | **鉴权耗时直方图**（单独埋点，覆盖过滤器 + 缓存 + 判定） | 验证 2.2 预算表；一旦劣化立即发现 |
| 鉴权 | 403 次数（按权限码维度） | 权限配置错误或攻击探测的信号 |
| 缓存 | 命中率、重建次数、重建耗时、重建失败次数 | 缓存健康度 |
| **缓存（fail-open 下的唯一透明度来源，必须新增）** | **缓存版本号**（各实例是否一致）、**当前陈旧时长**（`now - loadedAt`）的当前值与分布、重载失败次数、**受影响的用户数**、**用陈旧权限放行的请求数**、身份快照未命中率 | **本设计采用 fail-open，意味着系统会在权限可能过期时继续服务。这套指标不是"最好有"，而是"没有就等于在盲飞"** |
| 缓存 | Redis 订阅连接状态、断连次数、广播去抖触发次数 | 失效通道健康度 |
| 连接 | Tomcat 忙碌线程数、当前连接数、排队请求数 | 线程池与连接层容量 |
| 连接池 | Hikari 活跃/空闲连接、等待获取连接耗时 | 数据库瓶颈的最早信号 |
| DB | 慢查询计数（> 50ms）、QPS | 索引退化 |
| JVM | GC 次数与停顿、堆使用、线程数 | P99 长尾的根因 |
| 安全 | 登录失败次数、账号锁定次数、**令牌作废次数（40101 计数）**、**无效 XFF 计数** | 安全监测；`40101` 突增意味着批量踢人或令牌滥用 |
| 日志 | 异步 Appender 队列长度、丢弃条数、**安全事件丢弃条数** | **丢弃条数 > 0 必须告警**（见 [01 文档 FR-L5](./01-需求规格说明书.md)） |

### 8.2 告警阈值建议

| 指标 | 警告 | 严重 |
|---|---|---|
| A 档接口 P99 | > 25ms 持续 5 分钟 | > 30ms 持续 5 分钟 |
| 鉴权链路 P99 | > 1ms 持续 5 分钟 | > 3ms 持续 5 分钟 |
| 缓存命中率 | < 99.5% | < 99% |
| 缓存重建失败 | ≥ 1 次 | ≥ 3 次/5 分钟 |
| **缓存当前陈旧时长** | **> 30s** | **> 5 分钟**（权限判断可能已明显偏离事实） |
| **用陈旧权限放行的请求数** | **> 0**（说明已在降级状态） | **持续增长**（说明数据库长时间不可用） |
| **缓存重载持续失败** | ≥ 1 次 | 持续 > 5 分钟（此时用户仍在被服务，**必须人工介入**） |
| **各实例缓存版本不一致** | **持续 > 60s** | **持续 > 300s**（失效通道可能已断） |
| Redis 订阅断连 | ≥ 1 次 | 持续断连 > 1 分钟 |
| 缓存重建耗时 | > 100ms | > 500ms |
| **40101（令牌作废）次数** | 相比基线 ×5 | 相比基线 ×20 |
| **无效 XFF 计数** | ≥ 1 次 | 持续增长（可能是探测或代理配置错误） |
| Tomcat 忙碌线程 | > 150 | > 190 |
| Hikari 等待连接耗时 | > 10ms | > 100ms |
| GC 停顿 | P99 > 100ms | 出现 Full GC |
| 日志丢弃条数 | > 0 | > 100/分钟 |
| 403 次数突增 | 相比基线 ×5 | 相比基线 ×20（可能是权限配置事故或攻击） |

> **为什么"403 次数突增"要告警？** 它有两个典型含义：① 某次权限配置改错了，导致一批用户失去访问能力（业务事故）；② 有人在批量探测接口权限（攻击行为）。**无论哪一种，都需要在 5 分钟内被人类看到。**
>
> **为什么"缓存陈旧时长"是本次新增的关键告警？** 因为它是**唯一能提前发现"我们正在用过期权限服务"的指标**。只看"重建失败次数"是不够的——失败之后系统仍在正常响应（沿用了旧值），表面看一切健康，而权限可能已经不对了。

## 9. 容量扩展路径（到什么时候该怎么扩）

| 阶段 | 触发条件 | 扩展动作 | 说明 |
|---|---|---|---|
| **当前设计** | 峰值 ≤ 2,000 QPS、用户 ≤ 1 万 | 3 × 4C8G + 1 × 8C16G MySQL + 1 × 1C2G Redis | 负载率 < 40%，余量充足 |
| **第 1 档** | 峰值 2,000 ~ 6,000 QPS | 应用实例加到 4~5 台（线性扩展） | 应用无状态，直接加机器；**不需要改任何代码** |
| **第 2 档** | 读 QPS > 2,000 且慢查询上升 | MySQL 加 1 个只读从库，把列表/审计查询路由到从库 | 注意主从延迟：写完立刻读的场景仍走主库 |
| **第 3 档** | 写操作量级上升 100 倍（如审计覆盖全业务域） | 审计改为异步 + 独立库/表分区 | 见 [01 文档 AS-2](./01-需求规格说明书.md) 与 [README ADR-09](./README.md) |
| **第 4 档** | 用户数 > 10 万 | **本地全量缓存方案开始吃力**：内存 > 300MB、重建耗时上升 | 此时应改为"本地缓存角色权限矩阵 + 用户角色关系分片缓存"或引入 Redis 二级缓存。**这是一个真实的架构拐点，届时必须重新设计并压测** |
| **第 5 档** | 需要服务多个组织 | **按租户独立部署**（ADR-02 的既定方案） | 不改造为共享库多租户 |

**关于第 4 档的诚实说明**："权限数据全量进内存"这个方案的有效边界是**用户数 10 万以内**。超过之后，用户-角色关系表的数据量与重建耗时会成为问题（重建一次可能需要数百毫秒，且单飞会让那一个请求明显变慢）。**这个边界已被记录在容量假设 AS-1 中**，不是隐藏风险。

## 10. 性能相关假设汇总

| 编号 | 假设 | 若不成立的影响 |
|---|---|---|
| PA-1 | 峰值 QPS ≈ 2,000（10k 在线 × 10 次/分钟 × 1.5 峰值系数） | QPS 每翻一倍，应用实例需线性增加。**推导峰值为 2,500，设计目标 2,000（含 25% 余量），验收场景按 2,500 执行** |
| PA-2 | 用户 ≤ 1 万（远期 5 万） | 超过 10 万需改变缓存架构（见第 9 节） |
| PA-3 | 平均响应体 ≤ 5KB | 带宽与序列化耗时按比例上升 |
| PA-4 | 应用、DB、Redis 同机房（内网延迟 < 0.5ms） | 跨机房需重新计算预算 |
| PA-5 | 单条业务查询 ≤ 5ms（索引命中） | 慢查询会直接击穿 P99 |
| PA-6 | BCrypt 强度 10（约 50~150ms） | 提高强度会线性增加登录耗时（不影响 A 档接口） |
| PA-7 | 权限变更频率 < 1 次/秒 | 高频变更会放大缓存重建次数，需评估重建成本 |
| PA-8 | 身份快照 TTL = 30 秒，活跃用户 ≤ 1 万 → 额外约 333 QPS 单行主键查询 | 调大 TTL 会同时改变 [01 文档 FR-A9 的时效承诺](./01-需求规格说明书.md)；**两者必须同步修改** |
| PA-9 | Redis 发布订阅**不保证投递**（实例重连、重启期间的消息会永久丢失） | 这是"必须有 TTL 兜底 + 身份快照必须能自愈"的根本原因。任何"只依赖广播"的设计都是错的 |
| PA-10 | 缓存重载失败时的姿态 = **fail-open**（继续用最后一份成功数据），且 **`loadedAt` 绝不伪刷新** | 这是"可用优先"的明确选择；若改为 fail-closed，需重新评估可用性目标与验收场景 S14。**无论哪种姿态，"陈旧时长可观测"都是硬要求** |
| PA-11 | 所有性能数字（微秒/毫秒）是**预算假设**，不是实现保证 | 只有压测实测结果可作为验收依据；汇报时必须标明来源 |
