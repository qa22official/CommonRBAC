# 06 · 性能与容量设计

相关文档：[00 基线](./00-编码代理工作基线.md) · [01 需求](./01-需求规格说明书.md) · [02 总体设计](./02-总体设计说明书.md) · [03 数据模型](./03-数据模型设计.md)

## 1. 负载口径

| 项 | 取值 |
|---|---|
| 并发在线用户 | 10,000 |
| 每用户操作频率 | 6~10 次/分钟（取上限 10） |
| 峰值系数 | 1.5 |
| 推导峰值 | 10,000 × 10 ÷ 60 × 1.5 ≈ 2,500 QPS |
| 设计目标（容量配置依据） | 2,000 QPS（在推导峰值上留 25% 余量；不是限流阈值） |
| 验收场景 | 2,500 QPS 稳态 + 4,000 QPS 冲刺 |

同时在处理的请求数（利特尔法则 L = λ × W）：

```text
L = 2,000 QPS × 0.03 秒 = 60 个并发请求
```

| 数字 | 含义 | 决定 |
|---|---|---|
| 10,000 | 保持的 TCP 连接数 | `max-connections`、文件描述符上限、连接缓冲区内存 |
| 60 | 同时占用的工作线程数 | Tomcat 线程池大小（200 线程已有 3 倍余量） |

连接数不等于线程数：NIO 连接器用少量线程管理大量空闲连接，只有处理请求时才占用工作线程。

## 2. 30ms 预算

### 2.1 验收口径

| 口径 | 定义 |
|---|---|
| 服务器侧 P99 ≤ 30ms（验收口径） | 应用收到请求到写出响应的时间，不含公网传输；压测在同内网测量 |
| 端到端参考值 | 服务器侧 + 传输（同城内网约 +2~4ms），仅作体验评估 |

### 2.2 A 档接口耗时预算

以下为预算假设，不是实现保证。验收以压测实测为准。

| 环节 | P50 | P99 |
|---|---|---|
| Tomcat 接收与构建请求 | 0.15ms | 0.4ms |
| JWT 解析与验签（HS256） | 0.02ms | 0.06ms |
| 身份快照校验（内存命中） | 0.001ms | 0.005ms |
| 权限解析（本地缓存命中） | 0.02ms | 0.1ms |
| 权限码比对 | 0.005ms | 0.02ms |
| 业务逻辑 + MyBatis 索引查询 | 1.5ms | 4ms |
| JSON 序列化 | 0.3ms | 1ms |
| 日志（异步 Appender） | 0.01ms | 0.05ms |
| 响应写出 | 0.1ms | 0.3ms |
| 合计 | 约 2.1ms | 约 6.0ms |

关键结论：

- 鉴权链路 P99 合计约 0.19ms，占 30ms 目标的 0.6%。
- 最大单项是业务数据库查询，优化重点在业务 SQL 的索引。
- P99 约为 P50 的 3 倍，差距来自数据库长尾；慢查询治理是保障 P99 的第一优先级。
- B 档接口增加 1~3ms（同步审计写入），P99 约 10ms，远低于 200ms 上限。

### 2.3 缓存未命中的额外开销

| 项 | 值 |
|---|---|
| 全量重建耗时 | 30~60ms（两张映射表约 4 万行） |
| 触发时机 | 权限变更后首个请求，或 TTL 到期后首个请求 |
| 影响范围 | 仅触发重建的那一个请求；其他请求继续用旧缓存（单飞） |

实现要求：先加载新数据再原子替换缓存引用，不得"先清空再加载"。否则清空窗口内的请求会同时穿透到数据库。

### 2.4 登录接口例外

BCrypt 校验耗时 50~150ms，属故意设计。登录接口不受 30ms 约束，必须使用独立线程池隔离。

## 3. 容量参数

### 3.1 应用实例

| 项 | 值 |
|---|---|
| 单请求 CPU 时间（不含 DB 等待） | 约 0.5ms |
| 单实例理论上限 | 4 vCPU × 70% ÷ 0.0005s ≈ 5,600 QPS |
| 单实例保守容量 | 约 1,800 QPS（安全系数取 1/3） |
| 部署数量 | 3（性能上 2 台足够；第 3 台用于单机故障与滚动发布） |
| 峰值负载率 | 2,000 ÷ (3 × 1,800) ≈ 37% |

### 3.2 内存

| 项 | 值 |
|---|---|
| 权限与身份缓存 | 初期 < 10MB，远期 < 30MB |
| Caffeine 结构与淘汰开销 | 缓存数据的 30~50% |
| 线程栈 | 约 250 线程，`-Xss512k` 时约 128MB |
| 元空间、编译缓存、Direct Buffer | 约 500MB（NIO 连接缓冲 10k × 8KB ≈ 80MB） |
| 堆配置 | 3~4GB |

### 3.3 数据库连接池

| 项 | 值 |
|---|---|
| `maximumPoolSize` | 20（4 vCPU；单连接在 2ms 查询下每秒可完成 500 次） |
| `minimumIdle` | 5 |
| `connectionTimeout` | 3,000ms |
| 3 实例总连接数 | 60 |
| MySQL `max_connections` | 建议 300 |

连接数应与 CPU 核心数同量级，不与并发请求数同量级。

### 3.4 数据库

| 指标 | 值 |
|---|---|
| 读 QPS | < 1,100（业务查询约 600 + 身份快照约 333） |
| 写 QPS | < 1（RBAC 配置操作 + 业务白名单审计，人工触发） |
| 单机能力 | 简单索引查询 3,000~5,000 QPS |
| 数据量 | 业务表 < 20 万行；审计表 180 天 50~150 万行 |
| 结论 | 单主 8C16G + SSD 足够；不加从库、不分库分表 |

身份快照额外读负载：10,000 活跃用户 ÷ 30 秒 TTL ≈ 333 QPS 的单行主键查询。调整 TTL 必须同步修改 01 文档 FR-A9 的时效承诺，两者一一对应。

读从库的触发条件：读 QPS 超过 2,000 且慢查询占比上升。

### 3.5 Redis

| 指标 | 值 |
|---|---|
| 用途 | 失效广播 + 登录限流计数；不存业务数据，不做数据缓存 |
| 发布消息量 | 每天几次到几百次，QPS ≈ 0.01 |
| 订阅连接数 | 每实例 1 条 |
| 内存占用 | < 10MB |
| 结论 | 1C2G 单实例足够；不使用哨兵或集群 |

### 3.6 网络与文件描述符

| 项 | 值 |
|---|---|
| 应用→客户端带宽 | 2,000 QPS × 5KB ≈ 10MB/s ≈ 80Mbps |
| 审计磁盘增长 | 每天数 MB，180 天 < 1GB |
| `ulimit -n` | ≥ 65,536 |

### 3.7 容量汇总

| 组件 | 规格 | 数量 | 峰值负载率 |
|---|---|---|---|
| Nginx | 2C4G | 1 | < 5% |
| 应用 | 4C8G（堆 3~4G） | 3 | CPU < 20%，内存 < 50% |
| MySQL | 8C16G + SSD | 1 | CPU < 30%，连接 60/300 |
| Redis | 1C2G | 1 | 内存 < 5% |

## 4. 禁止的三种做法

| 做法 | 禁止原因 |
|---|---|
| WebFlux / 响应式 | 同时处理的请求只有 60 个；10k 空闲连接由 NIO 处理不占工作线程。引入会带来调试困难与 ThreadLocal 语义变化，收益为负 |
| 虚拟线程 | 会失去线程池提供的背压保护（过载时同时压垮数据库） |
| 用 Redis 做集中式权限缓存 | 会把已消除的一次网络往返重新加回鉴权链路，并使 Redis 成为关键路径 |

## 5. P99 风险点与对策

| 风险 | 对策 | 验证 |
|---|---|---|
| GC 停顿 | 堆设 3~4GB；G1，`MaxGCPauseMillis=100`；限制大对象（分页 size ≤ 200，导出走流式） | 压测观察 GC 日志 |
| 同步日志写盘 | 异步 Appender + 有界队列，不丢弃 WARN/ERROR，丢弃需计数告警 | 对比开关日志的差异 |
| 审计在业务事务内同步写入 | 低频可接受；批量操作分批提交（每 200 条一事务）；导出类归例外档 | 批量演练 + 导出接口基线 |
| 慢接口占满线程池 | 登录用独立线程池（20 线程）；导出与批量用独立线程池并限并发（5）；设置请求级超时 | S3 |
| 缓存雪崩 | 惰性重建 + 单飞 + 先加载后原子替换；广播去抖 | S5 |
| Redis 故障 | TTL 兜底，最坏 30 秒收敛；重连后强制全量失效 | S6、S16 |
| 数据库抖动 | 沿用旧值且不刷新 loadedAt；已变更状态用户立即拒绝；恢复后立即全量重载 | S14 |
| 实例重启期间旧令牌可用 | 身份快照：缓存为空时首个请求必须读库 | S12 |
| 长连接数超过 `max-connections` | `max-connections=20000`，`accept-count=500`，`ulimit -n ≥ 65536` | S7 |
| 时钟漂移 | NTP 同步；令牌校验允许 60 秒偏移 | 部署检查 |
| 密钥轮换期间多实例不一致 | 启动时校验 kid 映射一致，不一致则启动失败；强制发布顺序 | S13 |
| 并发授权丢失更新 | 乐观锁 + 行锁双防线 | S15 |

## 6. 压测场景

工具：JMeter 或 Gatling；压测脚本必须进版本库。压测机与被测系统同内网、独立机器。

数据规模：1 万用户、200 角色、3,000 权限点、平均每用户 3 个角色。除冷启动场景外，缓存需预热。

| 场景 | 描述 | 目标 QPS | 通过标准 |
|---|---|---|---|
| S1 | 持续调用 `/api/auth/me` 与轻量读接口，缓存全命中 | 2,000 | P99 ≤ 30ms，错误率 < 0.1% |
| S2 | 70% 简单读 + 30% 列表分页查询 | 2,000 | P99 ≤ 30ms，无 > 50ms 的 SQL |
| S3 | 95% 业务读 + 5% 登录 | 2,100 | A 档接口 P99 不劣化 |
| S4 | S1 压力下每秒触发一次权限变更广播 | 2,000 | P99 抬升 < 10ms，无重建失败导致的报错 |
| S5 | 清空全部实例缓存后立即加压 | 2,000 | 仅首个请求变慢（≤ 100ms），DB QPS 无尖峰 |
| S6 | 压测中停掉 Redis | 2,000 | P99 无变化；权限变更 30 秒内生效 |
| S7 | 维持 10,000 条 keep-alive 连接并加压 | 2,000 | 无连接被拒，内存与文件描述符无异常增长 |
| S8 | 一分钟内从 0 拉到 4,000 QPS | 4,000 | 无雪崩，可通过限流平滑降级，不出现 500 |
| S9 | S2 持续 8 小时 | 2,000 | 无内存泄漏，P99 无随时间劣化 |
| S10 | 按推导峰值加压 | 2,500 | P99 ≤ 30ms，错误率 < 0.1%（正式验收场景） |
| S11 | 一分钟内拉到 4,000 QPS | 4,000 | 无雪崩，错误率可控且无 500 |
| S12 | 滚动重启全部实例，同时用已作废令牌持续请求 | 2,000 | 全部返回 40101 |
| S13 | 执行完整密钥轮换（三阶段），持续压测 | 2,000 | 无因 kid 不匹配导致的 401；阶段 1、2 可回滚 |
| S14 | 停掉数据库（先 10 秒后延长至 10 分钟），同时执行权限撤销 | 2,000 | 鉴权不中断；陈旧时长如实增长；被撤销用户被拒；恢复后立即重载并归零；告警触发 |
| S15 | 两个线程用同一 `expectedVersion` 同时提交覆盖式授权 | — | 一个成功、一个返回 40950；无静默覆盖 |
| S16 | 断开实例订阅连接（Redis 本身正常），执行变更后恢复 | 2,000 | 恢复后强制全量失效；变更 30 秒内生效，不停留在旧权限 |
| S17 | 用目标数据量执行 `EXPLAIN ANALYZE` | — | 命中预期索引；单次 ≤ 5ms（读）/ ≤ 20ms（审计） |
| S18 | 从全量备份 + binlog 恢复到干净实例并跑通登录鉴权 | — | 实测恢复耗时符合 02 文档 RTO 承诺；数据完整。每季度执行一次 |

执行顺序：

```text
1. 单接口基准
2. S1 → 鉴权链路
3. S2 → 业务查询与索引
4. S5 → 缓存重建
5. S4 / S6 / S16 → 失效与 Redis 降级
6. S3 → 线程池隔离
7. S7 → 连接层
8. S8 / S10 / S11 → 过载与峰值
9. S9 → 长稳定性
10. S12 → 重启期间令牌失效
11. S14 → 数据库故障注入
12. S15 → 并发授权
13. S13 → 密钥轮换
14. S17 → 索引验证
15. S18 → 备份恢复演练（每季度）
```

前一步不通过不进入下一步。S12、S14、S15 属正确性验证，与性能无关，可并行推进。

## 7. 验收清单

| 项 | 标准 |
|---|---|
| A 档接口服务器侧 P99 | ≤ 30ms（在 2,500 QPS 场景下测量） |
| B 档接口服务器侧 P99 | ≤ 200ms |
| 鉴权链路自身耗时 | ≤ 1ms（单独埋点；标注是预算值还是实测值） |
| 缓存命中率 | > 99.9% |
| 错误率 | < 0.1% |
| 应用 CPU 峰值 | < 60% |
| 应用堆使用 | 稳定，无持续增长 |
| DB 慢查询（> 50ms） | 0 条 |
| DB 连接池等待超时 | 0 次 |
| GC 停顿 | P99 < 100ms，无 Full GC |
| Redis 故障时 A 档接口 | P99 无劣化 |
| 权限变更生效时间 | ≤ 1 秒（Redis 正常）/ ≤ 30 秒（Redis 故障） |

## 8. 监控与告警

### 8.1 必须暴露的指标

| 类别 | 指标 |
|---|---|
| 接口 | 每接口耗时分位图、QPS、错误率（按 401/403/5xx 分类） |
| 鉴权 | 鉴权耗时直方图（单独埋点）；403 次数（按权限码维度） |
| 缓存 | 命中率、重建次数与耗时、重建失败次数 |
| 缓存（关键） | 缓存版本号一致性、当前陈旧时长分布、受影响用户数、用陈旧权限放行的请求数、身份快照未命中率 |
| 失效通道 | Redis 订阅连接状态、断连次数、广播去抖触发次数 |
| 连接 | Tomcat 忙碌线程数、当前连接数、排队请求数 |
| 连接池 | Hikari 活跃与空闲连接、等待获取连接耗时 |
| 数据库 | 慢查询计数（> 50ms）、QPS |
| JVM | GC 次数与停顿、堆使用、线程数 |
| 安全 | 登录失败次数、账号锁定次数、40101 计数、无效 XFF 计数 |
| 日志 | 异步 Appender 队列长度、丢弃条数、安全事件丢弃条数 |

失败模式下的可观测性是硬要求：本设计采用 fail-open，若缺少陈旧时长与放行请求数指标，将无法判断是否正在使用过期权限。

### 8.2 告警阈值

| 指标 | 警告 | 严重 |
|---|---|---|
| A 档接口 P99 | > 25ms 持续 5 分钟 | > 30ms 持续 5 分钟 |
| 鉴权链路 P99 | > 1ms 持续 5 分钟 | > 3ms 持续 5 分钟 |
| 缓存命中率 | < 99.5% | < 99% |
| 缓存重建失败 | ≥ 1 次 | ≥ 3 次 / 5 分钟 |
| 缓存当前陈旧时长 | > 30 秒 | > 5 分钟 |
| 用陈旧权限放行的请求数 | > 0 | 持续增长 |
| 缓存重载持续失败 | ≥ 1 次 | 持续 > 5 分钟 |
| 各实例缓存版本不一致 | 持续 > 60 秒 | 持续 > 300 秒 |
| Redis 订阅断连 | ≥ 1 次 | 持续 > 1 分钟 |
| 缓存重建耗时 | > 100ms | > 500ms |
| 40101 次数 | 相比基线 ×5 | 相比基线 ×20 |
| 无效 XFF 计数 | ≥ 1 次 | 持续增长 |
| 403 次数 | 相比基线 ×5 | 相比基线 ×20 |
| Tomcat 忙碌线程 | > 150 | > 190 |
| Hikari 等待连接耗时 | > 10ms | > 100ms |
| GC 停顿 | P99 > 100ms | 出现 Full GC |
| 日志丢弃条数 | > 0 | > 100/分钟 |

403 突增有两种含义：权限配置错误导致一批用户失去访问能力，或有人在批量探测接口权限。两者都需要在 5 分钟内被人工确认。

## 9. 扩展路径

| 阶段 | 触发条件 | 动作 |
|---|---|---|
| 当前 | 峰值 ≤ 2,000 QPS、用户 ≤ 1 万 | 3 × 4C8G + 8C16G MySQL + 1C2G Redis |
| 1 | 峰值 2,000 ~ 6,000 QPS | 应用实例加到 4~5 台 |
| 2 | 读 QPS > 2,000 且慢查询上升 | MySQL 加只读从库，列表与审计查询路由到从库 |
| 3 | 写量级上升 100 倍（审计扩到全业务域） | 审计改异步 + 独立存储或分区 |
| 4 | 用户数 > 10 万 | 改为角色权限矩阵本地缓存 + 用户角色关系分片缓存，或引入二级缓存 |
| 5 | 需要服务多个组织 | 按租户独立部署 |

## 10. 假设

| 编号 | 假设 | 不成立时的影响 |
|---|---|---|
| PA-1 | 峰值约 2,000 QPS（推导 2,500，验收按 2,500 执行） | QPS 每翻一倍，应用实例需线性增加 |
| PA-2 | 用户 ≤ 1 万（远期 5 万） | 超过 10 万需改变缓存架构 |
| PA-3 | 平均响应体 ≤ 5KB | 带宽与序列化耗时按比例上升 |
| PA-4 | 应用、数据库、Redis 同机房（内网延迟 < 0.5ms） | 跨机房需重算预算 |
| PA-5 | 单条业务查询 ≤ 5ms | 慢查询直接击穿 P99 |
| PA-6 | BCrypt 强度 10（50~150ms） | 提高强度会线性增加登录耗时 |
| PA-7 | 权限变更频率 < 1 次/秒 | 高频变更放大重建次数 |
| PA-8 | 身份快照 TTL = 30 秒 → 约 333 QPS 额外主键查询 | 调大 TTL 会改变 01 文档 FR-A9 的时效承诺，必须同步修改 |
| PA-9 | Redis Pub/Sub 不保证投递 | 这是必须有 TTL 兜底与身份快照自愈的原因 |
| PA-10 | 重载失败策略为 fail-open | 改为 fail-closed 需重估可用性目标与 S14 |
| PA-11 | 文中毫秒与微秒数字均为预算假设 | 只有压测实测结果可作为验收依据 |
