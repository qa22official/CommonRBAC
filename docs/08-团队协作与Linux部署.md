# 08 · 团队协作与 Linux 部署

> 目标：规定任务如何分配、代码如何合并、成果如何部署到 Linux 服务器。
> 适用对象：项目负责人、后端、前端、数据库/测试和运维成员。

## 1. 最简单的协作流程

```text
负责人写任务
→ 成员领取任务
→ 新建自己的分支
→ 编码并在本地测试
→ 提交代码并推送分支
→ 发起 PR/MR，检查通过
→ 合并到 develop
→ 测试环境验证
→ 合并到 main
→ 发布到生产服务器
```

这里的几个词：

- **分支**：每个人自己的代码副本，避免多人同时改乱同一份代码；
- **PR/MR**：请求把自己的代码合并进去，并让队友先检查；
- **develop**：测试版本；
- **main**：准备发布的正式版本；
- **CI**：服务器自动编译和运行测试，不需要成员手工操作。

所有成员只需要记住四条规则：

1. 不直接修改 `main` 和 `develop`；
2. 一个任务建立一个分支；
3. 代码合并前必须经过自动检查和至少一名队友检查；
4. 生产服务器只运行已经批准的版本，不运行个人电脑上的代码。

## 2. 任务分配

### 2.1 角色分工

| 角色 | 主要职责 | 不负责的事项 |
|---|---|---|
| 项目负责人 | 把大需求拆成小任务、分配任务、确认结果 | 不跳过检查直接发布 |
| 后端成员 | 编写接口和业务代码，并补充测试 | 不直接修改别人负责的模块 |
| 前端成员 | 编写页面、调用接口、处理页面权限 | 不把页面隐藏当成真正的安全控制 |
| 测试/数据库成员 | 准备测试、检查数据表和迁移脚本 | 不在生产服务器手工改表 |
| 发布负责人 | 执行测试环境和生产环境发布、回滚 | 不发布未经批准的代码 |

小团队中可以一人承担多个角色，但写代码的人最好不要独自批准自己的生产发布。

### 2.2 按交付物拆任务

推荐按以下顺序推进：

| 顺序 | 任务 | 负责人 |
|---|---|---|
| 1 | 建立项目骨架、数据库表和基础配置 | 后端/数据库成员 |
| 2 | 实现登录、JWT 和身份校验 | 后端成员 |
| 3 | 实现用户、角色、权限和授权接口 | 后端成员 |
| 4 | 实现权限缓存、越权拦截和审计 | 后端成员 |
| 5 | 实现登录页、用户页、角色页和权限页 | 前端成员 |
| 6 | 编写单元测试、接口测试和越权测试 | 测试成员 |
| 7 | 配置 Docker、CI 和 Linux 测试环境 | 发布负责人 |

### 2.3 任务卡片模板

每个任务在 GitHub Issue 中只需先填写：

```text
任务标题：
负责人：
修改范围：
完成标准：
```

## 3. Git 分支和提交规则

### 3.1 分支

```text
main                    正式版本
develop                 测试版本
feature/<issue>-<name>  新功能或普通修改
fix/<issue>-<name>      修复问题
```

新成员只需要使用 `feature` 或 `fix` 分支。创建示例：

```bash
git switch develop
git pull
git switch -c feature/12-user-list
```

规则：

- `main` 和 `develop` 不允许直接推送；
- 不提交密码、私钥、JWT 密钥、生产配置和数据库备份；
- 一个分支尽量只完成一个任务；
- 任务完成后及时合并，不要长期保留个人分支。

### 3.2 提交和推送

提交信息使用“做了什么”的简单描述即可：

```text
feat: add user list
fix: correct permission check
test: add login test
```

常用命令：

```bash
git add .
git commit -m "feat: add user list"
git push -u origin feature/12-user-list
```

如果修改了数据库、接口或配置，要在提交说明和 PR/MR 中特别写出来。

## 4. Pull Request / Merge Request 要求

发起 PR/MR 时填写：

- 关联 Issue；
- 改了什么；
- 如何测试；
- 是否改了数据库、接口或配置；
- 前端任务附截图或接口示例。

队友只需重点检查：

1. 能否编译和测试；
2. 是否实现了任务要求；
3. 是否可能绕过权限；
4. 是否泄露密码、令牌或其他敏感信息；
5. 是否补充了必要测试；
6. 是否需要同步修改设计文档。

## 5. CI/CD 流程

### 5.1 CI 做什么

CI 是代码托管平台上的自动检查机器人：

| 操作 | CI 做什么 | 结果 |
|---|---|---|
| 推送个人分支 | 编译和运行基础测试 | 发现问题就修改 |
| 发起 PR/MR | 运行完整检查 | 通过后才能合并 |
| 合并 `develop` | 构建版本并部署测试环境 | 团队测试 |
| 合并 `main` 或发布版本 | 构建正式版本 | 等待负责人批准生产发布 |

成员不需要手工登录 CI 服务器。只要检查结果失败，就打开日志，根据错误修改代码后重新推送。

### 5.2 CI 必须执行的检查

```text
后端：
  mvn -B verify
  权限注解覆盖检查（确认需要保护的接口都配置了权限）
  ArchUnit（检查模块之间是否越界调用）
  单元测试
  集成测试

前端：
  npm ci
  npm run lint
  npm run type-check（检查 TypeScript 类型）
  npm run build

发布前：
  镜像漏洞扫描（检查依赖和镜像是否有已知漏洞）
  Flyway 校验（检查数据库变更脚本）
  配置项检查（确认服务器需要的配置都已提供）
  SQL EXPLAIN 验证（确认查询使用了索引）
```

具体命令以项目实际 `pom.xml`、`package.json` 和 CI 配置为准；没有对应脚本时应先补脚本，不要在 CI 中写无法本地复现的特殊命令。

### 5.3 制品规则

- 镜像使用不可变标签，例如 `20261012-abc1234`；
- 禁止生产使用 `latest`；
- 镜像仓库只允许 CI 写入；
- 生产服务器只允许拉取已批准的版本；
- 发布记录保存：版本、commit、构建编号、迁移版本、发布人、发布时间；
- 保留当前版本和上一稳定版本。

## 6. Linux 服务器准备

以下以 Ubuntu 22.04/24.04 或同类发行版为例。

### 6.1 服务器分层

推荐至少区分：

```text
开发环境：成员本地或共享开发机
测试环境：用于 develop 自动部署
生产环境：只接受批准版本
```

如果只有一台 Linux 服务器，至少使用不同目录、不同 Compose project 和不同数据库：

```text
/opt/rbac/test/
/opt/rbac/prod/
/opt/rbac/backups/
/var/log/rbac/
```

不建议在同一台服务器上同时运行测试库和生产库而不做隔离。

### 6.2 服务器账号和权限

创建专用发布账号：

```text
deploy     负责拉取镜像、执行发布脚本
rbac       负责应用进程或容器运行
```

要求：

- 禁止 CI 使用 root 登录；
- 禁止把 SSH 私钥写入仓库；
- CI 使用专用部署密钥，只允许登录部署账号；
- `sudo` 只开放必要命令；
- SSH 只允许密钥登录；
- 关闭密码登录和 root 远程登录；
- 防火墙只开放 80/443 和必要的运维入口；
- MySQL、Redis 不直接暴露公网；
- 生产配置只放在服务器受限目录或密钥管理系统。

### 6.3 服务器目录

```text
/opt/rbac/
├── prod/
│   ├── compose.yml
│   ├── .env                 # 不进入 Git
│   ├── releases/
│   │   ├── 20261012-abc1234/
│   │   └── 20261010-def5678/
│   ├── current -> releases/20261012-abc1234
│   └── scripts/
├── test/
└── backups/
```

`.env` 至少包含：

```text
MYSQL_PASSWORD
REDIS_PASSWORD
JWT_ACTIVE_KEY
JWT_PREVIOUS_KEY
JWT_ACTIVE_KID
```

密钥不得通过命令行参数传递，避免出现在进程列表和 CI 日志中。

## 7. Docker Compose 部署

### 7.1 服务边界

生产 Compose 至少包含：

```text
nginx
rbac-app
mysql
redis
```

如果数据库和 Redis 使用外部托管服务，则从 Compose 中移除对应服务，只保留连接配置。

### 7.2 发布步骤

生产发布必须由 CI 或发布负责人执行：

```text
1. 选择已通过 CI 的不可变版本；
2. 检查当前版本、数据库连接和磁盘空间；
3. 备份数据库并记录备份位置；
4. 拉取指定版本镜像；
5. 运行 Flyway 迁移；
6. 启动或滚动更新应用；
7. 执行健康检查；
8. 执行登录、鉴权、数据库和 Redis 基础烟囱测试；
9. 观察错误率、响应时间、缓存重载和审计指标；
10. 发布成功后保留上一版本。
```

### 7.3 健康检查

健康检查至少包括：

- 进程存活；
- 应用 readiness；
- MySQL 连接；
- Redis 连接或降级状态；
- Flyway 版本；
- JWT 密钥配置；
- 当前构建版本；
- 权限缓存加载状态。

健康检查接口不得泄露数据库地址、密钥、堆栈和内部详细信息。

## 8. 回滚

### 8.1 应用回滚

应用回滚优先切换到上一稳定镜像，不重新构建：

```text
1. 停止发布流程；
2. 记录失败版本和错误；
3. 切换 Compose 使用上一稳定镜像；
4. 重启或滚动更新；
5. 执行健康检查和核心烟囱测试；
6. 标记失败版本，禁止再次自动发布；
7. 创建缺陷任务。
```

### 8.2 数据库回滚

Flyway 社区版不自动回滚。数据库变更必须遵守：

- 优先使用向后兼容的“加表、加列、加索引”；
- 删除或改语义前先经过独立评审；
- 每个迁移脚本配套回滚方案；
- 应用回滚前确认旧版本可以读取新结构；
- 不在生产直接执行未经评审的 SQL；
- 破坏性变更采用“扩展 → 双写/迁移 → 切换 → 清理”多阶段发布。

### 8.3 失败判定

出现以下任一情况，发布失败：

- 数据库迁移失败；
- readiness 不通过；
- 核心登录或鉴权失败；
- 错误率超过发布阈值；
- P99 明显超过当前验收目标；
- 审计写入失败；
- 权限缓存无法加载且没有可用快照；
- 发现敏感配置进入日志。

## 9. 发布记录和责任边界

每次发布保存：

```text
版本号：
Git commit：
CI 构建编号：
数据库迁移版本：
发布人：
审批人：
发布时间：
发布环境：
健康检查结果：
监控观察窗口：
是否回滚：
回滚原因：
```

责任边界：

- 任务负责人保证功能和测试；
- 评审人保证设计和代码质量；
- 测试负责人保证验收证据；
- 发布负责人保证制品、配置、发布和回滚；
- 项目负责人批准生产发布。
