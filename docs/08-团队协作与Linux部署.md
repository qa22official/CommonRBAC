# 08 · 团队协作与 Linux 部署

## 1. 协作流程

```text
负责人写任务 → 成员领取 → 新建分支 → 编码并本地测试
→ 推送分支 → 发起 PR/MR 并通过检查 → 合并 develop → 测试环境验证
→ 合并 main → 发布生产
```

四条硬规则：

1. 不直接修改 `main` 与 `develop`
2. 一个任务一个分支
3. 合并前必须通过自动检查与至少一名队友检查
4. 生产只运行已批准的版本

## 2. 任务分配

| 角色 | 职责 | 禁止 |
|---|---|---|
| 项目负责人 | 拆解任务、分配、确认结果 | 跳过检查直接发布 |
| 后端成员 | 接口与业务代码 + 测试 | 直接修改他人负责的模块 |
| 前端成员 | 页面、接口调用、页面权限 | 把页面隐藏当成安全控制 |
| 测试/数据库成员 | 准备测试、检查表结构与迁移脚本 | 在生产手工改表 |
| 发布负责人 | 执行测试与生产发布、回滚 | 发布未批准代码 |

一人可兼任多角色，但不得独自批准自己的生产发布。

按交付物推进顺序：

| 顺序 | 任务 |
|---|---|
| 1 | 项目骨架、数据库表、基础配置 |
| 2 | 登录、JWT、身份校验 |
| 3 | 用户、角色、权限、授权接口 |
| 4 | 权限缓存、越权拦截、审计 |
| 5 | 登录页、用户页、角色页、权限页 |
| 6 | 单元测试、接口测试、越权测试 |
| 7 | Docker、CI、Linux 测试环境 |

任务卡片字段：任务标题、负责人、修改范围、完成标准。

## 3. 分支与提交

```text
main                    正式版本
develop                 测试版本
feature/<issue>-<name>  新功能
fix/<issue>-<name>      修复
```

```bash
git switch develop
git pull
git switch -c feature/12-user-list
```

规则：

- `main` 与 `develop` 不允许直接推送
- 不提交密码、私钥、JWT 密钥、生产配置、数据库备份
- 一个分支只完成一个任务；完成后及时合并

提交信息格式：

```text
feat: add user list
fix: correct permission check
test: add login test
```

修改了数据库、接口或配置时，必须在提交说明与 PR/MR 中写明。

## 4. PR/MR 要求

发起时填写：关联 Issue、改动内容、测试方式、是否改数据库/接口/配置；前端任务附截图或接口示例。

评审重点：

1. 能否编译与测试通过
2. 是否实现任务要求
3. 是否可能绕过权限
4. 是否泄露密码、令牌或敏感信息
5. 是否补充必要测试
6. 是否需要同步修改设计文档

## 5. CI/CD

| 触发 | 动作 |
|---|---|
| 推送个人分支 | 编译 + 基础测试 |
| 发起 PR/MR | 完整检查，通过后才能合并 |
| 合并 `develop` | 构建并部署测试环境 |
| 合并 `main` 或发布 | 构建正式版本，等待负责人批准生产发布 |

必须执行的检查：

```text
后端：
  mvn -B verify
  权限注解覆盖检查
  权限码定义一致性检查
  业务接口审计声明检查（敏感关键词接口必须调用 AuditRecorder 或标注 @NoAudit）
  ArchUnit（模块依赖规则，含业务模块只依赖 rbac-api）
  单元测试
  集成测试

前端：
  npm ci
  npm run lint
  npm run type-check
  npm run build

发布前：
  镜像漏洞扫描
  Flyway 校验
  配置项检查
  SQL EXPLAIN 验证
```

命令以项目实际配置为准；缺少脚本时先补脚本，不在 CI 中写无法本地复现的命令。

制品规则：

- 镜像使用不可变标签，如 `20261012-abc1234`
- 生产禁止使用 `latest`
- 镜像仓库只允许 CI 写入
- 生产只允许拉取已批准版本
- 保留当前版本与上一稳定版本

## 6. 服务器准备

环境分层：开发（本地或共享开发机）、测试（develop 自动部署）、生产（只接受批准版本）。

单台服务器时必须使用不同目录、不同 Compose project 与不同数据库：

```text
/opt/rbac/test/
/opt/rbac/prod/
/opt/rbac/backups/
/var/log/rbac/
```

账号：

| 账号 | 用途 |
|---|---|
| deploy | 拉取镜像、执行发布脚本 |
| rbac | 运行应用进程或容器 |

安全要求：

- CI 不得使用 root 登录；不得把 SSH 私钥写入仓库
- CI 使用专用部署密钥，只允许登录部署账号
- `sudo` 只开放必要命令
- SSH 只允许密钥登录，关闭密码登录与 root 远程登录
- 防火墙只开放 80/443 与必要运维入口
- MySQL、Redis 不直接暴露公网
- 生产配置只放在服务器受限目录或密钥管理系统

目录结构：

```text
/opt/rbac/
├── prod/
│   ├── compose.yml
│   ├── .env                 # 不进入 Git
│   ├── releases/
│   │   ├── 20261012-abc1234/
│   │   └── 20261010-def5678/
│   ├── current -> releases/20261012-abc1234
│   └── scripts/
├── test/
└── backups/
```

`.env` 至少包含：

```text
MYSQL_PASSWORD
REDIS_PASSWORD
JWT_ACTIVE_KEY
JWT_PREVIOUS_KEY
JWT_ACTIVE_KID
```

密钥不得通过命令行参数传递（会出现在进程列表与 CI 日志中）。

## 7. 部署

生产 Compose 至少包含 `nginx`、`rbac-app`、`mysql`、`redis`。使用外部托管数据库或 Redis 时，从 Compose 移除对应服务，只保留连接配置。

发布步骤：

```text
1. 选择已通过 CI 的不可变版本
2. 检查当前版本、数据库连接、磁盘空间
3. 备份数据库并记录备份位置
4. 拉取指定版本镜像
5. 运行 Flyway 迁移
6. 启动或滚动更新应用
7. 执行健康检查
8. 执行登录、鉴权、数据库、Redis 的烟测
9. 观察错误率、响应时间、缓存重载与审计指标
10. 保留上一版本
```

健康检查项：进程存活、readiness、MySQL 连接、Redis 连接或降级状态、Flyway 版本、JWT 密钥配置、当前构建版本、权限缓存加载状态。

健康检查接口不得泄露数据库地址、密钥、堆栈与内部细节。

## 8. 回滚

应用回滚优先切换上一稳定镜像，不重新构建：

```text
1. 停止发布流程
2. 记录失败版本与错误
3. 切换 Compose 使用上一稳定镜像
4. 重启或滚动更新
5. 执行健康检查与烟测
6. 标记失败版本，禁止再次自动发布
7. 创建缺陷任务
```

数据库回滚（Flyway 社区版不自动回滚）：

- 优先使用向后兼容的加表、加列、加索引
- 删除或改语义前必须单独评审
- 每个迁移脚本配套回滚方案
- 应用回滚前确认旧版本能读取新结构
- 不在生产直接执行未经评审的 SQL
- 破坏性变更采用"扩展 → 双写或迁移 → 切换 → 清理"多阶段发布

发布失败判定（出现任一即失败）：

- 数据库迁移失败
- readiness 不通过
- 核心登录或鉴权失败
- 错误率超过发布阈值
- P99 明显超过验收目标
- 审计写入失败
- 权限缓存无法加载且无可用快照
- 敏感配置进入日志

## 9. 发布记录

每次发布保存：版本号、Git commit、CI 构建编号、数据库迁移版本、发布人、审批人、发布时间、发布环境、健康检查结果、监控观察窗口、是否回滚、回滚原因。

责任边界：任务负责人保证功能与测试；评审人保证设计与代码质量；测试负责人保证验收证据；发布负责人保证制品、配置、发布与回滚；项目负责人批准生产发布。
