# 01 · 需求规格说明书（RBAC 权限系统）

> 相关文档：[文档索引](./README.md) · [总体设计](./02-总体设计说明书.md) · [演进设计](./05-RBAC0到RBAC3演进设计.md)

---

## 1. 背景与目标

### 1.1 要解决的问题

系统需要一套统一的"谁可以做什么"的判定机制。没有它，每个业务模块都会自己写一套判断逻辑（这个接口判断一下部门、那个接口判断一下职级），结果是：权限规则散落各处、改名要改十处、审计无法追溯、新人不敢改代码。

**我们要做的不是"给每个接口加判断"，而是把权限判定收敛成一条唯一的通道**：所有需要保护的接口都通过同一套机制判定，业务代码只说"我需要 `sys:user:create` 这个权限"，不关心这个权限是从哪个角色来的、角色之间有没有继承关系。

### 1.2 阶段目标

| 阶段 | 目标 | 本设计文档的覆盖情况 |
|---|---|---|
| 本期 | 完成 **RBAC0**（用户 → 角色 → 权限 三层模型）搭建并上线 | 完整设计（含表结构、接口、鉴权链路） |
| 后续 1 | 升级到 **RBAC1**（增加角色继承） | 已给出升级方案与扩展点定义 |
| 后续 2 | 升级到 **RBAC2**（增加角色约束） | 已给出升级方案与扩展点定义 |
| 后续 3 | 达到 **RBAC3**（RBAC1 + RBAC2） | 由阶段 1、2 正交叠加自然达成，无需独立动作 |

> **核心设计诉求**：升级过程**不推翻现有模型、不重写业务代码、不改鉴权主链路**。这条诉求是全文设计取舍的最高优先级判据，详见 [05 演进设计](./05-RBAC0到RBAC3演进设计.md)。

### 1.3 已确认的前提（来自需求澄清）

| 项 | 结论 |
|---|---|
| 架构形态 | 模块化单体（一套 Spring Boot 应用，内部按模块隔离，可横向多实例部署） |
| 组织模型 | 单组织，模型不引入租户维度 |
| 鉴权数据存放 | 实例本地缓存 + Redis 广播失效 + TTL 兜底；**身份快照（30s TTL）用于令牌作废判定** |
| 权限范围 | 只做功能权限（菜单 / 按钮 / 接口），不做数据权限 |
| 审计 | **拆成两类**：变更审计（CHANGE，与业务同事务落库，强合规、不丢弃）；安全事件（SECURITY，独立落库、失败不回滚业务、可丢弃但必须计数告警） |
| 性能口径 | 10k 并发**在线用户**；推导峰值 2.5k QPS、设计目标 2k QPS（含 25% 余量）、验收按 2.5k 稳态 + 4k 冲刺；鉴权类接口 P99 ≤ 30ms |
| 令牌作废的保证等级 | 正常 ≤ 1 秒；Redis 故障 ≤ 30 秒；实例重启**立即**；数据库故障时受影响用户立即被拒（见 FR-A9） |
| 角色继承语义 | `inherit_role_id` = "我从哪个角色继承权限"；**不存储组织上下级关系** |
| 缓存重载失败的姿态 | **fail-open（可用优先）**：继续用最后一份成功数据 + 强告警；已知状态变化的用户仍被拒绝；预留 `stale-policy` 开关 |
| 高可用投入 | **MySQL / Redis / Nginx 全部单点，不提供自动故障切换**（明确成本取舍）；保留将来扩容的扩展点约束 |
| 技术栈 | Java 21 + Spring Boot 3.x + MyBatis + MySQL 8.0；前端 Vue 3；不使用 Spring Security 全套框架 |

## 2. 系统使用角色（Who uses this system）

这里要区分两个"角色"概念，**很容易混淆**，先说清楚：

- **系统角色（业务概念）**：管理员、普通用户……这是被 RBAC 管理的数据。
- **RBAC 操作者（人）**：真正登录后台去配置权限的人。

本节说的是后者。

| 操作者 | 能做什么 | 对应权限码前缀 |
|---|---|---|
| 超级管理员 | 一切操作，包括创建角色、分配任意权限；**不可被删除、不可被降权**（防止把自己锁在门外） | `*` |
| 权限管理员 | 管理用户、角色、权限、授权关系；不能删除超级管理员 | `sys:user:*` `sys:role:*` `sys:perm:*` |
| 审计员 | **只能读**审计日志，不能改任何配置 | `sys:audit:read` |
| 业务用户 | 仅按被授予的角色使用业务功能 | 由业务权限码决定 |

> **设计含义**：超级管理员需要一条"逃生通道"（Break-glass）。做法不是给它单独写一套代码，而是给它绑定一个内置角色 `SUPER_ADMIN`，该角色的权限集合包含一个特殊权限码 `*`（全部）。这样"超级管理员"的判定仍然是**普通的权限码判定**，主链路上不出现 `if (isSuperAdmin)` 这类分支——分支一旦写进鉴权代码，升级 RBAC 时就会被一起改动。

## 3. 范围边界

### 3.1 做什么（In Scope）

| 模块 | 内容 |
|---|---|
| 认证 | 账号密码登录、登出、修改密码、会话续期 |
| 用户 | 用户的增删改查、启用/停用、重置密码 |
| 角色 | 角色的增删改查、角色授权限 |
| 权限 | 权限（资源点）的增删改查、权限树维护 |
| 授权 | 给用户分配/回收角色 |
| 鉴权 | 接口级、菜单级、按钮级三层鉴权；统一鉴权入口 |
| 前端权限 | 动态菜单渲染、按钮级显隐、路由守卫 |
| 审计 | RBAC 域写操作的审计日志，同事务落库，可查询 |
| 失效机制 | 权限变更后各实例缓存失效与重新加载 |

### 3.2 不做什么（Out of Scope）——**明确排除，避免范围蔓延**

| 排除项 | 为什么排除 | 将来要做的话，代价在哪 |
|---|---|---|
| 数据权限（行级/字段级，如"只能看本部门数据"） | 已确认本期不做。标准 RBAC 模型本身表达不了它，硬做会把鉴权主链路复杂化 | 需在鉴权之后**追加**一层数据范围过滤，属于"插入新环节"，不是"改造旧环节" |
| 多租户 | 已确认单组织 | 需在几乎所有表加 `tenant_id` 并改造全部 SQL，属重大改造 |
| 单点登录 / 第三方认证 | 本期账号密码即可 | 认证模块内部替换认证方式，鉴权模块不受影响 |
| 字段级加密、数据脱敏 | 不属于权限系统职责 | 独立关注点 |
| 工作流审批（如"授权需审批后生效"） | 属于业务流程，不是权限模型 | 可通过"待生效角色"扩展，届时新增状态与审批表 |
| 图形验证码、短信验证码 | 本期未要求（登录防暴力破解用其他手段，见 5.3） | 认证模块内新增校验步骤 |

> **为什么要显式写"不做什么"？** 因为 90% 的项目延期不是"做不完要做的"，而是"顺手做了不该做的"。需求范围一旦模糊，实现者会顺着直觉补功能，最后主链路被各种特例污染，升级 RBAC 时无处下手。

## 4. 功能需求

### 4.1 认证（FR-A 系列）

| 编号 | 需求 | 说明与约束 |
|---|---|---|
| FR-A1 | 用户可凭账号密码登录 | 密码以 BCrypt 哈希存储，**任何日志、响应、审计中不得出现明文或哈希** |
| FR-A2 | 登录成功返回访问令牌（JWT） | 令牌内含：用户标识（`sub`）、令牌版本号（`ver`）、密钥标识（`kid`）、`iss`/`aud`、签发与过期时间。**不包含角色或权限明细**（原因见 [02 文档 5.1](./02-总体设计说明书.md)） |
| FR-A3 | 令牌有效期与续期 | 访问令牌短期有效（建议 2 小时）；提供续期接口，续期时重新读取最新权限版本 |
| FR-A4 | 用户可主动登出 | 登出后该令牌作废（`token_version` 自增 + 广播失效），**时效承诺见 FR-A9** |
| FR-A5 | 用户可修改自己的密码 | 改密后**所有历史令牌作废**（防止密码泄露后旧令牌仍可用），**时效承诺见 FR-A9** |
| FR-A6 | 连续登录失败锁定 | 同一账号连续失败 N 次（建议 5 次）锁定 M 分钟（建议 15 分钟）；锁定信息不依赖数据库高频写入 |
| FR-A7 | 停用的账号不可登录，且已登录会话失效 | 停用属于"管理动作"，走令牌作废通道，**时效承诺见 FR-A9** |
| FR-A8 | 登录接口限流 | 按账号 + 来源 IP 双维度限流，防止撞库；**IP 必须取可信代理的解析结果**（见 NFR-3 的 IP 规则） |
| FR-A9 | 令牌作废的保证等级 | **必须写清楚承诺到什么程度**，见 4.1.1 |
| FR-A10 | 全局令牌作废 | 密钥泄露等场景需要"一次性作废全部令牌"：全局令牌版本基线自增，时效同 FR-A9 |

#### 4.1.1 FR-A9：令牌作废的保证等级（本系统给出的明确承诺）

| 条件 | 承诺的生效时间 | 依赖的机制 |
|---|---|---|
| 正常（Redis 可用） | **≤ 1 秒** | 广播触发本地快照失效，下一次请求重载 |
| Redis 不可用 / 广播丢失 | **≤ 30 秒** | 本地身份快照 TTL（30 秒）到期后重载 |
| 实例重启 / 新增实例 | **立即**（不依赖任何消息） | 缓存为空，首个请求直接读数据库 |
| 数据库不可用 | **受影响用户立即被拒绝**（已知其状态变化）；其他用户的鉴权继续用最后一份成功数据**放行**（fail-open，配合强告警）；管理类写操作直接失败 | 见 [02 文档 5.3.2](./02-总体设计说明书.md) |

> **为什么不承诺"任何故障下的即时失效"？**
> 因为那需要每个请求都去查一次共享存储（Redis 或数据库），而本系统的核心性能设计恰恰建立在"鉴权链路零网络、零数据库"之上。10,000 在线用户下每请求一次 Redis 往返，既让 P99 逼近 30ms 上限，也把 Redis 变成关键路径——**用一次故障窗口换取一个持续的、每次都存在的依赖，是明显更差的选择**。
>
> **必须避免的错误做法**：文档里写"立即作废"、实现上却是"最坏 30 秒"。**承诺与实际不符比承诺得宽松更危险**——它会让安全审计与应急预案建立在错误假设上。

> **关于"高风险账号需要更严格失效"**：如果确有此类需求（如财务、超管），正确做法是**缩短这些账号的令牌有效期**（例如 15 分钟自动续期），用同一套机制把上界压到令牌有效期内；**不要**为它们单独开一条查询通道或引入逐令牌黑名单（`jti`）——那会引入一个只服务于少数账号的特例路径，长期维护成本远高于收益。

### 4.2 用户管理（FR-U 系列）

| 编号 | 需求 | 说明与约束 |
|---|---|---|
| FR-U1 | 用户列表（分页 + 按账号/昵称/状态筛选） | 列表接口是**高频读接口**，必须受 30ms 约束 |
| FR-U2 | 新增/编辑/删除用户 | 删除为逻辑删除（`status = DELETED`），保证审计可追溯 |
| FR-U3 | 启用/停用用户 | 停用需触发会话失效广播 |
| FR-U4 | 重置用户密码 | 重置后该用户所有令牌作废 |
| FR-U5 | 给用户分配角色 / 回收角色 | 变更后该用户的权限立即（秒级）生效 |
| FR-U6 | 不可删除或停用超级管理员 | 由"内置账号保护"规则保证，见 4.6 |

### 4.3 角色管理（FR-R 系列）

| 编号 | 需求 | 说明与约束 |
|---|---|---|
| FR-R1 | 角色列表（分页 + 筛选）、详情 | 角色表数据量小（百级），可全量缓存 |
| FR-R2 | 新增/编辑/删除角色 | 角色编码 `code` 全局唯一且**创建后不可修改**（业务代码用编码引用角色） |
| FR-R3 | 启用/停用角色 | 停用角色后，其承载的权限不再对用户生效 |
| FR-R4 | 删除角色前校验引用 | 若仍有用户绑定该角色，禁止删除并提示关联用户数 |
| FR-R5 | 给角色分配权限 / 回收权限 | 变更后所有拥有该角色的用户权限秒级生效 |
| FR-R6 | 内置角色不可删除 | `SUPER_ADMIN` 等内置角色受保护 |

### 4.4 权限（资源点）管理（FR-P 系列）

| 编号 | 需求 | 说明与约束 |
|---|---|---|
| FR-P1 | 权限树查询 | 权限以树形组织（如 `系统管理 → 用户管理 → 删除用户`） |
| FR-P2 | 权限的增删改查 | 权限分三类：`MENU`（菜单/页面）、`BUTTON`（页面内按钮）、`API`（后端接口） |
| FR-P3 | 权限码全局唯一 | 权限码是**业务与权限系统之间唯一的契约**，创建后不可修改 |
| FR-P4 | 删除权限前校验引用 | 若已被角色引用，禁止删除并提示 |
| FR-P5 | 权限可控制显隐与排序 | 前端菜单渲染依赖 `sort` 与 `status` |

> **为什么权限要分 MENU / BUTTON / API 三类，而不是只做接口权限？**
> 因为三者服务于不同的展示场景：`MENU` 决定侧边栏显示哪些菜单，`BUTTON` 决定页面里"删除"按钮显示不显示，`API` 决定后端放不放行。
> **关键约束：前端权限只是"体验优化"，不是安全边界。** 真正拦人的只有后端 `API` 权限。因此 API 权限必须与接口严格一一对应，且**每个受保护接口都必须声明所需权限码**——这条要靠自动化检查兜底（见 NFR-8）。

### 4.5 审计（FR-L 系列）

**首先把它分成两类**——这是原设计的漏洞：把两类"事务性质完全不同"的事件塞进同一套语义，会同时导致**审计缺失**和**业务被不必要地回滚**。

| 类别 | 覆盖内容 | 事务要求 |
|---|---|---|
| **变更审计（CHANGE）** | 用户/角色/权限的增删改、授权关系变更、启停、重置密码 | **与业务数据同一事务**：业务失败则审计不落库；审计写入失败则业务回滚 |
| **安全事件（SECURITY）** | 登录成功/失败、登出、令牌作废、越权访问（403）、限流触发、缓存降级 | **独立事件**，不与业务同事务；**记录失败绝不能回滚业务**——多数安全事件（如一次失败的登录）根本没有对应的业务变更可回滚 |

| 编号 | 需求 | 说明与约束 |
|---|---|---|
| FR-L1 | 记录变更审计 | 覆盖：用户增删改、角色增删改、权限增删改、授权关系变更、启停、重置密码 |
| FR-L2 | 审计内容 | 审计类别、操作人、操作类型、目标对象类型与 ID、**变更前后快照**（脱敏后）、事件时间、来源 IP、User-Agent、traceId |
| FR-L3 | 变更审计与业务同事务 | 见上表。这是用户明确选择的**强合规**口径，**不允许异步化或事后补偿** |
| FR-L4 | 安全事件独立落库 | 安全事件写入失败**不得**回滚业务；允许异步/排队写入 |
| FR-L5 | 写入降级规则（必须写死，否则实现时会各自发挥） | 变更审计：**不允许丢弃**，写入失败即整个业务操作失败；安全事件：允许在持续失败时丢弃，但**必须计数并告警**（丢弃必须可见，禁止静默丢弃） |
| FR-L6 | 审计日志只读不可改 | 接口层只提供查询，不提供修改/删除接口 |
| FR-L7 | 审计日志查询 | 支持按类别、时间范围、操作人、操作类型、目标对象筛选；游标分页 |
| FR-L8 | 审计日志保留与归档 | 默认保留 180 天，超期归档/清理；清理动作本身记录系统日志 |
| FR-L9 | 登录失败（含账号不存在）必须记录 | 账户不存在时的失败尝试是**撞库探测的关键信号**。因此 `operator_id` 允许为空，`operator_name` 记录提交的账号名（需脱敏） |
| FR-L10 | 快照脱敏 | 变更前后快照必须经过统一脱敏过滤器，剔除 `password_hash`、令牌、密钥等字段（**这是审计功能最常被忽视的安全漏洞**） |
| FR-L11 | 严格一致性 | 不存在"业务成功但变更审计缺失"的情况；由同事务保证，并用事务异常注入测试验证（AC-7） |

> **为什么"安全事件允许丢弃但必须计数"是可接受的？** 因为安全事件的量级远大于变更审计（每次 403、每次登录都算），若一律"不可丢弃"，就等于让一个纯记录动作**反噬**业务可用性——例如日志系统堵塞导致全体用户无法登录。**取舍原则是：绝不能因为"记录失败"而让系统失去服务能力**；但丢弃必须留下痕迹（计数器 + 告警），否则会静默丢失排查线索。

> **性能影响必须诚实说明**：FR-L3 意味着每次写操作多一次事务与磁盘写入。**但本系统写操作 QPS 极低**（RBAC 配置类操作每天可能只有几十到几百次），对 2k QPS 的整体指标影响可忽略。**唯一的真实风险是批量操作**（如一次性导入 5000 个用户），该场景需单独设计（见 [06 文档 §6.3](./06-性能与容量设计.md)）。

### 4.6 内置保护规则（FR-G 系列）

这些规则看起来是"特例"，但它们**不写在鉴权主链路上**，而是作为**数据规则 + 校验器**存在，因此不会影响 RBAC 升级：

| 编号 | 规则 |
|---|---|
| FR-G1 | `SUPER_ADMIN` 角色不可删除、不可停用；其权限集合不可被移除 `*` 权限码 |
| FR-G2 | 系统必须始终至少保留 1 个启用状态的超级管理员账号 |
| FR-G3 | 用户不能删除/停用自己（防止自锁） |
| FR-G4 | 用户不能移除自己的最后一个管理类角色（防止自锁） |
| FR-G5 | 权限码 `code`、角色码 `code`、账号 `username` 创建后不可修改 |

> 实现方式：FR-G4/G2 属于"基数约束"思路，**恰好与 RBAC2 的约束机制同构**。因此这两条规则的实现载体就是 [05 文档 §3.4](./05-RBAC0到RBAC3演进设计.md) 中定义的 `ConstraintValidator` 校验链——**RBAC0 阶段先放 4 个具体校验器，RBAC2 阶段继续往同一个链上追加互斥与基数校验器**。这是"顺手把升级点预留好"的典型例子，不增加任何额外成本。

## 5. 非功能需求

### 5.1 性能（NFR-1）

| 项 | 指标 | 口径说明 |
|---|---|---|
| 负载规模 | 10,000 并发**在线用户** | 在线≠每秒都发请求，按每人每分钟 6~10 次操作估算 |
| 推导峰值 | 约 2,500 QPS | 10,000 × 10 ÷ 60 × 1.5（峰值系数），见 [06 文档第 1 节](./06-性能与容量设计.md) |
| **设计目标（容量 sizing 依据）** | **2,000 QPS** | 保守取值：在推导峰值上预留 25% 余量，**不是"允许拒绝额外流量"的上限** |
| **验收场景（必须实测）** | **2,500 QPS 稳态 + 4,000 QPS 冲刺** | 见 [06 文档 §7.2](./06-性能与容量设计.md)；冲刺场景允许通过限流平滑降级，但不得雪崩 |
| 鉴权类接口 | **P99 ≤ 30ms** | 含登录后的所有读接口与简单写接口（服务器侧处理耗时，不含公网传输） |
| 复杂管理类接口 | P99 ≤ 200ms | 如权限树全量查询、审计日志分页深翻、批量授权 |
| 缓存失效后的首次请求 | P99 ≤ 100ms | 允许一次性的缓存重建开销 |
| 错误率 | < 0.1% | 不含客户端主动取消 |
| 缓存命中率 | > 99.9% | 鉴权缓存的命中率，是 30ms 目标的根本保障 |

> **关于"预算 / 目标 / 实测"的口径纪律**：本文与 [06 文档](./06-性能与容量设计.md) 中出现的微秒级数字（如"验签 10 微秒"）是**预算假设**，用于指导设计与定位瓶颈，**不是实现保证**；只有压测实测结果才能作为验收依据。任何引用这些数字的汇报都必须标明是"预算"还是"实测"。
>
> **为什么把接口分成两档？** 因为把"审计日志深翻页"也压到 30ms 是不经济的（需要额外索引与存储成本），而它每天被调用几十次，慢一点无人感知。**为低频接口付出高频接口的成本，是常见的过度设计。**

### 5.2 可用性（NFR-2）

| 项 | 要求 |
|---|---|
| 部署形态 | 后端**无状态**，多实例（建议 3 实例起步），支持滚动发布不中断 |
| **高可用现状（必须如实声明）** | **MySQL / Redis / Nginx 均为单实例，不提供自动故障切换**。这是明确的**成本取舍**，不是"已具备冗余"。故障时需要人工介入恢复，RTO/RPO 见 [02 文档 §7.2](./02-总体设计说明书.md) |
| Redis 故障降级 | Redis 不可用时：权限变更与令牌作废退化为 TTL 兜底（**最坏 30 秒生效**，见 FR-A9）；**登录与鉴权不得中断**；RTO ≈ 0（服务不中断），RPO 不适用（无持久化数据） |
| 数据库故障 | **采用 fail-open（可用优先）**：鉴权继续用最后一份成功加载的数据放行，配合强告警；**已知状态变化的用户（如刚被停用）立即被拒绝**；**从不成功加载过缓存的新实例**拒绝鉴权请求；写故障时管理功能报错并友好提示。**代价必须被管理起来**：陈旧时长与受影响用户数必须可观测、恢复后必须全量失效、故障期间撤销的权限必须可追溯（见 [02 §5.3.2](./02-总体设计说明书.md)） |
| 应用单实例故障 | 由负载均衡摘除，用户无感知（应用层是**唯一**做了冗余的一层） |
| **RTO（各组件，人工恢复）** | 应用实例：≤ 5 分钟（自动摘除 + 重启）；Nginx：≤ 30 分钟（重启）/ ≤ 4 小时（机器重建）；MySQL：≤ 1 小时（**前提：binlog 完好**，见 02 §7.2）/ 最长 24 小时（依赖每日备份恢复，RPO 随之恶化）；Redis：≤ 5 分钟（重启即恢复，服务期间不中断） |
| **RPO（最多允许丢失的数据量）** | **权限配置数据（业务表）：≈ 0**——前提是开启 binlog 且**备份文件与 binlog 存放在独立于数据库主机的存储上**；若不满足该前提，RPO 退化为"自上次全量备份以来"（最长 24 小时）；审计日志：同权限数据；缓存数据：无意义（可从数据库完全重建） |
| **目标可用性（分档，不混为一谈）** | **鉴权读路径：99.9%**（应用层多实例 + 本地缓存，不受单点存储影响）；**含写操作的端到端整体：受 MySQL 单点约束，无法承诺 99.9%**。若业务确实需要整体 99.9%，**必须为 MySQL 做高可用**（见 [02 §7.2 的扩展点](./02-总体设计说明书.md)） |
| **必须做的运维动作** | ① 每日全量备份 + binlog 增量，**且备份与 binlog 必须存放在数据库主机之外**；② **每季度至少一次恢复演练**（RTO/RPO 只在演练中才能被验证，写在纸上的一律不算）；③ 明确值班响应流程与各组件的人工恢复手册 |

> **为什么要把"没做高可用"写得这么直白？**
> 因为**故障发生时才发现"原来没有自动切换"，比一开始就知道，代价高得多**——前者会伴随误判（"是不是应用挂了？"）、反复重启、以及决策延误。文档里写清楚"这是取舍"，运维才能提前准备好切换脚本与演练；写不清楚，就会有人以为系统会自动恢复。

### 5.3 安全（NFR-3）

| 项 | 要求 |
|---|---|
| 密码存储 | BCrypt（强度 10~12），禁止 MD5/SHA1/明文 |
| 密码策略 | 长度 ≥ 8，含大小写字母与数字；禁止与账号相同 |
| 传输安全 | 全链路 HTTPS；令牌只放 `Authorization: Bearer` 请求头，**不放 URL 参数**（避免进日志） |
| 令牌安全 | HMAC-SHA256 签名，令牌带 `kid`、`iss`、`aud`；密钥 ≥ 256 位、经环境变量/配置中心下发，禁止硬编码；**密钥轮换必须有可执行协议**（见 [02 文档 §5.1](./02-总体设计说明书.md)），多实例启动时校验密钥集合一致 |
| 会话作废 | 改密、登出、停用、全局作废均使历史令牌失效；**时效承诺见 FR-A9（正常 ≤ 1 秒，Redis 故障 ≤ 30 秒）**，不得写成"立即失效" |
| 客户端 IP 可信性 | 只信任来自可信代理的 `X-Forwarded-For`，且由**唯一组件**解析（见 [02 文档 §5.7](./02-总体设计说明书.md)）；限流、审计、安全告警共用同一解析结果 |
| 防暴力破解 | 登录失败计数 + 锁定 + 限流（FR-A6/A8） |
| 防越权 | 垂直越权由 API 权限码拦截；水平越权（看别人的数据）由业务模块自行做资源归属校验，本系统只提供"身份"不提供"归属"判定 |
| CSRF | 令牌放在自定义请求头而非 Cookie，天然免疫 CSRF；同时禁用基于 Cookie 的会话 |
| CORS | 白名单精确配置，禁止 `*` 与凭据共存 |
| XSS | 前端对动态内容转义；后端输出 `Content-Type: application/json` |
| SQL 注入 | 全部使用参数化查询（MyBatis `#{}`），禁止 `${}` 拼接 |
| 敏感信息 | 密码、令牌、密钥严禁出现在日志、异常堆栈、审计快照中 |
| 权限最小化 | 新用户默认无任何权限；新角色默认无任何权限 |
| 越权自检 | 每个受保护接口必须有权限码声明，由自动化测试保证（NFR-8） |
| 审计不可抵赖 | 审计日志记录操作人真实身份与来源 IP；应用账号无删除审计表权限 |

### 5.4 可观测性（NFR-4）

| 项 | 要求 |
|---|---|
| 指标暴露 | Spring Boot Actuator + Micrometer，暴露 Prometheus 格式指标 |
| 核心指标 | 接口耗时直方图（含 P50/P95/P99）、鉴权缓存命中率、鉴权失败计数、登录失败计数、缓存重载次数与耗时、Redis 订阅连接状态 |
| **缓存健康度指标（必须新增，fail-open 下是唯一的透明度来源）** | 缓存**版本号**、**当前陈旧时长**（`now - loadedAt`）的当前值与分布、重载失败次数、**受影响的用户数**、**用陈旧权限放行的请求数**。**fail-open 意味着系统会在权限可能过期时继续服务，因此这套指标不是"最好有"，而是"没有就等于在盲飞"**（503 计数仅在切换到 fail-closed 姿态时才有意义） |
| 日志 | 结构化日志（JSON）；**日志输出使用异步 Appender**（同步写盘会直接吃掉 30ms 预算） |
| 链路追踪 | 每个请求生成 traceId 并透传到响应头，便于定位单次慢请求 |
| 慢请求治理 | 超过阈值（如 100ms）的请求记录业务上下文（用户、权限码、SQL） |

### 5.5 可维护性与可演进性（NFR-5）——**本项目的关键指标**

| 项 | 要求 |
|---|---|
| 升级代价 | 升级到 RBAC1 / RBAC2 时，**以下部分不需要改动**：① 业务接口上的权限声明（`@RequiresPermission` 的取值）；② 鉴权入口（过滤器、拦截器、注解）的接口与调用方式；③ 已有表结构不做破坏性变更（只新增表、新增列或启用已预留字段）。**以下部分仍然会有改动**（完整清单见 [05 文档第 8 节](./05-RBAC0到RBAC3演进设计.md)）：权限计算的内部实现、缓存加载语句、管理端与前端配置界面、数据库迁移脚本、回归测试。**"改动 0 行"这种表述是错的**，正确的目标是"改动被限制在少数几处，且升级与回滚都能靠改数据完成，而不是重新发版本" |
| 可测试性 | 鉴权模块的单元测试覆盖权限计算的全部路径；权限计算的输入输出可脱离 HTTP 单独测试 |
| 模块边界 | 由 ArchUnit 自动检查依赖方向，违反则构建失败 |
| 接口稳定性 | 对外接口路径与权限码一经发布即视为契约，变更需评审 |
| 文档同步 | 数据模型或权限码变更时，必须同步更新 03 / 04 文档 |

### 5.6 环境与资源约束（NFR-6）

| 项 | 约束 |
|---|---|
| 服务器资源 | 有限，按"够用 + 高可用冗余"配置，不做过度采购（容量测算见 [06 文档](./06-性能与容量设计.md)） |
| 运行环境 | Linux；JDK 21；MySQL 8.0；Redis 6+；Nginx 前置 |
| 浏览器 | Chrome / Edge 最近两个大版本（内部管理系统，不做旧浏览器兼容） |

### 5.7 兼容性与数据一致性（NFR-7）

| 项 | 要求 |
|---|---|
| 事务边界 | 一次管理操作 = 一个事务（业务数据 + 审计日志） |
| 缓存一致性 | 采用"**失效（invalidate）而非更新（update）**"策略：变更后只丢弃缓存，下次读取时重建。避免并发下"多实例互相覆盖导致脏数据" |
| 缓存失效时效 | 正常情况 ≤ 1s（广播生效）；Redis 故障时 ≤ 30s（TTL 兜底） |
| 幂等性 | 授权/回收类接口天然幂等（集合操作）；创建类接口以唯一约束兜底重复提交 |

### 5.8 自动化质量门禁（NFR-8）

| 门禁 | 内容 | 为什么必须有 |
|---|---|---|
| 接口权限覆盖检查 | 扫描所有 `@RequestMapping` 方法，缺少 `@RequiresPermission` 或未标注"公开接口"的，**构建失败** | "漏加注解"是权限系统最致命的漏洞，靠人审查必漏 |
| 模块依赖检查 | ArchUnit 检查模块依赖方向 | 模块化单体的边界一旦破了就无法恢复 |
| 权限计算单元测试 | 覆盖：无角色、单角色、多角色、停用角色、停用权限、超级管理员 | 权限计算是安全核心 |
| 越权集成测试 | 用低权账号访问高权接口，必须返回 403 | 端到端验证 |
| 性能回归测试 | 鉴权链路压测，P99 不达标则告警 | 30ms 是硬指标 |

## 6. 关键用例

### UC-1：用户登录

```
角色：普通用户
前置：账号已创建且状态为"启用"
主流程：
  1. 用户提交账号 + 密码
  2. 系统校验账号状态、密码哈希、登录失败次数
  3. 生成访问令牌（含用户标识与令牌版本号）
  4. 记录登录审计日志
  5. 返回令牌 + 用户基本信息
异常分支：
  2a. 账号或密码错误 → 失败计数 +1，返回统一错误提示（不区分"账号不存在"与"密码错误"，避免账号枚举）
  2b. 账号被停用 → 提示联系管理员
  2c. 连续失败超阈值 → 锁定，提示剩余锁定时间
性能约束：服务器侧处理 P99 ≤ 30ms（BCrypt 哈希校验约 50~100ms，属于**例外**，见下方说明）
```

> **重要澄清**：BCrypt 校验本身需要 50~100ms（这是它的设计目的——故意慢，让暴力破解代价高昂）。因此**登录接口不受 30ms 约束**，30ms 约束适用于"登录之后的高频业务请求"。这一点必须在性能测试时区分对待，否则会陷入"为了满足登录 30ms 而把密码哈希调到不安全强度"的误区。
> 优化手段：登录接口独立线程池隔离，避免慢请求占满通用线程池（见 [06 文档 §6.4](./06-性能与容量设计.md)）。

### UC-2：管理员给角色调整权限（核心链路）

```
角色：权限管理员
主流程：
  1. 前端提交"角色 ID + 新的权限码集合"
  2. 系统校验操作者自身权限（需 `sys:role:assign-perm`）
  3. 开启事务：覆盖式写入角色-权限关系表 + 写入审计日志（前后快照）→ 提交
  4. 事务提交成功后：自增全局权限版本号，向 Redis 频道发布失效广播
  5. 返回成功
异常分支：
  3a. 校验失败（如试图移除内置角色的 * 权限）→ 回滚，返回明确错误（FR-G1）
  4a. Redis 不可用 → 广播失败但不影响本次操作成功；记录告警，各实例靠 30s TTL 兜底
性能约束：P99 ≤ 200ms（低频管理接口）
```

> **注意第 4 步的顺序**：必须是"**先提交事务，后发广播**"。反过来的话，广播发出去了但事务回滚了，各实例会白刷一次缓存（无害）；更糟的是如果缓存**先失效、再读、事务才提交**，会把旧数据重新读进缓存并长期驻留——这是缓存与事务顺序的经典陷阱。

### UC-3：业务用户访问受保护接口（最高频链路，必须 30ms 内）

```
步骤（全部进程内完成，无网络、无数据库）：
  1. 过滤器解析请求头中的令牌，验签并检查过期时间
  2. 取出用户标识与令牌版本号，与本地"已作废令牌"集合比对
  3. 从实例本地缓存取该用户的权限码集合（未命中则单飞重建）
  4. 读取接口上声明的所需权限码，比对是否包含
  5. 通过 → 写入请求上下文（当前用户）→ 放行到业务方法
失败 → 统一返回 401（未认证）/ 403（无权限），不进入业务方法
性能约束：步骤 1~5 合计 P99 ≤ 3ms（占用 30ms 预算的 10%，其余留给业务查询与序列化）
```

### UC-4：权限变更后的跨实例生效（一致性链路）

```
  1. 实例 A 提交权限变更事务，成功后向 Redis 频道发布消息
  2. 实例 B、C 订阅到消息 → 清空本地权限缓存（不立即重载，避免 N 个实例同时压垮数据库）
  3. 各实例在**下一个请求**到来时惰性重载，并通过"单飞"机制保证同一时刻只有 1 个线程真正查库
  4. 重连/重启的实例：启动时主动全量加载；订阅重连后强制全量失效一次
预期时效：正常 ≤ 1s；Redis 不可用 ≤ 30s（TTL）
```

> **为什么是"惰性重载 + 单飞"而不是"收到广播就立刻重载"？**
> 假设有 20 个实例，一次广播后 20 个实例同时查库，就是一次人为制造的流量尖峰（业内叫"缓存雪崩的微观版"）。惰性重载把这次查询摊薄到各个请求里，单飞保证不多查。这是"高并发下优先考虑响应速度"的直接应用。

## 7. 验收标准

| 编号 | 验收项 | 判定方式 |
|---|---|---|
| AC-1 | RBAC0 全部功能需求（FR-A/U/R/P/L/G）可用 | 功能测试用例全通过 |
| AC-2 | 鉴权类接口 P99 ≤ 30ms | 压测报告：**2,500 QPS 稳态**（见 [06 §7.2 S10](./06-性能与容量设计.md)） |
| AC-3 | 权限变更在 1s 内在全部实例生效（Redis 正常时） | 多实例联调验证 |
| AC-4 | 停用 Redis 后，鉴权不中断，权限变更与令牌作废在 30s 内生效 | 故障演练（S6 / S16） |
| AC-5 | 每个受保护接口均有权限码声明（门禁检查通过） | 构建流水线检查 |
| AC-6 | 低权用户访问高权接口全部返回 403 | 越权测试集 |
| AC-7 | 审计日志与业务数据严格一致（无"业务成功但变更审计缺失"的情况） | 事务异常注入测试 |
| AC-8 | 升级到 RBAC1 的预演：**权限声明与鉴权入口契约不变**，其余改动限于权限计算实现、缓存 SQL、界面与测试；且回归通过 | 升级预演（在阶段 0 末期执行一次） |
| **AC-9** | **滚动重启全部实例期间，重启前签发且已被作废的令牌一律被拒（40101）** | 场景 S12 |
| **AC-10** | **数据库故障期间系统按 fail-open 继续服务，且关键指标可如实观测**：陈旧时长如实增长（不被伪刷新为 0）、受影响用户数、用陈旧权限放行的请求数均可见；恢复后立即全量重载、陈旧时长归零 | 场景 S14 |
| **AC-11** | **并发覆盖式授权不产生静默丢失**：同一 `expectedVersion` 的并发提交恰好一个成功、一个返回 40950 | 场景 S15 |
| **AC-12** | **JWT 密钥轮换期间无因 kid 不匹配导致的 401，且阶段 1、2 可回滚** | 场景 S13 |
| **AC-13** | **备份恢复演练实测耗时符合 [02 §7.2](./02-总体设计说明书.md) 的 RTO 承诺，数据完整（RPO 达标）** | 场景 S18，**每季度重复** |
| **AC-14** | **用户列表与审计查询在目标数据量下索引达标**（命中预期索引、单次耗时达标） | 场景 S17 的 `EXPLAIN ANALYZE` 报告 |

> **AC-8 是本设计最特殊的验收项**。我们无法等到真要升级时才发现"预留没做对"。因此要求在 RBAC0 上线前，**用最小成本做一次升级预演**（在分支上实现一个简化版角色继承，跑通回归用例）。这相当于"防火演习"——成本很低，但能提前暴露设计缺陷。
>
> **AC-9 ~ AC-14 是本次评审新增的验收项**，它们覆盖的不是功能也不是性能，而是**"系统在最坏情况下是否还在正确地拒绝 / 是否还能被观测"**。其中 **AC-10 是 fail-open 选择的直接后果**：既然选择了"数据库故障时继续服务"，就必须能回答"这次故障期间有多少请求是用陈旧权限放行的"——**回答不了，就等于无法向业务与审计解释**。

> **AC-8 是本设计最特殊的验收项**。我们无法等到真要升级时才发现"预留没做对"。因此要求在 RBAC0 上线前，**用最小成本做一次升级预演**（在分支上实现一个简化版角色继承，跑通回归用例）。这相当于"防火演习"——成本很低，但能提前暴露设计缺陷。

## 8. 约束与假设

| 编号 | 假设 / 约束 | 若不成立的影响 |
|---|---|---|
| AS-1 | 用户规模 ≤ 1 万（远期 5 万），角色 ≤ 200，权限点 ≤ 3000 | 超出后本地缓存内存与重载耗时需重新评估（但 10 倍以内余量充足） |
| AS-2 | 权限配置类写操作 QPS < 1，审计日志每天几千条 | 若写操作量级上升 100 倍，同步审计需改为异步或分库 |
| AS-3 | 用户操作频率为"每人每分钟 6~10 次" | 若为"每秒多次"，QPS 会上升一个数量级，需扩容并重新压测 |
| AS-4 | 后端与数据库、Redis 在同机房（内网延迟 < 0.5ms） | 跨机房部署需重新计算 30ms 预算 |
| AS-5 | 鉴权只做"是/否"判定，不做数据范围过滤 | 见范围边界 3.2 |
| AS-6 | 权限模型为"正向授权"（只加不减，无拒绝优先规则） | 若需"拒绝优先"，需要在权限计算中引入优先级，属模型变更 |
| **AS-7** | **缓存重载失败时的姿态为 fail-open**（数据库故障期间继续用最后一份成功数据服务） | 若改为 fail-closed，鉴权在数据库长故障时会整体不可用，**可用性目标与验收场景 S14 都要重写** |
| **AS-8** | **MySQL / Redis / Nginx 均为单点，无自动故障切换**，依赖人工恢复 | 若要承诺端到端 99.9%，**必须为 MySQL 做高可用**；这是唯一的前置条件 |
| **AS-9** | **备份文件与 binlog 存放在数据库主机之外的存储上** | 若不满足，RPO 从"≈0"退化为"自上次全量备份以来（最长 24 小时）"，[02 §7.2](./02-总体设计说明书.md) 的承诺即不成立 |
| **AS-10** | Redis 只承载"可丢弃"的数据（广播通知 + 限流计数），**不承载任何业务数据** | 若将来有业务数据落入 Redis，它就从"可随时丢弃的加速器"变成"必须做高可用的存储"，成本与风险跳升 |
