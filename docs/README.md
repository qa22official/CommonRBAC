**为什么拆成 8 份，而不是写 1 份大文档？**

因为这八份东西的"变化原因"完全不同：编码基线约束实现行为，需求随业务变、接口随前后端契约变、表结构随数据结构变、性能方案随规模变，协作部署文档记录团队和运行环境变化。把它们混在一份文件里，任何一处小改动都要求你重读全文，而且极易漏改——**变化频率、变化原因不同的内容应分开维护。**

## 2. 关键决策记录（ADR）

这一节是全文最该先看的部分。每条决策都写清了"换来了什么"和"代价是什么"——**没有代价的决策不存在，只有还没写出来的代价**。

| 编号 | 决策主题 | 我们的选择 | 换来了什么 | 代价是什么 |
|---|---|---|---|---|
| ADR-01 | 架构形态 | **模块化单体**（一套 Spring Boot 应用，内部按模块分包，可横向多实例部署） | 进程内调用零网络开销，最容易守住 30ms；部署与运维组件最少 | 无法按模块独立扩容；模块边界靠纪律与自动检查（ArchUnit）维护 |
| ADR-02 | 组织模型 | **单组织**，数据模型不引入 `tenant_id` | 表更少、索引更小、SQL 不会有"忘记带租户条件"的越权风险 | 一套部署只能服务一个组织；将来要多租户需按租户独立部署 |
| ADR-03 | 鉴权数据存放 | **实例本地缓存（Caffeine）+ Redis 广播主动失效 + 30s TTL 兜底**；另设**身份快照缓存**（`userId → 令牌版本号 + 状态`，30s TTL）用于令牌作废判定 | 鉴权链路 **零网络、零数据库查询**（快照未命中也只是单行主键查询），10k 并发下不给 Redis/MySQL 增加任何压力 | 权限变更为秒级生效（非强实时）；Redis 故障时最坏 30 秒收敛；身份快照带来约 333 QPS 的额外主键查询（@1 万活跃用户） |
| ADR-04 | 权限抽象 | 统一用**权限码**（如 `sys:user:create`）表达，权限分 MENU / BUTTON / API / SYSTEM 四类 | 业务代码只认权限码，不认"角色、继承、约束"——升级 RBAC1/2/3 时**权限声明与鉴权入口契约不变** | 管理端需维护"权限码 ↔ 接口"的对应关系；**升级仍需改动权限计算实现、缓存 SQL、管理端与前端**（详见 ADR-10） |
| ADR-05 | 权限范围 | 只做**功能权限**（菜单/按钮/接口），不做数据权限 | 模型最精简，鉴权链路最短 | 将来若要"张三只能看本部门数据"，需在鉴权主链路上增加一层数据范围过滤（本次已明确不预留） |
| ADR-06 | 安全框架 | **不引入 Spring Security 全套**，自研轻量 JWT 过滤器 + `@RequiresPermission` 注解；密码哈希仅引入 `spring-security-crypto` 组件包 | 鉴权链路全透明、无黑盒、性能最优、启动更快；避免为一个注解吃透一整套过滤器链 | CORS、统一异常、密码策略、防暴力破解等边界要自己写并自己写测试守住 |
| ADR-07 | 并发模型 | **同步阻塞（Tomcat 线程池）**，不使用 WebFlux 响应式 | 代码简单、可调试、栈信息可读；吞吐已远超需求（论证见 06 文档） | 若将来出现大量慢接口（如导出报表），需单独隔离线程池或独立部署 |
| ADR-08 | 数据访问 | **MyBatis 手写 SQL** | 每条 SQL 可被索引精确覆盖，无隐式查询、无懒加载意外、无意外全表扫描 | 需要多写一些 SQL 与映射（本系统仅 6 张表，总量可控） |
| ADR-09 | 审计日志 | **拆成两类**：变更审计（CHANGE）与业务数据同事务、绝不丢弃；安全事件（SECURITY）独立落库、失败不回滚业务、允许丢弃但必须计数告警 | 兼容"强合规"与"日志故障不得导致业务不可用"两个冲突诉求 | 实现上要维护两条写入路径；安全事件存在极端情况下丢失的可能（已通过计数告警兜底） |
| ADR-10 | 升级路径 | **RBAC0 起步**，仅预留继承关系字段，并预留两个代码扩展点（权限计算、授权校验） | 升级到 RBAC1/2/3 时**权限声明与鉴权入口契约不变**，升级与回滚主要通过改数据完成 | 预留字段与抽象接口在 RBAC0 阶段暂时"用不满"，存在轻微冗余；**升级仍需改动权限计算实现、缓存 SQL、管理端与前端**（不是"零工作量"） |
| ADR-11 | 数据库变更管理 | 引入 **Flyway** 管理 DDL 版本 | 建库、升级脚本可版本化、可审计、可重复执行；配合 RBAC 分阶段升级，脚本与阶段一一对应 | 多一个轻量依赖（一个 jar） |
| ADR-12 | 性能口径 | 10k **并发在线用户**；推导峰值 2,500 QPS；**设计目标 2,000 QPS（含 25% 余量）**；验收按 **2,500 稳态 + 4,000 冲刺**；鉴权类接口 **P99 ≤ 30ms** | 目标可测量、可验收；避免按 10k QPS 过度采购机器 | 若真实业务行为比假设更激进（如每用户每秒多请求），需重新评估容量 |
| ADR-13 | 令牌作废的一致性等级 | **不承诺"任何时候都立即失效"**。正常 ≤ 1 秒；Redis 故障 ≤ 30 秒（TTL 兜底）；实例重启**立即**（缓存为空，首请求读库）；数据库故障时受影响用户被拒绝 | 让"承诺"与"实现"一致；避免安全审计建立在错误假设上；同时保住"鉴权零网络"的性能设计 | 需要**每活跃用户每 30 秒一次主键查询**（1 万活跃用户 ≈ 333 QPS）；缓存失效场景下最坏 30 秒收敛 |
| ADR-14 | 缓存重载失败时的放行策略 | **fail-open（可用优先）**：继续用最后一份成功数据服务 + 强告警；**唯一例外**是"已知状态变化的用户"被立即拒绝；另预留 `stale-policy` 配置开关可切到 fail-closed | 数据库抖动或长时间故障都不影响用户办公（管理类后台常有连续作业需求）；同时不放过已知被作废的令牌 | **权限撤销在故障期间可能延迟生效（最长可达整个故障时长）**，合规上需要解释；必须配套"陈旧时长可观测 + 恢复后立即重载 + 故障期撤销可追溯"三项管理动作 |
| ADR-15 | 覆盖式授权的并发保护 | **乐观锁（`expectedVersion`，返回 40950）+ 行级锁双防线** | 把"静默丢失更新"变成"显式冲突"；同时保证约束校验不被并发穿透 | 前端必须处理 40950 并引导用户刷新重试，不能静默重放 |
| ADR-16 | 客户端 IP 可信性 | 由**唯一组件** `ClientIpResolver` 在可信代理边界内解析；限流、审计、告警共用同一结果 | 避免 XFF 伪造导致限流形同虚设、审计失去证据价值 | 需要正确的代理配置（应用端口不对公网开放、代理覆盖而非追加 XFF） |
| ADR-17 | 角色继承的字段语义 | **`sys_role.inherit_role_id` = "我从哪个角色继承权限"**（不是"组织上级"）；算法沿链收集；界面展示方向可自由渲染 | 消除原设计的语义歧义（歧义会导致权限方向搞反 = 真实越权）；与 NIST RBAC 主流存法一致 | 字段名与常见的 `parent_id` 不同，团队需要适应；组织上下级关系若将来需要，必须新建独立的表 |
| ADR-18 | 高可用边界 | **MySQL / Redis / Nginx 全部单实例，不做自动故障切换**；只保留"将来可加高可用"的扩展点约束；如实声明 RTO/RPO 与"整体 99.9% 不成立" | 把成本花在真正需要的地方（应用层冗余）；避免为不在关键路径上的 Redis 付高可用成本 | 单点故障需要人工恢复；**整体可用性受 MySQL 单点约束**；必须配套"异机备份 + 季度恢复演练" |

## 3. 术语表（人话版）

| 术语 | 一句话解释 | 类比 |
|---|---|---|
| 认证（Authentication） | 判断"你是谁" | 出示身份证 |
| 鉴权（Authorization） | 判断"你能不能做这件事" | 门禁刷卡决定这扇门开不开 |
| RBAC | "基于角色的访问控制"：不给每个人单独配权限，而是先配到"角色"上，再把人放进角色 | 先定岗位职责，再招人入岗 |
| RBAC0 | 最基础的三层：用户 → 角色 → 权限 | 岗位 + 职责，无上下级、无规则 |
| RBAC1 | 在 RBAC0 基础上增加**角色继承**（经理角色天然拥有员工角色的全部权限） | 岗位有上下级，汇报关系自动继承职责 |
| RBAC2 | 在 RBAC0 基础上增加**约束**（如"财务审批"和"付款执行"两个角色不能给同一个人） | 公司制度：不相容岗位分离 |
| RBAC3 | RBAC1 + RBAC2 的合并（继承 + 约束同时生效） | 完整版 |
| 权限码 | 一个字符串标识"某个操作"，如 `sys:user:create`、`biz:order:export` | 每把钥匙的编号 |
| JWT | 一段经过签名的字符串，服务端不查库就能验证"这张工牌是真的、且没过期" | 带防伪标记的工牌 |
| 本地缓存 | 每个后端实例在自己内存里存一份数据，读取是纳秒级，不经过网络 | 每个办事窗口自己贴一张对照表 |
| 身份快照 | 每个实例内存里存的一份 `用户 → 令牌版本号 + 状态`。请求时比对令牌里的版本号，不一致就说明令牌已被作废 | 窗口自己留一张"工牌作废名单"，办事先查一眼 |
| 缓存失效 | 数据改了之后，把旧的缓存丢掉、重新加载 | 人事改了表，群发通知让各窗口重贴 |
| 陈旧时长 | 缓存里的最后一份成功数据距今有多久。**fail-open 下它是唯一能反映"权限判断有多旧"的指标** | 冰箱里那盒牛奶放了几天 |
| fail-open / fail-closed | 数据不可用时"继续放行（可用优先）"和"直接拒绝（安全优先）"两种姿态 | 停电时：门自动打开逃生 / 门锁死不放人 |
| 乐观锁 / 版本号 | 提交时带上"我读到的是第几版"，版本对不上就报冲突而不是默默覆盖 | 文档编辑时提示"别人已修改，请刷新" |
| `kid`（密钥标识） | 令牌里记录"用哪把钥匙签的"，让服务器能直接选对钥匙 | 门上写的"用 3 号钥匙" |
| RTO / RPO | RTO = 故障后多久恢复服务；RPO = 最多允许丢多少数据 | 停电后多久来电 / 停了这么久会丢多少东西 |
| P99 | 100 个请求里，99 个的耗时都不超过这个值（只有最差的 1 个可能超） | 严格口径，"几乎所有人都满意" |
| QPS | 每秒处理的请求数 | 水管每秒流多少水 |
| 在线用户数 | 同时"挂着"的用户数（不等于每秒都发请求） | 商场里的顾客人数 ≠ 每秒通过闸机的人数 |
| 模块化单体 | 一个进程内跑完所有功能，但代码按模块严格分包隔离，禁止互相乱调 | 一栋大楼分成各部门，门禁分明，而不是一栋没有隔断的大仓库 |

### 4.2 仍需确认（阻塞编码，需业务方拍板）

| 编号 | 问题 | 当前假设 | 建议 |
|---|---|---|---|
| Q-H1 | 审计范围是否只限 RBAC 域？ | 只限 RBAC 域 | 若扩到业务域，写入量上升 2~3 个数量级，同步落库方案需重估 |
| Q-H2 | 是否需要对接 SSO / 第三方登录？ | 不需要 | 若有规划，认证模块预留 `AuthProvider` 接口即可，成本很低 |
| Q-H3 | 是否存在存量用户数据需要迁移？ | 无，全新系统 | 若有，需补充一次性导入与密码重置方案 |
| Q-H4 | 令牌有效期与续期策略的具体数值？ | 访问令牌 2 小时，静默续期 | 需结合公司安全要求确认；**这也是"高风险账号更严格失效"的正确实现方式** |
| Q-H5 | 审计日志保留期限？ | 180 天 | 视合规要求确认 |
| Q-H6 | 变更审计是否需要"前后值快照"？ | CHANGE 类需要，SECURITY 类不需要 | 影响审计表体积与写入耗时 |
| Q-H7 | JDK 与 Spring Boot 具体版本？ | Java 21 (LTS) + Spring Boot 3.x | 若团队环境停留在 Java 8/11，部分写法需调整（**架构结论不变**，但 JWT 库、Actuator 指标等细节会变） |
| Q-H8 | **fail-open 的代价需要业务方书面确认**：数据库长时间故障期间，已撤销的权限可能延迟生效（最长可达整个故障时长） | 已由用户选择 fail-open | 建议由业务/合规确认并留档；若将来要求收紧，把 `rbac.cache.stale-policy` 改为 `fail-closed` 即可，无需改代码 |
| Q-H9 | 备份与 binlog 是否已规划存放在数据库主机之外？ | 假设已具备 | **若没有，RPO≈0 的承诺不成立**，须立即补齐（见 [02 §7.2](./02-总体设计说明书.md)） |

> **规则**：以上任一问题未拍板前，不允许开始写数据库脚本与接口实现——它们都会直接落在这些决定之上。**先定语义，再写代码。**
