## 2. 实现范围

### 2.1 本期必须实现

- RBAC0 五张关系表：用户、角色、权限、用户角色关系、角色权限关系
- 认证：账号密码登录、登出、续期、修改密码
- 管理：用户、角色、权限、授权关系的增删改查与启停
- 三类功能权限：API、菜单（MENU）、按钮（BUTTON）
- 鉴权注解：`@PublicApi`、`@RequiresLogin`、`@RequiresPermission`；三者都不标的接口默认拒绝
- 缓存：单个 `PermissionSnapshot` + 独立身份快照；Redis 失效通知 + 30 秒软 TTL
- 身份快照缓存与 token_version 校验；多会话（登录不递增版本，登出/改密/停用为账号级撤销）
- rbac-api 契约：注解、权限码常量、应用服务契约、快照模型、错误码（清单见 02 §4.1、02 §20）
- `sys_user.must_change_password` 迁移脚本与初始 admin 初始化器

### 2.2 本期禁止实现

- 多租户
- 数据权限、行级权限、字段权限
- SSO、OAuth2、第三方认证
- 工作流审批
- DSD 动态角色激活
- 运行期用 URL 匹配权限
- 在业务代码或前端权限判断中出现角色名、角色编码
- 微服务、网关、注册中心、WebFlux、分布式锁、专用日志数据库

## 3. 架构约束

### 3.1 技术栈与模块依赖

- 技术栈：Java 21、Spring Boot 3.x、MyBatis、MySQL 8、Redis、Vue 3、TypeScript
- 模块间只允许依赖 rbac-api。除 rbac-bootstrap（装配模块）外，任何模块不得依赖其他模块。
  依据：依赖方向由编译器强制，防止模块化单体退化为大泥球。
- 业务模块与 rbac-* 模块平级，只允许依赖 rbac-api，不得引用 rbac-core / rbac-cache / rbac-audit 的任何类型。
  依据：这是"RBAC 升级时业务代码零改动"的物理保证。
- 业务模块与权限系统只有两个耦合点：`@RequiresPermission`、`AuditRecorder`。
- 权限码常量分层：框架级（`*`、`sys:*`）放 rbac-api；业务级（`biz:*`）放各业务模块自己的常量类。
  依据：避免 rbac-api 变成所有人的公共变更点。
- `rbac-api` 是唯一跨模块契约层：`rbac-core` 实现持久化与领域服务，`rbac-auth` / `rbac-cache` / `rbac-audit` / `rbac-admin` 只依赖 `rbac-api` 接口，`rbac-bootstrap` 负责注入实现；任何模块不得直接 import 其他模块的实现类。
  依据：保持严格依赖方向，同时避免 auth/admin/cache 绕过契约直接访问 core 的 Mapper。
- `rbac-api` 只放契约与 DTO，不放实现；应用服务契约的最小集合见 02 §4.1。
- rbac-guard 不访问数据库。
- `PermissionResolver` 契约不可变：`Set<String> resolve(long userId)`；返回不可变集合；不返回 null；不抛出与权限无关的异常。
- `ConstraintValidator` 是 core 内部扩展点，只读校验，不写数据库；不放进 rbac-api。

### 3.2 新增模块或接口的强制约定

- 业务表与 RBAC 表同库。
  依据：CHANGE 审计要求与业务同事务，且禁止跨库事务。
- Flyway 单一序列，脚本名带模块前缀；多人并行时分段分配版本号（如 V20x、V21x）。
  依据：两人同用 V20 会导致迁移记录冲突。
- 新接口必须归入性能档位：A 档 P99 ≤ 30ms / B 档 P99 ≤ 200ms / 例外档无指标；导出类不得归 A 档。
  依据：30ms 预算只给业务逻辑留约 24ms；导出结果集与审计写入不可控。
- 涉及"只能操作自己的数据"的接口必须写归属校验，并配一条负向测试。
  依据：权限码只回答"能不能用这个功能"，回答不了"能不能动这一条数据"。
- 业务表结构与 RBAC 域一致：逻辑删除 + created_by/at + updated_by/at。
- 业务模块不得在 Redis 存放业务数据。
  依据：Redis 一旦承载业务数据，就从"可丢弃的加速器"变成"必须做高可用的存储"。
- 新模块若引入新缓存对象，必须同步更新失效逻辑；权限相关事实优先并入 `PermissionSnapshot`，不新增分键缓存。
- 每个业务接口必须显式声明审计意图（见 3.7）。
- 新增接口自查四项：权限码有定义且有初始化数据 / 性能档位已归类 / 归属校验是否需要 / 审计意图已声明。

### 3.3 鉴权链路

固定顺序，不得调整：

```text
JWT 验签
→ 身份快照校验（tokenVersion、enabled、mustChangePassword）
→ 强制改密检查（mustChangePassword 时仅放行改密/登出/me）
→ 注解判定
→ PermissionResolver 取权限码集合
→ 权限码匹配
→ 进入业务方法
```

- `mustChangePassword = true` 时，除 `PUT /api/auth/password`、`POST /api/auth/logout`、`GET /api/auth/me` 外一律拒绝。
- 登录与刷新都不得写 `token_version`；只有登出、改密、停用才自增。
- 外部服务只允许使用专用账号接入；禁止用真人账号对外提供服务，禁止代最终用户操作。
- `@RequiresPermission` 只接受 API 权限码或通配权限码（`*`、`sys:*`、`sys:user:*`），且只支持方法级注解。
- 前端权限只决定菜单/路由/按钮显隐，不是安全边界。
- 业务代码不得判断角色名、角色编码、是否超级管理员。
- JWT 不包含权限明细；至少包含 `userId`、`tokenVersion`、`kid`、`iss`、`aud`、`iat`、`exp`。
- 签名用 HS256；所有实例必须同时支持当前密钥与轮换中的旧密钥。

### 3.4 令牌失效口径

| 场景 | 要求 |
|---|---|
| 登录 | 不递增 `token_version`；新令牌与既有令牌共存。禁止在登录路径写版本号 |
| 登出 / 改密 / 停用 | `token_version + 1` + 广播；该账号全部令牌失效（账号级，不是单令牌） |
| Redis 正常 | ≤ 1 秒传播 |
| Redis 故障 | ≤ 30 秒收敛（本地身份快照 TTL 兜底） |
| 应用实例重启 | 身份快照为空，首次访问必须读库 |
| 数据库故障 | 受影响用户拒绝；其他用户按 3.5 处理 |

事实来源是数据库的 `token_version` 与用户 `status`；Redis Pub/Sub 只负责加速通知。全局令牌作废不新增版本字段：按密钥轮换执行，移除旧密钥后旧令牌验签失败返回 40100。

### 3.5 缓存失败策略

- 缓存只存事实，不存派生结果。权限事实合并为一个 `PermissionSnapshot`（roleId→权限码、userId→roleId、roleId→{status,inheritRoleId}、permissionCode→id（仅启用权限））；身份事实为 `userId→{tokenVersion,enabled,mustChangePassword}`。
- 权限快照是单个不可变对象，失效时整体重载并原子替换；不做按 key 的局部加载。
- 快照元数据必须包含 loadedAt；`PermissionSnapshot` 另含来源版本与 state；30 秒是软 TTL，到期只触发刷新，不丢弃数据。
- 重载失败时：不得刷新 loadedAt；继续使用最后一份成功数据（fail-open）；告警。
  依据：若 loadedAt 被伪刷新，"陈旧时长"指标永远为 0，监控将无法发现正在使用过期权限。
- 数据本身永不丢弃。
  依据：丢弃会导致重载失败时无数据可用，被迫拒绝服务，fail-open 无法成立。
- 收到 `TOKEN_REVOKED(userId)` 后该用户必须拒绝，不得使用旧快照。
- 数据库恢复后立即全量重载。
- 必须暴露指标：当前陈旧时长、重载失败次数、受影响用户数、用陈旧权限放行的请求数。
- 保留配置开关 `rbac.cache.stale-policy`，取值 fail-open | fail-closed。

### 3.6 RBAC1 字段语义

- 字段：`sys_role.inherit_role_id`，含义为"当前角色从哪个角色继承权限"；0 表示不继承。
- 它不是组织上级字段；禁止恢复使用含义不明确的 `parent_id`。
- 计算方式：沿 inherit_role_id 收集并集，按角色 ID 去重；按路径深度限制 5 层（5 条边），超限告警并跳过该分支，不抛异常。
- RBAC0 阶段该列全为 0；未配置继承的用户，权限快照必须与升级前逐条一致。

### 3.7 审计

两类事务语义，不可混用：

| 类别 | 事务 | 失败策略 |
|---|---|---|
| CHANGE | 与业务变更同事务 | 审计失败则业务回滚 |
| SECURITY | 独立写入，不参与业务事务 | 不回滚业务；允许丢弃但必须计数与告警 |

范围：RBAC 域全量 + 业务域白名单。

白名单判定基于两个客观问题：影响面（1 条还是成百上千条）、可逆性（能否恢复、数据是否离开系统）。

| 类别 | 判据 | 要求 |
|---|---|---|
| 不可逆 + 数据外带 | 导出、下载、打印、外部推送 | 必须审计 |
| 不可逆 + 影响面大 | 批量删除、数据清除、批量导入覆盖、审批、批量授权 | 必须审计 |
| 可逆 + 影响面大 | 批量改状态 | 应当审计 |
| 影响面小 | 单条增删改 | 可选 |
| 纯读 | 不改变数据且不出系统 | 不审计 |

业务接口声明规则：

- 方法体内调用 `AuditRecorder`，或
- 方法上标注 `@NoAudit("原因")`，value 必填且不得为空串
- 两者皆无视为未完成，构建失败

导出类操作必须记录三项，存放于 `detail_after` 的固定结构：

```json
{ "scope": "FILTERED|ALL|SINGLE", "resultCount": 1842, "condition": { } }
```

其他硬性要求：

- `AuditRecord` 必须能承载审计表全部业务列：target_type、target_id、detail_before、detail_after、result、fail_reason、client_ip、user_agent、trace_id、operator_name。
  依据：字段不足会让审计白名单退化为"只记下谁干过、记不下干了什么"。
- `target_type` 对业务域为开放取值（如 ORDER），RBAC 域使用固定枚举。
- 业务快照脱敏由业务模块自己负责（统一脱敏器只认识 RBAC 域字段）。
- 密码、密码哈希、令牌、密钥不得进入日志、审计快照、响应或异常信息。

### 3.8 授权并发

- 覆盖式授权接口必须携带 `expectedVersion`。
- 版本不匹配返回 40950，不得静默覆盖。
- 事务内顺序：先 `SELECT ... FOR UPDATE` 锁目标行 → 校验约束 → 覆盖写入 → 版本号 +1。
- 乐观锁负责发现丢失更新；行锁负责防止约束被并发绕过；两者都需要。

### 3.9 可用性边界

- 应用 3 实例；MySQL、Redis、Nginx 均为单实例，无自动故障切换。
- 必须做异机备份（数据文件与 binlog 不得与数据库同机）与季度恢复演练。
- 不得在任何文档或代码注释中宣称具备整体 99.9% 自动容灾。
- RTO/RPO 以 README ADR-18 为准。

## 4. 数据库实现规则

- Flyway 管理迁移；已发布脚本禁止修改。
- 不使用物理外键；引用校验在事务内完成。
- 用户、角色、权限使用逻辑删除（status = 2）。
- 关系表必须有唯一约束防重复。
- 全部 SQL 使用 `#{}` 参数绑定，禁止 `${}` 拼接。
- 新增索引必须提供四项：查询场景、选择性、写入代价、`EXPLAIN ANALYZE` 结果。
- 模糊查询只做前缀匹配 `LIKE 'kw%'`；禁止 `LIKE '%kw%'`。
- 审计查询必须带时间范围与游标条件。
- 版本字段：`sys_user.role_version`、`sys_role.perm_version`。
- 审计表必备列：`audit_category`、`transaction_id`、`event_time`，并在 `event_time` 上建索引。
- 枚举归属：RBAC 域枚举放 rbac-api；业务枚举放业务模块内部。

## 5. HTTP 实现规则

- 基础路径 `/api`；JSON；字段驼峰。
- 成功 `code = 0`；HTTP 状态按 code 前缀映射：400xx→400、401xx→401、403xx→403、409xx→409、429xx→429、5xxxx→5xx；完整业务码见 04 §1.3。
- 分页 `size` 上限 200，超过返回 40000，不静默截断。
- 创建类依赖数据库唯一约束；覆盖式与目标状态操作必须幂等（传目标值，不用 toggle 语义）。
- 错误响应不得包含所需权限码、堆栈、SQL、密钥、敏感字段。
- `ClientIpResolver` 是唯一客户端 IP 解析组件；限流、审计、告警必须复用同一结果。
- 只信任可信代理网段的 `X-Forwarded-For`；应用端口不对公网开放。
- 每个业务接口必须显式声明审计意图；导出类必须记录条件与条数。
- 新增接口完成 3.2 的四项自查。

## 6. 编码顺序

1. Maven 多模块与依赖
2. Flyway：RBAC0 表、索引、初始化数据
3. rbac-api：DTO、事件、注解、应用服务契约
4. 领域模型、权限计算、约束校验（core 实现 rbac-api 契约）
5. PermissionSnapshot、身份快照、失效通知、重载状态
6. JWT、密码、登录与刷新、首次改密、登录限流、会话接口
7. 鉴权过滤器、拦截器、统一异常
8. 管理端接口 + CHANGE / SECURITY 审计
9. 前端：权限状态、菜单、路由、v-perm 指令
10. 构建门禁、单元测试、集成测试、并发测试
11. 索引验证与压测（按目标数据量）
12. Redis 故障、数据库故障、实例重启、密钥轮换演练

每完成一个阶段即运行该阶段最小测试集，不要等全部完成后再首次验证。

## 8. 完成定义

- 每个受保护接口有且只有一个鉴权声明
- 默认拒绝与越权测试通过
- 登录不递增版本、登出/改密/停用使该账号全部令牌失效、缓存失效、Redis 丢消息、实例重启测试通过
- 并发授权冲突返回 40950，无静默丢失更新
- CHANGE 审计与业务事务一致
- SECURITY 事件具备失败计数与告警
- 所有业务接口已显式声明审计意图（`AuditRecorder` 或 `@NoAudit`），敏感关键词门禁零豁免通过
- 白名单内的导出/批量操作可查到操作人、条件与结果条数
- 角色继承方向与深度保护测试通过（含 6 个直接角色、宽菱形、成环）；RBAC0 快照无变化
- 首次登录强制改密规则生效；初始 admin 不在脚本中写密码
- 密钥轮换导致旧令牌返回 40100，不误报 40101
- 目标数据量下关键 SQL 的执行计划已验证
- 2,500 QPS 稳态与 4,000 QPS 冲刺满足 01 §5.1 的验收口径
- 所有框架修改已在 [07 修订记录](./07-修订记录.md) 中登记
- 文档、迁移脚本、接口清单、权限码清单、测试结果一致
